# 해결 사례 AI 가이드화 (M4)

담당자가 해결한 티켓 중 가이드에 없는 내용을 7일 단위로 찾아, 관리자가 고쳐서 등록할 초안으로 만든다.
결과는 DB 의 `guide_clusters`(묶음·초안)와 `ticket_guide_states`(티켓 상태)에 쓴다. Jira 로 보내지 않는다.

```python
from app.agent.guide import run_round
judged, drafted = run_round(session, port, search_fn, embed_fn)   # 판단 → 묶기 → 초안
# embed_fn: 글 목록 → 벡터 목록 (Embedder('bge-m3').embed_documents). 기준값이 bge-m3 로 정해졌다
```

7일 실행은 서버의 `guide-worker` 컨테이너가 매주 월요일 00:00(KST)에 한다 (`app/workers/guide_analysis.py`). 지금 바로 한 번 돌리려면 `python -m app.workers.guide_analysis --once`.

`case` 를 주지 않으면 이 Session 의 PostgreSQL 연결로 김태연 님 `case_guide` 함수를 부른다.

## 파일

| 파일 | 하는 일 |
| --- | --- |
| `run.py` | `run_round`: 한 회차. `judge_round`(판단, 티켓마다 커밋) → `draft_round`(묶기·초안, 묶음마다 커밋) |
| `collect.py` | 대상 티켓 모으기, AI 없이 정하는 것, 같은 분류 가이드, 비교 항목 검색 (DB 읽기만) |
| `judge.py` | 판단 프롬프트, 출력 형식, 가림·치환, 호출과 검사 |
| `cluster.py` | 그룹 나누기, 유사도로 묶기, 기존 묶음과 비교 (AI 없음) |
| `draft.py` | 초안 프롬프트, 출력 형식, 검사, 조각 조립 |
| `case.py` | 김태연 님 `open_basis`·`ticket_warnings` 연결 (psycopg 연결을 넘김) |
| `store.py` | 티켓 상태·묶음·호출 기록 저장 |

## 한 회차 흐름

1. **모으기:** `work_status = CLS` 이고 상태 행이 없거나, 상태가 비었거나, `WAITING` 인 티켓
2. **AI 없이 정하기** (`collect.precheck`)

   | 조건 | 처리 |
   | --- | --- |
   | 분류 없음 | `EXCLUDED` "분류 없음" |
   | SEC | `EXCLUDED` "SEC 티켓은 가이드화하지 않음" (M4 결정, 2026-11-10) |
   | 처리 결과 없음, 20자 미만 | `EXCLUDED` |

   SEC 를 빼는 이유: 보안 티켓은 AI 에 보내지 않아 초안이 티켓 글을 옮긴 것뿐이고, 보안 글을 초안으로 한 번 더 저장하게 된다.
   보안 가이드(IT-SEC-*)는 관리자가 직접 고친다. `SEC_MANUAL` 판단값·화면 칸은 남아 있지만 이 워커는 만들지 않는다.

3. **비교 항목:** 요약·증상·처리 결과로 같은 분류 문서를 관리자 권한으로 검색해 상위 5개
4. **AI 판단:** 티켓 1건당 1회 (thinking 켬). 실패하면 한 번 다시 부른다

   | 결과 | 처리 |
   | --- | --- |
   | `NOT_TARGET`, `EXISTS` | `EXCLUDED`, 이유 앞에 "대상 아님:" 또는 "이미 있음 (문서 항목):" |
   | `ADD_ITEM`, `CHANGE`, `NEW_GUIDE`, `MANUAL_CANDIDATE` | 상태를 쓰지 않고 묶기로 넘김. 실패 기록만 0 으로 |
   | 실패 | 상태는 그대로, `fail_code`·`fail_count + 1`. 다음 회차에 다시 |
   | 예상 못 한 오류 | 그 티켓만 되돌리고 `UNEXPECTED` 로 실패 기록. 다음 티켓을 계속 처리한다 |

5. **묶기** (`cluster.py`): 아래 "묶기 설정"
6. **초안** (`draft.py`): 묶음 하나당 1회 (thinking 켬). 아래 "초안"
7. **저장:** 묶음 1행과 티켓 `REVIEWING` 을 한 트랜잭션으로. 실패하면 티켓 상태는 그대로 (`fail_code` 만), 다음 회차에 판단부터 다시

## 묶기 설정 (M4 결정, 2026-11-09)

| 설정 | 값 | 뜻 |
| --- | --- | --- |
| `cluster.THRESHOLD` | 0.75 | 요약+증상 임베딩(bge-m3)의 코사인 유사도가 이 값 이상이면 같은 묶음 |
| `cluster.MIN_TICKETS` | 1 | 1건이어도 바로 초안을 만든다. 이보다 적으면 `WAITING` |
| 매뉴얼 후보 | AI 호출 | AI 가 "매뉴얼에 넣을 만한 내용"을 정리한다. 매뉴얼 글은 쓰지 않는다 |

**그룹:** 판단과 대상이 같은 티켓끼리만 묶는다. 항목 추가는 분류+넣을 문서, 변경은 분류+문서+항목 (김태연 님 Q2 "한 묶음은 한 항목"),
새 가이드·매뉴얼 후보는 분류. 그룹 안에서 접수 순서대로 한 건씩, 가장 비슷한 묶음의 평균 벡터와 비교해 넣거나 새 묶음을 만든다.

**기존 묶음과 비교** (같은 그룹, 같은 기준값)

| 비슷한 기존 묶음 | 처리 |
| --- | --- |
| 검토 중, 등록 전 | 그 묶음의 근거 티켓에 추가. 초안은 그대로, 새 티켓의 경고만 더한다. AI 호출 없음 |
| 검토 중, 등록 후 | 티켓 `WAITING`. 다음 회차에 다시 판단 (그사이 현행이 되면 "이미 있음") |
| 거절 | 새 묶음을 만들고 경고 맨 위에 "이전에 거절된 주제"와 거절 사유 |

**기준값 근거:** 과거 이력 356건(SEC 제외)을 실제와 같은 방식으로 묶어 시나리오 번호(정답)와 비교했다. 과거 이력에는 요약이 없어 제목+내용을 썼다.

| 기준값 | 다른 문의가 섞인 티켓 | 문의 1개가 나뉜 묶음 수 |
| --- | --- | --- |
| 0.65 | 17% (예: VPN 개인 접속 불가 + 전사 장애가 한 묶음) | 1.7 |
| 0.75 | 1.4% | 2.9 |
| 0.85 | 1.1% | 3.6 |

0.75 를 넘기면 섞임은 거의 그대로이고 묶음만 잘게 나뉜다. 0.75 에서 나뉜 것은 대부분 같은 시나리오 안의 다른 증상이다
(예: 사내 Wi-Fi → 인증서 오류 / 목록에 안 보임 / 연결되는데 인터넷 안 됨). 만든 데이터라 실제 티켓이 쌓이면 다시 확인한다.

## 초안 (`draft.py`)

AI 는 항목 제목과 본문만 쓴다. 제목 줄 `### 3.N`, 머리 줄(문의 유형·처리 구분·담당 부서·관련 FAQ), "해결되지 않으면" 문단,
"문의 시 알려 주실 정보" 목록은 서버가 티켓 값과 AI 칸으로 조립한다. 티켓마다 머리 줄 값이 다르면 가장 많은 값을 쓰고 경고한다.

| 판단 | AI 가 쓰는 칸 | 서버가 하는 일 | `draft_md` |
| --- | --- | --- | --- |
| 항목 추가 | 형식, 제목, 본문, 알려 줄 정보, 관련 FAQ | `open_basis` 기준 + 조각 조립 | `### 3.N` 조각 |
| 변경 | 형식, 제목, 고친 본문 전체, 변경 이유, 관련 FAQ | 기존 항목 본문만 보냄. 기존 번호·머리 줄을 붙임 | `### 3.x` 조각 |
| 새 가이드 | 위 + 가이드 제목 | 조각을 `open_basis` 뼈대에 넣음 (1·2장은 관리자가 채워야 등록) | 뼈대 전체 |
| 매뉴얼 후보 | 넣을 만한 내용 | 비교한 매뉴얼 항목 제목을 붙임 | 없음 |

- **문제 해결형**(이런 경우 → 원인 → 조치 방법 → 해결 확인)과 **신청형**(이럴 때 신청합니다 → 신청 방법 → 처리 기간과 결과 확인 →
  반려·보완되는 경우)은 실제 가이드 형식을 따른다. 신청형에는 "해결되지 않으면"을 붙이지 않는다.
- **변경 대상이 `ALLOWED` 가 아니면 AI 를 부르지 않는다.** 가려서 보낸 글을 "원문 그대로" 돌려받으면 ●●● 가 가이드에 들어가기 때문이다.
  기존 항목을 초안으로 두고 경고한다.
- **검사** (틀리면 한 번 다시 부른다): JSON·자료형, 판단별 필수 칸, 보낸 목록에 없는 FAQ 번호(`INVALID_REFERENCE`),
  본문의 `#`~`###` 제목·안 닫힌 코드 울타리·반영 표식(`INVALID_FORMAT`, 김태연 님 조각 약속), `[직원1]` 같은 치환 표시·●·접수 번호(`INVALID_CONTENT`)
- **경고** (`review_info.warnings`): `open_basis` 경고, 민감정보(`sensitive_warnings`, 변경은 더한 줄만), 재처리·짧은 처리(`ticket_warnings`), 머리 줄 값 차이

**검토 정보** (`review_info`). 화면은 지금 `reason`·`warnings` 만 보여 준다.

| 키 | 내용 |
| --- | --- |
| `reason` | 티켓별 판단 이유 (같은 것은 한 번) |
| `warnings` | 위 경고. 거절된 주제면 맨 위 |
| `form` | `TROUBLESHOOT` · `REQUEST` |
| `guessed` | 추론으로 쓴 칸 (예: 원인) |
| `differences` | 티켓 간 해결 방법 차이 |
| `change_note` | 변경 이유 (변경) |
| `guide_title` | 새 가이드 제목 (새 가이드) |
| `manual_note`, `manual_items` | 매뉴얼에 넣을 만한 내용, 가까운 매뉴얼 항목 (매뉴얼 후보) |
| `rejected_before` | `{cluster_id, reject_reason}` 이전에 거절된 비슷한 묶음 |

## 외부 전송

- 티켓 요약·증상·대상 시스템·처리 결과: A·B 가림(`mask_secrets`) + C·D 치환(`Pseudonymizer`) (docs/10). 초안은 묶음 티켓을 한 번에 치환한다
- 비교 항목: `ALLOWED` 그대로, `MASKED` 가림+치환, `BLOCKED` 는 제목만 (`content_hidden: true`). 초안도 판단 때와 같다
- 변경 대상 항목 본문: `ALLOWED` 일 때만 원문
- 임베딩은 서버 안에서 돈다 (외부 전송 아님)
- 검색 결과의 정책은 매뉴얼 항목 값이 있으면 그 값이다 (검색 `content_transfer_policy` 우선)

## 서버 검사 (`judge.check`)

| 판단 | `target_doc` | `target_item` |
| --- | --- | --- |
| `ADD_ITEM` | 같은 분류 가이드 목록 안 | 비움 |
| `CHANGE` | 같은 분류 가이드 목록 안 | 보낸 항목 중 그 가이드의 3.x 항목 (`ITEM`). 장·FAQ 는 안 됨 |
| `EXISTS` | 보낸 항목 안 (매뉴얼도 됨) | 보낸 항목 안 |
| 그 밖 | 비움 | 비움 |

틀리면 `INVALID_REFERENCE` 로 한 번 다시 부른다. 항목 추가·변경 대상이 매뉴얼이면 틀린 것이다 (매뉴얼에 넣을 내용은 `MANUAL_CANDIDATE`).

## 호출 기록

`llm_calls` 에 목적 `GUIDE_JUDGE`(티켓의 `inquiry_id`), `GUIDE_DRAFT`(묶음 첫 티켓의 `inquiry_id`)로 남긴다. 프롬프트·응답 원문은 남기지 않는다.

## 실패 코드 (`ticket_guide_states.fail_code`)

판단·초안 호출 오류(`TIMEOUT` 등, `INVALID_*`, `SCHEMA_INVALID`), `SEARCH_FAILED`(비교 항목 검색), `EMBED_FAILED`(묶기 임베딩),
`BASIS_FAILED`(`open_basis` 거부: 현행 없음·항목 없음 등), `FILTER_FAILED`(가림·치환), `UNEXPECTED`

## 시험

`tests/test_guide_judge.py`, `tests/test_guide_draft.py`: Mock 모델, 가짜 임베딩, 가짜 `case_guide` 함수, SQLite 메모리 DB. 외부로 아무것도 보내지 않는다.

## 한계

- **초안 품질은 실제 모델로 확인하지 않았다.** Mock 시험은 형식과 검사만 본다. 특히 내부 절차를 임직원용 글로 바꾸는지는 실제 응답으로 확인하고,
  구멍이 보이면 프롬프트를 고친다.
- **잘게 나뉜 묶음:** 같은 문의라도 증상이 다르면 다른 묶음이 된다. 관리자가 비슷한 초안을 여러 개 볼 수 있다.
- **큰 묶음:** 묶음의 티켓을 모두 한 호출에 보낸다. 건수 상한은 아직 없다.
- **화면:** 매뉴얼 후보의 `manual_note`, 변경 이유 등은 `review_info` 에 있지만 화면은 아직 `reason`·`warnings` 만 보여 준다.
- **가이드·매뉴얼 구분:** AI가 "그 조치를 누가 하느냐"로 가이드(항목 추가·변경·새 가이드)와 매뉴얼 후보를 나눈다.
  잘못 나뉘면 관리자는 거절만 할 수 있고, 판단을 바꾸는 기능은 없다. 잘못 나뉘는 일이 많으면 추가한다 (제안).
