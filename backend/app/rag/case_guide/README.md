# 해결 사례 가이드화 (M2-3-2)

해결된 티켓 하나를 **그 문의 유형을 다루는 기존 가이드의 다음 버전 초안**으로 만든다 (SRS GUIDE-03).
새 문서를 만들지 않는다. 사례는 이미 7분류 중 한 문의 유형으로 처리된 티켓이라, 넣을 가이드가 반드시 있다.

```
CLS 티켓 ─▶ draft() ─▶ 관리자 수정 ─▶ register() ─▶ ingest_version() (M2-3-1) ─▶ activate() (관리자 승인, DC-09)
            초안 md      (화면 F·API A,    파일 + 버전 행     DONE = 초안                  현행 = 검색됨
            DB 안 씀      아직 없음)        PENDING·비현행     검색에 안 나옴
```

## 무엇을 바꾸나

현행 md(이어 쓰는 초안이 있으면 그 md)를 복사해서. 현행이 docx·pptx·pdf·txt 면 파싱 결과를 가이드 md 로 바꿔 기준으로 쓴다 (`ingest/upload.py` `to_checked_md` → `parser/to_md.py`, 경고):

| 위치 | 바뀌는 것 |
|---|---|
| 머리말 `version`, 첫머리 `> 문서 번호 \| … \| v2.0 \|` | 다음 버전 (`v2.0` → `v2.1`, 문서의 가장 높은 vX.Y 다음) |
| 3장 끝 | 새 항목 `### 3.N <티켓 요약>`: 머리 정보(문의 유형 · 처리 구분 🔵 IT 담당자 처리 · 담당 부서), `#### 이런 경우`(증상·대상 시스템), `#### 조치 방법`(해결 내용), 해결되지 않으면 |
| 3장 항목 표 (3장 제목과 첫 항목 사이) | `\| 3.N \| <제목> \| <문의 유형> \| 🔵 IT 담당자 처리 \| <담당 부서> \|` 한 줄 (표 끝). 3장 제목 뒤 **첫 표**만 본다 (빈 줄에서 표가 끝나고, ``` 코드 블록 안은 건너뜀). 머리줄이 `번호 \| 제목 \| 문의 유형 \| 처리 구분 \| 담당 부서`(가이드 27종 모두)가 아니거나 표가 없으면 고치지 않고 경고. 지난 줄은 채우지 않는다: 표 번호와 3장 항목 번호가 다르면 (예: 이 기능 전 초안에 이어 쓰기) 경고 |
| 목차 | `- 3.N <제목>` 한 줄 |
| 개정 이력 | `\| v2.1 \| 날짜 \| 담당 부서 \| 해결 사례 반영 (<접수 번호>): 3.N <제목> \|` |

나머지 줄은 그대로다. 같은 가이드의 pdf·docx·pptx와 짝 매뉴얼(-M)은 바꾸지 않는다 (검색은 md 로 충분).

## 쓰는 티켓 칸

| 가이드 | 티켓 |
|---|---|
| 항목 제목 | `summary` (없으면 `symptom` 첫 줄) |
| 이런 경우 | `symptom`, `target_system` |
| 조치 방법 | `resolution_note` (담당자가 WIP→FIN 때 씀) |
| 문의 유형 · 담당 부서 | `inquiry_type_id` → `inquiry_types.code`, `group_id` → `support_groups.name` |

문의자 이름·연락처, `occurred_at`·`business_impact`·`tried_actions`는 쓰지 않는다. 티켓 글의 제목(`#`) 줄은 글로 바꾼다 (항목이 나뉘지 않게).

## 규칙

| 경우 | 하는 일 |
|---|---|
| `CLS`가 아님 (`FIN`은 미해결로 돌아갈 수 있음) / 해결 내용 없음 | 거부 |
| 다시 처리된 접수 (상태 이력에 `FIN → WIP`가 있음) | **경고만**: 횟수와 TK-08 이력 위치. 본문에는 마지막 처리 결과(`tickets.resolution_note`)만 넣는다. 앞선 처리 결과·남은 증상은 문의자·담당자가 쓴 글이라 원문을 경고에 넣지 않는다. 쓸모 있으면 관리자가 이력을 보고 "해결되지 않으면"에 직접 쓴다. 횟수는 **기록에 남은** `FIN → WIP` 줄 수다 (다시 완료 때 처리 결과를 필수로 받는 `TicketRepository.has_reopened`와 같은 기준). 경고가 없다고 재처리가 없었다는 뜻은 아니다: 해결 확인(`CLS`) 뒤 새 문의로 다시 물은 경우(다른 티켓), Jira 에서 직접 `FIN → RDY`로 되돌린 경우, 웹훅이 최신 상태만 읽는 사이 Jira 에서 `FIN → WIP → FIN`이 지나간 경우는 세지 못한다 |
| 넣을 가이드 | 그 문의 유형이 항목에 적힌 현행 임직원용 가이드 (매뉴얼 제외), 여럿이면 항목이 많은 쪽 + 경고. 문의 유형이 없으면 `doc_code`(명령 `--doc`)로 고른다 |
| 기준 파일이 md 가 아님 | **경고만**: md 로 바꿔 기준으로 쓴다 (`to_checked_md`). 새 버전은 md. 바꾼 md 를 다시 읽으면 원래 파일과 청크가 같다. 빠지는 것은 쪽 번호·문서 안 그림 내용 해시·이모지 (`parser/to_md.py` 머리 설명). 그림은 바꾸기 **전에** 배포 그림과 맞춰 보고, 없거나 내용이 다르면 이름표 없이 본문 설명만 남긴다 (업로드 적재와 같은 결과 + 그림 경고. 같은 그림 번호를 쓰는 그림 중 하나라도 다르면 그 번호 그림은 모두 설명만 — md 링크로는 구분할 수 없음). 읽지 못하는 파일이면 거부 |
| 같은 가이드에 승인 전 사례 초안이 있음 | 새 버전을 만들지 않고 그 초안에 이어 쓴다 (3.N+1, 개정 이력 그 버전 줄에 덧붙임) |
| 사례가 아닌 다른 초안이 있음 | 경고 (둘 다 승인하면 나중 것만 현행) |
| 접수 번호가 이미 기준 md 에 있음 | 거부 (두 번 넣지 않음). 개정 이력 표식 `해결 사례 반영 (<접수 번호>)`에서 **정확히** 뽑아 비교 (`TK-1`과 `TK-10`은 다르다) |
| 민감정보 | **경고만** (지우거나 막지 않음). 새로 더한 줄만, D 의 탐지 규칙 = docs/10 2장 목록 전부: 전화·이메일·사번·직원 이름(`Pseudonymizer`), 비밀·고유식별(`mask_secrets`). 해결 사례 검토에 쓸 목록은 2장 목록이다 (docs/10 1.3). 경고에는 종류와 줄 번호만, 값은 넣지 않는다. 목록(탐지 함수)은 그대로 쓰지만 새 줄마다 따로 검사하므로 여러 줄에 걸친 값(예: `비밀번호:` 다음 줄의 값)이나 기존 줄은 못 잡을 수 있다. 경고가 없다고 공개·전송이 안전하다는 뜻은 아니다 |
| 열람 범위·전송 정책 | **관리자가 등록할 때 고른다** (docs/10 1.3 "해결 사례를 Guide 로 쓸 때 `transfer_policy`를 반드시 고르게 한다"). 현행 값과 다르면 경고 (승인하면 가이드 전체에 적용). 없는 값은 거부 |

민감정보를 막지 않는 이유: 초안은 비현행이라 검색·외부 전송에 나가지 않고, 승인 전 사람의 검토(정확성·정보 보호·공개 범위)가 명세에 있다 (GUIDE-03).
정규식으로 막으면 기존 가이드 문의처의 공식 연락처(`it-helpdesk@ict.example`, 내선)도 걸린다.

### 관리자가 고친 md 검사 `check()`

문제(등록 안 됨): 파서·청커가 못 읽음, 문서 번호·버전이 초안과 다름, 기준 가이드의 항목이 빠짐, 이 티켓의 표식이 없음,
**기준에 있던 다른 사례의 표식이 빠짐** (이어 쓰던 초안의 사례를 오래된 md 가 지우지 않게).
새 항목 3.N 을 지우고 기존 항목(예: 3.7 표의 행)으로 옮기는 것은 된다. 개정 이력의 표식만 남기면 된다.

`Draft`는 만들 때의 기준(현행·이어 쓰던 초안 `file_path`·기준 md)을 담는다. 관리자가 고치는 동안 보관했다가 `register`에 **그대로** 준다
(`d.save(path)` / `Draft.load(path)`, API 는 같은 값을 저장해 두면 된다). 등록 때 초안을 새로 만들면 그새 들어간 사례를 못 지킨다 (검수 P1).

### 등록 `register()`

- 파일: `<files_root>/storage/case_guides/<문서 번호>/<버전>_<접수 번호>.md`. 쓸 때마다 다른 경로 (M2-3-1 전제). 이어 쓰기에서 경로가 바뀌므로, 이전 파일을 읽던 적재는 쓰기 전에 알아채고 건너뛴다 (업로드 적재 쓰기 행). `file_path`에는 **files_root 기준 상대 경로**만 넣는다: 저장 위치를 옮길 때는 폴더를 옮기고 `files_root`만 바꾼다
- 버전 행: 새 버전이면 PENDING·비현행으로 넣고, 열람 범위·전송 정책은 **관리자가 고른 값**(`view_scope`·`transfer_policy`, 필수)을 쓴다. 이어 쓰기면 그 초안 행의 `file_path`와 정책을 바꾸고 PENDING 으로 (적재가 청크를 통째로 바꾼다)
- 감사 로그 `CASE_GUIDE_REGISTER` (result `<접수 번호> → <버전>`). 후보 목록 `candidates()`는 이것으로 등록한 티켓을 뺀다
- 문서를 잠근 뒤 다시 본다: 초안을 만든 뒤 현행이 바뀌었거나, 이어 쓰던 초안이 바뀌었거나, 같은 버전이 그새 생겼으면 거부 ("초안을 다시 만드세요"). 거부하면 파일도 남기지 않는다
- 승인(현행 전환)은 하지 않는다. 승인하면 가이드 전체가 새 버전으로 바뀐다 (항목 하나만 승인하는 방법은 없다)

## 명령 (검토·승인 API·화면 전까지 시연·검수용)

```
python -m app.rag.case_guide --database-url <DB> candidates [--category SW]
python -m app.rag.case_guide --database-url <DB> draft --ticket 12 [--doc IT-SW-001] --out case.md     # + case.md.json
python -m app.rag.case_guide --database-url <DB> register --file case.md --view-scope ALL --transfer-policy ALLOWED [--admin-id 3] [--embedder fake]
```

`draft`는 현행 버전의 열람 범위·전송 정책을 같이 보여 준다 (`register`에서 고를 때 참고). `draft --out`은 초안 정보를 `<out>.json`에 같이 쓰고, `register`는 그 기준으로 검사한다 (`--draft`로 다른 위치). 정보가 없으면 등록하지 않는다.
그새 같은 가이드에 다른 사례가 등록됐으면 "그새 생겼습니다/바뀌었습니다"로 거부되니 `draft`부터 다시 한다.
localhost 가 아닌 DB 는 `--allow-remote`, 저장 루트는 `--files-root` (기본: 저장소 루트, `/storage/`는 git 에 안 올림).

## API·화면을 붙일 때 지킬 것 (호출 약속)

- **초안 기준은 서버가 보관**한다: `draft()`가 돌려준 `Draft`를 서버에 저장했다가 `register()`에 그대로 준다. 클라이언트가 보낸 기준 md·문서 id·버전 id 는 믿지 않는다 (명령의 `<out>.json`은 시연용 로컬 파일이라 위변조 방지가 아니다)
- `register()` 뒤에는 **바로 `ingest_version()`**을 부른다 (업로드 DC-07 과 같은 백그라운드). 멈추면 10분 뒤 `resume_pending`이 받는다
- **새 경로·원본 보존은 필수**: 오래된 적재를 막는 것은 `file_path` 문자열 비교다 (내용 해시가 아님). 같은 경로에 파일을 덮어쓰거나 경로를 다시 쓰면 알아채지 못한다. `register()`는 등록마다 새 경로를 만든다
- **표식 보존 ≠ 내용 보존**: `check()`는 기준에 있던 사례의 개정 이력 표식과 기존 항목 번호가 남았는지만 본다. 관리자가 사례 본문을 고치거나 지운 것이 맞는지(정확성·정보 보호·공개 범위)는 승인자가 검토한다 (GUIDE-03)
- **열람 범위·전송 정책은 관리자가 고르게** 한다 (docs/10 1.3). 검토 화면에서 현행 값을 보여 주고 고른 값을 `register()`에 넘긴다. 고르지 않은 값을 서버가 채우지 않는다. 이 등록 경로는 고르지 않으면 **저장하지 않고 거부**한다 (함수는 인자 누락·없는 값 거부, 명령은 필수 옵션). docs/10 1.3 의 "고르지 않으면 BLOCKED 로 저장"보다 엄격하며, BLOCKED 행을 대신 만들지 않는다. DB 기본값·외부 전송 필터의 "모르는 값은 BLOCKED" 방어와는 별개다
- 승인은 기존 `activate()` (DC-09). 승인하면 가이드 전체가 새 버전으로 바뀐다
- 감사 로그 `event_type = 'CASE_GUIDE_REGISTER'`, `result = '<접수 번호> → <버전>'`

## 묶음 등록 조립 `assemble()` (`assemble.py`, 기획 v4)

해결 사례 **묶음**(주간 분석이 만든 초안)을 등록할 때 등록 API 가 부른다. 구조·약속은 `작업대/가이드화/draft_basis_구조_초안_20261108.md` (팀 노션에도 공유).

```python
out = assemble(conn, document_id, clusters, draft_version_id, view_scope='ALL', transfer_policy='ALLOWED', actor_id=admin_id)
# clusters = [{'id', 'judgment', 'draft_md', 'draft_basis', 'receipts'}]  — API 가 [그 버전 묶음(거절 제외) + 이번 묶음] 을 계산
# out = {'version_id', 'version', 'file_path', 'sections': {묶음 id: '3.4'}, 'warnings'}
# API: 같은 트랜잭션에서 묶음 registered_version_id·draft_basis.section_no 저장, 운영 기록, commit → submit_ingest
```

| | 동작 |
|---|---|
| 조립 | **현행 md + 조각들**로 처음부터. 같은 대기 버전을 다시 조립할 때(거절 뒤 등)도 현행에서 다시 만든다 |
| 항목 추가·SEC | 조각(`### 3.N 제목` 으로 시작, 번호는 아무거나)을 3장 끝에. 번호는 현행 번호·`section_no` 가 있는 조각 번호를 먼저 잡고 없는 조각에 다음 번호. 3장 항목 표·목차 한 줄씩 |

## 초안 기준 `open_basis()` · `ticket_fragment()` (`open_basis.py`, 기획 v4)

주간 분석 워커(M4)가 묶음 초안을 만들 때 부른다. 돌려준 값을 워커가 묶음 표(`draft_basis`, 새 가이드면 `draft_md` 도)에 그대로 저장한다. **DB 쓰기·commit 없음.**

```python
open_basis(conn, 'ADD_ITEM', document_id=7, receipts_=['RCPT-0101'])   # 항목 추가·SEC_MANUAL
open_basis(conn, 'CHANGE', document_id=7, target_section='3.3')        # 변경
open_basis(conn, 'NEW_GUIDE', category_code='NET', title='…', fragments=[조각, …])   # 새 가이드 뼈대
# → {'draft_basis': {...}, 'draft_md': None | 뼈대, 'warnings': [...]}.  MANUAL_CANDIDATE → 모두 None
fragment, warnings = ticket_fragment(conn, ticket_id)                  # SEC 직접 검토: 티켓 글 → '### 3.N 제목' 조각 (AI 없음)
```

| 판단 | `draft_basis` |
|---|---|
| 항목 추가·SEC | `schema` · `judgment` · `base_version_id`(현행) · `base_md`(현행 원문, 비md 면 바꾼 md) · `section_no: null` |
| 변경 | 위 + `target_section` · `target_md` (= `assemble.item_text` 와 같은 모양 — 등록 때 그대로 비교) |
| 새 가이드 | `base_version_id`·`base_md` null · `category_code` · `required: ['1','2','3']` |

- 이미 현행에 반영된 접수 번호는 경고 (등록 때는 `assemble` 이 거부).
- 새 가이드 뼈대 (김현나 Q9): `version: v1.0`, `doc_no` 빈칸(등록 때 DC-02 문서 번호), 1장·2장 `(작성 필요)` 한 줄, 2장 증상별 바로가기 표, 3장 항목 표 + 조각들(3.1부터), 4·5장·부록 제목만(청커가 원래 빈 장은 청크로 만들지 않는다), **6장 문의처는 같은 분류 현행 가이드의 6장 복사** (없으면 다른 분류, 그래도 없으면 경고·자리 표시. 가이드 27종 6장은 모두 같다), 개정 이력 표 머리.
