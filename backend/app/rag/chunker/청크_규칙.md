# 청크 규칙 (WBS M2-1-2)

> 가이드 문서를 검색 단위(청크)로 나누는 규칙. 코드: [`chunker/__init__.py`](__init__.py) (`CHUNKER_VERSION` 1.0)
> 청크에 붙는 정보와 표 구조는 [청크_메타데이터.md](../청크_메타데이터.md)에 있다.
> 바꿀 때는 C(검색)와 같이 정하고 `CHUNKER_VERSION`을 올린다.

## 1. 원칙

설계서 7장 "한 상황의 확인 사항과 해결 절차를 함께 유지"를 따른다. 가이드에서 문의 상황 하나는 3.x 항목 하나다. 그래서 **3.x 항목 하나를 청크 하나**로 만드는 것이 기본이다.

## 2. 무엇을 청크 하나로 만드나

| 문서 부분 | 청크 (`chunk_type`) | 이유 |
|---|---|---|
| 3.x 항목 | 항목 하나 = 청크 하나 (`ITEM`) | 이런 경우·원인·조치 방법·해결 확인·해결되지 않으면이 한 청크에 있어야 답이 끊기지 않는다 |
| 항목이 없는 장 (개요·사전 확인·접수 기준·주의사항·문의처·부록) | 장 하나 = 청크 하나 (`CHAPTER`). 3장 첫머리의 항목 목록 표도 장 청크 | 대부분 짧다 (중앙 280자) |
| 자주 묻는 질문 | 질문·답변 한 쌍 = 청크 하나 (`FAQ`). FAQ 장이 하위 절(5.1·5.2)로 나뉘어도 질문 단위. 답변이 길면 항목과 같은 길이 규칙으로 나눈다. 질문 사이의 소제목(분류)은 다음 질문에 붙는다 | 질문 하나가 검색 질의와 바로 맞는다 |
| 첫 장 앞 서문 (템플릿이 아닌 문서) | `PREFACE` | 내용을 버리지 않는다 |
| 개정 이력(번호가 붙거나 `부록 ·`으로 시작해도)·문서 정보·목차·표지 | 만들지 않음 | 검색 근거가 아니다. 문서 정보는 메타데이터로 간다 |

## 3. 길이

본문이 **1,500자**(`MAX_CHARS`)를 넘으면 나눈다.

1. 소제목(이런 경우·조치 방법 …) 단위로 묶어 **1,000자**(`TARGET_CHARS`) 안팎씩 나눈다.
2. 소제목 하나가 1,500자를 넘으면 요소(문단·목록·표) 단위로 나눈다. 소제목 줄은 내용과 같은 조각으로 가고, 중간에서 시작하는 조각에는 `### 조치 방법 (계속)`을 붙인다.
3. 표는 행 단위로 나누고 조각마다 머리 행을 반복한다. 구조 없는 긴 문단은 문장 단위로 나눈다 (순서는 그대로).
4. 마지막 조각이 **200자**(`MIN_CHARS`)보다 짧으면 앞 조각에 붙인다.
5. 나뉜 조각은 같은 `unit_key`를 갖는다. 검색이 3.x 항목의 조각을 다시 붙여서 돌려준다 ([청크_메타데이터.md](../청크_메타데이터.md) 8장).

**기준값 근거** (정리본 57종): 3.x 항목 본문은 중앙 500자, 90%가 874자 이하, 최대 1,931자다. 1,500자에서 자르면 항목 대부분이 한 청크로 남고, 나뉘는 것은 화면 따라하기가 긴 항목과 공통 기준 문서의 긴 장뿐이다. 임베딩 모델(KURE-v1·BGE-M3, 8,192토큰)의 한계보다 훨씬 짧게 잡은 것은 검색 정밀도 때문이다. 검색 평가(M2-2-2, M3-2-1) 결과를 보고 바꿀 수 있다.

3.x 항목 하나(조각을 모두 합친 것)는 **4,500자**(`ITEM_UNIT_MAX`)를 넘으면 적재 검증에서 걸린다. 검색이 항목을 통째로 붙이기 때문이다. 넘으면 문서를 고친다.

## 4. 청크 글의 모양

청크 `text` 맨 앞에 **어디서 왔는지(머리말)** 를 붙인다. 이 글이 임베딩 입력(`document_chunk_embeddings.source_text`)이다. 표의 `document_chunks.content`에는 본문만 들어간다.

- 첫 줄: `문서 제목 > 장 > 항목`. 나뉜 조각은 끝에 `(2/3)`
- 둘째 줄 (항목만): 항목 머리 (가이드는 문의 유형·처리 구분·담당 부서, 매뉴얼은 문의 유형·기본 긴급도·1차 처리·이관 대상)
- 본문: 소제목은 `### `, 표는 마크다운 표(`| 칸 | 칸 |` 줄, 머리 행 뒤에 `|---|`, 칸 안의 `|`는 `\|`, 짧은 행은 빈 칸으로 채움), 그림은 `[그림] 설명`. 긴 문단을 나눌 때도 줄바꿈은 그대로 둔다

## 5. 문서 사이 중복

문의처·연락처·처리 기록 기준·대형 장애 대응 장은 최대 27개 문서에 글자까지 똑같이 들어 있다. **지우지 않고 문서마다 적재한다.** 하나만 남기면 남긴 문서가 비활성화될 때 다른 활성 문서의 근거까지 사라지고, 분류가 다른 문서의 출처가 엉뚱하게 보인다. 같은 본문은 검색 결과에서 묶는다 ([청크_메타데이터.md](../청크_메타데이터.md) 8장). `duplicate_groups()`는 묶음을 확인하는 용도다.

## 6. `unit_key`

같은 항목·장·질문의 조각을 묶는 이름이다.

| 종류 | `unit_key` | 버전을 뺀 참조 `unit_ref()` (평가 정답·피드백용) |
|---|---|---|
| 3.x 항목 | `IT-SW-003@v2.0/item:3.1` | `IT-SW-003/item:3.1` |
| 장 | `IT-SW-003@v2.0/chapter:2` · 부록은 `/chapter:부록` | `IT-SW-003/chapter:2` |
| FAQ | 질문 줄에 FAQ 번호가 있으면 `/faq:FAQ-035`, 없으면 질문 글의 지문 `/faq:q-1a2b3c4d` (순번이 아니라서 앞에 질문이 늘어도 바뀌지 않는다) | `IT-SW-002/faq:FAQ-035` |
| 서문 | `/preface:1` | `IT-X-001/preface:1` |

절 번호가 없거나 겹치면 문서 안 단위 순번(`/item:u07`)으로 대신한다 (정리본에는 없음).

**쓸 때 주의** (키에 쓰이는 글자는 `-` `@` `.` `/` `:`와 영문·숫자, 부록의 한글 `부록`뿐이다. SQL 와일드카드 `%`·`_`나 작은따옴표는 없다)
- **정렬은 `seq`로 한다.** `unit_key`나 절 번호를 글자로 정렬하면 `3.10`이 `3.2`보다 앞에 온다 (정리본에 3.10~3.13이 있다).
- **URL 경로에 넣지 않는다.** `/`가 경로 구분자로 읽힌다. API는 `document_chunks.id`를 쓰거나, 키는 쿼리 문자열로 인코딩해서 넘긴다.
- SQL에는 값을 직접 이어 붙이지 말고 바인드 변수(`:unit_key`)로 넘긴다.

`chunk_key`(`문서@버전#순번`)는 DB에 저장하지 않고 `doc_code`·`version`·`seq`로 계산한다. 입력과 `CHUNKER_VERSION`이 같을 때만 안정적이다. 앞쪽에 청크가 하나 늘면 뒤 순번이 다 바뀐다. 평가 정답처럼 오래 가는 참조에는 `unit_ref()`를 쓴다.

## 7. 샘플

정리본 md에서 뽑은 실제 결과다 (본문 일부 생략). 문서 하나 전체를 보려면 아래 "확인 명령"으로 미리보기를 만든다.

**3.x 항목이 세 조각으로 나뉜 경우** (IT-SW-003 3.1, 2,598자 → 710 · 841 · 1,047자). 세 조각 모두 `unit_key`가 `IT-SW-003@v2.0/item:3.1`이라 검색이 다시 붙인다.

```text

문의 유형: SW-03 · 처리 구분: 사용자 직접 조치 · 담당 부서: 서비스데스크

### 이런 경우
- 업무 프로그램이 "응답 없음"으로 멈춥니다.
- 프로그램을 열면 바로 꺼집니다.
…  (2/3은 '### 버전 확인·업데이트 (③·④)'부터, 3/3은 '### 추가 기능·확장 프로그램 확인 (⑥)'부터 '해결 확인·해결되지 않으면'까지)
```

## 9. 확인 명령 (저장소 루트에서)

```bash
cd backend && python -m app.rag.chunker ../dataset/guides/SW/guide/*.md --out ../참고/chunks   # 문서마다 <이름>.chunks.md 미리보기
pytest tests/test_chunker.py
```

문서마다 형식 하나만 넣어야 마지막 줄의 "같은 본문" 수가 맞다 (폴더를 통째로 주면 네 형식이 다 들어간다).

## 10. 한계·나중에 정할 것

- 기준값(1,000·1,500자)과 FAQ 머리말의 효과는 검색 평가(M2-2-2, M3-2-1)에서 다시 본다.
- "형식이 달라도 청크 경계가 같다"는 정리본에서 확인한 사실이다. 일반 업로드 문서는 원본을 보존하고, 원본을 파싱한 결과를 등록한다.
- 보수 모드로 읽힌 문서는 제목 구조가 약해 장·항목 단위가 덜 잡힌다. 그래도 길이 기준으로 나뉘고 내용은 빠지지 않는다.
- 장을 통째로 복원할지는 평가에서 장 조각만으로 답이 부족한 사례가 나오면 다시 정한다.
