# 검색 평가 (WBS M2-2-2) · 판단 평가 (M2-4-1)

질문 → 검색 → 상위 k개 안에 정답이 있는지를 **묶음별로** 채점합니다. 명령 한 번으로 점수가 나옵니다. 분류·세부 유형·긴급도·처리 방향·팀 채점은 아래 [판단 평가](#판단-평가-m2-4-1)(`judgment.py`)가 합니다.

## 명령 (backend 폴더에서)

```bash
uv run python -m app.rag.evaluation                                                   # BM25 기준선 (DB·모델 없이, 약 10초)
uv run python -m app.rag.evaluation --retriever search:bge-m3 --database-url <DB>     # 실제 검색 기능 search() (챗봇 경로)
uv run python -m app.rag.evaluation --retriever db:bge-m3 --database-url <DB>         # 적재된 벡터만 읽어 순위 (묶기는 평가 쪽에서)
uv run python -m app.rag.evaluation --role EMPLOYEE                                   # 직원 권한 (매뉴얼 제외)
uv run pytest tests/test_evaluation.py                                                # 테스트 (저장소 루트에서)
```

BM25는 기본 설치(`uv sync`)로 돈다. `search:`·`db:`는 임베딩 모델 패키지가 필요해 `uv sync --extra embedding`으로 설치한다.

| 옵션 | 뜻 |
|---|---|
| `--retriever` | `bm25`, `search:<모델>`, `db:<모델>` (쉼표로 여럿). 기본 `bm25`. 공유 DB에는 `bge-m3`만 있다 (KURE-v1은 10.26 삭제) |
| `--database-url` | `search:`·`db:` 검색기가 읽을 DB. **읽기만 한다** (`search:`는 읽기 전용 트랜잭션). `.env`는 읽지 않는다 |
| `--role` | `AGENT`(기본, 모든 문서) · `EMPLOYEE`(사내 일반만) · `ADMIN`. 역할이 볼 수 없는 문서만 정답인 질문은 빼고 수를 적는다 |
| `--sets` | `guide`(가이드 검색 질문) · `eval`(평가셋). 기본 둘 다 |
| `--questions` · `--out` | 질문 폴더(기본 `dataset/guide_review`) · 결과 폴더(기본 `작업대/평가결과`) |

결과: `<out>/<날짜시각>_<검색기>_<역할>/`에 `질문별.csv`(순위·상위 5개), `요약.md`, `요약.json`. 요약 머리에 git 커밋, 질문 파일 해시, 검색기·모델 이름, 역할을 남깁니다. **시험지가 다르면 점수를 비교하지 않습니다.**

## 시험지

| 시험지 | 정답 | 채점 |
|---|---|---|
| 가이드 검색 질문 228개 (`dataset/guide_review/*_질문.csv`) | `정답 단위` (`;`로 여럿) | 단위 적중·문서 적중. **본문이 같은 단위는 같은 정답** (같은 FAQ가 여러 문서에 있으면 검색 API가 하나로 묶으므로) |
| 평가셋 50건 (`dataset/data/eval_inquiries.csv`) | 문서: `expected_scenario` → `taxonomy.json` `scenarios[].manual`의 가이드 번호. 단위: 항목 머리 문의 유형에 그 시나리오가 있는 단위 (C의 `search/compare.py`와 같은 정의) | 문서·단위 적중. 시나리오가 `-`인 4건(EV-037~040: 가이드 없음·범위 밖·모호·정책)은 빼고 수만 적는다 |

지표: Hit@1·3·5, MRR@10. 검색 결과는 **단위** 단위로 셉니다 (나뉜 조각은 한 단위, 점수는 조각 중 가장 높은 값 — `청크_메타데이터.md` 8장 `unit_score`). **본문·외부 전송 정책이 같은 결과는 처음 나온 것 하나로 묶고**(8장 3번) 그다음 k개로 자릅니다. 묶여 들어간 출처도 정답으로 셉니다. 요약에는 git·코드 지문·단위 지문·질문 파일 해시를 남겨, 커밋 전 변경이나 가이드 변경도 구분합니다.

**묶음** (섞어서 보지 않는다)

- 가이드 질문: 전체 / 반말·무례 56 · 반말 제외 / 쉬움 36 · 쉬움 제외 / 가이드·기준 질문 · 매뉴얼 질문 / 작성자별 / 분기 질문 8 (조건부 수용 단위의 분기)
- 평가셋: 전체 / 기존 평가 40건 / 확장 평가 10건 (README 규칙상 따로 보고)

## 검색기

| 이름 | 하는 일 | 필요한 것 |
|---|---|---|
| `bm25` | 청커 결과를 메모리에 올려 키워드 검색 (단어 + 한글 2글자 묶음). **기준선** | 없음 |
| `search:<모델>` | **실제 검색 기능** `search()` (C, M3-2-2): 조각 복원·같은 본문 묶기·k×6 재시도·권한 필터 그대로. 챗봇이 쓰는 경로 | 적재된 DB, 모델 파일 |
| `db:<모델>` | DB의 청크 벡터(현행·DONE·활성 문서·역할 열람 범위)만 읽고, 질문만 `Embedder`로 임베딩해 내적. 묶기는 평가 쪽에서 | 적재된 DB, 모델 파일 (`embedding/README.md`) |

새 검색기는 `search(query, k) -> list[Hit]`만 있으면 끼울 수 있습니다. 검색 API(M3-2-2)가 생기면 그것을 감싸 넣습니다.

## 판단 평가 (M2-4-1)

평가셋 50건을 **실제 판단 흐름**(D, M4-2-1 `run_flow`)에 넣고 확정값을 채점합니다. 검색은 실제 `search()`, 분류 체계·팀·직원 이름은 같은 DB에서 읽습니다 (읽기 전용).

```bash
uv run python -m app.rag.evaluation.judgment --judge mock:oracle --database-url <로컬 DB>          # 키 없이 끝까지 (도구 확인)
uv run python -m app.rag.evaluation.judgment --judge mock:safe --database-url <로컬 DB>            # 안전 기본값만 (바닥 점수)
uv run python -m app.rag.evaluation.judgment --judge claude --database-url <로컬 DB> --limit 3     # 실제 Claude, 먼저 몇 건만
uv run python -m app.rag.evaluation.judgment --judge claude --database-url <로컬 DB> --repeat 3    # 50건 × 3회 (범위)
uv run pytest tests/test_evaluation_judgment.py                                                    # 테스트 (저장소 루트에서)
```

`langgraph`·`anthropic`(기본 설치)과 임베딩 패키지(`--extra embedding`)가 필요합니다. `--ids EV-001,EV-040`으로 문항을 고를 수 있습니다.

| 판단기 | 하는 일 |
|---|---|
| `claude` | 서버와 같은 설정 (`get_llm_adapter`: 루트 `.env`의 `LLM_API_KEY`·`LLM_MODEL`). 문항당 기본 1~2회 호출 (형식 오류·안전하지 않은 답이면 다시 부르고, SDK 재시도는 따로 있어 최대 횟수는 아님). 키가 없으면 검색 모델을 열기 전에 멈춘다 |
| `mock:oracle` | 평가셋 정답 라벨을 AI 출력으로 넣는 가짜 AI. 2차 ANSWER는 정답 세부 유형이 붙은 검색 결과(없으면 1위)를 근거로 든다. **흐름 연결과, 보정·서버 팀 규칙이 정답을 바꾸는 곳**을 본다. facts(사고 사실)는 비워 두므로 사실 기반 긴급도 규칙(보안 의심·전사 영향 등)을 검증하지는 않는다 |
| `mock:safe` | 모든 호출이 안전 기본값 (담당자 연결 제안). 바닥 점수 |

- 한 문항 = 새 대화의 첫 글 하나 (이전 대화·모은 사실 없음), 사용자는 직원(`EMPLOYEE`).
- **팀**은 서버 규칙 그대로: 범위 밖이거나 세부 유형을 모르면 서비스데스크, 아니면 세부 유형의 기본 그룹 (`services/inquiry.py`). `배정팀 비교` 26건·`안내 지원팀 비교` 22건 모두 이 값과 비교하고 따로 적는다. AI는 담당팀을 내지 않고 서버가 정하며, 답변에서 안내하는 팀 이름도 **서버가 추천 결과를 템플릿으로 넣는다** (docs/08 4.3·5.1. 프롬프트의 "담당팀·담당자 이름을 정하지 않습니다"는 AI가 reply에 팀을 지어 쓰지 말라는 뜻) → dataset README의 "답변에서 안내한 팀" = 추천 그룹이라 답변 글은 보지 않는다. 정답은 데이터셋이 시나리오마다 정한 팀(`taxonomy.json` `team`, 50개 시나리오 모두 DB 세부 유형 기본 그룹과 같음, 11.02 확인)이고, 시나리오 없는 EV-037·EV-040만 따로 정한 값이다. 추천 순서의 첫 단계인 예외 규칙(`routing_rules`)은 서버에 아직 없고 공유 DB에도 0건이라 같이 빠져 있다 (서버가 쓰기 시작하면 `team_of`도 맞춘다). `팀 평가 제외` 2건은 뺀다.
- 정답이 `-`인 칸과, EV-038(범위 밖)·EV-039(모호)의 분류·긴급도·팀은 채점에서 뺀다 (dataset README 채점 규칙). 처리 방향은 전부. 긴급도는 정확 일치 + (참고) ±1. 추가 처리(URGENT_HANDOFF·POLICY_GUIDANCE)는 2건뿐이라 목록으로.
- 기존 40건 / 확장 10건 따로. 틀린 문항은 원인 쪽(조사 후보)으로 나눈다: 검색 결과에 정답 가이드가 없음 → **검색: 가이드**, 가이드는 있는데 정답 항목(그 시나리오 코드가 붙은 단위)이 없음 → **검색: 항목** (C, M3-4-1), 그 밖 → **판단** (D, M4-4-1). 같은 본문이라 대표 결과에 묶인 결과(`also_in`)도 찾은 것으로 센다 (검색 평가와 같음).
- **EV-040 팀은 알려진 틀림**: 시나리오 없는 정책 안내라 서버 추천 그룹은 서비스데스크, 정답은 정보보안팀. 정답 처리 방향이 ANSWER(티켓을 넘기지 않음)라 평가셋·서버 규칙은 바꾸지 않고, 점수에는 그대로 세며 팀이 틀렸을 때 틀린 문항 목록에 이유를 붙인다 (`KNOWN_MISSES`). 비고는 추천 그룹 불일치만 설명하고, 같은 문항의 다른 칸 틀림(예: 처리 방향)은 따로 본다.
- 결과: `작업대/평가결과/<날짜시각>_판단_<판단기>/`에 `문항별.csv`(정답·예측·보정 규칙·검색 상위 3·근거 단위·정답 가이드/항목 찾음·실패 사유), `요약.md`, `요약.json`. 머리에 판단기·모델·git·판단 코드 지문·프롬프트 지문·평가셋 해시·검색 모델·검색 대상 지문(실행 시작 때 한 번: 현행 청크의 단위·문서 제목·머리말·위치·본문·이름표·정책, 현행 청크 벡터의 모델별 수·입력 글, 과거 사례 벡터 수·입력 글. 벡터 값 자체는 보지 않는다)·호출 수·토큰을 남긴다. **프롬프트·응답 원문(reply)은 저장하지 않는다** (docs/10 5.3).
- 검색·DB 오류나 Ctrl+C로 멈추면 **그때까지 끝낸 문항을 기록**하고 `중단`에 멈춘 문항과 오류 종류를 적는다 (종료 코드 1). 다시 돌리면 처음부터 한다. 멈춘 문항에서 이미 쓴 호출·토큰은 합계에 들어가지 않는다 (합계는 끝낸 문항 기준, 청구 내역 아님). 반복 범위는 끝까지 돈 회차만으로 낸다. `--limit`·`--repeat`는 1 이상, `--ids`에 없는 문항이 있으면 DB·모델을 열기 전에 멈춘다.
- LLM 결과는 실행마다 다를 수 있어 `--repeat`로 여러 번 돌려 범위를 적는다. 정확도는 회차별로, 혼동표는 회차 합, 틀린 문항은 모든 회차를 적는다. 50건이라 1건 = 2%p, 확장 10건은 1건 = 10%p → 점수보다 틀린 문항 목록을 본다.

## 알려진 것

- **같은 본문이 많은 장(예: 27개 문서의 '문의처')은 후보를 많이 차지한다.** 검색 API 8장의 "k × 3개 후보"만으로는 묶은 뒤 결과가 k개보다 적어질 수 있다 (BM25 기준 IT-STD-001 #4는 30개 후보에서 결과 4개). 실제 `search()`는 모자라면 k × 6으로 다시 뽑아 이 데이터에서는 문제가 없다 (후보를 충분히 받은 `db:` 결과와 순위가 모두 같음). 가이드가 늘어 같은 본문이 더 많아지면 다시 확인한다.
- `db:`와 BM25는 후보를 k × 100개 받아 평가 쪽에서 묶는다 (순위 실력만 잼). `search:`는 `search()`의 규칙을 그대로 쓴다.
- C의 `search/compare.py`(모델 선택용: 평가셋 46문항, 직원 범위, DB 없이)와 목적이 다르다. 이 도구는 M2-2-2 상시 채점용: 가이드 질문 228개 + 평가셋, 역할·묶음별, 결과에 지문·해시 기록.
