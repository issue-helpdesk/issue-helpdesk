# 청크 메타데이터 형식 (WBS M2-1-3)

> 가이드 문서·버전·청크에 넣는 값과, 검색·판단이 그 값을 쓰는 방법.
> **표 구조는 [테이블 설계서 v0.4](../../../docs/06.테이블_설계서.md)(A)를 따른다.** 이 문서는 그 표에 RAG 값을 어떻게 채우는지와, RAG에 필요해서 A에게 요청하는 수정(6장)을 담는다.
> A(DB)·C(검색)·D(AI 판단·정보 보호)가 같이 지키는 약속이라 바꿀 때는 같이 정한다. 청크를 나누는 규칙은 [청크_규칙.md](chunker/청크_규칙.md), 코드는 [`chunker/`](chunker/__init__.py).

## 1. 한눈에

- 문서 하나 → `knowledge_documents` 한 행, 버전 하나 → `document_versions` 한 행, 청크 하나 → `document_chunks` 한 행, 모델마다 임베딩 하나 → `document_chunk_embeddings` 한 행.
- **열람 범위**(`view_scope`)와 **외부 전송 정책**(`transfer_policy`)은 버전마다 따로 둔다. 외부 전송은 열람 등급으로 추론하지 않고, 없으면 `BLOCKED`다.
- 검색 필터(현행 여부·열람 범위·분류)는 청크에 복사하지 않고 `document_versions`·`knowledge_documents`와 조인해서 건다. 적재 대상이 713개라 조인 비용이 작고, 복사본을 맞추는 일이 없어진다.
- 담당 그룹·긴급도는 A의 설계대로 `inquiry_types`(기본값) + `routing_rules`(예외)로 정한다. 청크는 세부 유형 코드와 문서 원문을 `meta`에 갖는다.
- 전용 칸은 SQL 조회·정렬·제약에 쓰는 값만 둔다 (`seq`·`unit_key`·`chunk_type`·`part`·`meta`). 계산할 수 있는 값은 저장하지 않는다.

| 설계서 7.3 최소 항목 | 칸 |
|---|---|
| 문서·Chunk ID | `knowledge_documents.doc_code` · `document_chunks.id` · `seq` · `unit_key` |
| 문서 버전·활성 여부 | `document_versions.version` · `is_current` · `ingest_status` |
| 카테고리·제목·소제목 | `knowledge_documents.category_code` · `title` · `document_chunks.heading_path` |
| 열람 범위·보안 등급 | `document_versions.view_scope` |
| 외부 전송 정책 | `document_versions.transfer_policy` |
| 페이지·슬라이드·절 위치 | `document_chunks.location` · `meta.section_no` · `meta.page_start`·`page_end` |
| 본문·Embedding | `document_chunks.content` · `document_chunk_embeddings.embedding` · `source_text` |

## 2. 문서·버전 → `knowledge_documents` · `document_versions`

`document_row(doc)` · `version_row(doc, path, registration)`가 행을 만든다. `registration`은 등록 입력(`manifest.json` 한 행 또는 `POST /guides` 본문)이다.

| 칸 | 넣는 값 | 비고 |
|---|---|---|
| `knowledge_documents.doc_code` | `IT-SW-002` | |
| `doc_type` | `GUIDE`(가이드) · `MANUAL`(매뉴얼) · **`STANDARD`**(공통 기준 IT-STD-001·002) | `STANDARD`는 추가 요청 (6장) |
| `title` · `category_code` | 문서 제목 · `ACC`~`SEC` | 공통 기준은 분류가 없어 `NULL` |
| `owner_group_id` | 문서의 관리 부서 이름 → `support_groups.id` | 적재 스크립트가 바꾼다 |
| `document_versions.version` · `file_path` · `file_format` | `v2.0` · 원문 위치 · `MD` | 정리본은 문서마다 md 하나만 등록한다 |
| `view_scope` | 열람 등급에서: `사내 일반` → `ALL`, `사내 제한` → `AGENT` | 모르는 등급은 `ADMIN` (A의 기본값) |
| `transfer_policy` | 등록 입력의 값 (3장) | 없거나 모르는 값은 `BLOCKED` |
| `is_current` · `ingest_status` | 적재 스크립트·활성화 함수가 정한다 (7장) | |

`IT-AI-001`(AI 응대 정책, `rag_target=false`)은 시스템 프롬프트로 관리하므로 Knowledge 표에 넣지 않는다.

## 3. 외부 전송 정책 `transfer_policy`

테이블 설계서 결정 2를 따른다: `ALLOWED`(그대로 전송) / `MASKED`(민감정보 제거 후 전송) / `BLOCKED`(전송 금지). 값이 없거나 불명확하면 `BLOCKED`.

- **열람 등급에서 자동으로 정하지 않는다** (설계서 7장, IT-STD-002 "외부 모델 전송 허용 여부는 열람 등급과 따로 정합니다"). 등록 입력에 명시한 값만 쓴다.
- 대상은 외부 모델(Claude API) 호출이다. 임베딩은 로컬 모델이라 해당하지 않는다.
- 정리본 57종의 값은 D가 정한 뒤 `manifest.json`에 `transfer_policy`로 넣는다. **정하기 전에는 모두 `BLOCKED`라서 외부 모델 답변 경로가 막힌다.**

| 문서 | 들어 있는 정보 (정리본 조사) | 제안 값 |
|---|---|---|
| 임직원용 가이드 27 · 공통 기준 2 | 직원 실명 0건. 공용 헬프데스크 내선·메일과 "팀장 승인" 같은 역할 이름만 | `ALLOWED` |
| 담당자용 매뉴얼 27 | 16종에 직원 실명이 3~8번씩 (예: "서비스데스크 팀장(이건우)"), 팀 내선번호, 내부 처리 절차 | **`MASKED`** 또는 `BLOCKED` (D 결정) |

`MASKED`로 하면 실명을 지우고 보내므로 IT 운영 담당자가 매뉴얼 근거 답변을 받을 수 있다. 정할 규칙:
- 지울 민감정보의 범위는 D가 정한다. 정리본에서 확인된 것은 직원 실명(`users.name`에 목록이 있음)과 팀 내선번호다.
- **마스킹이 구현되지 않았거나 실패하면 `BLOCKED`로 처리한다.** 그래야 구현 전에도 실명이 나가지 않는다.
- `BLOCKED`면 매뉴얼은 열람·검색은 되지만 외부 모델에는 들어가지 않고, 근거가 없으면 담당자 연결로 넘어간다 (PRD "전송 금지 Guide를 묻는 질문에는 AI가 답하지 않고 담당자 연결을 제안").

## 4. 열람 범위 `view_scope`

| `view_scope` | 볼 수 있는 `users.service_role` | 정리본 문서 |
|---|---|---|
| `ALL` | `EMPLOYEE` · `AGENT` · `ADMIN` | 가이드 27 · 공통 기준 2 |
| `AGENT` | `AGENT` · `ADMIN` | 매뉴얼 27 |
| `ADMIN` | `ADMIN` | 없음 (열람 등급을 모를 때의 기본값) |

열람 범위가 다른 문서는 한 청크로 합치지 않는다 (설계서 7.3). 범위 밖 청크는 검색 결과·답변·출처 어디에도 나오지 않는다. 검색 단계에서 거른다 (8장).

## 5. 청크 → `document_chunks` · `document_chunk_embeddings`

`chunk_row(chunk)`가 행을 만든다. 임베딩 입력은 `chunk.text`(머리말 + 본문)이고 `document_chunk_embeddings.source_text`에 넣는다.

**전용 칸은 SQL로 조회·정렬·제약을 거는 값만 둔다.** 나머지는 `meta`에 넣고, 계산할 수 있는 값은 저장하지 않는다. 나중에 SQL 필터가 실제로 필요해지면 그 값만 칸으로 꺼낸다.

| 칸 | 넣는 값 | 비고 |
|---|---|---|
| `id` | bigint (DB가 만든다) | `message_sources.chunk_id`가 가리킨다 |
| `version_id` | 버전 id | |
| `heading_path` | `3. 항목별 안내 > 3.1 유료 프로그램 라이선스 신청` | 장 > 항목 |
| `location` | `3.1` · `3.1 · p.4-6` · `4 · FAQ-035` | 출처 표시는 `doc_code` + `location` (예: `IT-ACC-001 3.3`, 설계서 7.3) |
| `content` | 본문 (머리말 빼고) | 답변 근거로 보여 줄 때는 `heading_path`와 같이 쓴다 |
| 아래는 **추가 요청 칸** (6장) | | |
| `seq` | `4` | 문서 안 순번. 순서대로 붙이기, 앞뒤 조각 찾기 |
| `unit_key` | `IT-SW-002@v2.0/item:3.1` | 같은 항목·장·질문의 조각 묶음 ([청크_규칙.md](chunker/청크_규칙.md) 6장) |
| `chunk_type` | `ITEM` · `CHAPTER` · `FAQ` · `PREFACE` | 복원 방식이 다르다 (8장) |
| `part` | `1` | 같은 `unit_key` 안의 조각 번호 |
| `meta` (jsonb) | 아래 "meta 계약" | 구조화 정보 보존 |

**저장하지 않고 계산하는 값**

| 값 | 계산 | 쓰는 곳 |
|---|---|---|
| `chunk_key` | `doc_code@version#seq` (예: `IT-SW-002@v2.0#004`) | 로그·미리보기에서 사람이 읽는 이름표 |
| `parts` | 같은 `unit_key` 행 수 | 조각 표시 `(2/3)` |
| 본문 지문 | `sha1(content)` | 검색 후보끼리 같은 본문 묶기 (8장) |

**meta 계약** (키 이름·타입 고정. 값이 없어도 키는 항상 있고 빈 값을 넣는다)

| 키 | 타입 | 예 | 쓰는 곳 |
|---|---|---|---|
| `section_no` | 문자열 | `3.1` · `부록` | 절 번호 |
| `inquiry_type_codes` | 문자열 배열 | `["SW-02"]` | 세부 유형 (`inquiry_types.code`). 평가 채점 연결. 적재 때 DB에 있는 코드인지 검사한다 |
| `page_start` · `page_end` | 정수 또는 null | `4` · `6` | 쪽 범위 (pdf·pptx). md·docx는 null |
| `props` | object | `{"문의 유형": "SW-02", "처리 구분": "신청·승인 후 처리"}` | 항목 머리 원문 (조건 메모 포함) |
| `subheadings` · `faq_ids` · `images` | 문자열 배열 | `["이런 경우"]` · `["FAQ-023"]` · `["sw002_license_form.png"]` | 소제목, 관련 FAQ, 그림 |
| `handling` | 문자열 | `신청·승인 후 처리` | 가이드 처리 구분 (매뉴얼은 `""`) |
| `team` | 문자열 | `엔드포인트지원팀` | 가이드 담당 부서·매뉴얼 1차 처리 (`support_groups.name` 값만) |
| `escalation_teams` | 문자열 배열 | `["네트워크팀"]` | 매뉴얼 이관 대상 |
| `urgency` | 문자열 | `P1` | 매뉴얼 기본 긴급도 (가이드는 `""`) |

`meta` 키를 바꾸거나 더하면 `CHUNKER_VERSION`을 올리고 이 표를 고친다.

`meta.team`·`meta.urgency`는 배정에 직접 쓰지 않는다. 배정은 `inquiry_types` + `routing_rules`로 한다. 정리본에서 가이드 담당 팀은 156건 중 151건이 세부 유형의 기본 그룹과 같고, 다른 5건은 `routing_rules` 예외로 넣으면 된다 (6장 끝).

**임베딩 값 규칙** (`document_chunk_embeddings`, 마이그레이션 `d20ad6bde15c`. PK `(chunk_id, model)`, `vector(1024)`, 청크를 지우면 같이 지워짐): `model`에는 이름만이 아니라 리비전·입력 처리 설정까지 적는다 (`kure-v1@6b8c…/v1`). `source_text`는 표에서 NULL을 허용하지만 적재 스크립트가 반드시 채운다. 재적재 때 같은 `model` + 같은 `source_text`인 벡터만 다시 쓴다. 벡터 인덱스는 없다 (적재 대상 713개라 전체 비교로 충분).

## 6. A에게 요청하는 수정

### 지금 (1단계 적재 전) — 청크 적재에 필요한 것

반영됨: 마이그레이션 `ce3d205d86d4`(PR #35), 공유 DB 10.20. 그 뒤 FAQ는 Knowledge에서 빠져 `faqs` 표로 옮겨졌다(`549d091e441b`, PR #39). 그래서 Knowledge에는 가이드·매뉴얼·공통 기준만 들어가고 `doc_type`은 `GUIDE`·`MANUAL`·`STANDARD`다.

| # | 표 | 수정 | 이유 |
|---|---|---|---|
| 1 | `document_chunks` | `seq int`, `unit_key text`, `chunk_type text`, `part int`, `meta jsonb default '{}'` (모두 NOT NULL) | 순서, 조각 복원, 복원 방식 구분, 구조화 정보 |
| 2 | `document_chunks` | `unique (version_id, seq)`, `unique (version_id, unit_key, part)`, `check (part >= 1)`, `check (chunk_type in ('ITEM','CHAPTER','FAQ','PREFACE'))`, `unit_key` 인덱스 | 순번·조각 번호가 겹치지 않게, 복원 조회. 조각이 빠지지 않았는지는 적재 검증(`validate()`·기준표)이 맡는다 |
| 3 | `knowledge_documents` | `doc_type` CHECK에 `STANDARD` 추가 | 공통 기준 IT-STD-001·002 (검색 대상, 분류 없음) |
| 4 | `document_versions` | `create unique index … on document_versions (document_id) where is_current`, `check (not is_current or ingest_status = 'DONE')` | 현행은 문서마다 최대 하나, 적재가 끝난 버전만 현행 (SRS GUIDE-05) |
| 5 | 기존 데이터·시드 | 기존 FAQ 청크 행 채우기(backfill), 시드의 FAQ 버전을 `is_current=false`로 | 당시 시드는 FAQ 버전을 `is_current=true` + `PENDING`으로 넣어서 #4에 걸렸다. 지금은 FAQ가 `faqs` 표로 옮겨져 시드가 Knowledge에 넣지 않는다 |

마이그레이션은 ① 새 칸을 NULL 허용으로 추가 → ② 기존 FAQ 행 채우기 → ③ 빈 값·중복·현행 둘 이상 검사 → ④ 제약 적용 순서로 한다.

### 메시지 표를 만들 때 — 답변 출처 저장에 필요한 것

반영됨: 설계서 v0.4, 마이그레이션 `d20ad6bde15c`(공유 DB 10.20). 아래대로 만들어졌다 (`matched`는 보류 그대로).

| 수정 | 이유 |
|---|---|
| `source_kind` (`DOCUMENT`/`LEGACY`) + 종류별 CHECK (`DOCUMENT`면 `legacy_inquiry_id is null and doc_code is not null and version is not null`, `LEGACY`면 `chunk_id is null and legacy_inquiry_id is not null`) | 원래 CHECK("둘 중 정확히 하나")는 청크가 지워져 `chunk_id`가 비면 깨진다 |
| `chunk_id` FK `ON DELETE SET NULL` | 같은 버전을 다시 적재해 청크가 교체돼도 출처 행이 남는다 |
| 스냅샷 `doc_code`·`version`·`location`·`excerpt` | 답변 당시의 출처를 그대로 보존한다. `excerpt`는 요약이 아니라 **실제로 근거로 쓴 본문 전체**다 |
| (보류) `matched` | 검색에 직접 맞은 조각과 복원으로 붙인 조각 구분. 검색 분석용이라 나중에 추가해도 된다 |

스냅샷을 보여 주는 API도 **열람 권한을 검사한다.** 매뉴얼(`AGENT`) 청크가 지워져도 스냅샷에는 본문이 남으므로, 일반 임직원이 그 출처를 열 수 있으면 안 된다.

**용량**: 답변 하나의 스냅샷은 약 5~6KB다 (청크 본문 평균 1.0KB × 근거 단위 5개 안팎). 프로젝트 규모(수천 건)면 수십 MB라 문제없다.
- 답변이 많아지면(예: 하루 1,000건이면 연 2GB 안팎) **같은 본문은 한 번만 저장**하도록 바꾼다: 본문은 `source_snapshots(content_hash PK, doc_code, version, location, content)`에 한 줄만 넣고, `message_sources`는 그 지문만 가리킨다. 용량이 답변 수가 아니라 서로 다른 본문 수에 비례하게 된다.
- 보존 기간은 데이터 보존 정책(설계서 미결 사항 "상담·로그 보존 기간과 삭제 기준")을 따른다. 상담을 지울 때 스냅샷도 같이 지운다.

| `effective_date`, `keywords` | 문서 원본·`ingest_meta` | 시행일 표시·키워드 검색(BM25)을 만들 때 |
| `parser_version`·`chunker_version`·파싱 경고 | `document_versions`에 `ingest_meta jsonb` 하나로 | 버전별 재적재를 골라야 할 때 |
| `page_start`·`page_end`, `section_no`, `inquiry_type_codes` | `meta` | 숫자 범위 검색·원문 뷰어·SQL 필터가 필요할 때 |
| 본문 지문 | 검색 때 계산 | DB에서 지문으로 조회해야 할 때 (+ 인덱스) |
| `document_chunks.version_id` FK `ON DELETE CASCADE` | 없음 | 버전 삭제 기능을 만들 때 |

**우리 쪽에서 거둬들인 것**: 청크 표의 필터 복사본(`access_level`·`category`·`is_active`), `embed_hash`(→ `source_text`로 비교), 청크 표의 `team`·`urgency` 칸(→ `meta`), `chunk_key`·`parts`·`content_hash`·`section_no`·`inquiry_type_codes`·`page_start`/`page_end` 전용 칸(→ 계산 또는 `meta`), 별도 표 이름(`guides`·`guide_versions`·`guide_chunks`).

**`routing_rules` 초기 규칙 후보** (테이블 설계서 5장 미결 사항). 가이드의 담당 부서가 세부 유형의 기본 그룹과 다른 곳이다.

| 세부 유형 | 대상 | 기본 그룹 | 가이드 담당 부서 | 근거 |
|---|---|---|---|---|
| ACS-01 | 개발·검증 서버·DB 권한 | 업무시스템팀 | 시스템인프라팀 | IT-ACS-002 3.1~3.4 |
| ACS-02 | 퇴사 후에도 접속·권한이 남은 것 같을 때 | 업무시스템팀 | 정보보안팀 | IT-ACS-003 3.5 |

## 7. 적재·버전 전환 (M2-2-1 적재 스크립트 · A 활성화 함수)

**준비 → 검증 → 짧은 트랜잭션으로 교체**. 준비나 검증에서 실패하면 DB에 손대지 않는다.

1. **준비** (DB 밖): 파싱 → 청크 → 선택 모델로 임베딩한다. 같은 `model` 값(`이름@리비전/전처리`, 예 `kure-v1@6b8c…/v1`)과 같은 `source_text`인 기존 벡터만 다시 쓴다. 청크를 지우면 임베딩도 같이 지워지므로(`ON DELETE CASCADE`) 다시 쓸 벡터는 이 단계에서 미리 읽어 둔다. `source_text`는 반드시 채운다.
2. **검증**: 아래를 모두 통과해야 다음 단계로 간다.
   - 파서 경고 0건, `validate(chunks) == []` (조각 번호, 3.x 항목 4,500자 이하)
   - 정리본이면 문서별 청크·항목·단위 수가 [`chunker/baseline.json`](chunker/baseline.json)과 같다. 새 문서는 담당자 확인
   - 모든 청크에 선택 모델의 임베딩이 있다
   - `meta.inquiry_type_codes`가 모두 `inquiry_types.code`에 있다
   - `manifest.json`에 `transfer_policy`가 없으면 경고한다 (`BLOCKED`로 적재)
3. **교체**
   - 새 버전: `is_current=false`, `ingest_status='PENDING'`으로 넣고, 청크·임베딩을 넣은 뒤 `DONE`. 활성화 함수(A)가 한 트랜잭션에서 이전 버전 `is_current=false`, 새 버전 `true`로 바꾼다. 실패하면 `FAILED`와 `ingest_error`가 남고 이전 버전이 그대로 현행이다.
   - 같은 버전 다시 적재 (개발 중 파서·청커 수정 뒤): 한 트랜잭션에서 그 버전의 청크를 **통째로 지우고 새로 넣는다**. 순번으로 upsert하면 앞에 청크가 늘었을 때 같은 `id`에 다른 내용이 들어가 예전 답변의 출처가 엉뚱한 글을 가리킨다. 예전 출처는 `message_sources`의 스냅샷으로 남는다 (6장). 운영 중 내용이 바뀌면 새 버전으로 등록한다.

SRS GUIDE-05의 `현행`·`초안`·`만료`는 `is_current`와 이력으로 읽는다: 현행 = `is_current`, 초안 = 한 번도 현행이 아니었던 버전, 만료 = 현행이었다가 내려온 버전. 화면에서 구분이 따로 필요하면 A와 상태 칸을 정한다.

## 8. 검색 결과 형식 (M3-1-1, C → D)

검색 API는 아래 순서로 처리한다.

1. **벡터 검색**: 선택 모델 하나의 임베딩(`document_chunk_embeddings.model`)으로 k × 3개 청크를 뽑는다. 조인 조건:
   - `knowledge_documents.is_active` (삭제·비활성 문서 제외)
   - `document_versions.is_current and ingest_status = 'DONE'`
   - `view_scope`가 사용자 역할에 맞는 것 (4장)
   - 분류로 거를 때는 `knowledge_documents.category_code = :분류 or category_code is null` (공통 기준 포함)
2. **단위 복원** (붙이는 조각과 `also_in` 출처도 1의 조건을 똑같이 통과해야 한다): `ITEM`·`FAQ`·`PREFACE`는 같은 `unit_key`의 조각을 모두 `part` 순서로 붙인다 (지금 항목은 최대 3조각). `CHAPTER`는 맞은 조각과 그 앞뒤 조각만 붙인다 (장은 최대 8조각, 약 6,500자라 통째로 넣지 않는다).
3. **중복 묶기**:
   - 본문이 같고(`sha1(content)`를 이 자리에서 계산) `transfer_policy`도 같은 단위만 하나로 묶는다. 대표는 문의 분류와 같은 문서 → 공통 문서 → 점수 순.
   - FAQ 번호만 같다고 묶지는 않는다. `faq.csv` 40건은 게시판용 `faqs` 표에 있고 검색 대상이 아니다 (설계서 결정 사항 8). 검색 근거는 가이드 안의 FAQ 청크다.
   - 묶인 나머지 출처는 `also_in`에 남긴다 (검색 후보 안에서만).
4. **개수 맞추기**: 단위가 k개보다 적으면 k × 6개로 한 번 더 뽑고, 그래도 모자라면 있는 만큼 돌려준다.

결과 하나 = 단위 하나:

```json
{
  "unit_key": "IT-SW-003@v2.0/item:3.1",
  "chunk_type": "ITEM",
  "doc_code": "IT-SW-003", "title": "업무용 SW 실행·오류 대응 가이드", "version": "v2.0",
  "location": "3.1", "heading_path": "3. 증상별 조치 방법 > 3.1 프로그램이 멈추거나 바로 꺼질 때 (기본 조치)",
  "text": "머리말 + 조각을 part 순서로 붙인 본문",
  "chunks": [{"id": 104, "part": 1, "score": null}, {"id": 105, "part": 2, "score": 0.71}, {"id": 106, "part": 3, "score": null}],
  "unit_score": 0.71,
  "score_type": "cosine:kure-v1@6b8c…/v1",
  "inquiry_type_codes": ["SW-03"],
  "handling": "사용자 직접 조치",
  "view_scope": "ALL",
  "transfer_policy": "ALLOWED",
  "also_in": []
}
```

- `chunks[].id`는 `document_chunks.id`다. 답변을 저장할 때 근거로 쓴 조각을 모두 `message_sources`에 넣고, 당시 `doc_code`·`version`·`location`과 실제로 쓴 본문(`excerpt`)을 같이 저장한다 (6장).
- `inquiry_type_codes`·`handling`은 대표 조각의 `meta`에서 꺼낸 값이다.
- `unit_score`는 실제로 맞은 조각 점수 중 가장 높은 값이다. 붙이기만 한 조각의 `score`는 `null`이다.
- 출처는 `doc_code` + `location`으로 보여 준다 (예: `IT-SW-003 3.1`). 제목·버전은 덧붙이는 정보다.
- D는 외부 모델을 부르기 직전에 `transfer_policy`를 다시 확인한다: `ALLOWED`는 그대로, `MASKED`는 마스킹한 뒤, `BLOCKED`는 빼고 보낸다. 근거가 남지 않으면 담당자 연결로 보낸다 (설계서 7장).
