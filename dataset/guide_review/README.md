# 가이드 검증 결과 (WBS D1~D6)

가이드 56종(`dataset/guides`의 검색 대상)을 DB에 넣기(M2-2-1) 전에 확인한 결과와, 검색 평가에 쓸 질문 228개입니다 (이 중 56개는 반말·무례 말투 묶음).

| 파일 | 내용 |
|---|---|
| `{분류}_검증시트.md` | 문서마다 자동 대조 결과와 검색 단위(항목 3.x · 장 · FAQ) 목록, 단위마다 확인 표시 |
| `{분류}_질문.csv` | 문서마다 검색 질문 3개 이상과 정답 단위 (`IT-ACC-001/item:3.2` 형식) |

분류는 ACC · ACS · HW · SW · NET · SYS · SEC · STD 8개입니다. 만드는 도구와 명령은 [`backend/app/rag/review/README.md`](../../backend/app/rag/review/README.md)에 있습니다.

## 왜 필요한가

- **적재 전 확인**: 틀린 파싱·잘못 나뉜 단위·틀린 열람 등급이 DB에 들어가면 검색과 권한 필터가 그 값을 그대로 씁니다. WBS는 가이드 검증(D1~D6)을 적재(M2-2-1)의 선행 작업으로 둡니다.
- **검색 시험지**: 질문은 평가 도구(M2-2-2)에서 검색 적중률(Hit@k · MRR)을 잴 때 씁니다. 평가셋(`dataset/data/eval_inquiries.csv`, 50건)은 실제 문의 말투로 AI 전체를 채점하고, 이 질문들은 **문서·단위마다 빠짐없이** 검색을 시험합니다. 임베딩 모델 비교(M3-2-1)에도 같은 질문을 씁니다.

WBS 완료 기준(문서마다): ① 파싱 결과 = 원문 ② 분류·열람 권한 확인 ③ 검색 질문 3개와 정답 근거.

## 어떻게 만들었나

| 단계 | 누가 | 결과 |
|---|---|---|
| ① 원문 ↔ 파싱 결과 | 자동 (`tests/check_guides.py`) | 57종 × 4형식 구조 57/57 · 내용 1.000 |
| ① 파싱 결과 ↔ 단위 본문 (빠짐·순서) | 자동 (시트의 "단위 본문 ↔ 파싱 결과" 줄) | 56종, 문단·목록·표 칸·그림 설명 14,534개 대조, 빠짐 0 · 순서 0 |
| ① 단위 경계가 자연스러운지 | Codex (청커를 만들지 않은 쪽이 검토) | 689단위 중 ☑ 685, 조건부 수용 4 (아래) |
| ② 분류·열람 권한 | 자동 (문서 ↔ `manifest.json`, 열람 등급 규칙, 시나리오 ↔ 분류체계) | 56종 ⚠ 0 |
| ③ 질문 초안 | Claude 116 + Codex 56 | 문서마다 3개 이상, 평가셋과 같거나 비슷한 질문 0 (`check`) |
| ③ 반말·무례 말투 질문 | Codex 56 (문서마다 1개) | 짧고 퉁명스러운 실제 챗봇 문의에도 검색되는지 보는 묶음. `메모`=`말투: 반말·무례`, 평가 도구가 따로 집계 |
| ③ 정답 교차 검사 | 질문을 쓰지 않은 쪽이 정답을 가린 채 다시 고름 | 기존 172: Codex 167 일치, 다른 5건 중 4건 반영(문서에 근거 없는 질문 2개 수정, 정답 추가 2개). 반말 56: Claude가 42개 블라인드로 41 일치, 1건 정답 추가 (나머지 14개는 블라인드 아님) |

질문 작성 규칙: 직원·담당자가 실제로 칠 법한 말투(반말 묶음은 욕설·비하 없이 반말·명령조·줄임말), 문서 제목·본문 문장을 그대로 옮기지 않음, 평가셋 문장 금지, 오류 메시지 원문은 허용. `작성자` 칸에 누가 썼는지, `메모` 칸에 고친 이유가 있습니다.

### 조건부 수용 4건

원문이 서로 다른 두 상황을 한 항목에 묶은 경우입니다. 청커는 "항목 하나 = 단위 하나" 규칙대로 나눴고, 분기별 조치가 구분돼 내용이 보존되므로 **이번 적재는 현 구조로** 갑니다. 각 분기를 따로 묻는 질문(메모에 `분기:` 표시)으로 검색과 답변을 평가한 뒤 원문 분리 여부를 정합니다.

| 단위 | 묶인 두 상황 | 후속 |
|---|---|---|
| IT-SW-003-M 3.2 | 보호된 보기 해제 · 앱 로그인 창 멈춤 | 분리 검토 1순위. 먼저 항목 안 분기 소제목 명확화 |
| IT-ACS-001-M 3.4 | 정책에 따른 권한 회수 · 임시·고권한 부여 | 답변에서 두 승인 조건을 혼동하는지 확인 |
| IT-NET-001 3.2 · IT-NET-001-M 3.2 | VPN 후 사내 시스템 안 열림(DNS) · 화상회의 느림(분할 터널링) | 유지에 무게 |

## 남은 일

1. **사람 검수 — 질문**: 228개의 말투·난이도. 정답은 교차 검사로 확인됐고, 반말 묶음 중 블라인드가 안 된 14개는 정답도 봅니다. 다 본 줄은 `메모`에 `검수`(고쳤으면 `검수·수정`).
2. **사람 검수 — 경계 표본**: 분류마다 1개 문서(STD-002 · ACC-001 · ACS-001 · NET-002 · SW-001 · HW-001 · SYS-001 · SEC-003-M)는 사람이 미리보기와 원문을 비교합니다. 확인하면 그 문서 단위의 `문제` 칸 `Codex` 뒤에 ` · 사람 확인`을 적습니다.
3. **팀 확인**: D1~D6은 6명이 나눠 맡은 일인데 56종 전체를 한 번에 진행했습니다. 각 담당자는 자기 분류의 시트·질문을 훑어보고 의견을 남깁니다.
4. 위가 끝나면 노션 D1~D6 Done, 적재(M2-2-1) 시작.

## 이어서 작업할 때

- **질문 추가**: 언제든 됩니다. 같은 문서 번호로 줄을 추가하고(`번호` 4, 5 …) `check`로 오류 0 · 경고 0을 확인합니다. 단, 평가 결과를 비교할 때는 같은 시점의 질문 파일을 써야 합니다 (평가 도구가 커밋을 함께 기록).
- **가이드가 바뀌면**: 시트를 다시 만들어야 하는데 `--force`는 확인 표시와 `문제` 칸을 지웁니다. 바뀐 문서만 `--name`을 따로 줘서 새로 만든 뒤 비교하고, 기존 시트의 해당 문서 부분만 바꿉니다. 질문의 정답 단위가 사라졌으면 `check`가 오류로 알려 줍니다.
- 평가셋 문장은 질문에 쓰지 않습니다 (`dataset/README.md`).
