## 1. 개요

#### 목적

IT-ACS-002로 들어오는 개발·검증 서버·DB 권한 요청(신규, 변경·연장·종료, 승인 후 접속 실패)을 같은 기준으로 처리한다.

#### 담당 범위

| 항목 | 내용 |
| --- | --- |
| 1차 처리 | 서비스데스크(L1): 신청 경로 안내, 권한 문제와 장애 구분 |
| 2차 이관 | 시스템인프라팀(L2): 서버·DB 계정·역할·인증 수단 반영·회수 / 네트워크팀: VPN·경로 |
| 배정 기준 | 업무시스템팀 전자결재·권한 담당(서준호, 신유나)이 접수·승인을 확인하고, 서버 작업은 시스템인프라팀 개발 서버·DB 담당(하소율, 연하린)이 한다. 재배정은 각 팀장이 승인 |
| 관련 시스템 | 서버·DB 접근 관리 화면, 그룹웨어 IT 요청·전자결재, VPN 관리 콘솔 |

## 2. 접수·분류 기준

임직원용 가이드의 항목별 기본값입니다. 긴급도 기준은 IT-STD-001 IT 서비스 운영 기준을 따릅니다.

| 번호 | 문의 유형 | 증상·요청 | 기본 긴급도 | 1차 처리 | 처리 방식 | 이관 대상 |
| --- | --- | --- | --- | --- | --- | --- |
| 3.1 | ACS-01 | 서버·DB 권한 신규 반영 | P4 | 시스템인프라팀 | 티켓 | 없음 |
| 3.2 | ACS-01 | 변경·연장·종료 | P4 | 시스템인프라팀 | 티켓 | 없음 |
| 3.3 | ACS-01 | 승인 후 접속 실패 진단 | P4 | 서비스데스크 | 티켓 | 시스템인프라팀 / 네트워크팀 |

#### 처리 방식

- 즉시 처리: 안내만으로 끝낸 건. 티켓 없이 상담 기록만 남긴다.
- 티켓: 담당자 조치가 필요한 건. 담당 팀에 배정하고 상태를 RDY → WIP → FIN → CLS 로 관리한다. FIN은 담당자 처리 완료, CLS는 문의자가 해결을 확인한 최종 종료다.

#### 긴급도 조정 조건

- ACS-01은 기본 P4다. 팀 배포가 막혔다면 권한이 아니라 장애(SYS-15, P2)인지 먼저 확인한다.
- 무단 접근·키 노출 의심은 최소 P2로 보고 정보보안팀에 넘긴다.

## 3. 증상별 처리 절차

### 3.1 서버·DB 권한 신규 반영

**문의 유형** ACS-01 · **기본 긴급도** P4 · **1차 처리** 시스템인프라팀 · **처리 방식** 티켓 · **이관 대상** 없음

**접수 시 확인 질문**

- 자원 소유·환경(사내/고객사, 개발/검증/운영)은?
- 필요한 작업(조회·실행·배포)과 기간은?
- 접속 수단(VPN·경로·인증 수단)은?

**판단 기준**

- 운영·고객사·관리자 권한은 별도 승인 경로를 확인한다. 경로가 불명확하면 보류한다.
- 신청자에게 개인키·비밀번호·토큰을 요구하지 않는다.


#### 처리 절차

1. 기존 계정·역할·인증 등록 상태를 조회한다.
2. 승인된 역할·그룹·인증 수단만 자원별 운영 절차로 적용한다. 일반 신청을 관리자 권한으로 대체하지 않는다.
3. 승인 환경에서 접속과 허용 기능을 확인하고 과도한 권한이 없는지 대조한다.
4. 종료 시점과 회수 담당을 등록하고 FIN 처리한다.

#### 서버 권한 작업 기록

| 항목 | 적을 내용 |
| --- | --- |
| 요청·승인 | 신청번호, 대상자, 승인 기록, 자원 소유자 |
| 환경·권한 | 환경·자원, 현재 역할과 승인된 변경 범위 |
| 기간·회수 | 시작·종료 시점, 자동 만료 여부, 회수 담당 |
| 적용·검증 | 작업자·시각, 변경 전후 상태, 검증 결과 |

#### 처리 후 안내 문구

> 서버 접근권한을 반영했습니다. 안내드린 접속 방법으로 승인된 작업만 확인해 주세요.

**재발 방지**

- 없음

**이관 시 전달 정보**

- 신청번호
- 환경·자원
- 승인 범위와 기간


### 3.2 변경·연장·종료

**문의 유형** ACS-01 · **기본 긴급도** P4 · **1차 처리** 시스템인프라팀 · **처리 방식** 티켓 · **이관 대상** 없음

**접수 시 확인 질문**

- 기존 신청번호와 현재 권한·종료일은?
- 새로 필요한 작업이나 새 종료일은?

**판단 기준**

- 프로젝트 일정 변경은 자동 연장을 뜻하지 않는다.
- 불필요해진 기존 권한도 함께 확인한다.


#### 처리 절차

1. 현재·요청 권한의 차이를 확인하고 추가 승인 범위만 적용한다.
2. 연장이면 만료 설정과 회수 예정 작업을 함께 갱신한다.
3. 종료면 자원별 접근·인증 수단을 회수하고 실제 남은 접근이 없는지 확인한다.
4. 일부 회수 실패는 범위·영향을 기록하고 후속 조치를 요청한다.

#### 처리 후 안내 문구

> 요청하신 범위(기간)로 서버 권한을 변경했습니다.

**재발 방지**

- 없음

**이관 시 전달 정보**

- 신청번호
- 변경 전후 권한·기간


### 3.3 승인 후 접속 실패 진단

**문의 유형** ACS-01 · **기본 긴급도** P4 · **1차 처리** 서비스데스크 · **처리 방식** 티켓 · **이관 대상** 시스템인프라팀 / 네트워크팀

**접수 시 확인 질문**

- 오류가 인증 실패인가요, 시간 초과인가요?
- VPN에 연결돼 있나요?
- 다른 사람도 같은가요? 배포가 막혔나요?

**판단 기준**

- 인증 실패·접근 거부: 계정·인증 등록·역할·기간을 확인한다.
- 시간 초과·연결 거부: VPN·경로·서비스 상태를 점검하고 네트워크팀 또는 서버 운영과 연계한다.
- 여러 명이 동시에 안 되거나 배포가 막히면 SYS-15로 전환한다 (IT-SYS-008-M).
- 무단 접근·키 노출 의심은 정보보안팀에 넘긴다.


#### 처리 절차

1. 반영 여부를 관리 기록과 현재 설정으로 확인한다.
2. 원인별로 위 기준에 따라 조치하거나 연계한다.
3. 사용자 접속 확인 후 FIN 처리한다.

#### 처리 후 안내 문구

> 확인 결과 권한은 정상이고 VPN 연결 문제였습니다. VPN을 다시 연결한 뒤 접속해 주세요.

**재발 방지**

- 없음

**이관 시 전달 정보**

- 오류 문구·시각
- 영향 인원·막힌 작업
- 확인 결과


> ★ **사용자에게 방화벽 해제·개인키 전송·서버 재시작을 요구하지 않는다**
>
> 허용되지 않은 조치를 대체 방법으로 안내하지 않는다.

## 4. 대형 장애 대응

- 인사 발령 자동 반영이 여러 사람에게 한꺼번에 되지 않으면 개별 처리를 멈추고 대표 티켓 1건으로 묶어 업무시스템팀장에게 알린다.
- 권한관리 시스템·디렉터리 동기화 장애면 시스템인프라팀과 연계하고, 복구 후 반영 결과를 대상자별로 확인한다.
- 여러 사람이 동시에 같은 시스템에 접근하지 못하면 권한이 아니라 시스템 장애로 보고 IT-SYS-003-M을 따른다.
- 복구 후 연결된 티켓을 한꺼번에 종료하고(해결 방법: "MI-YYYY-NN 대형 장애 복구로 일괄 해결") 장애 보고서를 남긴다.

## 5. 처리 기록 기준

티켓을 종료(FIN)할 때 아래 항목을 남깁니다.

| 항목 | 적는 내용 |
| --- | --- |
| 요청·승인 연결 | 기존 신청번호, 승인 기록 참조, 요청자·대상자 |
| 변경 대상 | 시스템·메뉴·폴더, 현재 권한, 요청 권한, 적용 기간 |
| 결과와 증빙 | 변경 전후 설정, 수행 시각·처리자, 승인 대조 결과, 검증 결과 |
| 남은 작업 | 미완료 항목·사유·담당자·다음 안내 일정, 사용자 확인 결과 |
| 가이드 반영 | 임직원용 가이드에 추가·수정이 필요한지 (필요 / 불필요) |
