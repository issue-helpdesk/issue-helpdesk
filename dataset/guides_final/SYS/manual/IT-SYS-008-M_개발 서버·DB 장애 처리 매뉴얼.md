## 1. 개요

#### 목적

개발 서버·DB 장애(SYS-15) 문의를 접수·처리하는 내부 절차를 정한다. 사용자 안내는 IT-SYS-008을 기준으로 한다.

#### 담당 범위

| 항목 | 내용 |
| --- | --- |
| 1차 처리 | 서비스데스크(L1): 서버 이름·영향 범위 확인 후 시스템인프라팀 배정 |
| 2차 이관 | 시스템인프라팀(L2): 서버 디스크·로그 정리와 로그 순환 설정, 빌드 연동 토큰 재발급, DB 동기화 커넥터 조정 |
| 배정 기준 | 시스템인프라팀 L2 · 개발 서버·DB 영역 (SYS-15) |
| 관련 시스템 | 서버 모니터링 화면, 빌드 서버 관리 화면, DB 관리 화면 |

## 2. 접수·분류 기준

사용자 가이드의 블록별 기본값이다. 긴급도 기준은 IT-STD-001 IT 서비스 운영 기준을 따른다.

| 번호 | 문의 유형 | 증상·요청 | 기본 긴급도 | 1차 처리 | 처리 방식 | 이관 대상 |
| --- | --- | --- | --- | --- | --- | --- |
| 3.1 | SYS-15 | 개발 서버 SSH 불가·배포 막힘 | P2 | 시스템인프라팀 | 티켓 | 없음 |
| 3.2 | SYS-15 | Git·빌드 서버 연동 실패 | P2 | 시스템인프라팀 | 티켓 | 없음 |
| 3.3 | SYS-15 | 개발 DB·검색엔진 동기화 실패 | P2 | 시스템인프라팀 | 티켓 | 없음 |

#### 처리 방식

- 즉시 처리: 서비스데스크(L1)가 안내만으로 끝낸 건. 티켓 없이 상담 기록만 남긴다.
- 티켓: 담당자 조치가 필요한 건. 담당팀에 배정하고 상태를 RDY → IP → FIN → CLS 으로 관리한다.

#### 긴급도 조정 조건

- 배포 일정이 막힌 팀 단위 장애는 기본 P2로 처리한다.
- 여러 개발팀이 동시에 서버를 쓰지 못하면 P1로 올리고 대표 티켓으로 묶는다.
- 서버에서 무단 접근 흔적이 보이면 SEC-05로 정보보안팀에 바로 연결한다.

## 3. 증상별 처리 절차

### 3.1 개발 서버에 SSH 접속이 안 되고 배포가 막힘

**문의 유형** SYS-15 · **기본 긴급도** P2 · **1차 처리** 시스템인프라팀 · **이관 대상** 없음

**접수 시 확인 질문**

- 어느 서버인가요?
- 팀 전체가 접속하지 못하나요?
- 사내망·VPN에서 접속했나요?

**판단 기준**

- 팀 전체가 안 되면 P2 티켓으로 시스템인프라팀에 배정한다.
- 혼자만 안 되면 계정·권한(ACS-01) 문제로 분류한다.


#### 처리 절차

1. 서버 디스크 사용률을 확인한다.
2. 오래된 로그를 정리하고 로그 순환을 설정한다.
3. 서비스를 재시작하고 SSH·배포를 확인한다.

#### 처리 후 안내 문구

> 서버 디스크를 정리하고 서비스를 다시 시작했습니다. 접속과 배포를 확인해 주세요.

**재발 방지**

- 서버 디스크 사용률 80% 알림 설정

**이관 시 전달 정보**

- 없음 (시스템인프라팀에서 종결)


### 3.2 업데이트 이후 Git 저장소와 빌드 서버 연동이 실패함

**문의 유형** SYS-15 · **기본 긴급도** P2 · **1차 처리** 시스템인프라팀 · **이관 대상** 없음

**접수 시 확인 질문**

- 어느 저장소·빌드 작업인가요?
- 업데이트 이후부터인가요?
- 빌드 로그가 있나요?

**판단 기준**

- 인증 오류면 티켓으로 토큰을 다시 발급한다.


#### 처리 절차

1. 빌드 로그에서 인증 오류를 확인한다.
2. 연동 토큰을 다시 발급하고 연동 설정을 갱신한다.
3. 빌드를 다시 실행해 확인한다.

#### 처리 후 안내 문구

> 빌드 연동 토큰을 다시 발급했습니다. 빌드를 다시 실행해 주세요.

**재발 방지**

- 토큰 만료 사전 알림 등록

**이관 시 전달 정보**

- 없음 (시스템인프라팀에서 종결)


### 3.3 업데이트 이후 개발 DB와 검색엔진 동기화가 실패함

**문의 유형** SYS-15 · **기본 긴급도** P2 · **1차 처리** 시스템인프라팀 · **이관 대상** 없음

**접수 시 확인 질문**

- 어느 DB·인덱스인가요?
- 업데이트 일시는 언제인가요?

**판단 기준**

- 업데이트 후 동기화 실패면 티켓으로 커넥터 호환성을 점검한다.


#### 처리 절차

1. 커넥터와 DB·검색엔진 버전을 확인한다.
2. 커넥터 버전을 맞춘다.
3. 전체를 다시 동기화하고 결과를 확인한다.

#### 처리 후 안내 문구

> 동기화 커넥터 버전을 맞추고 전체를 다시 동기화했습니다.

**재발 방지**

- 업데이트 전 호환성 검증 단계 추가

**이관 시 전달 정보**

- 없음 (시스템인프라팀에서 종결)


## 4. 대형 장애 대응

1. 여러 개발팀이 동시에 개발 서버·DB를 쓰지 못하면 대형 장애로 판단한다.
2. 대표 티켓(MI-YYYY-NN)을 만들고, 같은 증상의 개별 문의는 대표 티켓에 연결한다.
3. 그룹웨어 공지사항에 장애 공지를 올리고 30분마다 갱신한다.
4. 복구 후 개별 문의를 대표 티켓 기준으로 일괄 완료(FIN) 처리하고, IT운영·보안 조직장에게 원인을 보고한다.

처리 완료(FIN) 시 티켓에 아래 항목을 남긴다. 반복되는 건은 사용자 가이드 반영 여부를 검토한다.

| 항목 | 기록 내용 |
| --- | --- |
| 원인 | 확인된 원인 한 줄 (예: VPN 클라이언트 구버전 사용) |
| 조치 내용 | 실제로 한 조치. 즉시 처리면 앞에 [즉시 처리] |
| 재발 방지 | 같은 문의를 줄이기 위한 조치 (없으면 '없음') |
| 관련 FAQ | 안내에 쓴 FAQ 번호 |
| 가이드 반영 | 사용자 가이드에 추가·수정이 필요한지 (필요 / 불필요) |
