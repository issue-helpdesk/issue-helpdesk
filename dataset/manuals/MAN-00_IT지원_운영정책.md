# MAN-00. IT 지원 운영 정책

> 가상 ICT 기업의 IT 지원 가이드입니다. 실존 조직·시스템과 무관합니다.
> 근거 데이터: ITssue_HelpDesk_데이터셋_최종본 (분류체계·문의 이력 400건·FAQ·담당자)

## 공통 규칙 (모든 문의에 똑같이 적용)

1. **본인 확인 후 조치**: 비밀번호 초기화, 계정 잠금 해제, MFA 초기화처럼 계정에 손대는 조치는 본인 확인(사번 + 휴대폰 인증) 후에만 합니다. 비밀번호는 메신저·메일로 그대로 보내지 않습니다.
2. **보안 우회 안내 금지**: 보안 프로그램(백신/EDR)을 끄거나 지우는 방법, SSL 인증서 검증을 끄는 방법(verify=False 등)처럼 보안 장치를 피해 가는 방법은 안내하지 않습니다.
3. **관리자 권한 미부여**: 사용자에게 PC 관리자 권한을 주지 않습니다. 설치가 필요하면 담당자가 원격으로 설치합니다.
4. **승인이 필요한 일은 담당자에게**: 권한 부여, 보안 예외 승인처럼 승인이 필요한 일은 AI가 직접 처리하지 않습니다. 절차를 묻는 문의는 안내(ANSWER)하고, 실제 처리 요청은 담당자 배정(ESCALATE)으로 넘깁니다.
5. **영향 범위 먼저 확인**: 한 명만 겪는 문제(개인)인지, 팀·층 전체(부서)인지, 회사 전체(전사)인지 먼저 확인합니다. 범위가 넓을수록 긴급도가 높습니다.
6. **긴급도 올리기**: "팀 전체", "다른 분들도", "전부"처럼 여러 사람이 영향을 받으면 한 단계 이상 올립니다. 링크 클릭·비밀번호 입력·계정 도용 의심처럼 보안 사고 가능성이 있으면 최소 P2로 처리하고 정보보안팀에 바로 넘깁니다. 당일 마감·고객 미팅처럼 시간 제약이 있으면 한 단계 올릴 수 있습니다.
7. **대형 장애 후보 알리기**: 짧은 시간에 같은 증상 문의가 여러 건 들어오면 대형 장애 후보로 보고 담당팀에 바로 알립니다.
8. **장비 안전**: 물에 젖었거나 파손된 장비는 전원을 끄고 충전기를 분리한 뒤 다시 켜지 않도록 안내합니다.
9. **기밀 정보 보호**: 고객 정보·개인정보·소스코드 같은 기밀은 생성형 AI 등 승인되지 않은 외부 도구에 입력하지 않도록 안내합니다.

## 1. 접수 채널

- **ITssue 도입 전**: 전화(내선 가상 1000), 메일, 메신저 #it-helpdesk 채널로 접수했습니다. 서비스데스크 상담원(L1)이 먼저 받아 간단한 문의는 바로 안내해 끝내고(즉시 처리), 나머지는 티켓을 만들어 처리했습니다.
- **ITssue 도입 후**: ITssue 챗봇 하나로 접수합니다. 챗봇이 바로 안내하거나, 담당자 조치가 필요하면 티켓을 만들어 배정합니다. (FAQ-040)

|---|---|---|---|
| ACC | 계정·로그인 | 비밀번호 만료·초기화, 계정 잠금, MFA, 통합 로그인(SSO) 장애 | MAN-01 |
| ACS | 접근권한 | 시스템·폴더 접근권한 신청, 부서 이동·퇴사에 따른 권한 변경 | MAN-02 |
| NET | VPN·네트워크 | 사내 Wi-Fi, 유선 LAN, 인터넷 속도, 개인·전사 VPN 장애 | MAN-03 |
| SW | SW·라이선스 | SW 설치·라이선스, 오피스 문서, 비밀번호 관리자, 개발도구 인증서, 메일 프로그램 | MAN-04 |
| HW | HW·업무 PC | 업무 PC 속도·부팅, 모니터·도킹, 장비 수리·교체·반납, OS 업데이트, 프린터·복합기 | MAN-05 |
| SYS | 사내 시스템 | 전자결재, ERP, 인사·근태, 업무 협업 플랫폼, 메일·메신저·화상회의, 공유 드라이브·파일서버, 개발 서버·DB | MAN-06 |
| SEC | 정보보안 | 피싱 메일, 악성코드·보안 알림, 매체·반출 예외, 시스템 침해 의심, 계정 도용, 웹사이트 차단 해제, 장비 분실 | MAN-07 |

분류가 헷갈리기 쉬운 경우:

- 계정 도용 의심·이상 로그인 알림 → ACC가 아니라 **SEC-06**
- 업무 사이트 차단 해제 → NET이 아니라 **SEC-07**
- 메일 프로그램(PC에 설치된 앱) 오류 → SYS가 아니라 **SW-06**
- 메일 수신·반송·서버, 메신저·화상회의 → **SYS**
- 프린터·복합기 → **HW**

## 3. 긴급도 기준

| 등급 | 명칭 | 판단 기준 | 응답 목표 | 해결 목표 |
|---|---|---|---|---|
| P1 | 긴급 | 전사 또는 여러 부서의 업무가 멈춘 경우 | 15분 | 240분 |
| P2 | 높음 | 부서 단위로 영향이 있거나 개인 업무를 전혀 할 수 없는 경우 | 30분 | 480분 |
| P3 | 보통 | 개인 업무 일부에 지장이 있지만 우회할 수 있는 경우 | 120분 | 960분 |
| P4 | 낮음 | 단순 문의·요청으로 업무 지장이 없는 경우 | 240분 | 2400분 |

> 응답·해결 목표 시간은 기존 헬프데스크 데이터의 값입니다.

긴급도를 올리는 기준은 맨 위 공통 규칙(5~7번)을 따릅니다. 과거 문의 이력에서도 "급합니다", "오늘 마감" 문의는 P3 → P2로 처리했습니다.

## 4. 처리 단계와 처리 상태

| 단계 | ITssue 도입 전 | ITssue 도입 후 |
|---|---|---|
| 접수·1차 안내 | 서비스데스크 상담원(L1)이 전화·메일·메신저로 받아 간단한 건은 바로 안내 (즉시 처리) | 챗봇이 FAQ·가이드를 근거로 안내 |
| L1 서비스데스크 | 계정 잠금 해제, 원격 지원, 기본 조치 | 같음 (챗봇이 넘긴 티켓 중 사람이 해야 하는 1차 조치) |
| L2 전문팀 | 엔드포인트지원팀, 네트워크팀, 시스템인프라팀, 업무시스템팀, 정보보안팀 | 같음 |

과거 문의 이력 400건 중 티켓으로 처리한 건은 350건, 상담원이 바로 끝낸 즉시 처리 건은 50건입니다.

티켓 처리 상태는 RDY(배정됨, 작업 전) · WIP(처리 중) · FIN(처리 완료) 세 가지입니다.

## 5. 챗봇 응대 원칙

| 행동 | 언제 | 예 |
|---|---|---|
| ANSWER (안내) | 가이드·FAQ로 사용자가 직접 해결할 수 있을 때, 절차·정책을 물을 때 | 비밀번호 재설정 방법, USB 사용 신청 절차 |
| ASK_MORE (추가 질문) | 증상이 모호해 분류·긴급도를 정할 수 없을 때 | "노트북이 이상해요" |
| ESCALATE (담당자 배정 제안) | 담당자 조치가 필요할 때, 실제 승인·권한 부여 요청, 보안 사고 의심, 다수 영향 장애 | ERP 전사 장애, 피싱 링크 클릭 |
| OUT_OF_SCOPE (범위 밖) | IT와 무관한 질문 | 점심 메뉴 추천 |

- 보안 사고 의심은 안내와 함께 긴급 담당자 연결(URGENT_HANDOFF)을 합니다.
- 정책 질문(예: 생성형 AI 사용)은 정책 안내(POLICY_GUIDANCE)를 포함해 답합니다.

### 담당자 역할

| 역할 | 배정 가능 | 하는 일 |
|---|---|---|
| L1 상담 | Y | 서비스데스크 상담원. 문의를 처음 받아 FAQ 안내, 계정 잠금 해제 같은 1차 조치를 하고, 해결하지 못하면 전문팀(L2)으로 넘깁니다. |
| L2 담당 | Y | 전문팀 담당자. 장비 수리, 서버·네트워크 작업, 보안 조사처럼 전문 지식이 필요한 티켓을 처리합니다. |
| 팀장 | N | 팀을 총괄하고 담당자 재배정을 승인합니다. 티켓을 직접 배정받지 않습니다. |
| 조직장 | N | IT운영·보안 조직 전체를 총괄합니다. 티켓을 직접 배정받지 않습니다. |

시나리오별 담당팀과 담당자는 각 분류 가이드(MAN-01~07)와 assignees.csv에 있습니다.

## 7. 대형 장애(Major Incident) 처리

1. 대표 티켓 1건을 정하고, 이후 들어오는 같은 증상 티켓은 대표 티켓에 연결합니다.
2. 전사 공지를 보내고 챗봇 첫 화면에 장애 안내를 띄웁니다.
3. 복구되면 연결된 티켓을 한꺼번에 종료하고(해결 방법: "MI-xxxx 대형 장애 복구로 일괄 해결"), 장애 보고서(원인·조치·재발 방지)를 작성합니다.
