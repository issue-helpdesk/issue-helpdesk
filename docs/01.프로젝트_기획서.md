## 1. 프로젝트 개요

**ITssue HelpDesk**는 사내에서 반복적으로 발생하는 IT 문의를 AI Agent가 이해하고, 사내 Guide를 기반으로 1차 대응하는 서비스이다.

임직원 약 400명의 **가상 ICT 기업**을 대상으로, 일반 임직원의 문의를 서비스데스크와 분야별 IT 담당자가 지원하는 환경을 가정한다.

AI만으로 해결하기 어려운 문제나 실제 담당자의 조치가 필요한 요청은 **사용자의 확인을 거쳐 Jira Ticket으로 연결**한다. 담당 그룹을 추천하고 개인 담당자를 자동배정하며, 이후 처리 상태와 결과까지 사용자에게 안내한다.

> **문의 → AI 안내 → 필요 시 사용자 확인 → Ticket 생성·담당자 배정 → 실제 처리 → 결과 확인**
> 

캡스톤에서는 Claude API를 사용하되, **향후 사내 모델로 교체할 수 있는 구조와 외부 모델 사용에 따른 정보 보호를 함께 고려**한다.

## 2. 기획 배경 및 문제 정의

기업 내부에서는 계정·로그인, 접근권한, VPN·네트워크, Software·라이선스, Hardware·업무 PC, 사내 시스템, 정보보안 등 다양한 IT 문의가 반복적으로 발생한다.

간단한 문제라도 사용자는 관련 Guide나 담당자를 직접 찾아야 하고, IT 담당자는 반복적인 문의에 지속적으로 대응해야 한다.

또한 AI가 해결 방법을 안내하더라도 실제 권한 변경이나 시스템 조치가 필요한 경우, 사용자는 다시 별도의 HelpDesk나 Ticket 시스템을 찾아 요청해야 하는 경우가 많다.

### Problem

**① 반복적인 IT 문의**

유사한 문의가 반복적으로 발생하면서 IT 담당자의 대응 리소스가 소모된다.

**② 정보 탐색 및 담당자 연결의 어려움**

사용자는 적절한 Guide와 담당자를 직접 찾아야 한다. 접수 이후에도 문의를 어느 팀과 담당자에게 전달할지 판단하는 과정이 필요하다.

**③ AI 안내와 실제 업무의 단절**

실제 권한 변경이나 시스템 조치가 필요한 문제는 담당자에게 다시 요청하고, 문의 내용과 시도한 조치를 반복 설명하게 된다.

**④ 해결 경험의 재사용 부족**

담당자의 해결 경험이 조직의 Guide로 축적되지 않으면 유사한 문의가 반복되고, 지식이 개인에게 분산된다.

**⑤ 문의 이력의 분산과 추적 어려움**

메신저·메일·전화·구두 등 여러 경로로 접수된 문의의 내용과 처리 과정이 일관되게 기록되지 않아 진행 상태와 과거 해결 이력을 확인하기 어렵다.

> ITssue는 문의의 접수·안내·배정·실제 처리·결과 확인을 연결하고, 해결 경험을 재사용하는 것에서 시작한다.

## 3. 서비스 목표

AI가 대응할 수 있는 반복 문의는 근거 기반으로 안내하고, 사람의 판단이나 실제 조치가 필요한 업무는 **필요한 정보가 정리된 상태로 적절한 담당자에게 연결**한다.

### Goal

- 사내 Guide 기반 IT 문의 1차 대응
- 정보가 부족한 문의에 대한 추가 질문
- 문의 유형·긴급도·처리 방향 판단
- 사용자 확인을 거친 Jira Ticket 생성
- 담당 그룹 자동 추천 및 개인 담당자 자동배정
- 처리 상태와 결과 안내
- 담당자의 해결 경험을 사내 지식으로 축적
- **민감정보 보호와 향후 모델 교체를 고려한 서비스 구성**

## 4. Target User 및 지원 범위

## 4-1. Target User

### 👤 일반 임직원

IT 문제를 문의하고 해결 방법을 안내받는다. 담당자 처리가 필요한 경우 Ticket 초안을 확인한 뒤 접수하며, 이후 진행 상태와 결과를 확인한다.

**Needs**

- 담당자를 몰라도 바로 문의하고 싶다.
- 간단한 문제는 빠르게 해결하고 싶다.
- 해결되지 않는 문제는 적절한 담당자에게 연결하고 싶다.
- 요청 이후 진행 상황을 확인하고 싶다.

### 🛠 IT 운영 담당자

자신에게 배정된 Ticket을 전달받아 실제 조치를 수행한다.

**Needs**

- 반복적인 단순 문의를 줄이고 싶다.
- 증상·업무 영향·시도한 조치가 정리된 요청을 받고 싶다.
- 문의의 긴급도와 배정 근거를 확인하고 싶다.
- 실제 조치가 필요한 업무에 집중하고 싶다.

### ⚙️ 관리자

문의·Ticket·배정 현황과 사용자·권한·Guide를 관리한다. 필요한 경우 담당자를 재배정하고, 해결 사례를 검토하여 Guide로 활용한다.

## 4-2. IT 지원 범위

데이터셋의 분류체계에 따라 문의를 다음 **7개 카테고리**로 구분한다.

| 코드 | 카테고리 | 주요 지원 범위 |
| --- | --- | --- |
| **ACC** | 계정·로그인 | 비밀번호, 계정 잠금, MFA, 통합 로그인 |
| **ACS** | 접근권한 | 시스템·폴더 권한 신청 및 변경·회수 |
| **NET** | VPN·네트워크 | VPN, Wi-Fi, 유선 네트워크, 인터넷 |
| **SW** | Software·라이선스 | 소프트웨어 설치·오류·라이선스 |
| **HW** | Hardware·업무 PC | PC, 주변기기, 프린터, 장비 수리·교체 |
| **SYS** | 사내 시스템 | ERP, 전자결재, 인사·근태, 협업 시스템, 서버·DB |
| **SEC** | 정보보안 | 피싱, 악성코드, 침해·도용 의심, 보안 예외, 장비 분실 |

세부 조직·사용자·IT 환경과 운영 정책은 **가상 기업 환경 정의서**에서 관리한다.

## 5. 핵심 서비스 Flow

> ITssue는 **사용자 문의와 추가 질문의 답변**에서 보안 사고 의심 징후와 장애 영향 범위를 확인한다. AI의 해석과 사전 정의된 규칙으로 긴급 대응이 필요한 문의를 조기에 식별하여 **담당자 연결을 제안**한다. 실제 사고 여부와 원인은 담당자가 확인한다.
> 

### 기본 문의 Flow

: ✏️ 통합 검색은 사용자가 열람할 수 있는 **사내 Guide를 먼저 검색하고, Guide로 근거가 부족하면 도입 이전 처리 이력(과거 이력)을 검토**한다.

```
로그인
  ↓
IT 문의
  ↓
문의 명확성 확인
  ↓
필요 시 추가 질문
  ↓
통합 검색
(✏️ Guide 우선 → 부족 시 과거 이력)
  ↓
문의 유형·긴급도 분류
  ↓
처리 방향 판단
```

### Case A. AI로 해결된 경우

```
처리 방향 판단
  ↓
AI 답변 가능
  ↓
근거 기반 AI 답변
  ↓
해결 여부 확인
  ↓
해결시  (미해결 이면 추가 확인 또는 담당자 연결로 이어진다)
  ↓
종료
```

### Case B. 사람의 조치가 필요한 경우

```
담당자 처리 필요 / AI 답변 후 미해결
  ↓
담당 그룹 추천·연결 제안
  ↓
사용자 선택 (Yes 일 경우, No 일 경우 미연결로 종료)
  ↓
Ticket 초안 확인·수정
  ↓
최종 접수 확인
  ↓
내부 접수 저장·접수번호 발급
  ↓
Jira 생성·개인 자동배정
  ↓
담당자 처리
  ↓
결과 안내·사용자 해결 확인
```

> 
> 
> 
> **접수는 사용자가 담당자 연결을 선택하고 Ticket 초안을 최종 확인한 후 진행한다.**
> 
> 내부 접수번호는 `RCPT-1041`, Jira Ticket 번호는 `ITSD-1520`처럼 구분해 표시한다 (프로토타입 기준 예시).
> 
> 개인 담당자는 정해진 배정 기준에 따라 자동배정한다. 개인 선정과 관리자 확인·재배정의 세부 규칙은 별도 배정 기준과 PRD·SRS에서 정의한다.
>

## 6. 핵심 기능 및 서비스 특징

### ① Guide 기반 AI 문의 대응

사용자의 자연어 문의를 이해하고, 정보가 부족하면 추가 질문으로 문의를 명확하게 한다.

✏️ Guide를 우선 검색하고, 근거가 부족하면 과거 이력에서 유사 사례를 검토하여 처리 방향을 판단한다. 답변 가능한 문의에는 **근거와 함께 해결 방법을 안내**한다.

**기존 사람이 사용하던 Guide를 지식 기반**으로 활용하며, **AI 도입에 따른 응대 원칙은 시스템 프롬프트와 서비스 정책으로 별도 관리**한다.

### ② 권한과 외부 전송 조건을 고려한 검색

사용자의 부서와 접근 권한을 확인하여 열람 가능한 정보만 검색·답변에 활용한다.

사용자가 열람할 수 있는 정보라도 **외부 모델로 전송할 수 있는지는 별도로 판단**한다. ✏️ **과거 이력에 포함된 개인정보·업무정보에도 같은 보호 기준**을 적용한다.

### ③ 상황을 고려한 긴급도 판단

긴급도는 **P1~P4**로 구분하고, 영향 범위·업무 중단 정도·허용된 대체 방법·시간 제약·보안 위험을 종합하여 판단한다.

카테고리별 기본 긴급도를 참고하되 실제 상황에 따라 조정하며, 긴급도와 담당자 처리 필요 여부는 구분한다.

### ④ 담당 그룹 추천 및 개인 담당자 자동배정

문의 유형을 기반으로 담당 그룹을 추천하고, 사용자 확인 후 생성된 Ticket을 개인 담당자에게 자동배정한다.

배정 근거와 결과를 기록하고 관리자가 확인·재배정할 수 있도록 한다. 개인 선정과 예외 처리의 세부 규칙은 별도 배정 기준에서 정의한다.

### ⑤ AI와 사람의 업무 연결

승인·권한 변경·실제 시스템 조치가 필요한 요청은 담당자에게 연결한다.

Ticket 초안에는 문의 내용·긴급도·업무 영향·시도한 조치 등 처리에 필요한 정보를 정리한다. 접수는 사용자의 최종 확인을 거치며, AI는 실제 접근권한을 독자적으로 승인·부여하거나 시스템 조치를 수행하지 않는다.

### ⑥ 처리 상태 및 결과 연결

Jira Ticket의 진행 상태와 처리 결과를 사용자에게 안내한다. 이를 통해 사용자는 자신의 요청이 현재 어떤 상태인지 확인할 수 있다.

향후 사용자와 담당자의 추가 문의를 Ticket 중심으로 연결할 수 있도록, **Ticket에 관련 상담 세션의 식별정보**를 남긴다.

### ⑦ 해결 경험의 Knowledge화

담당자가 해결한 사례를 관리자가 검토하여 Guide로 활용한다. 이를 통해 담당자의 해결 경험을 조직의 IT 지원 지식으로 지속적으로 축적한다.

> **담당자 해결 → 관리자 검토 → Guide화 → RAG Knowledge 반영 → 다음 유사 문의에 활용**
> 

반영 전에는 **내용의 정확성·민감정보·공개 범위를 확인**한다.

### ⑧ 정보 보호 및 운영 기록

**외부 모델 호출 전 필요한 정보만 선별하고, 민감정보를 제거·가명 처리하거나 전송을 차단한다.**

**사용자 권한과 도구 실행 조건은 백엔드에서 검사**하며, **시스템 프롬프트만**으로 **보안을 통제하지 않는다.**

**문의 분류·배정·처리·모델 호출의 주요 이력을 기록하되, 로그에도 민감정보 보호 기준을 적용한다.**

### ⑨ 모델 교체를 고려한 구성

캡스톤에서는 Claude API를 사용하되, 모델 호출 계층을 분리하여 향후 사내 모델이나 다른 제공 모델로 교체할 수 있도록 설계한다.

초기에는 **싱글 Agent 기반의 명시적인 처리 흐름**을 중심으로 구현하여 비용과 복잡도를 관리한다.

## 7. 프로젝트 구현 범위

AI 문의 대응부터 사용자 확인을 거친 내부 접수, Jira 생성·개인 자동배정, 처리 결과 및 해결 확인까지 연결한다. 접수 이후의 연동·배정 예외를 내부에서 복구하는 흐름도 구현 범위에 포함한다.

### 핵심 구현 영역

- AI 기반 IT 문의 대응
- 7개 카테고리 기반 문의 분류
- 추가 질문 및 긴급도 판단
- ✏️ Guide 우선·과거 이력 보조 RAG
- 사용자 권한 및 외부 전송 조건 검사
- 민감정보 처리와 주요 운영 이력 기록
- 사용자 확인을 거친 내부 접수·접수번호 발급 및 연동·배정 예외 복구
- 담당 그룹 추천 및 개인 담당자 자동배정
- Jira 연동과 처리 상태 관리
- Ticket과 상담 세션의 연결
- 모델 교체를 고려한 호출 구조
- AI·RAG·배정·보안 동작 검증

### 확장 검토 영역

- **Ticket 기반 양방향 소통:** 사용자와 담당자의 추가 문의를 AI가 요약·정리하여 전달하는 기능. 대리 답변 범위와 사용자 확인 방식 등을 팀 내에서 논의한 후 결정한다.
- **모델 파인튜닝 실험:** 일정과 데이터가 확보되면 문의 분류 등 제한된 과제에서 효과를 비교한다. 핵심 서비스 구현의 필수 전제로 두지 않는다.
- **UI 프로토타입에서 제안된 기능 (팀 확정 전):** 아래 기능은 프로토타입에서 화면으로 구현해 본 제안이며, 구현 여부와 범위는 PRD에서 정리하고 팀 논의 후 결정한다.
    - 로그인 전 계정·로그인 상담
    - 보안·감사 알림 (접수되지 않은 보안 의심 신호를 관리자가 확인)
    - 담당자와 문의자 사이의 추가 정보 요청·답변
    - FAQ 게시와 관리

### 구현 제외 범위

- 실제 PC 원격제어 및 자동 복구
- AI의 독자적인 권한 승인
- 복잡한 전자결재 시스템
- 실제 기업 내부 데이터
- Mobile App / Voice Interface

> 세부 기능과 Must·Should·Could 우선순위는 **PRD에서 정의한다.** Must를 우선 완성하고 Should까지 구현하는 것을 목표로 하며, Could는 일정과 추가 합의에 따라 결정한다.

## 8. 기대 효과

ITssue는 반복적인 IT 문의를 AI가 1차 대응하고, 실제 조치가 필요한 업무는 담당자에게 연결함으로써 **사용자의 문제 해결 경험과 IT 운영 효율을 함께 개선**하는 것을 목표로 한다.

| 대상 | 기대 효과 |
| --- | --- |
| 일반 임직원 | Guide와 담당자를 직접 찾는 과정을 줄이고, 문의부터 처리 결과까지 하나의 Flow에서 확인한다. |
| IT 운영 담당자 | 반복 문의 부담을 줄이고, 필요한 정보와 긴급도가 정리된 Ticket을 전달받는다. |
| 관리자 | 문의·배정·처리 현황을 확인하고, 해결 사례를 Guide로 관리한다. |
| 조직 | IT 지원 과정의 단절을 줄이고, 해결 경험을 재사용 가능한 지식으로 축적한다. |

### 확장 가능성

ITssue는 다음 구조를 기반으로 한다.

> **사내 Knowledge 검색 → AI 1차 대응 → 담당자 업무 연결 → 처리 결과의 Knowledge화**
> 

향후 충분한 Knowledge와 업무 프로세스가 확보되면 인사·총무·구매 등 다른 사내 지원 업무로 적용 범위를 확장할 수 있다.

모델 교체 구조와 정보 보호 정책을 바탕으로 기업별 운영 환경에 맞춘 적용을 고려한다.

이를 통해 단순 IT 문의 Chatbot을 넘어, **반복적인 사내 문의와 실제 업무 처리를 연결하는 Enterprise AI Agent로의 확장 가능성**을 가진다.
