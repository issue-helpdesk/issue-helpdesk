## 1. 문서 개요

본 문서는 PRD에서 정의한 제품 범위를 기반으로 시스템이 충족해야 하는 **기능·비기능 요구사항과 검증 기준**을 정의한다.

각 요구사항에 고유 ID와 우선순위를 부여하여 구현 및 테스트 결과를 추적한다.

### 1.1 요구사항 ID 규칙

| 구분 | 형식 | 예시 |
| --- | --- | --- |
| 기능 요구사항 | `[영역]-[번호]` | INQ-01 |
| 비기능 요구사항 | `NFR-[영역]-[번호]` | NFR-SEC-01 |

기존 ID는 유지하고 신규 요구사항은 번호를 추가한다.

### 1.2 우선순위

| 우선순위 | 기준 |
| --- | --- |
| **Must** | MVP에 반드시 필요한 기능·보호·검증 요구사항 |
| **Should** | Must 완성 후 구현을 목표로 하는 요구사항 |
| **Could** | 일정과 추가 합의에 따라 구현을 검토하는 요구사항 |

우선순위는 PRD의 MVP Scope와 동일한 기준을 사용한다.

# 2. 기능 요구사항

모든 기능에는 **3장의 공통 보안·신뢰성 요구사항**을 적용한다. 개별 기능 표에는 동일한 보호 조건을 반복하지 않는다.

## 2.1 사용자 및 권한

: 지금 로그인한 사용자가 누구이며 무엇에 접근할 수 있는지 확인

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| USER-01 | 로그인 사용자를 식별하고 **계정 상태·부서·Role·권한 정보를 확인할 수 있어야 한다.** | Must |

접근 제한의 적용 범위와 검사 원칙은 **3.1 보안**에서 정의한다.

## 2.2 IT 문의 접수 및 명확성 확인

: 문의를 받고, 처리할 만큼 내용이 충분한지 확인

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| INQ-01 | 사용자가 자연어로 IT 문의를 입력할 수 있어야 한다. | Must |
| INQ-02 | **필요한 확인 항목**의 수집 여부를 점검하고 누락·모호한 항목을 식별해야 한다. | Must |
| INQ-03 | 부족한 정보에 대해 추가 질문하고, 답변을 기존 문의와 함께 활용해야 한다. | Must |
| INQ-04 | 접수·추가 답변에서 긴급 대응 징후를 식별하면 일반 검색 완료를 기다리지 않고 담당자 연결을 제안해야 한다. | Must |

확인 항목은 필요한 경우 **대상 시스템·영향 범위·업무 중단·대체 방법·시간 제약·보안 위험**을 포함한다.

징후는 사용자 문의와 답변에서 식별하며, 실제 사고 여부와 원인은 담당자가 확인한다.

## 2.4 문의 유형 및 긴급도 분류

: 이 문의가 무엇이며 얼마나 긴급한지 판단

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| CLASS-01 | 지원 범위의 문의를 7개 Category와 정의된 세부 유형으로 분류해야 한다. | Must |
| CLASS-02 | 문의와 추가 답변에 긴급도 규칙을 적용하여 P1~P4를 판단해야 한다. | Must |
| CLASS-03 | 분류 결과·긴급도·판단 근거를 저장해야 한다. | Must |

> **지원 Category** : 범위 밖이거나 정보가 부족한 문의를 임의의 Category로 확정하지 않는다.
> 

| 코드 | Category |
| --- | --- |
| ACC | 계정·로그인 |
| ACS | 접근권한 |
| NET | VPN·네트워크 |
| SW | Software·라이선스 |
| HW | Hardware·업무 PC |
| SYS | 사내 시스템 |
| SEC | 정보보안 |

> **긴급도 판단 기준**
> 

| Level | 명칭 | 판단 기준 |
| --- | --- | --- |
| P1 | 긴급 | 전사·여러 부서의 주요 업무 중단 또는 광범위한 보안 대응 필요 |
| P2 | 높음 | 부서 단위 업무 영향, 개인 업무 전면 중단 또는 보안 사고 의심 |
| P3 | 보통 | 개인 업무 일부에 지장이 있으나 허용된 대체 방법으로 진행 가능 |
| P4 | 낮음 | 현재 업무 지장이 없는 문의·사전 신청 |

영향 범위·업무 중단·대체 방법·시간 제약·보안 위험을 종합한다.

- “급하다”는 표현이나 일괄 신청 인원만으로 상향하지 않는다.
- 계정 공유·보안 우회는 대체 방법으로 인정하지 않는다.
- 보안 사고 의심은 최소 P2로 판단한다.
- 같은 사유로 중복 상향하지 않으며, P1 조건이 확인된 경우 P1을 적용한다.
- 긴급도와 담당자 처리 필요 여부는 별도로 판단한다.

**AI는 사실을 추출·해석하고, 백엔드는 사전 정의된 규칙을 적용한다.** 추가 답변으로 결과가 달라지면 판단을 갱신한다. 상세 기준은 공통 운영 기준에서 관리한다.

## 2.5 처리 방향 판단

: AI가 처리할 것인가, 담당자가 처리할 것인가

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| ACTION-01 | 문의와 검색 근거를 바탕으로 AI 안내·추가 확인·담당자 처리 중 처리 방향을 판단해야 한다. | Must |
| ACTION-02 | 실제 조치·승인·권한 변경·전문 판단이 필요하거나 답변 근거를 확보할 수 없으면 담당자 연결을 제안해야 한다. | Must |

외부 전송 제한으로 답변이 불가능한 경우에도 담당자 연결을 제공한다.

## 2.6 AI 답변 및 해결 확인

: AI 처리 건에 실제 답변을 주고 결과를 확인

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| ANSWER-01 | 검색 근거 기반 답변과 활용한 Guide의 출처를 제공해야 한다. | Must |
| ANSWER-02 | 답변 후 해결 여부를 확인하고, 미해결이면 추가 확인 또는 담당자 연결로 이어져야 한다. | Must |
| ANSWER-03 | AI 답변 후 설정된 시간 동안 응답이 없으면 Session을 종료하고 문의를 미확인 상태로 유지해야 한다. | Must |
| ANSWER-04 | 보관 정책에 따라 이력을 유지하고, 사용자가 종료된 문의를 다시 열어 대화를 이어갈 수 있어야 한다. | Must |

출처에는 문서와 해당 근거 위치를 식별할 수 있는 정보를 포함한다. 미응답에 따른 Session 종료 시간과 재개·후속 처리 기준은 별도로 확정한다. 미응답을 해결 완료로 처리하지 않는 원칙은 **3.2 신뢰성**을 따른다.

## 2.7 담당자 연결 및 자동 배정

: 담당자 처리가 필요한 문의를 사람에게 넘길지 사용자가 결정 하고 담당자 개인을 배정한다.

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| ASSIGN-01 | 담당자 연결을 제안하고 사용자가 진행 여부를 선택할 수 있어야 한다. | Must |
| ASSIGN-02 | 동의하면 초안 단계로, 거절하면 미해결·미연결 종료로 이어져야 한다. | Must |
| ASSIGN-03 | 문의 유형·대상 시스템과 운영 기준에 따라 담당 그룹을 추천해야 한다. | Must |
| ASSIGN-04 | Jira Ticket에 배정 규칙을 만족하는 개인 담당자를 자동배정해야 한다. | Must |
| ASSIGN-05 | 자동배정이 불가능하면 접수 건을 유지하고 관리자 확인 사유와 확인할 그룹을 기록해야 한다. | Must |

> 기본 담당 그룹은 다음과 같다.
> 

| 문의 유형 | 기본 담당 그룹 | 주요 처리 범위 |
| --- | --- | --- |
| 계정·로그인 (ACC) | 서비스데스크 | 비밀번호 초기화, 계정 잠금, MFA 등 1차 지원 |
| 접근권한 (ACS) | 업무시스템팀 | 시스템 접근권한 신청·변경·회수 |
| 사내 시스템 (SYS) | 업무시스템팀 | ERP, 전자결재, 인사시스템 장애 |
| SW·라이선스 (SW) | 엔드포인트지원팀 | 프로그램 설치·오류, 라이선스 |
| HW·업무 PC (HW) | 엔드포인트지원팀 | PC·주변기기 장애, 장비 교체 |
| VPN·네트워크 (NET) | 네트워크팀 | VPN, Wi-Fi, LAN, 인터넷 장애 |
| 정보보안 (SEC) | 정보보안팀 | 피싱, 악성코드, 계정 침해 의심 |

대상 시스템·세부 업무 규칙에 따라 다른 그룹으로 조정한다.

AI는 문의 정보를 추출하고, **백엔드는 배정 규칙에 따라 개인 선정과 배정을 수행한다.** 업무량 산정·동률 처리·제외 조건·동시 배정 규칙은 별도로 확정한다.

## 2.8 Ticket 초안 및 사용자 확인

: Jira에 보내기 전에 Ticket 내용을 확정

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| TICKET-01 | 문의 요약·대상·Category·긴급도와 근거·업무 영향·시도한 조치·추천 그룹을 포함한 초안을 생성해야 한다. | Must |
| TICKET-02 | 사용자가 초안을 확인·수정하고 최종 접수 여부를 선택할 수 있어야 한다. | Must |
| TICKET-03 | 최종 확인된 내용을 ITssue에 저장하고 내부 접수번호를 발급해야 한다. 저장 성공이 확인된 경우에만 접수 완료를 안내해야 한다. | Must |
| TICKET-04 | 접수 건에 문의·Session을 연결하고, Jira 생성 후 Ticket 식별자를 추가해야 한다. | Must |

> 
> 
> 
> 사용자 수정이 분류·긴급도·배정에 영향을 주면 재검사하고, 최종 접수할 내용이 변경되면 다시 확인받는다.
> 
> **ITssue 접수 완료와 Jira Ticket 생성 완료는 구분한다.** Jira 연동 실패가 발생해도 저장된 접수 건을 유지하며, 사용자에게 동일 문의의 재접수를 요구하지 않는다.
>

## 2.9 Jira 연동 및 Ticket 처리

: 실제 Ticket을 만들고 담당자가 처리

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| JIRA-01 | ITssue에 저장된 최종 확인 접수 건을 기준으로 Jira Ticket을 생성해야 한다. | Must |
| JIRA-02 | 생성 결과가 불명확하거나 실패하면 생성 여부 확인·재시도를 수행하고, 자동 복구가 불가능하면 관리자 확인 대상으로 전환해야 한다. | Must |
| JIRA-03 | 권한 있는 담당자가 RDY → WIP → FIN으로 상태를 변경할 수 있어야 한다. | Must |
| JIRA-04 | FIN에서 문의자가 해결을 확인하면 CLS 전환을 요청하고 반영 결과를 확인해야 한다. | Must |
| JIRA-05 | Jira 상태와 처리 결과를 ITssue에 연동해야 한다. | Must |

> 실패 건은 다음 주체가 확인하는 운영 방향으로 정의한다.
> 

| 상황 | 확인 주체 |
| --- | --- |
| Jira 생성 실패·결과 불명확 | 서비스데스크 관리자 |
| 담당 그룹 불확실 | 서비스데스크 관리자 |
| 개인 후보 없음·배정 실패 | 해당 담당 그룹 관리자 |

서비스데스크 관리자는 접수 누락 방지와 후속 처리를 맡는다. 연동 오류의 기술적 복구 담당·재시도 한도·관리자 확인 기한은 별도 확정한다.

## 2.12 관리자 및 Dashboard

: 운영 관점의 관리 및 현황 확인

| ID | 요구사항 | 우선순위 |
| --- | --- | --- |

# 4. 상태 정의

문의 상태·Jira 연동 상태·배정 상태·Ticket 처리 상태를 구분한다.

**접수 완료는 ITssue가 문의를 저장하고 후속 처리를 맡았다는 의미이며, Jira 생성이나 문제 해결 완료를 의미하지 않는다.**

## 4.1 문의 처리 상태

: ITssue의 문의 상태는 **AI 문의 처리 과정**과 **담당자 이관 여부를 기준**으로 관리한다.

| 상태 | 의미 |
| --- | --- |
| `진행 중` | 추가 질문·검색·판단·답변·해결 확인·초안 확인 등을 진행 중 |
| `AI 해결` | AI 안내 후 사용자가 해결을 확인 |
| `미확인` | AI 답변 후 해결 여부 응답 없이 Session 종료 |
| `미해결 종료` | 담당자 연결을 거절하거나 최종 접수를 취소 |
| `접수 완료` | 최종 확인된 요청이 ITssue에 저장되고 내부 접수번호가 발급됨 |
| `담당자 이관` | Jira Ticket 생성과 개인 담당자 배정이 확인됨 |

### 4.2 Jira 연동 상태 — 내부 관리

| 상태 | 의미 | 후속 처리 |
| --- | --- | --- |
| 연동 대기 | 내부 접수 완료 후 Jira 생성 대기 | 생성 요청 |
| 결과 확인 중 | 생성 요청 결과가 불명확함 | 실제 생성 여부 확인 |
| 연동 완료 | 생성과 Ticket 식별자 연결이 확인됨 | 개인 배정 및 처리 |
| 관리자 확인 필요 | 자동 확인·재시도로 완료하지 못함 | 서비스데스크 관리자 확인 |

사용자에게 기술적 오류 상태를 그대로 제시하기보다 접수번호와 연결 진행 상황을 안내한다. 실패 사유·시도·확인 결과는 내부에 기록한다.

### 4.3 배정 상태 — 내부 관리

| 상태 | 의미 | 후속 처리 |
| --- | --- | --- |
| **배정 대기·진행 중** | 담당 그룹·개인 선정 또는 Jira 배정 진행 중 | 결과 확인 |
| **배정 완료** | 유효한 개인 담당자의 Jira 배정 확인 | 담당자 처리 |
| **관리자 확인 필요** | 그룹 불확실·후보 없음·배정 실패 | 관리자 지정·재배정 |

관리자 지정 결과가 Jira에 반영되면 `배정 완료`로 변경한다.

관리자 확인은 배정 문제의 처리이며, 관리자가 실제 문의 담당자가 됐다는 의미는 아니다.

## 4.4 Ticket 처리 상태

: **Jira Ticket이 생성된 접수 건의 업무 처리 상태는 다음과 같이 관리한다.** 개인 배정 여부는 4.3의 배정 상태로 별도 관리한다.

| 상태 | 의미 |
| --- | --- |
| `RDY` | Jira Ticket 생성 후 실제 처리 대기 |
| `WIP` | 담당자 처리 중 |
| `FIN` | 담당자 처리 완료 / 문의자 해결 확인 대기 |
| `CLS` | 문의자 해결 확인 후 최종 종료 |

기본 Ticket 상태 Flow는 다음과 같다.

**`RDY → WIP → FIN → CLS`**

`FIN`은 **담당자의 처리 완료**, `CLS`는 **문의자의 해결 확인까지 완료된 최종 종료 상태**를 의미한다.

개인 배정 전에도 Ticket은 RDY일 수 있다. **FIN 이후 미해결·미응답은 자동 CLS 처리하지 않으며, 후속 정책은 별도 확정한다.**
실제 Jira 상태 매핑은 시스템 설계서에서 정의한다.

# 5. 평가 및 검증

: ITssue는 **AI / RAG 품질과 시스템 기능을 구분하여 평가 및 검증**한다.

## 5.1 Golden Set 평가

: Golden Set은 AI 및 RAG의 판단 품질을 평가하기 위한 **정답이 정의된 평가 데이터셋**이다.

| 영역 | 검증 내용 |
| --- | --- |
| 추가 질문 | 누락·모호한 정보 확인의 적절성 |
| 문의 분류 | Category·세부 유형 판단 |
| 긴급도 | Level·조정 근거·긴급 대응 징후 |
| 검색 | 관련 Guide·과거 사례 적중 |
| 처리 방향 | 안내·추가 확인·담당자 연결 판단 |
| AI 답변 | 근거 일치·출처·금지 안내 여부 |

학습·프롬프트 조정용 사례와 최종 평가용 사례를 구분한다. 지표·목표 수치는 Test & Evaluation 자료에서 관리한다.

## 5.2 Test Case 검증

: Test Case는 시스템의 개별 기능과 End-to-End Flow가 SRS의 요구사항대로 동작하는지 검증하기 위한 **기능 테스트 시나리오**이다.

| 영역 | 핵심 검증 |
| --- | --- |
| 사용자·권한 | 권한 밖 정보 조회·기능 실행 차단 |
| 외부 전송 | 전송 금지 정보·정의된 비밀정보가 실제 요청에서 제외됨 |
| 사용자 확인 | 거절·취소·미확인 시 접수 실행 없음 |
| 내부 접수 | 저장 성공·접수번호 발급, 저장 실패 시 완료 안내 없음 |
| Jira 연동 | 실패·결과 불명확 처리, 중복 생성 방지 |
| 자동배정 | 유효 후보 선정·후보 없음·그룹 불확실·배정 실패 |
| 관리자 확인 | Jira 미생성 건 조회·재시도·지정·재배정 |
| 상태 분리 | 접수·생성·배정·해결 상태를 독립적으로 반영 |
| Session | 연결·재개·권한 검사·중복 접수 방지 |
| Ticket 종료 | 사용자 해결 확인에 따른 CLS 전환 |
| Logging | 주요 사건 기록·민감정보 제외 |
| 모델 교체 | 대체 Adapter의 공통 계약·보호 검사 유지 |
| E2E | AI 해결 및 개인 자동배정 포함 담당자 처리 |
| Should 기능 | Slack·Guide 관리·Knowledge화·Dashboard |

보안 검증은 화면뿐 아니라 **실제 외부 요청과 기록 결과**를 확인한다. 배정 테스트의 예상 결과는 확정된 배정 규칙을 기준으로 작성한다.
