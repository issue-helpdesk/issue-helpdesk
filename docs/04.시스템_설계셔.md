# 2. Technical Requirements

## 2.1 기술 설계 원칙

ITssue는 다음 원칙을 기준으로 시스템을 구성한다.

### 기능별 책임 분리

Frontend, Backend, AI Agent, RAG, Database, 외부 서비스 연동의 책임을 분리한다.

### Layer 기반 Backend 구조

Backend는 기본적으로 다음 구조를 사용한다.

```
Router
  ↓
Service
  ↓
Repository
  ↓
Database
```

- **Router** : HTTP Request / Response 처리
- **Service** : Business Logic 수행
- **Repository** : Database 접근
- **Model** : Database Entity 정의
- **Schema** : API 입출력 데이터 검증

AI Agent 및 외부 서비스 연동은 Service Layer에서 필요한 기능을 호출하는 구조로 구성한다.

### 외부 서비스 의존성 분리

LLM, Jira, Slack 등 외부 서비스는 별도의 Integration Layer로 분리한다.

이를 통해 외부 API 또는 Model 변경이 핵심 Business Logic에 미치는 영향을 최소화한다.

### 설정과 코드 분리

API Key, Database URL, Model 설정 등의 환경별 설정은 `.env` 및 환경 변수로 관리하며 코드에 직접 포함하지 않는다.

# 3. Technology Stack

현재 기술 Stack은 교육 과정에서 사용한 기술을 우선 적용하며, 프로젝트 구현 과정에서 변경할 수 있다.

| 영역 | 기술 | 적용 | ITssue 적용 이유 | 대안 / 검토 사항 |
| --- | --- | --- | --- | --- |
| **Language** | **Python 3.12** | 적용 예정 | AI/RAG 생태계가 풍부하고 교육 과정의 Backend·AI 코드를 그대로 활용하기 좋다. | 변경 필요성 낮음 |
| **Frontend** | **Streamlit** | 적용 예정 | 짧은 개발 기간에 Chat·Dashboard·관리 화면을 빠르게 구현하기 적합하다. | **React/Next.js**가 UI 자유도는 높지만 MVP 기간에는 개발 부담이 큼 |
| **Backend API** | **FastAPI** | 적용 예정 | 비동기 API와 Pydantic 기반 검증을 지원하며 AI Service와 연동하기 편하다. | 변경 필요성 낮음 |
| **Validation** | **Pydantic v2** | 적용 예정 | AI 출력 및 API 입출력 데이터를 명확한 Schema로 검증할 수 있다. | FastAPI와 궁합이 좋아 유지 권장 |
| **ORM** | **SQLAlchemy** | 적용 예정 | User·Inquiry·Ticket·Guide 등의 관계형 데이터를 Python 객체 기반으로 관리하기 적합하다. | 변경 필요성 낮음 |
| **Migration** | **Alembic** | 적용 예정 | 팀 개발 중 변경되는 DB Schema를 Version 단위로 관리할 수 있다. | SQLAlchemy와 함께 사용 권장 |
| **Main DB** | **PostgreSQL** | 적용 예정 | 사용자·문의·Ticket 등의 관계형 데이터와 pgvector를 하나의 DB에서 관리할 수 있다. | SQLite는 초기 개발은 간단하지만 팀 프로젝트·Vector Search에는 PostgreSQL이 적합 |
| **Vector Search** | **pgvector** | 적용 예정 | PostgreSQL 안에서 Embedding Vector를 저장·검색하여 별도 Vector DB 없이 RAG를 구현할 수 있다. | **Qdrant / Chroma** 등도 가능하지만 MVP에서는 인프라가 추가됨 |
| **LLM Framework** | **LangChain** | 적용 예정 | Prompt, Parser, Retriever, Chain 등 LLM/RAG 구성 요소를 연결하고 관리하기 편하다. | 단순 호출만 필요하다면 SDK 직접 사용도 가능 |
| **Agent Workflow** | **LangGraph** | 적용 예정 | 추가 질문·검색·AI 답변·담당자 처리처럼 분기되는 Agent Flow를 상태 기반으로 표현하기 적합하다. | Flow가 단순해질 경우 일반 Python Service Logic으로도 구현 가능 |
| **LLM** | **Claude API** | 적용 예정 | 교육 과정에서 구축한 LLMPort/Adapter 구조를 재사용하면서 분류·판단·답변 생성에 활용할 수 있다. | **OpenAI API 등**으로 교체 가능하도록 Adapter 구조 유지 권장 |
| **Embedding** | **KURE-v1 / BGE-M3** | **비교 후 확정** | 한국어 사내 Guide 검색에 적합한 Model을 실제 ITssue 데이터로 비교하여 선택할 수 있다. | Golden Set으로 Retrieval 성능 비교 후 하나를 Main Model로 확정 권장 |
| **Observability** | **Langfuse** | 적용 예정 | LLM 호출·Prompt·Token·Latency·Retrieval 결과를 추적하여 Agent 문제를 분석하기 좋다. | MVP 시간 부족 시 핵심 Trace부터 제한 적용 가능 |
| **Ticket** | **Jira REST API** | 적용 예정 | AI가 해결하지 못한 문의를 실제 담당자 업무 Ticket으로 연결하고 상태를 관리할 수 있다. | 상태 동기화는 **Polling vs Webhook** 추가 결정 필요 |
| **Notification** | **Slack API** | 적용 예정 | Ticket 접수·배정·진행·처리 결과를 기존 업무 메신저 형태로 전달하기 적합하다. | FIN 해결 확인을 Slack 내부에서 할지 ITssue로 연결할지는 TBD |
| **Test** | **pytest** | 적용 예정 | Service·Repository·API 등의 기능을 자동화된 Test Case로 검증하기 적합하다. | 변경 필요성 낮음 |
| **Infra** | **Docker / Docker Compose** | 적용 예정 | 팀원별 개발 환경 차이를 줄이고 PostgreSQL·pgvector·Langfuse 등을 동일하게 실행할 수 있다. | 실제 배포 환경은 추후 결정 |
- 위 표에서 논의 필요한 내용 부가설명~
    
    **① Embedding Model**
    
    KURE-v1과 BGE-M3를 둘 다 최종 서비스에서 쓸 이유는 별로 없어. 수업에서 했던 것처럼 둘을 테스트한 뒤 **ITssue Guide 검색 성능이 좋은 하나를 선택**하는 게 좋아.
    
    **② LangGraph**
    
    수업에서 배운 기술이고 ITssue에도 꽤 잘 맞아. 문의 명확성 확인 → 추가 질문 → 검색 → 판단 → 답변/이관처럼 **분기가 있는 Agent**라 적용 이유도 충분해. 다만 일정이 촉박해서 구현 복잡도가 커지면 Python Service Logic으로 단순화할 수 있다는 정도만 대안으로 남기면 돼.
    
    **③ Jira 상태 동기화 방식**
    
    Jira 자체를 쓸지는 정해져 있지만, `ITssue가 Jira 상태를 어떻게 가져올 것인가`는 아직 결정할 필요가 있어.
    
    `Polling`은 구현이 단순하고, `Webhook`은 변경 즉시 반영하기 좋지만 설정이 조금 더 들어가. **2주짜리 MVP라면 처음엔 Polling/API 조회가 더 안전하고, 여유가 있으면 Webhook으로 확장**하는 쪽을 추천해.

# 5. Backend Architecture

## 5.1 기본 구조

Backend는 기능별 Module과 Layer를 분리한다.

```
backend/
└─ app/
   ├─ api/
   │   └─ routers/
   │
   ├─ schemas/
   ├─ services/
   ├─ repositories/
   ├─ models/
   │
   ├─ agent/
   ├─ rag/
   ├─ integrations/
   │
   ├─ core/
   └─ main.py
```

각 영역의 역할은 다음과 같다.

| 영역 | 역할 |
| --- | --- |
| `api/routers` | API Endpoint |
| `schemas` | Pydantic Request / Response |
| `services` | Business Logic |
| `repositories` | DB 접근 |
| `models` | SQLAlchemy Model |
| `agent` | 문의 처리 Workflow |
| `rag` | 검색 및 Document Pipeline |
| `integrations` | LLM / Jira / Slack |
| `core` | Config / DB / Logging / Exception |

> 실제 Directory 구조는 구현 과정에서 기능별 Module 구성에 따라 조정할 수 있다.

# 6. AI Agent 설계

## 6.1 Agent 처리 Flow

```
사용자 문의
   ↓
사용자 / 권한 확인
   ↓
문의 명확성 확인
   ↓
정보 부족?
 ┌─ YES ─→ 추가 질문
 │            ↓
 └──────── 재입력
              ↓
          통합 검색
              ↓
      Guide + 유사 Ticket
              ↓
       유형·긴급도 분류
              ↓
         처리 방향 판단
          ↙          ↘
      AI 답변       담당자 처리
         ↓               ↓
    해결 여부 확인    담당자 배정 제안
```

담당자 처리 이후의 Ticket 생성 및 처리 Flow는 Backend Service와 Jira Integration에서 수행한다.

---

## 6.2 Agent State

LangGraph를 사용할 경우 다음 정보를 Agent State 후보로 관리한다.

```
user
inquiry
clarification
search_results
category
urgency
decision
answer
sources
```

Ticket 및 Jira 처리 상태는 Agent State에 장기간 보관하기보다 Database 및 Jira에서 관리한다.

> **제안:** Agent는 “문의 판단과 답변”에 집중하고, Ticket Lifecycle은 Backend/Jira에서 관리하는 구조를 권장한다. Agent가 모든 업무 상태를 소유하지 않게 하여 책임을 분리할 수 있다.
> 

---

## 6.3 LLM Adapter

LLM 호출은 Business Logic에서 특정 Model SDK를 직접 호출하지 않고 Adapter를 통해 수행한다.

```
Service / Agent
      ↓
    LLMPort
      ↓
 ClaudeAdapter
      ↓
  Claude API
```

이를 통해 향후 LLM 변경 시 Agent 및 Service 코드의 변경을 최소화한다.

# 7. RAG 설계

## 7.1 Knowledge Source

검색 대상은 두 종류로 구성한다.

### Guide

관리자가 등록한 사내 IT Guide.

지원 Format:

- PPTX
- PDF
- DOCX

### 과거 유사 Ticket

기존 문의 및 담당자 처리 결과 중 검색에 활용할 수 있는 데이터.

---

## 7.2 Document Ingestion Pipeline

```
Guide Upload
     ↓
Parsing
     ↓
Chunking
     ↓
Metadata 생성
     ↓
Embedding
     ↓
PostgreSQL + pgvector 저장
```

Guide의 원본 문서 정보와 Chunk를 연결하여 검색 결과에서 출처를 확인할 수 있도록 한다.

---

## 7.3 Chunk Metadata

최소 Metadata 후보는 다음과 같다.

| Field | 설명 |
| --- | --- |
| `document_id` | 원본 Guide 식별자 |
| `category` | IT 문의 Category |
| `department` | 관련 부서 |
| `security_level` | 접근 등급 |
| `version` | 문서 Version |
| `locator` | 원본 문서 내 위치 |
| `text` | Chunk 본문 |

필요한 경우 Heading, Page 등의 정보를 추가한다.

---

## 7.4 Retrieval Flow

```
사용자 문의
   ↓
Query Embedding
   ↓
사용자 권한 Filter
   ↓
Vector Search
   ↓
Guide 검색 결과
   +
과거 유사 Ticket
   ↓
검색 결과 구성
   ↓
Agent
```

권한 Filter는 **LLM에게 검색 결과를 전달한 이후 제거하는 방식이 아니라, 검색 단계에서 적용**한다.

이를 통해 사용자가 접근할 수 없는 Guide 내용이 LLM Context에 포함되지 않도록 한다.

---

## 7.5 Answer Grounding

AI 답변은 검색된 근거를 기반으로 생성한다.

검색 근거가 충분하지 않은 경우 임의의 해결 방법을 생성하지 않고 담당자 처리 대상으로 전환한다.

답변에는 사용된 Guide의 출처 정보를 함께 제공한다.

---

# 8. Database 설계

## 8.1 주요 Entity

MVP 기준 주요 Entity는 다음과 같이 구성한다.

| Entity | 역할 |
| --- | --- |
| User | 사용자 정보 및 권한 |
| Inquiry | 사용자의 IT 문의 |
| Message | 문의별 대화 이력 |
| Guide | Guide 원본 Metadata |
| GuideChunk | 검색용 Chunk 및 Vector |
| Ticket | ITssue와 Jira Ticket 연결 정보 |
| TicketHistory | Ticket 상태 변경 이력 |
| Evaluation | AI / RAG 평가 결과 |

`Evaluation`은 Langfuse 또는 별도 평가 데이터 관리 방식에 따라 제외할 수 있다.

---

## 8.2 ERD 초안

```
User
 │ 1
 │
 │ N
Inquiry
 │
 ├──── N Message
 │
 └──── 0..1 Ticket
              │
              └──── N TicketHistory

Guide
 │ 1
 │
 │ N
GuideChunk
```

과거 Ticket을 RAG 검색 대상으로 사용할 경우 Ticket 또는 별도의 검색용 Knowledge Entity와 Vector를 연결한다.

---

## 8.3 주요 데이터 관계

- User 한 명은 여러 Inquiry를 생성할 수 있다.
- Inquiry 하나는 여러 Message를 가질 수 있다.
- Inquiry는 필요 시 하나의 Jira Ticket과 연결된다.
- Ticket은 여러 상태 변경 이력을 가질 수 있다.
- Guide 하나는 여러 GuideChunk로 분리된다.
- GuideChunk는 검색용 Embedding Vector를 가진다.

# 9. API 설계

세부 Request / Response Schema는 구현 단계에서 확정하며, 본 문서에서는 주요 Endpoint를 정의한다.

## 9.1 User / Auth

| Method | Endpoint | 역할 |
| --- | --- | --- |
| POST | `/auth/login` | 로그인 |
| GET | `/users/me` | 현재 사용자 및 권한 조회 |

---

## 9.2 Inquiry / Chat

| Method | Endpoint | 역할 |
| --- | --- | --- |
| POST | `/inquiries` | 새 문의 생성 |
| GET | `/inquiries/{id}` | 문의 조회 |
| GET | `/inquiries` | 사용자 문의 목록 |
| POST | `/inquiries/{id}/messages` | 메시지 입력 및 AI 처리 |
| POST | `/inquiries/{id}/resolution` | 해결 여부 확인 |

---

## 9.3 Ticket

| Method | Endpoint | 역할 |
| --- | --- | --- |

# 10. 외부 서비스 연동

## 10.1 Jira

Jira는 **담당자 처리 업무와 Ticket 상태의 기준 시스템(Source of Truth)**으로 사용한다.

### 주요 연동 범위

```
Ticket 초안 사용자 확인
        ↓
Jira Issue 생성
        ↓
Issue Key 저장
        ↓
담당자 / 담당 그룹 지정
        ↓
RDY → IP → FIN
        ↓
문의자 해결 확인
        ↓
CLS
```

ITssue DB에는 Jira Issue Key를 저장하여 Inquiry 및 Ticket과 연결한다.

### 상태 동기화

Jira의 Ticket 상태 변경은 ITssue에 반영한다.

구현 방식은 다음 중 프로젝트 구현 과정에서 결정한다.

- Jira API 주기적 조회
- Jira Webhook

> **제안: Jira Webhook 우선 검토** — 상태 변경이 발생할 때 필요한 정보만 전달받을 수 있어 지속적인 API 조회보다 상태 동기화 구조가 명확하다.
> 

---

## 10.2 Slack

Slack은 담당자 처리 단계의 알림 Channel로 사용한다.

주요 알림 대상은 다음과 같다.

- Ticket 접수
- 담당자 배정
- 주요 상태 변경
- FIN 처리 결과
- 문의자 해결 확인 경로

`FIN` 이후 문의자의 해결 확인을 Slack에서 직접 수행할지 ITssue 화면으로 연결할지는 미확정 사항으로 둔다.

---

# 11. 상태 관리

## 11.1 Inquiry 상태

Inquiry 상태의 정의와 전환 조건은 SRS를 기준으로 한다.

시스템에서는 다음 상태를 저장할 수 있도록 구성한다.

```
진행 중
AI 해결
미확인
미해결 종료
담당자 이관
```

Chat Session이 종료되더라도 Inquiry 및 Message 데이터는 삭제하지 않는다.

사용자가 다시 문의를 열 경우 기존 Conversation을 기반으로 이어서 처리할 수 있도록 한다.

---

## 11.2 Ticket 상태

```
RDY → IP → FIN → CLS
```

- `RDY` : 담당자 처리 대기
- `IP` : 담당자 처리 중
- `FIN` : 담당자 처리 완료 / 문의자 확인 대기
- `CLS` : 문의자 해결 확인 완료 / 최종 종료

Ticket 상태의 기준은 Jira이며 ITssue는 필요한 상태를 동기화하여 제공한다.

# 12. 인증 및 권한

## 12.1 인증

사용자는 로그인 후 ITssue 기능을 사용할 수 있다.

MVP에서는 사번 기반 사용자를 식별하며, Demo 환경의 로그인 방식은 구현 환경에 따라 결정한다.

인증되지 않은 사용자는 보호된 API 및 서비스 기능에 접근할 수 없다.

---

## 12.2 권한

기본 Role은 다음과 같이 구성한다.

```
일반 임직원
IT 운영 담당자
관리자
```

사용자 Role 및 권한에 따라 접근 가능한 기능과 데이터를 제한한다.

Guide 검색 시에도 동일한 권한 정보를 사용한다.

# 14. Error Handling

외부 서비스 및 AI 처리 실패를 정상 완료로 처리하지 않는다.

주요 오류 유형은 다음과 같이 구분한다.

| 오류 | 기본 처리 |
| --- | --- |
| 인증 실패 | 로그인 요청 |
| 권한 없음 | 접근 거부 |
| 검색 실패 | 오류 처리 / 재시도 |
| 검색 근거 부족 | 담당자 처리 대상으로 전환 |
| LLM 호출 실패 | 오류 안내 / 재시도 |
| Jira 생성 실패 | 생성 실패 상태 기록 및 재시도 |
| Slack 전송 실패 | 알림 실패 기록 |
| Parsing / Embedding 실패 | Ingestion 실패 기록 |

세부 Retry 정책 및 오류 코드는 구현 과정에서 정의한다.
