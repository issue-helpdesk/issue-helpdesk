# ITssue 테이블 설계 초안 (v0.2)

> 기준: SRS v0.4 · 시스템 설계서 v0.2 / DB: PostgreSQL + pgvector
> 데이터셋(엑셀)은 데이터의 성격을 참고하는 데만 쓰고, 테이블 구조는 기능 요구사항에서 도출함

## 0. 확정된 결정 사항

| # | 항목 | 결정 |
|---|---|---|
| 1 | 로그인 방식 | 자체 비밀번호 로그인. SSO는 나중에 `user_identities` 테이블을 추가해 확장 |
| 2 | 열람 범위 `view_scope` | `ALL`(전 직원) / `AGENT`(IT 담당자 이상) / `ADMIN`(관리자만) |
| 2 | 외부 전송 정책 `transfer_policy` | `ALLOWED`(그대로 전송) / `MASKED`(민감정보 제거 후 전송) / `BLOCKED`(전송 금지). 값이 없거나 불명확하면 `BLOCKED`로 처리 |
| 3 | 담당 그룹 추천 | 세부 유형의 기본 그룹(`inquiry_types.default_group_id`)에 예외 규칙(`routing_rules`)을 더함 |
| 4 | 과거 이력 | `legacy_inquiries`에 한 번만 적재하고 이후에는 읽기 전용. 유사 사례 검색과 도입 이전 통계에만 사용. ITssue에서 쌓이는 데이터는 `inquiries`·`tickets`에 저장 |
| 5 | 권한과 배정 역할 분리 | `users.service_role`은 ITssue 화면·API 권한(인가), `support_group_members.member_role`은 담당 그룹 안에서의 배정 역할 |
| 6 | 임베딩 분리 | 검색 대상 원본(`document_chunks`, `legacy_inquiries`)과 임베딩(`document_chunk_embeddings`, `legacy_inquiry_embeddings`)을 별도 테이블로 관리. 원본은 그대로 유지하고, 임베딩은 모델별로 저장해 비교 실험이 가능하게 함 |
| 7 | 골든셋 | 평가 문항과 결과는 DB에 저장하지 않고 파일로 관리. 결과를 대시보드에서 비교할 필요가 생기면 평가 결과 테이블을 추가 |

### 담당 그룹 추천 순서
1. `routing_rules`에서 세부 유형과 대상 시스템이 일치하는 규칙을 찾으면 → 그 규칙의 그룹 (우선순위가 높은 규칙부터)
2. 일치하는 규칙이 없으면 → `inquiry_types.default_group_id`
3. 그래도 확정하기 어려우면 → `support_groups.is_triage = true`인 그룹(서비스데스크)이 확인

### 공통 규칙
- PK는 `bigint identity`. 사람이 읽는 번호(사번, 접수번호, 문서 코드)는 별도의 UNIQUE 컬럼
- 시각은 모두 `timestamptz`
- 상태·구분 값은 `text` + `CHECK` 제약

## 7. 배정 보완 제안 (M5-1-3 검토, 팀 확정 전)

> 담당자 시드(50명)와 세부 유형 50개를 대조한 결과. `db/seed.py`의 "기본 그룹에 배정 가능한 담당자가 없음" 경고와 같은 문제를 다룬다.

### 7.1 배정 사유 코드 (`tickets.assign_reason` 추가 제안)

| 코드 | 상황 | `assign_status` |
|---|---|---|
| `SCENARIO_NOT_IDENTIFIED` | 세부 유형을 판별하지 못해 `is_triage` 그룹으로 보냄 | PENDING → 검토 |
| `NO_ELIGIBLE_ASSIGNEE` | 그룹 안에 배정 가능한 후보가 없음 | NEEDS_ADMIN |
| `ACCOUNT_NOT_LINKED` | ITssue 배정은 했지만 담당자 Jira 계정이 없음 | ASSIGNED (Jira엔 레이블) |
| `JIRA_NOT_READY` | Jira 생성 전·실패 (`integration_jobs` 재시도) | 유지 |
| `JIRA_ASSIGNMENT_REJECTED` | 이슈는 있으나 Jira가 배정을 거절 | NEEDS_ADMIN |
| `ASSIGNMENT_RESULT_PENDING` | 응답 시간 초과, Jira 조회로 확인 중 (`jira_sync_status=VERIFYING`) | 유지 |

### 7.2 Jira 계정은 후보 조건이 아님
- Jira 무료 플랜은 담당자 계정이 3명이라, 계정 있는 사람만 후보로 남기면 43명 중 최대 3명만 배정된다.
- 담당자는 ITssue에서 먼저 정하고(`tickets.assignee_id`), Jira에는 `jira_account_id`가 있으면 assignee, 없으면 레이블 `asg-<사번>`과 처리 담당자 칸(customfield_10122)으로 남긴다.

### 7.3 후보 0명·1명
- SEC-08(장비 분실)은 `member_skills`에 담당자가 없어 항상 0명이다.
- 후보가 1명뿐인 세부 유형: SW-06 · SYS-04 · SYS-05 · SEC-03 · SEC-05 · SEC-07
- 제안: `member_skills` 일치 후보가 없으면 같은 그룹의 `assignable=true` 구성원 전체로 넓힌다(2차 규칙). 그래도 없으면 NEEDS_ADMIN.

### 7.4 P1 전사 장애 묶음
- 대상 세부 유형: ACC-04 · NET-03 · SYS-03 · SYS-09 · SYS-16 · SEC-04
- '미완료 적은 순'만 쓰면 같은 장애 문의가 팀원에게 한 건씩 흩어진다(과거 NET-03 12건이 4명에게 분산).
- 제안: 같은 세부 유형의 열린 P1 티켓이 있으면 같은 담당자에게 배정하고 그룹 MANAGER에게 알린다.

### 7.5 그룹 밖 skill
- 서비스데스크 곽지민·이윤호의 `member_skills`에 있는 HW-01 · HW-03 · NET-02 · SYS-14는 기본 그룹이 달라 후보로 뽑히지 않는다. 시드에서 빼거나 "서비스데스크 1차 점검" 규칙(`routing_rules`)으로 정한다.
