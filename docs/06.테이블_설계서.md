# ITssue 테이블 설계 초안 (v0.9)

> **현행 구현 기준:** 2026-11-08 · develop `bcaf885`.
> 화면→API→서비스→저장·외부 연동을 대조했다. 구현 경로 확인과 실제 운영·모델 품질 검증은 구분한다. 본문의 **미구현 요구/확장 계획**은 현재 제공 기능이 아니다.
> 근거는 본문의 코드 경로와 관련 문서를 따른다. 날짜가 있는 과거 변경 이력은 당시 기록으로 유지한다.

> **표기:** 🆕 신규 추가 · ✏️ 수정 (2026.10.26 정책 정정분)

> 기준: SRS v0.8 · 시스템 설계서 v0.6 / DB: PostgreSQL + pgvector
> 데이터셋(엑셀)은 데이터의 성격을 참고하는 데만 쓰고, 테이블 구조는 기능 요구사항에서 도출함

## 0. 확정된 결정 사항

| # | 항목 | 결정 |
|---|---|---|
| 1 | 로그인 방식 | 자체 비밀번호 로그인. SSO는 나중에 `user_identities` 테이블을 추가해 확장 |
| 2 | 열람 범위 `view_scope` | `ALL`(전 직원) / `AGENT`(IT 담당자 이상) / `ADMIN`(관리자만) |
| 2 | 외부 전송 정책 `transfer_policy` | `ALLOWED`(그대로 전송) / `MASKED`(민감정보 제거 후 전송) / `BLOCKED`(전송 금지). 값이 없거나 불명확하면 `BLOCKED`로 처리 |
| 3 | 담당 그룹 추천 | 세부 유형의 기본 그룹(`inquiry_types.default_group_id`)에 예외 규칙(`routing_rules`)을 더함 |
| 4 | 과거 이력 | `legacy_inquiries`에 한 번만 적재하고 이후에는 읽기 전용. 유사 사례 검색과 도입 이전 통계에만 사용. ITssue에서 쌓이는 데이터는 `inquiries`·`tickets`에 저장 |
| 5 | 권한과 배정 역할 분리 | `users.service_role`은 ITssue 화면·API 권한(인가), `support_group_members.member_role`은 담당 그룹 안에서의 배정 역할 |
| 6 | 임베딩 분리 | 검색 대상 원본(`document_chunks`, `legacy_inquiries`)과 임베딩(`document_chunk_embeddings`, `legacy_inquiry_embeddings`)을 별도 테이블로 관리. 원본은 그대로 유지하고, 임베딩은 모델별로 저장해 비교 실험이 가능하게 함 |
| 7 | 골든셋 | 평가 문항과 결과는 DB에 저장하지 않고 파일로 관리. 결과를 대시보드에서 비교할 필요가 생기면 평가 결과 테이블을 추가 |
| 8 | FAQ 분리 | FAQ는 게시판용 `faqs` 테이블로 따로 관리하고 Knowledge(검색 대상)에 넣지 않음. 같은 FAQ가 가이드 안에 청크로 이미 들어 있어(출처 위치 포함) AI 검색 근거는 가이드 청크를 사용 |
| 9 | pgvector 활성화 | 마이그레이션에서 `create extension if not exists vector`로 켬. Supabase 화면 설정에 기대지 않아 Docker 등 다른 PostgreSQL로 옮겨도 `alembic upgrade head`만으로 같은 DB가 만들어짐. 대신 그 PostgreSQL에 pgvector가 설치돼 있어야 함 (예: `pgvector/pgvector` 이미지) |

### 담당 그룹 추천 순서
1. `routing_rules`에서 세부 유형과 대상 시스템이 일치하는 규칙을 찾으면 → 그 규칙의 그룹 (우선순위가 높은 규칙부터)
2. 일치하는 규칙이 없으면 → `inquiry_types.default_group_id`
3. 그래도 확정하기 어려우면 → `support_groups.is_triage = true`인 그룹(서비스데스크)이 확인

### 공통 규칙
- PK는 `bigint identity`. 사람이 읽는 번호(사번, 접수번호, 문서 코드)는 별도의 UNIQUE 컬럼
- 시각은 모두 `timestamptz`
- 상태·구분 값은 `text` + `CHECK` 제약

## 0.1 물리 모델 대조

현재 모델 선언은 35개이며 `api_requests`는 아래 설계 표에만 있는 후속 테이블이다. `inquiries.processing_token`·유효활동·숨김·이탈 정리 컬럼도 현행 모델에 없다. 따라서 설계 표의 전체 수를 실제 구축 테이블 수로 쓰지 않는다. `UNCONFIRMED`·`NO_RESPONSE`는 CHECK에서 허용되지만 현재 문의 서비스의 미확인 표시는 파생값이고 시간 경과만으로 이 값을 쓰지 않는다. 실제 모델·컬럼·FK는 `backend/app/models/`와 Alembic 마이그레이션을 기준으로 확인한다.

- 행 하나 = 판단 시점 하나. 위의 분류·긴급도·처리 방향 칸은 규칙까지 적용한 **최종값**이고, `ai_output`은 같은 시점의 **AI 원래 판단**이다
- 규칙이 바꾼 것이 없으면 `override_reasons`는 빈 배열이다
- AI 단독 정확도와 규칙 적용 후 정확도를 나눠 보고, AI가 틀린 곳을 찾아 프롬프트를 고치는 데 쓴다 (SRS 2.4 "AI는 사실을 추출·해석하고, 백엔드는 사전 정의된 규칙을 적용")

| `URGENT_CLOSED` | 긴급 징후 후 접수 없이 종료 | 긴급 징후 확인 뒤 연결을 거절하고 종료 (`URGENT_CLOSED`, AUDIT-04 Must) | inquiry | HIGH |
| `MASS_QUERY` | 비정상 대량 질의 | 감지 기준 미정 (5장). 값만 먼저 둔다 | user | MEDIUM |

- **합치기**: 같은 `(alert_type, subject_user_id, target_type, target_id)`에 종결 전 알림이 있으면 새로 만들지 않고 `occurrence_count`·`last_detected_at`·`detail`을 갱신한다. 종결 뒤 다시 감지되면 새 알림을 만든다. 한 메시지에 여러 유형이 가려져도 알림은 하나다.
- **상태 이동**: `NEW` → `IN_REVIEW` → `CLOSED`만 허용한다. 되돌리지 않는다.
- **원문 열람**: `target_type = inquiry`면 그 문의의 사용자 메시지를 저장된 그대로(저장 전 가림 이후) 보여 준다. 비밀정보·고유식별·금융정보는 저장 전에 가려지므로 다시 볼 수 없다 (PRD 4.17, 10 5.2). `target_type = user`는 열람할 글이 없다.
- **처리 이력**: 확인 시작·종결·원문 열람은 `audit_logs`에 `target_type = security_alert`로 남긴다 (`SECURITY_ALERT_REVIEW`·`SECURITY_ALERT_CLOSE`·`SECURITY_ALERT_VIEW`, `reason`에 종결·열람 사유). 별도 이력 표는 두지 않는다.
- CHECK: `status = 'IN_REVIEW'`면 `reviewer_id`·`review_started_at` NOT NULL. `status = 'CLOSED'`면 위 둘과 `closed_by`·`closed_at`·`close_reason` NOT NULL.
- 인덱스: `(status, first_detected_at desc)` 목록·집계용, UNIQUE `(alert_type, subject_user_id, target_type, target_id) WHERE status <> 'CLOSED'` 합치기 보장.
- 알림이 있는 문의는 일반 이탈 삭제 대상에서 뺀다 (PRD 4.17 "보안·로그 대상이 된 문의는 삭제하지 않는다").

### H. 해결 사례 가이드화

해결 확인(CLS)된 티켓을 7일 단위로 분석해 가이드 초안을 만드는 데 쓴다 (기획 `기획_해결사례_가이드화`). 모두 ITssue DB에만 두고 Jira로 보내지 않는다. 마이그레이션 `d3a7f2c9e184`.

티켓별 상태는 `tickets`에 칸을 더하지 않고 `ticket_guide_states`로 나눈다. 칸이 5개 이상이고 주간 분석·가이드화 API만 쓰는 값이라, Jira 연동의 중심 표인 `tickets`와 섞지 않는다. 분석한 티켓만 행이 생긴다.

- CHECK: `status = 'REJECTED'`면 `reject_reason` NOT NULL.
- `draft_basis`가 필요한 이유: 관리자가 며칠 동안 고친 md를 등록할 때, 만들 때의 원본과 비교해 기존 항목·다른 사례 표식을 지우지 않았는지, 그사이 같은 가이드에 다른 초안이 등록되지 않았는지 검사한다. 등록 때 파일을 다시 읽으면 관리자가 본 원본과 달라질 수 있어 만들 때 저장한다.

- `SEC_MANUAL`은 SEC 티켓 1건당 1행이다. AI 없이 서버가 기존 1건 가이드화 기능으로 만든다.

#### ticket_guide_states: 티켓별 가이드화 상태
| 컬럼 | 타입 | 제약 | 설명 |
|---|---|---|---|
| ticket_id | bigint | PK, FK → tickets.id | 티켓당 한 행 |
| status | text | CHECK (WAITING/EXCLUDED/REVIEWING/APPLIED/REJECTED) | 비어 있으면 분석을 시도했지만 아직 판단을 받지 못함 (실패 기록만 있음) |

- 행이 없으면 아직 분석하지 않은 티켓이다. 매 회차 대상은 `work_status = 'CLS'`이면서 행이 없거나 `status`가 비었거나 `WAITING`인 티켓이다.

- 묶음에 속한 티켓의 `status`는 그 묶음의 `status`와 같다. 묶음 상태를 바꿀 때 같은 트랜잭션에서 함께 바꾼다.
- 티켓 하나는 묶음 하나에만 속한다. 거절된 티켓은 다시 분석하지 않고 새 티켓을 묶을 때 비교만 한다.
