## 2. 공통 규칙

### 2.1 기본 사항

| 항목 | 규칙 |
|---|---|
| Base URL | `/api/v1` (아래 Endpoint는 Base URL 이후 경로) |
| 형식 | `Content-Type: application/json; charset=utf-8`. 파일 업로드만 `multipart/form-data` |
| 인증 | `Authorization: Bearer {accessToken}`. 공개 API(로그인·헬스 체크·Jira 웹훅) 외에는 모두 인증 필요 |
| 요청 추적 | 요청에 `X-Request-Id`가 있으면 그대로 쓰고, 없으면 서버가 만든다. 응답 헤더와 에러 본문의 `traceId`로 돌려준다 |
| 문서화 | FastAPI가 만드는 Swagger(`/docs`)·OpenAPI(`/openapi.json`)를 함께 쓴다. 불일치하면 승인된 명세를 기준으로 원인을 확인하고 구현 또는 명세를 수정한다 |

### 2.2 Endpoint 규칙 (RESTful)

- 경로는 **리소스(명사·복수형)** 로 짓고, 동작은 HTTP Method로 표현한다.
- 단어 구분은 kebab-case를 쓴다. 예: `/ticket-drafts`, `/inquiry-types`
- Path 파라미터는 `{리소스Id}` 형식이다. 예: `/inquiries/{inquiryId}`
- 부모에 속한 리소스는 한 단계까지만 중첩한다. 예: `/inquiries/{inquiryId}/messages`
  - 자기 ID로 바로 찾을 수 있는 리소스는 최상위 경로를 쓴다. 예: 초안 생성은 `/inquiries/{inquiryId}/ticket-drafts`, 이후 조회·수정은 `/ticket-drafts/{draftId}`
- 권한별 경로(`/admin/...`)를 따로 두지 않는다. 같은 리소스는 같은 경로를 쓰고, **조회 범위와 실행 가능 여부는 서버가 권한으로 결정**한다.
- 상태 변경은 해당 리소스의 상태 컬럼을 `PATCH`로 바꾸는 방식으로 표현한다. 허용된 전이인지는 서버가 검사한다. 예: 업무 상태 변경 → `PATCH /tickets/{ticketId}` `{ "workStatus": "WIP" }`
- 재처리처럼 "새로 한 번 더 실행"하는 동작은 해당 작업 리소스를 새로 만드는 것으로 표현한다. 예: Jira 재처리 → `POST /tickets/{ticketId}/integration-jobs`

| Method | 용도 | 성공 상태 코드 |
|---|---|---|
| GET | 조회 | 200 |
| POST | 생성 | 201. 로그인·멱등 재요청·기존 이슈 연결 복구는 200, 로그아웃·웹훅은 204, 비동기 작업 접수는 202 |
| PATCH | 일부 변경 | 200 |
| PUT | 하위 단일 리소스 전체 지정 (예: 해결 확인, 배정) | 200 (비밀번호 변경은 204) |
| DELETE | 삭제 (대부분 `is_active = false` 처리) | 204 |

### 2.3 명명 규칙 (snake_case ↔ camelCase)

- 변수명은 **테이블 설계서의 컬럼명**을 그대로 쓴다.
- **Backend 내부**(Model·Schema·Service·Repository)는 컬럼명 그대로 **snake_case**를 쓴다.
- **Frontend와 주고받는 JSON**(Request·Response Body, Query 파라미터)은 **camelCase**로 변환한다.

| 테이블 컬럼 (Backend) | API 필드 (Frontend) |
|---|---|
| `employee_no` | `employeeNo` |
| `service_role` | `serviceRole` |
| `is_triage` | `isTriage` |
| `receipt_no` | `receiptNo` |
| `jira_sync_status` | `jiraSyncStatus` |
| `view_scope` | `viewScope` |
| `created_at` | `createdAt` |

Pydantic 공통 Base Schema로 변환한다.

```python
from pydantic import BaseModel, ConfigDict
from pydantic.alias_generators import to_camel


class CamelModel(BaseModel):
    model_config = ConfigDict(
        alias_generator=to_camel,  # 응답: snake_case → camelCase
        populate_by_name=True,     # 내부에서는 snake_case 이름으로도 생성 가능
        from_attributes=True,      # SQLAlchemy Model → Schema 변환
        extra="forbid",            # 정의하지 않은 필드는 422
    )
```

- Query 파라미터는 `Query(alias="categoryCode")`처럼 alias를 지정한다.
- **값(enum)은 변환하지 않는다.** DB의 CHECK 값 그대로 쓴다. 예: `"P1"`, `"IN_PROGRESS"`, `"RDY"`, `"ALLOWED"`
- 연결된 리소스는 FK 컬럼(`xxxId`)을 기본으로 주고, 화면에 이름이 필요하면 같은 이름의 객체를 함께 준다. 예: `groupId: 3`, `group: { "id": 3, "name": "서비스데스크" }`
- 테이블 컬럼이 아닌 값(계산값·집계값)은 명세서에 **파생 필드**로 표시한다. 예: 화면 배지 `displayStatus`(SRS 4.5)

### 2.4 데이터 형식

| 항목 | 규칙 |
|---|---|
| ID | `bigint` → JSON number |
| 시각 (`timestamptz`) | ISO 8601, 시간대 포함. 응답은 KST. 예: `"2026-10-21T14:03:00+09:00"` |
| 날짜 필터 | `YYYY-MM-DD`. 예: `createdFrom=2026-10-01` |
| `occurred_at` | 날짜가 아닌 **사용자 표현 그대로의 문자열** (`text`). 예: `"어제 업데이트 이후"` |
| 배열 (`text[]`) | JSON 배열. 예: `keywords: ["VPN", "접속"]` |
| `jsonb` | JSON 객체·배열 그대로 (키는 명세서에서 정의) |
| null | 값이 없는 필드도 빼지 않고 `null`로 준다 |
| Boolean | `is_` 접두어 컬럼은 그대로 `isActive`, `isCurrent` |

### 2.5 응답 형식

**단건** — 리소스 객체를 그대로 준다.

```json
{
  "id": 12,
  "receiptNo": "RCPT-0012",
  "workStatus": "RDY",
  "createdAt": "2026-10-21T14:03:00+09:00"
}
```

**목록** — 페이지 정보를 함께 준다.

```json
{
  "items": [ { "id": 12 } ],
  "page": 1,
  "size": 20,
  "totalCount": 134,
  "totalPages": 7
}
```

| Query | 규칙 |
|---|---|
| `page` | 1부터 시작. 기본 1 |
| `size` | 기본 20, 최대 100 |
| `sort` | `필드,방향`. 여러 개 가능. 예: `sort=createdAt,desc`. 기본은 API별로 명세서에서 정한다 |
| `q` | 검색어 (검색 대상 컬럼은 명세서에서 정의) |
| 필터 | 컬럼명의 camelCase. 예: `status=IN_PROGRESS&categoryCode=NET`. 여러 값은 반복 `status=RDY&status=WIP` |

**비동기 처리** — 오래 걸리는 작업은 접수 결과만 먼저 주고, 상태 컬럼으로 진행 상황을 확인한다.

| API | 먼저 주는 응답 | 진행 상황 확인 |
|---|---|---|
| 최종 접수 (TK-04) | 201 + `receiptNo`, `jiraSyncStatus: "PENDING"` | TK-06의 `jiraSyncStatus`·`assignStatus` |
| 업무 상태·처리 결과 변경 (TK-07) | 202 + 확인된 상태·`transitionStatus: "PENDING"` | TK-06의 `workStatus`·`transitionStatus` |
| 문서 버전 등록 (DC-07) | 202 + `ingestStatus: "PENDING"` | DC-08의 `ingestStatus` |

### 2.6 요청 규칙

- 서버가 관리하는 컬럼은 요청으로 받지 않는다: `id`, `created_at`·`updated_at`, `receipt_no`, `jira_key`, `jira_sync_status`, `assign_status`, `password_hash`, `ingest_status` 등
- 정의하지 않은 필드를 보내면 `422 VALIDATION_ERROR`
- Body에서 참조한 ID(예: `categoryCode`, `groupId`)가 없으면 `422 VALIDATION_ERROR`, `details[].reason = "NOT_FOUND"`
- 일반 문자열은 앞뒤 공백을 제거한다. 비밀번호·토큰·웹훅 비밀값은 원문 그대로 검사한다.
- PATCH에서 필드 생략은 유지, `null`은 nullable 필드의 값 제거이다. 빈 문자열은 trim 후 길이 제약으로 검증하며, 값을 지우려면 `null`을 보낸다. 필수·non-null 필드의 `null`은 422이다.

### 2.6.1 중복·동시 요청

- IQ-01·IQ-08·IQ-09는 `Idempotency-Key` 필수. 요청자·API·대상 리소스·키로 식별하고 정규화한 요청 본문 해시를 보존한다. 같은 키·같은 본문은 최초 HTTP 코드와 결과를 재사용한다. 다른 본문은 `409 IDEMPOTENCY_KEY_REUSED`, 처리 중이면 `409 REQUEST_IN_PROGRESS`이다. 누락은 `422 VALIDATION_ERROR`이다.
- 문의별 AI 처리는 한 번에 하나만 허용한다. DB의 처리 토큰을 원자적으로 획득하고 외부 호출 중 DB 트랜잭션을 유지하지 않는다. 완료 시 토큰과 문의 상태를 재검사하고 메시지·판단을 반영한다. 처리 중 추가 변경은 `409 REQUEST_IN_PROGRESS`이다. 만료·재시작으로 토큰이 바뀐 작업 결과는 반영하지 않는다.
- 문의 재개·초안 생성·최종 접수는 문의 행을 잠근 짧은 트랜잭션에서 상태를 검사한다. 문의당 활성 세션·작성 중 초안·최종 접수는 각각 최대 하나이다. 최종 접수와 초안 수정은 같은 잠금 순서(문의 → 초안)를 사용한다.
- TK-04의 동시 중복 요청은 기존 접수를 200으로 반환한다. UNIQUE 충돌을 일반 저장 실패로 안내하지 않는다.

### 2.6.2 설계 기준

API 경로·입출력의 상세 기준은 이 문서와 `docs/api/`이다. 04번 시스템 설계서의 경로·응답 설명과 차이가 있으며, 팀 협의 후 정리한다. 04번은 이번 개정에서 수정하거나 정합성을 확정하지 않는다.

업무 상태는 Jira에서 확인된 값을 반환한다. 변경 목표·작업 상태는 별도로 제공하며, Jira 반영 전 성공한 업무 상태로 표시하지 않는다.

## 3. 권한

### 3.1 권한 표기

| 표기 | 의미 | 기준 |
|---|---|---|
| 공개 | 인증 없이 호출 | |
| 로그인 | 인증된 모든 사용자 | `account_status = ACTIVE` |
| 본인 | 리소스의 소유자 | 문의·초안·접수의 `user_id`(문의자) |
| AGENT | IT 담당자 이상 | `users.service_role` ∈ (AGENT, ADMIN) |
| 담당 그룹 | 활성 그룹의 활성 구성원이며 현재 서비스 역할이 AGENT/ADMIN인 사용자 | `tickets.group_id`의 `support_group_members` |
| MANAGER | 접수의 배정 그룹 관리자 | 위 구성원 중 `member_role = MANAGER` |
| ADMIN | 관리자 | `users.service_role = ADMIN` |
| Jira | Jira 웹훅 | 웹훅 비밀값 검증 |

- 권한은 위계를 가진다: `ADMIN ⊇ AGENT ⊇ 로그인`. 단, **본인 데이터 범위는 권한과 별도로 적용**한다 (AGENT 권한만으로는 타인 문의를 볼 수 없다. 해당 접수의 활성 담당 그룹 구성원은 관련 문의·세션·메시지를 조회할 수 있다).
- 여러 표기가 함께 있으면 **하나라도 만족하면 허용**한다. 예: `본인·담당 그룹·ADMIN`

### 3.2 403과 404 구분

| 상황 | 응답 |
|---|---|
| 권한이 부족한 **기능** 호출 (예: EMPLOYEE가 사용자 관리 호출) | `403 FORBIDDEN` |
| 존재를 알려서는 안 되는 **데이터** 접근 (다른 사람의 문의·접수, 열람 범위 밖 문서) | `404 xxx_NOT_FOUND` |

열람 범위 밖 문서의 존재·제목·출처가 드러나지 않도록 한다 (SRS GUIDE-06).

## 5. 에러 처리

### 5.1 에러 응답 형식

헬스 체크(OP-05)의 배포용 상태 응답을 제외한 모든 에러는 같은 형식으로 응답한다. FastAPI 기본 형식(`{"detail": ...}`)은 공통 예외 처리기에서 이 형식으로 바꾼다.

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "입력값을 확인해 주세요.",
    "details": [
      {
        "field": "content",
        "reason": "REQUIRED",
        "message": "문의 내용을 입력해 주세요."
      }
    ],
    "traceId": "9f1c2a7e-3b4d-4e5f-8a9b-0c1d2e3f4a5b"
  }
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| `code` | string | 에러 코드 (5.4). Frontend는 **`message`가 아닌 `code`로 분기**한다 |
| `message` | string | 사용자에게 그대로 보여줄 수 있는 한국어 문장 |
| `details` | array \| null | 필드별 오류 또는 추가 정보. 없으면 `null` |
| `details[].field` | string | 요청 필드명 (camelCase). 중첩은 `.`, 배열은 `[i]`. 예: `keywords[0]` |
| `details[].reason` | string | 사유 코드 (5.3) |
| `details[].message` | string | 필드별 안내 문장 |
| `details[].value` | any | (선택) 추가 정보 값. 예: 잠금 해제 시각, 이미 있는 초안 ID |
| `traceId` | string | 요청 추적 ID. 서버 로그와 대조할 때 쓴다 |

필드 오류가 아닌 추가 정보는 `field` 없이 `reason`과 `value`로 넣는다. 예: 계정 잠금 `{ "reason": "LOCKED_UNTIL", "message": "잠금 해제 시각", "value": "2026-10-21T14:13:00+09:00" }`. API별 `details` 내용은 API 명세서에서 정한다.

### 5.2 에러 메시지 작성 규칙

- 사용자가 **다음에 무엇을 하면 되는지** 알 수 있게 쓴다. 예: "다시 로그인해 주세요."
- 민감정보·내부 정보를 넣지 않는다: 비밀번호, 토큰, SQL·스택 트레이스, 외부 API 응답 원문, 다른 사용자의 정보
- 로그인 실패는 사번이 없는지 비밀번호가 틀렸는지 구분하지 않는다.
- 외부 연동(Jira·Slack) 오류를 사용자에게 그대로 보이지 않는다. 접수번호와 진행 상황으로 안내한다 (SRS NFR-REL-06).
- 대체 접수 경로는 **IT 헬프데스크(내선 1000, 평일 09:00~18:00)·그룹웨어 IT 요청 메뉴**로 안내한다.

### 5.3 `details[].reason` 코드

| reason | 의미 |
|---|---|
| `REQUIRED` | 필수 값 없음 |
| `INVALID_FORMAT` | 형식 오류 (날짜·이메일 등) |
| `INVALID_VALUE` | 허용되지 않은 값 (enum 등) |
| `TOO_SHORT` / `TOO_LONG` | 길이 범위 밖 |
| `OUT_OF_RANGE` | 숫자 범위 밖 |
| `NOT_FOUND` | 참조한 ID·코드가 없음 |
| `DUPLICATE` | 중복 값 |
| `NOT_ALLOWED` | 이 권한·상태에서 바꿀 수 없는 필드 |

### 5.4 HTTP 상태 코드

| 코드 | 용도 |
|---|---|
| 200 OK | 조회·변경 성공, 멱등 재요청 (예: 같은 초안으로 TK-04 재요청) |
| 201 Created | 생성 성공 |
| 202 Accepted | 비동기 처리 시작 (DC-07) |
| 204 No Content | 삭제·로그아웃 성공 |
| 400 Bad Request | 형식은 맞지만 처리할 수 없는 요청 (JSON 파싱 실패, 필터 조합 오류 등) |
| 401 Unauthorized | 인증 없음·만료·실패 |
| 403 Forbidden | 권한 부족, 계정 상태로 인한 차단 |
| 404 Not Found | 리소스 없음, 또는 접근 권한 없는 데이터 (3.2) |
| 409 Conflict | 현재 상태와 충돌 (중복, 허용되지 않은 상태 전이) |
| 413 Payload Too Large | 업로드 파일 크기 초과 |
| 415 Unsupported Media Type | 지원하지 않는 파일 형식 |
| 422 Unprocessable Entity | 입력값 검증 실패 |
| 429 Too Many Requests | 요청 횟수 제한 초과 |
| 500 Internal Server Error | 서버 오류 |
| 503 Service Unavailable | 일시적으로 처리 불가 (AI 모델 호출 불가 등) |

### 5.7 Backend 구현 메모

- 도메인 에러는 `core`의 공통 예외 클래스(예: `AppError(code, status, message, details)`)로 던지고, 예외 처리기 한 곳에서 5.1 형식으로 바꾼다.
- 에러 코드·HTTP 상태·기본 message는 한 파일(예: `core/error_codes.py`)에 모아 이 문서의 표와 맞춘다.
- Pydantic 검증 오류(`RequestValidationError`)는 `VALIDATION_ERROR`로 바꾸고, `loc`의 필드명을 camelCase alias로 `details[].field`에 넣는다.
- 500 응답에는 원인을 넣지 않고, 원인은 `traceId`와 함께 서버 로그에만 남긴다 (민감정보 제외).

## 6. 미결 사항

| 항목 | 내용 |
|---|---|
| 토큰 방식 | Access Token(JWT) 유효 시간, Refresh Token 사용 여부와 저장 위치(httpOnly Cookie 등), 로그아웃 시 무효화 방식 |
| 비밀번호 규칙 | 길이·조합 규칙, 임시 비밀번호 유효 기간 |
| AI 응답 방식 | IQ-01·08의 동기 응답 유지 또는 스트리밍(SSE) 도입. 응답 시간 측정 후 결정 |
| 중복 방지 보존 기간 | 문의·메시지 생성 및 AI 해결 확인은 `Idempotency-Key` 필수. 키 보존 기간은 요청 시간 제한·재시도 기간 이상으로 운영 설정에서 확정 |
| 계정 상태 이력 | 시스템 설계서의 "계정 상태 이력" 테이블이 없어 우선 `audit_logs`에 사유를 남김. 별도 테이블 필요 여부 |
| 업로드 제한 | 문서 파일 최대 크기 |
| 요청 횟수 제한 | 로그인·메시지 전송 횟수 제한 기준 |
| Jira 웹훅 인증 | 비밀값 전달 방식 (Query·Header) |
| FAQ 식별자 | 경로에 `id`(bigint)를 쓰고 `faqCode`는 필드로 줌. 화면이 `FAQ-001`로 찾아야 하면 변경 |
