## 0. 개요

이 문서는 **백엔드 ↔ M4 AI 판단 노드** 사이에서 주고받는 데이터 형식을 정의한다.

- **입력(1장):** 서버가 AI 판단 노드에 넘기는 값
- **출력(2장):** AI 판단 노드가 서버에 돌려주는 값
- **검증(3장):** 출력이 잘못됐을 때 처리하는 기준
- **예시(4장):** 처리 방향별 실제 JSON
- **연동(5장):** AI 제안값과 서버 확정값의 구분, DB 저장 변환, 긴급도 규칙, 버전 규칙, 합의 항목

### 기본 원칙

1. **AI는 사실을 추출·해석하고, 백엔드는 규칙을 적용한다.** (PRD 4.3, SRS 2.4) AI 출력은 모두 **제안값**이며, 서버가 검증한 뒤 확정한다.
2. **판단이 불확실하면 사람에게 넘긴다.** 검증에 실패하면 `ANSWER`로 두지 않고 `ESCALATE`로 바꾼다. (PRD 5 "AI는 근거 없이 답변하지 않는다")
3. **AI는 담당팀·담당자·Ticket 생성·Jira에 관여하지 않는다.** (PRD 5 "모델의 제안은 서버에서 검증한 후 실행한다")
4. **LLM에는 필요한 정보만, 민감정보 필터를 거친 뒤 보낸다.** (PRD 4.13) 세부 기준은 M4-1-3 민감정보 정책을 따른다.
5. **이름은 DB 컬럼, 값은 DB 영문 코드를 쓴다.** (`07.API_계약서.md` 0장) 이 문서는 백엔드 내부(Python) 형식이라 snake_case를 쓰며, 프론트로 나가는 API JSON은 백엔드 응답 모델이 camelCase로 자동 변환한다.

## 1. 입력 스키마 (서버 → AI)

### 1.1 최상위 필드

`LLM 전송` 열의 뜻

- **전송:** LLM 프롬프트에 그대로 넣는다.
- **필터 후 전송:** 민감정보 필터(M4-1-3)를 통과한 내용만 넣는다.
- **서버만:** AI 판단 노드는 쓰지만 LLM에는 보내지 않는다.

| 필드 | 자료형 | 필수 | LLM 전송 | 설명 |
| --- | --- | --- | --- | --- |
| `schema_version` | string | ✅ | 서버만 | 입력 형식 버전. 현재 `"1.0"` |
| `session_id` | string | ✅ | 서버만 | 상담 Session ID |
| `inquiry_id` | string | ✅ | 서버만 | 문의 ID |
| `message` | string | ✅ | 필터 후 전송 | 이번 사용자 발화 |
| `history` | Message[] | – | 필터 후 전송 | 이전 대화. 최근 N턴만 (N은 5장에서 합의). 없으면 `[]` |
| `collected_facts` | Facts \| null | – | 필터 후 전송 | 이전 턴까지 모은 사실. 구조는 2.2 `Facts`와 같다. 첫 턴이면 `null` |
| ✏️ `ask_more_count` | int (≥ 0) | ✅ | 전송 | 기존 세션에서 수행한 추가 질문 횟수. 이어가기·재개 시 초기화하지 않고 잠정 유지 (09 4.2; 기준은 추후 변경 가능) |
| `ask_more_unanswered_count` | int (≥ 0) | – | 서버만 | 위 질문 중 답을 못 얻은 질문 수 (09 4.2). 없으면 `0` |
| `prior_urgent_signal` | bool | – | 서버만 | 이 문의의 이전 판단에서 `urgent_signal=true`가 한 번이라도 있었는가. 없으면 `false`. 긴급 고정 규칙(3.2 `URGENT_LATCH`)에 쓴다. LLM에는 보내지 않아 AI 단독 판단을 그대로 평가할 수 있게 둔다 |
| `prior_urgency` | enum \| null | – | 서버만 | 이 문의의 이전 판단 확정 긴급도 중 가장 높은 값 (P1–P4). 긴급도 유지 규칙(5.3 `URGENCY_KEEP`)에 쓴다. 첫 판단이거나 초안 수정으로 다시 판단할 때는 `null` |
| `user_context` | UserContext | ✅ | 아래 표 참조 | 문의자 정보 |
| `search` | SearchResponse \| null | ✅ | 필드별 (1.4) | M3 검색 응답 그대로. 검색 전 단계(명확성 확인·긴급 경로)에서는 `null` |

분류 체계(7개 Category, 50개 세부 유형, 긴급도 기준)는 입력 필드로 받지 않는다. 서버가 DB `categories`·`inquiry_types`(원본 `taxonomy.json`)를 읽어 시스템 프롬프트에 넣는다.

✏️ **이어가기 입력:** 문의·세션 ID를 유지하고 기존 대화와 추가 질문 횟수를 이어 쓴다. AI 미해결 재개는 담당자 연결 제안을 제공하며, 미확인 재개는 기존 답변의 해결·미해결 확인을 제공한다. 단순 조회·이어가기 버튼으로 AI를 재호출하거나 질문 횟수를 늘리지 않는다. FIN의 해결·미해결은 Ticket API가 처리하며 AI 입력으로 재판단하지 않는다. 횟수·이력의 집계 범위는 기존 세션을 기준으로 잠정 유지한다.

### 1.4 SearchResponse (M3 검색 응답)

**M3-1-1 검색 형식(`backend/app/rag/search/result.py`, `README.md`)을 그대로 받는다.** 문서 결과의 모양은 `청크_메타데이터.md` 8장을 따른다. 아래는 M4가 쓰는 방식을 정리한 것이며, 형식의 기준은 M3 코드다.

**SearchResponse**

| 필드 | 자료형 | LLM 전송 | 쓰는 곳 |
| --- | --- | --- | --- |
| `documents` | DocumentResult[] | 필드별 | Guide·매뉴얼·공통 기준 결과. 점수 높은 순 |
| `legacy` | LegacyResult[] | 필드별 | 과거 이력 결과. 점수 높은 순 |
| `sufficient` | bool | 서버만 | Guide 근거가 충분한지 (아래) |
| `best_score` · `threshold` | number | 서버만 | `sufficient` 판단에 쓴 값. 로그에 남긴다 |
| `query` · `model` · `took_ms` | | 서버만 | 로그용 |

**`sufficient`를 쓰는 방법** (PRD v0.8 4.2 검색 순서)

| `sufficient` | 뜻 | AI 판단 노드(M4)가 하는 일 |
| --- | --- | --- |
| `true` | Guide에서 충분히 맞는 내용을 찾음 | Guide 근거로 처리 방향을 정한다 |
| `false` | **Guide만으로는 부족함** | `legacy`(과거 사례)를 검토한다. 현재 Guide와 충돌하지 않으면 과거 사례로 답할 수 있다 ("과거 처리 사례 참고"). 그래도 근거가 없으면 추가 확인 또는 담당자 연결 |

`sufficient`는 문서 점수만 본다 (M3). `false`일 때 무엇을 할지는 M4가 정한다.

**DocumentResult** (문서 결과 하나 = 항목 단위 하나)

| 필드 | 자료형 | LLM 전송 | 쓰는 곳 |
| --- | --- | --- | --- |
| `unit_key` | string | 전송 | 근거 인용 키. 예: `IT-NET-001@v2.0/item:3.1` |
| `doc_code` · `title` · `location` · `heading_path` | string | 전송 | 출처 문맥. 화면 출처는 `citation`(`doc_code` + `location`, 예: `IT-NET-001 3.1`) |
| `text` | string | 필터 후 전송 | 근거 본문 (머리말 + 조각을 이어 붙인 글) |
| `evidence` | string[] (최대 3) | 전송 | M3가 고른 근거 문장. `text` 안에 그대로 있는 문장만 있다 |
| `unit_score` | number | 전송 | 검색 점수 |
| `inquiry_type_codes` | string[] | 전송 | 분류 힌트. 예: `["NET-02"]` |
| `handling` | string | 전송 | 처리 구분. 처리 방향 힌트로 쓴다 (아래). 매뉴얼은 `""` |
| `version` · `citation` | string | 서버만 | 답변 출처 표시 |
| `view_scope` | `ALL` \| `AGENT` \| `ADMIN` | 서버만 | 열람 범위. 사내 일반 · 사내 제한 · 관리자 전용 (PRD 4.10) |
| `transfer_policy` | `ALLOWED` \| `MASKED` \| `BLOCKED` | 서버만 | 외부 모델 전송 정책 (아래) |
| `source_kind` · `chunk_type` · `chunks` · `score_type` · `also_in` | | 서버만 | AI 입력에는 쓰지 않는다. `chunks[].id`는 근거 저장에 쓴다 (5.2) |

**LegacyResult** (과거 사례 하나, 원본 `legacy_inquiries`)

| 필드 | 자료형 | LLM 전송 | 쓰는 곳 |
| --- | --- | --- | --- |
| `legacy_no` | string | 전송 | 근거 인용 키. 예: `INQ-2026-00245` |
| `title` | string | 전송 | 사례 제목 |
| `text` · `root_cause` · `resolution` | string | 필터 후 전송 | 증상·원인·해결 방법 |
| `evidence` | string[] | 전송 | M3가 고른 근거 문장 |
| `inquiry_type_code` | string \| null | 전송 | 분류 힌트 |
| `resolved_at` | string \| null | 전송 | 해결 시각. 현재 정책과 맞는지 판단할 때 쓴다 |
| `score` | number | 전송 | 검색 점수 |
| `legacy_inquiry_id` · `citation` · `view_scope` · `transfer_policy` · `source_kind` · `score_type` | | 서버만 | 근거 저장·출처 표시·전송 검사 |

과거 사례 결과에는 요청자·담당자처럼 사람을 가리키는 칸이 없다. (M3) 일반 임직원도 과거 사례를 볼 수 있으며(팀 합의), 시드 값은 일반 사례 `ALL`·`MASKED`, 보안(SEC) 사례만 `AGENT`·`BLOCKED`다. (M3 README)

**`handling`과 처리 방향의 관계** (힌트일 뿐이며 최종 판단은 문의 내용과 함께 한다)

| `handling` | 처리 방향 후보 |
| --- | --- |
| 사용자 직접 조치 | `ANSWER` |
| 신청·승인 후 처리 | `ANSWER` (신청 절차 안내) 또는 `ESCALATE` (승인) |
| IT 담당자 처리 | `ESCALATE` (`실제조치`·`전문판단`) |
| 즉시 신고·이관 | `ESCALATE` (`긴급대응`) |
| `""` (매뉴얼) | 힌트 없음 |

**외부 전송 규칙** (PRD 4.10·4.13, 청크 문서 3장·8장) — 문서·과거 사례에 똑같이 적용

| `transfer_policy` | LLM 입력 처리 |
| --- | --- |
| `ALLOWED` | 그대로 넣는다 |
| `MASKED` | 민감정보를 제거·가명 처리한 내용만 넣는다 (M4-1-3 필터) |
| `BLOCKED` | 넣지 않는다 |
| 값이 없거나 그 밖의 값 | `BLOCKED`로 본다 |

- 열람 범위는 검색 단계(M3)에서 `service_role`로 이미 거른다. AI 판단 노드는 LLM을 부르기 직전에 `transfer_policy`를 다시 확인한다.
- 결과가 있었는데 모두 `BLOCKED`로 빠졌으면 LLM을 부르지 않고 `ESCALATE`, `escalation_reason=전송제한`이다. 처음부터 결과가 없었던 `근거부족`과 구분한다. (PRD 4.10, 3.2)

**과거 사례 사용 규칙** (PRD 4.2)

1. 과거 사례는 **Guide만으로 부족할 때**(`sufficient=false`) 검토한다.
2. 현재 Guide·운영 정책과 **충돌하지 않을 때만** 근거로 쓴다. 충돌하면 Guide를 우선한다.
3. 과거 사례를 근거로 답하면 `evidence.kind="LEGACY"`로 표시하고, 화면은 Guide 출처와 구분해 **"과거 처리 사례 참고"**로 보여 준다.

## 2. 출력 스키마 (AI → 서버)

### 2.1 최상위 필드

| 필드 | 자료형 | 필수 | 설명 |
| --- | --- | --- | --- |
| `schema_version` | string | ✅ | 출력 형식 버전. 현재 `"1.0"` |
| `action` | enum | ✅ | 처리 방향 제안. `ANSWER` · `ASK_MORE` · `ESCALATE` · `OUT_OF_SCOPE` |
| `urgent_signal` | bool | ✅ | 긴급 대응 징후. `true`면 검색 결과를 기다리지 않고 연결 제안으로 간다 |
| `title` | string | ✅ | 문의 제목 한 줄 (255자 이내). 문의 목록·Ticket 초안·Jira 요약에 쓴다 (`inquiries.title`) |
| `category_code` | enum \| null | ✅ | Category 제안. 확정하지 못하면 `null`(미분류) |
| `inquiry_type_code` | string \| null | ✅ | 세부 유형 제안. 예: `NET-02` |
| `request_kind` | enum \| null | ✅ | 문의 유형. `INCIDENT`(장애) · `REQUEST`(요청) · `QUESTION`(문의) |
| `urgency_suggested` | enum \| null | ✅ | 긴급도 제안. P1–P4. 비교·평가용 (5.3) |
| `facts` | Facts | ✅ | 긴급도 판단 재료와 Ticket 초안 재료 |
| `rationale` | Rationale | ✅ | 판단 근거 |
| `reply` | string | ✅ | 사용자에게 보여 줄 문장 (답변·추가 질문·연결 제안·범위 밖 안내) |
| `evidence` | Evidence[] | ✅ | 답변에 쓴 근거. 쓴 순서대로. 없으면 `[]` |
| `missing_items` | enum[] | ✅ | 부족한 정보 항목 (3.1). 없으면 `[]` |
| `escalation_reason` | enum \| null | ✅ | 담당자 처리가 필요한 이유 |
| `confidence` | number (0–1) | – | 판단 확신도. 내부 분석용이며 Jira로 보내지 않는다 |

모든 필드는 항상 키가 있어야 한다. 값이 없으면 `null` 또는 `[]`를 넣는다. 그래야 서버가 "AI가 빠뜨린 것"과 "해당 없음"을 구분할 수 있다.

### 2.2 Facts

AI가 문의와 대화에서 뽑아낸 사실이다. 대화 원문은 Ticket·Jira로 넘기지 않으므로 (PRD 4.6), 담당자에게 필요한 정보는 여기에 담는다. DB 판단 이력의 `facts`(jsonb)에 그대로 저장하고, Ticket 초안 항목은 초안 테이블의 같은 이름 컬럼에 넣는다. (5.2)

Jira 접수 내용은 Jira 연동 모듈이 초안 항목(`field_mapping.yaml` `create.description_parts`)을 이어 붙여 만든다.

| 필드 | 자료형 | 필수 | 설명 |
| --- | --- | --- | --- |
| `summary` | string | ✅ | 문의 요약 한두 문장 (초안의 "문의 내용") |
| `target_system` | string \| null | ✅ | 대상 시스템·도구. 예: 사내 VPN, ERP. Jira "대상 도구" |
| `symptom` | string \| null | ✅ | 증상. 예: "'서버에 연결할 수 없습니다' 오류". DB `ticket_drafts.symptom` |

| `impact_scope` | `PERSONAL` \| `DEPARTMENT` \| `COMPANY` \| null | ✅ | 영향 범위 (개인 · 부서 · 전사). 모르면 `null`. 여러 명을 한꺼번에 **신청**하는 것은 여러 사람 장애가 아니므로 올리지 않는다 (SRS 2.4) |
| `work_stopped` | enum | ✅ | `full` (전면 중단) · `partial` (일부 지장) · `none` (지장 없음) · `unknown` |
| `has_workaround` | bool \| null | ✅ | 허용된 대체 방법이 있는지. 모르면 `null`. 계정 공유·보안 우회는 대체 방법으로 치지 않는다 (SRS 2.4) |
| `time_constraint` | string \| null | ✅ | 시간 제약. 구체적인 시각·마감이 있을 때만 적는다. 예: "오늘 14:00 고객 미팅", "오늘 18시 보고서 마감". "급해요"·"빨리"는 넣지 않는다 (IT-STD-001 3장) |
| `business_impact` | string \| null | ✅ | 업무 영향 한두 문장. 초안에 그대로 보여 준다. 예: "재택 근무 중 사내 시스템 접속 불가, 대체 방법 없음" |
| `security_suspected` | bool | ✅ | 보안 사고 의심 여부 |
| `tried_actions` | string[] | ✅ | 사용자가 이미 해 본 조치. 없으면 `[]`. DB에 넣을 때는 서버가 줄바꿈으로 합친다 (5.2) |

## 3. 허용값 및 검증 규칙

### 3.1 허용값

| 필드 | 허용값 | 출처 |
| --- | --- | --- |
| `action` | `ANSWER` · `ASK_MORE` · `ESCALATE` · `OUT_OF_SCOPE` | `eval_inquiries.csv`의 `expected_action`, DB `inquiries.action`과 같은 코드. 평가할 때 변환 없이 바로 채점한다 |
| `category_code` | `ACC` · `ACS` · `NET` · `SW` · `HW` · `SYS` · `SEC` | DB `categories.code` |
| `inquiry_type_code` | 세부 유형 코드 50개 (예: `ACC-01` … `SEC-08`) | DB `inquiry_types.code` |
| `request_kind` | `INCIDENT` · `REQUEST` · `QUESTION` | DB `inquiry_types.request_kind` |
| `urgency_suggested` | `P1` · `P2` · `P3` · `P4` | DB `urgency` CHECK |
| `facts.impact_scope` | `PERSONAL` · `DEPARTMENT` · `COMPANY` · `null` | DB `impact_scope` CHECK, Jira 영향 범위 선택값 |
| `facts.work_stopped` | `full` · `partial` · `none` · `unknown` | 이 문서 |
| `missing_items` | `target_system` · `symptom` · `occurred_at` · `impact` · `tried_actions` | PRD 4.1 추가 질문 5항목 (`impact`는 영향 범위와 업무 중단 정도) |
| `evidence.kind` | `DOCUMENT` · `LEGACY` | M3 `source_kind`, DB `message_sources.source_kind` |
| `escalation_reason` | `실제조치` · `승인` · `권한변경` · `전문판단` · `근거부족` · `전송제한` · `긴급대응` | PRD 4.4, SRS ACTION-02 |

PRD 4.4의 처리 방향과는 이렇게 대응한다. AI 안내 → `ANSWER`, 추가 확인 → `ASK_MORE`, 담당자 처리 → `ESCALATE`, 지원 범위 밖 → `OUT_OF_SCOPE`.

**추가 질문 대상 (`ASK_MORE`)**

PRD 4.1의 5항목을 모두 확인하되, **언제 묻는지**를 나눈다.

| 항목 | 언제 묻나 |
| --- | --- |
| `target_system` · `symptom` · `impact` | 판단 단계. 빠져서 분류·긴급도·처리 방향을 정할 수 없으면 `ASK_MORE` |
| `occurred_at` · `tried_actions` | 담당자 연결이 정해진 뒤 Ticket 초안 단계 (M4-3-2). 이것만 빠졌다는 이유로 `ASK_MORE` 하지 않는다 |

이미 답한 항목은 다시 묻지 않는다. (PRD 4.1)

### 3.2 검증 순서와 처리 기준

**AI 판단 노드(M4)는** LLM 출력을 아래 순서로 검사·보정한 뒤, 검증된 출력만 백엔드(M1)에 넘긴다. 앞 단계에서 실패하면 뒤 단계는 하지 않는다.

| 순서 | 검사 | 실패하면 |
| --- | --- | --- |
| 1 | `schema_version`이 서버가 지원하는 버전인가 | **처리하지 않고 오류로 기록한다.** 사용자에게는 담당자 연결을 제안한다 |
| 2 | JSON으로 읽히는가 | 한 번 다시 호출한다. 또 실패하면 안전 기본값(3.3)을 쓴다 |
| 3 | 필수 키가 모두 있고 자료형이 맞는가 (Pydantic v2) | 한 번 다시 호출한다. 또 실패하면 안전 기본값(3.3)을 쓴다 |
| 4 | enum 값이 3.1 허용값 안에 있는가 | 그 필드를 `null`로 바꾸고 기록한다 (`INVALID_VALUE`). 목록 필드는 허용값 밖의 항목만 버린다. `action`이 허용값 밖이면 `ESCALATE`로 바꾼다 |
| 5 | `inquiry_type_code`가 DB `inquiry_types`에 있고 `category_code`와 접두어가 같은가 | `inquiry_type_code`만 `null`로 바꾼다 (`TYPE_CODE_MISMATCH`). `category_code`는 유지한다 |
| 6 | `missing_items`가 질문할 항목만 담았는가 | `collected_facts`에 이미 값이 있는 항목과, 판단 단계에서 묻지 않는 `occurred_at`·`tried_actions`를 뺀다 (3.1) |
| 7 | 2.5 처리 방향별 필수 값을 지켰는가 | 아래 표. `title`이 비었으면 `summary` 앞부분으로 채우고, 255자를 넘으면 자른다 |
| 8 | `evidence`가 실제 검색 결과에서 나왔는가 | `kind`에 맞는 목록(`DOCUMENT`→`search.documents`, `LEGACY`→`search.legacy`) 중 LLM에 보낸 결과에 `source_id`가 없거나, `quote`가 그 `text`에 없으면 그 항목을 버린다 |
| 9 | `reply`가 안전한가 | 비밀번호·인증번호·API 키를 요청하거나, Ticket이 접수됐다고 말하면 한 번 다시 생성한다. 또 실패하면 안전 기본값(3.3)을 쓴다 |

6~8단계 이후 처리 방향 보정

판단은 검색 전 1차(`search=null`, 명확성·긴급 징후 확인)와 검색 뒤 2차로 나뉜다. (`09.대화_상태_정의.md` 4.1) **1차에서는 `urgent_signal`·`ASK_MORE`만 다음 상태를 정하고, 그 밖의 `action`은 "검색으로 진행"으로 본다.** 그래서 근거를 보는 `NO_EVIDENCE`·`GUIDE_INSUFFICIENT`·`ALL_BLOCKED`는 2차에만 적용한다. 나머지 줄은 1·2차 모두 적용한다.

| 경우 | 처리 | `rule` |
| --- | --- | --- |
| `ANSWER`인데 남은 `evidence`가 0개 | `ESCALATE`, `escalation_reason=근거부족` | `NO_EVIDENCE` |
| `ANSWER`인데 `search.sufficient=false`이고 `LEGACY` 근거도 없음 | `ESCALATE`, `escalation_reason=근거부족` (Guide 부족 시 과거 사례로만 답할 수 있음, 1.4) | `GUIDE_INSUFFICIENT` |
| `ASK_MORE`인데 6단계 뒤 `missing_items`가 비어 있음 | `ESCALATE`, `escalation_reason=전문판단` | `ASK_MORE_EMPTY` |
| `ASK_MORE`인데 `ask_more_unanswered_count`가 `ASK_MORE_UNANSWERED_LIMIT`(환경변수, 시작값 2)에 도달 | `ESCALATE`, `escalation_reason=전문판단` (09 4.2) | `ASK_MORE_UNANSWERED` |
| `ASK_MORE`인데 `ask_more_count`가 `ASK_MORE_TOTAL_LIMIT`(환경변수, 시작값 5)에 도달 | `ESCALATE`, `escalation_reason=전문판단` (09 4.2) | `ASK_MORE_LIMIT` |
| `ESCALATE`인데 `escalation_reason`이 `null` | `escalation_reason=전문판단`으로 채운다 | `INVALID_VALUE` |
| `prior_urgent_signal=true`인데 이번 `urgent_signal=false` | `urgent_signal=true`로 되돌린다. 한 번 잡힌 긴급 징후는 이 문의에서 내리지 않는다 (실제 사고 여부는 담당자가 확인). 이어서 아래 `URGENT_SIGNAL` 줄이 적용된다 | `URGENT_LATCH` |
| `urgent_signal=true`인데 `action`이 `ESCALATE`가 아님 | `ESCALATE`, `escalation_reason=긴급대응` | `URGENT_SIGNAL` |
| 검색 결과가 있었지만 모두 `BLOCKED`라 LLM에 보내지 못함 | LLM을 부르지 않고 `ESCALATE`, `escalation_reason=전송제한` (PRD 4.4·4.10). `ai_output`은 `null` | `ALL_BLOCKED` |

**`rule` 코드 목록** — 서버가 AI 판단을 바꿀 때 `override_reasons`(5.4)에 남기는 규칙 이름이다. M4가 정하며, 새 규칙이 생기면 허용값 추가(5.5)로 늘린다.

| 코드 | 언제 | 정의한 곳 |
| --- | --- | --- |
| `AI_FAILED` | JSON 오류·필수 키 누락·안전하지 않은 `reply`, 모델 거절, API 오류(시간 초과·연결 오류 등)로 안전 기본값을 썼을 때. `ai_output`은 `null` | 3.2 2·3·9단계, 3.3 |
| `INVALID_VALUE` | 허용값 밖의 값을 `null`로 바꾸거나 빈 필수 값을 채웠을 때 | 3.2 4·7단계 |
| `TYPE_CODE_MISMATCH` | `inquiry_type_code`가 없거나 Category와 맞지 않아 `null`로 바꿨을 때 | 3.2 5단계 |
| `NO_EVIDENCE` · `GUIDE_INSUFFICIENT` · `ASK_MORE_EMPTY` · `ASK_MORE_UNANSWERED` · `ASK_MORE_LIMIT` · `URGENT_LATCH` · `URGENT_SIGNAL` · `ALL_BLOCKED` | 처리 방향 보정 | 위 표 |
| `TYPE_DEFAULT` · `SEC_MIN_P2` · `PERSONAL_FULL_MIN_P2` · `DEPT_UP1` · `COMPANY_P1` · `TIME_UP1` · `URGENCY_KEEP` | 긴급도 확정 | 5.3 |

## 5. 백엔드 연동 규칙

### 5.1 AI 제안값과 서버 확정값

| 항목 | AI (제안) | 서버 (확정) |
| --- | --- | --- |
| 문의 제목 | `title` | 3장 검증 후 `inquiries.title`에 저장. Ticket 초안·Jira 요약의 처음 값 |
| Category·세부 유형 | `category_code`, `inquiry_type_code` | 3장 검증을 통과하면 그대로 확정. `category_code`가 `null`이면 미분류로 두고 서비스데스크 확인 (PRD 4.6) |
| 문의 유형 | `request_kind` | AI 값이 `null`이면 세부 유형의 `inquiry_types.request_kind` 사용 |
| 긴급도 | `urgency_suggested`, `facts` | 5.3 규칙으로 확정 → 판단 이력 `urgency` (5.4) |
| 처리 방향 | `action` | 3.2 보정 규칙을 거쳐 확정 → 판단 이력 `action` (5.4) |
| 담당팀 | **내지 않음** | 담당 그룹 추천 순서(예외 규칙 → 세부 유형 기본 그룹 → 서비스데스크)로 정함 (PRD 4.7, 테이블 설계서 0장) |
| 개인 담당자 | **내지 않음** | 배정 규칙(M1·M5)으로 선정 |
| Ticket 초안 | `title`, `facts`, `rationale` 제공 | 초안 조립은 M4-3-2, 저장은 서버. 비어 있는 `occurred_at`·`tried_actions`는 초안 단계에서 묻는다 (3.1). 초안의 "AI 안내 내용"(`ai_summary`)은 서버가 대화 기록의 `reply`에서 가져온다 |
| Ticket 접수·Jira 생성 | **관여하지 않음** | 사용자가 초안을 최종 확인한 뒤 서버가 실행 (PRD 5). Jira 접수 내용은 Jira 연동 모듈이 조립한다 |

### 5.2 DB 저장 변환

이름과 값은 DB와 같게 맞췄으므로 대부분 그대로 저장한다. 아래만 서버가 바꾼다.

| AI 출력 | DB 저장 | 변환 |
| --- | --- | --- |
| `inquiry_type_code`: `"NET-02"` | `inquiry_type_id` (bigint) | `inquiry_types.code`로 조회 (API 계약서 5장) |
| `rationale.urgency_reasons` (string[]) | `urgency_reason` (text, 판단 이력·초안·접수) | 줄바꿈으로 합침. 읽을 때 줄 단위로 나눔 (API 계약서 3장) |
| `facts.tried_actions` (string[]) | `ticket_drafts.tried_actions` (text) | 줄바꿈으로 합침 |
| `facts` | `inquiry_assessments.facts` (jsonb) | 그대로 |
| `urgent_signal` · `missing_items` · `action` · `category_code` | `inquiry_assessments`의 같은 이름 컬럼 | 그대로 |
| `title` | `inquiries.title` | 그대로. `ticket_drafts`·`tickets`의 `title` 컬럼은 API 계약서 제안 #13 합의 후 |
| `facts.summary` · `target_system` · `symptom` · `occurred_at` · `business_impact` | `ticket_drafts`·`tickets`의 같은 이름 컬럼 | 그대로 (테이블 설계서 v0.4) |
| `facts.impact_scope` | `ticket_drafts`·`tickets`에 아직 컬럼 없음 | API 계약서 제안 #9 합의 후. Jira에는 바로 보낼 수 있다 |
| `evidence` (쓴 순서) | `message_sources` (스냅샷) | `evidence`가 가리키는 검색 결과를 쓴 순서대로 M3 `message_source_rows(used)`에 넘긴다. 문서는 조각마다 한 행, 과거 사례는 한 행이며 `doc_code`·`version`·`location`·`excerpt`가 함께 저장된다 (M3 README 4장, 테이블 설계서 v0.4) |

### 5.3 긴급도 확정 규칙

공통 운영 기준 **IT-STD-001 3장**(긴급도와 처리 목표)과 SRS 2.4를 따른다. (PRD 4.3) **AI 판단 노드(M4)가 LLM 밖의 코드 규칙으로** 긴급도를 확정한다. `facts`만 보고 판단하며 `reply`나 원문 표현은 보지 않는다.

**시작값**

| 경우 | 시작값 |
| --- | --- |
| 세부 유형을 앎 (`inquiry_type_code` 있음) | 세부 유형 기본 긴급도 (`inquiry_types.default_urgency`). AI 제안값과 다르면 `TYPE_DEFAULT`로 기록 |
| 세부 유형을 모름 | AI 제안값 (`urgency_suggested`) |
| 둘 다 없음 | `P3`, 서비스데스크 확인 대상으로 표시 |

AI 제안값을 시작값으로 바로 쓰지 않는 이유: AI 제안에는 "여러 사람 영향" 같은 이유가 이미 반영돼 있을 수 있어, 서버 규칙이 같은 이유를 한 번 더 반영하게 된다. (IT-STD-001 "같은 이유를 두 번 반영하지 않습니다") AI 제안값은 비교·평가용으로 기록한다. (5.4)

**올리는 규칙** (IT-STD-001 3장)

| 규칙 | 조건 (`facts`) | 결과 | `rule` |
| --- | --- | --- | --- |
| 보안 사고 의심 | `security_suspected=true` | **최소 P2** | `SEC_MIN_P2` |
| 개인 업무 전면 중단 | `impact_scope=PERSONAL`, `work_stopped=full`, `has_workaround=false` | **최소 P2** (P2 기준) | `PERSONAL_FULL_MIN_P2` |
| 여러 사람 영향 — 부서 | `impact_scope=DEPARTMENT` | **한 단계 올림, 최소 P2** | `DEPT_UP1` |
| 여러 사람 영향 — 전사 | `impact_scope=COMPANY`, `work_stopped`가 `full` 또는 `partial` | **P1** | `COMPANY_P1` |
| 시간 제약 | `time_constraint` 있음, `work_stopped`가 `full` 또는 `partial` | **한 단계 올림** | `TIME_UP1` |

**지키는 것**

1. **P1은 전사·여러 부서 업무가 멈춘 경우에만** 준다 (P1 기준). 다른 규칙으로 올릴 때는 최대 P2다. 예: 부서 영향 + 시간 제약이 겹쳐도 P2.
2. **같은 이유는 한 번만** 반영한다. 서로 다른 이유는 함께 반영할 수 있지만 1번 상한을 넘지 않는다.
3. **"급하다"는 표현만으로는 올리지 않는다.** 구체적인 시각·마감이 없으면 `time_constraint`에 넣지 않는다. (2.2)
4. **내리는 규칙은 없다.** 기본값보다 낮추지 않으며, 필요하면 담당자가 조정한다.
   - **대화 중에는 이전 값보다도 내리지 않는다.** 위 규칙으로 계산한 값이 `prior_urgency`보다 낮으면 `prior_urgency`를 쓰고 `URGENCY_KEEP`으로 기록한다. 예: "링크를 눌렀어요"(P2) 뒤 "별거 아닌 것 같아요"라고 해도 P2 유지. 초안에서 사용자가 내용을 직접 고쳐 다시 판단할 때는 적용하지 않는다 (`prior_urgency=null`, 바뀌면 다시 확인, SRS 2.8) (09 4.2)
5. 확정 긴급도는 판단 이력의 `urgency`에 넣고, AI 제안값과 다르면 바뀐 내용을 `override_reasons`에 `rule` 코드와 함께 남긴다. (5.4)

**예시**

| 문의 | 시작값 | 적용 규칙 | 결과 |
| --- | --- | --- | --- |
| 재택 VPN 오류, 나만 | P3 (NET-02) | 없음 | P3 |
| 팀 전체가 공유 드라이브 접속 불가 | P2 (SYS-13) | 부서 영향 → 최소 P2이지만 한 단계 올림은 P1 상한에 걸림 | P2 |
| 전사 VPN 안 됨 | P1 (NET-03) | 전사 + 업무 중단 | P1 |
| 2시 고객 미팅인데 VPN이 안 붙음 | P3 (NET-02) | 시간 제약 + 업무 지장 → 한 단계 | P2 |
| 다음 주 신입 PC 미리 신청, 월요일까지 | P4 (HW-05) | 시간 제약이 있지만 업무 지장 없음 | P4 |
| 노트북 침수, 업무 전혀 못 함 | P3 (HW-04) | 개인 업무 전면 중단 | P2 |

### 5.4 저장

**백엔드(M1)가** 판단 결과를 판단 이력(`inquiry_assessments`)에 저장한다. **AI 원래 값과 확정값을 함께** 남긴다. AI가 어디서 틀렸는지 보고 보완하는 데(M4-4-1)와 AI 운영 지표(PRD 4.14)에 쓴다.

| 저장 위치 | 넣는 값 | 비고 |
| --- | --- | --- |
| 기존 컬럼 (`category_code` · `inquiry_type_id` · `urgency` · `urgency_reason` · `action` · `facts` · `missing_items` · `urgent_signal`) | **확정값** (3.2 보정·5.3 긴급도 규칙 적용 후) | 테이블 설계서 v0.5 그대로 |
| `ai_output` (jsonb) | 3.2 검증 전 AI 판단 원본 (2장 출력 형식, 민감정보 필터 적용). **구조화된 판단 결과만** 넣고 모델 응답 원문은 넣지 않는다. 안전 기본값을 썼거나(`AI_FAILED`) LLM을 부르지 않았으면(`ALL_BLOCKED`) `null` | 테이블 설계서 v0.5 |
| `override_reasons` (jsonb, 기본 `[]`) | 서버 규칙이 AI 판단을 바꾼 항목과 이유. 항목마다 `field` · `ai` · `final` · `rule` · `reason`. `rule`은 3.2 `rule` 코드 목록의 값. 바뀐 게 없으면 `[]` | 테이블 설계서 v0.5 |

`override_reasons` 예 (테이블 설계서 v0.5 형식)

```json
[
  { "field": "urgency", "ai": "P3", "final": "P2", "rule": "SEC_MIN_P2", "reason": "보안 사고 의심은 최소 P2" },
  { "field": "action", "ai": "ANSWER", "final": "ESCALATE", "rule": "NO_EVIDENCE", "reason": "남은 근거가 없음" }
]
```

모델 호출 정보(모델·토큰·지연·성공 여부)는 `llm_calls`에 따로 남는다. 답변 근거는 `message_sources`에 저장한다. (5.2)
