## 0. 개요

이 문서는 **무엇을, 어디서, 어떻게 막고, 무엇을 남기는지**를 정한다. M4-2-3 민감정보 필터는 이 문서를 기준으로 만든다.

- **외부 전송 대상(1장):** 회사 밖으로 나가는 곳과 이미 정한 원칙
- **민감정보 목록(2장):** 무엇을 민감정보로 보고 어떻게 찾는지
- **처리 방식(3장):** 등급마다 가림·치환·그대로·차단 중 무엇을 하는지, 필터가 실패하면 어떻게 하는지
- **처리 위치(4장):** 요청 하나가 들어와서 나갈 때까지 어느 지점에서 거르는지
- **기록·보관(5장):** 로그에 무엇을 남기고 무엇을 남기지 않는지, 삭제하지 않고 남길 건
- **안내 문구·탐지 한계·시험 예시(6장):** 사용자에게 무엇을 알리는지, 규칙으로 못 잡는 것, M4-2-3 테스트 재료
- **요청과 남은 일(7장)**

### 2.3 찾는 방법

찾는 일은 **회사 안의 서버 코드**(정규식과 직원 명부 비교)가 한다. 민감정보인지 판단하려고 원문을 외부 모델에 보내지 않는다.

| 항목 | 등급 | 찾는 규칙 | `mask.ts`에 있나 |
| --- | --- | --- | --- |
| 개인 키 | A | `-----BEGIN … PRIVATE KEY-----` 블록 | 없음 |
| API 키·토큰 | A | 알려진 접두어(`sk-`·`ghp_`·`AKIA`·`xoxb-`·`Bearer `) 뒤 20자 이상, 또는 `API 키`·`토큰`·`token`·`secret` 뒤 16자 이상 값 | 없음 |
| 이름 뒤에 값이 붙은 비밀번호·인증번호 | A | `비밀번호`·`비번`·`패스워드`·`암호`·`인증번호`·`인증 번호`·`인증코드`·`보안코드`·`OTP`·`PIN`·`password`·`passwd`·`pwd`·`pw` 뒤에 `는`·`은`·`이`·`가`·`:`·`=`와 값. 이름과 구분자 사이에 `값`·`번호`·`코드`가 끼어도 된다 (`PIN값이 1245`). 값에 숫자·영문·기호가 있을 때만 | 있음 (`LABELED`). `비번`·`인증코드`·`pwd`는 없음 |
| 주민등록번호 | B | 숫자 6 + `-` + 숫자 7 | 사실상 걸림 (앞 6자리·뒤 7자리가 각각 `LONG_DIGITS`) |
| 카드번호 | B | 숫자 4개씩 4묶음 (`-`·공백 구분) | 없음 |
| 휴대폰 번호 | C | `01X` 뒤에 숫자 7~8자리 (`-`·공백이 있어도 없어도). 앞뒤에 숫자가 붙으면 아님 | 없음 (붙여 쓰면 `LONG_DIGITS`로 걸림) |
| 유선 전화번호 | C | 지역번호(`02`·`031`~`064`)·`070` + `-`·공백 + 숫자 3~4 + `-`·공백 + 숫자 4. 구분자 필수 | 없음 (계좌번호로 가려짐) |
| 이메일 주소 | C | `이름@도메인` | 없음 |
| 사번 | C | `EMP-` + 숫자 4자리 (데이터셋 형식, `employees.csv`) | 없음 |
| 직원 실명 | D | `users.name` 목록과 일치 (직원 명부 400명은 모두 세 글자) | 없음 |
| 계좌번호 | B | `-`로 이은 숫자 묶음, 숫자 합계 10자리 이상. 위 규칙에 걸리지 않은 것만 | 없음 |
| 6자리 이상 연속 숫자 | A | 숫자 6개 이상. 인증번호·OTP로 본다 | 있음 (`LONG_DIGITS`) |

- **적용 순서:** 표의 위에서 아래로 적용한다. 형식이 분명한 것부터 잡아야 서로 겹치지 않는다. 예를 들어 `010-1234-5678`은 계좌번호(합계 11자리)보다 먼저 휴대폰으로 잡힌다.
- 전화번호(휴대폰·유선)도 계좌번호 규칙(숫자를 `-`로 이은 10자리 이상)에 걸린다. 그래서 ② 저장 전에도 **전화번호·이메일·사번인지 먼저 확인하고, 맞으면 가리지 않고 넘어간다.**
- 유선 전화는 회사 대표번호처럼 공개된 번호도 있지만 개인 직통번호일 수도 있다. 코드로 구분할 수 없으므로 휴대폰과 같은 C 등급으로 둔다 (저장은 그대로, 외부 모델에는 `[전화번호N]`).
- **예외:** `0x`로 시작하는 16진 오류 코드(예: `0x80070005`)는 6자리 이상 숫자 규칙에서 뺀다. 진단에 필요한 값인데 지금 `mask.ts` 규칙으로는 가려진다.
- 서버 필터가 기준이다. `mask.ts`는 시연(mock)과 로그인 전 상담 화면용이며, 서버와 같은 규칙으로 맞춘다 (7장 ②).

## 3. 처리 방식

### 3.1 방식 네 가지

| 방식 | 하는 일 | 예 |
| --- | --- | --- |
| **가림** | 값을 `●●●●●●`로 바꾼다. 앞의 이름("비밀번호는")은 남겨 AI가 맥락을 알게 한다. 원래 값은 어디에도 남기지 않는다 | `비밀번호는 Abc123!` → `비밀번호는 ●●●●●●` |
| **치환** | 외부 모델에 보낼 때만 번호 붙은 유형 이름으로 바꾼다. DB에는 그대로 둔다 | `김민지 팀장님 010-1234-5678` → `[직원1] 팀장님 [전화번호1]` |
| **그대로** | 바꾸지 않는다 | 내선 1119, `0x80070005` |
| **차단** | 내용 전체를 외부 모델에 보내지 않는다 | `BLOCKED` 문서·사례 |

**가림 규칙**
- 가림 문자는 `mask.ts`와 같은 `●●●●●●`(6개)로 맞춰 화면 표시를 통일한다.

**치환 규칙 (M4 결정)**
- 이름: `[직원N]`·`[전화번호N]`·`[이메일N]`·`[사번N]`. N은 1부터.
- 번호는 **외부 모델을 부를 때마다 메모리에서** 매긴다. 이전 대화(`history`)부터 이번 글(`message`)까지 처음 나온 순서대로 번호를 붙이므로 턴마다 같은 사람은 같은 번호가 된다. AI가 "[직원1]과 [직원2]"를 구분할 수 있다.
- **대응표(치환 매핑)는 저장하지 않는다.** 호출이 끝나면 버린다. "가명 ↔ 실명" 표가 생기면 그것도 지켜야 할 보관물이 되기 때문이다. 그래서 SRS NFR-SEC-08의 "치환 매핑 보관·삭제"는 해당 항목이 없다.
- **AI 답변을 원래 이름으로 되돌리지 않는다.** 되돌리다 다른 사람 이름이 붙을 위험이 있고, 필요한 경우가 드물다. 대신 시스템 프롬프트에 "치환 이름을 답변에 그대로 쓰지 말고 '말씀하신 분'처럼 표현한다"를 넣는다 (4장 ⑥).

### 3.2 등급별 처리 (M4 결정)

| 등급 | DB 저장 | 외부 모델 | Jira | Slack |
| --- | --- | --- | --- | --- |
| A. 비밀정보 | **가림** (저장 전) | 가림된 글 | 가림된 글 | 넣지 않음 |
| B. 고유식별·금융 | **가림** (저장 전) | 가림된 글 | 가림된 글 | 넣지 않음 |
| C. 연락처·사내 식별 | 그대로 | **치환** | 그대로 (담당자 연락·권한 처리에 필요) | 넣지 않음 (최소 정보) |
| D. 직원 실명 | 그대로 | **치환** (08 1.3에서 문의자 이름을 빼는 것과 같은 기준) | 그대로 | 넣지 않음 (최소 정보) |

- **사용자 글은 차단하지 않는다.** 가림·치환 뒤 그대로 대화를 이어 간다. 비밀정보 하나 때문에 상담이 끊기지 않게 하고, 안내 문구로 다시 입력하지 않도록 알린다 (6장).
- A·B를 저장 전에 가리면 그 뒤의 모든 경로(이전 대화, 초안, Jira)에 원래 값이 없게 된다. 경로마다 따로 거를 필요가 없다. 단, 저장 전에 지나가는 요청 로그·오류 로그는 5장에서 따로 막는다.

### 3.3 필터가 실패하면 (M4 결정)

**실패하면 보내지 않는다.** 필터 코드에서 오류가 나거나 결과를 확인할 수 없으면 가리지 않은 글이 나갈 수 있기 때문이다.

| 실패한 곳 | 처리 |
| --- | --- |
| ② 저장 전 가림 | 글을 저장하지 않고 `500` 오류로 응답한다. 원인은 응답에 넣지 않는다 (07 5.7). 원문을 저장하거나 로그에 남기지 않는다 |
| ④ 외부 모델 호출 전 치환 | 외부 모델을 부르지 않고 담당자 연결 제안으로 넘긴다 (AI 호출 실패와 같은 경로, 09 T11). `FAIL` 기록 (5장) |
| `MASKED` 문서·사례 가림 | 그 근거만 `BLOCKED`로 보고 뺀다 (`청크_메타데이터.md` 3장, 팀 결정) |

## 5. 기록·보관

### 5.1 로그 네 가지

| 로그 | 어디에 | 남기는 것 | 남기지 않는 것 |
| --- | --- | --- | --- |
| 운영 기록 | DB `audit_logs` | 누가·언제·무엇(`event_type`·`result`)·사유 | 원문 (06 G장, 팀 결정) |
| 모델 호출 기록 | DB `llm_calls` | 목적·모델·시간·토큰 수·성공 여부·오류 코드 | 프롬프트·응답 원문 (06 G장, 칸이 없음) |
| 서버 로그 | Python logging | 요청 식별자·경로·상태 코드·처리 시간·오류 종류 | 요청 본문, 사용자 글, 외부 모델 요청·응답 원문 (설계서 13장) |

### 5.2 무엇을 기록하나 (M4 결정)

| 기록 | `event_type` · `result` | 남기는 값 | 이유 |
| --- | --- | --- | --- |
| **민감정보 입력** | `SENSITIVE_INPUT` · 유형 (`PASSWORD`·`OTP`·`API_KEY`·`PRIVATE_KEY`·`RRN`·`CARD`·`ACCOUNT`) | 문의 ID, 사용자, 유형별 개수. **값과 원문은 남기지 않는다** | 같은 사람이 반복 입력하면 보안팀이 알아야 한다 (PRD 4.17). 값이 없으므로 기록 자체는 위험하지 않다 |
| **문서 차단** | `BLOCK` · `DOC_BLOCKED` | 문의 ID, 빠진 문서 번호 (`doc_code`) | 매뉴얼 `BLOCKED`가 실제로 답변을 얼마나 막는지 볼 수 있다 |
| 근거가 모두 차단됨 | `BLOCK` · `ALL_BLOCKED` | 문의 ID | 09 3.3 (기존) |
| 필터 실패 | `FAIL` · `FILTER_FAILED` | 문의 ID, 실패한 위치 (②·④) | 3.3 |

- 한 글에 유형이 여러 개면 **유형마다 한 줄씩** 기록한다 (예: 비밀번호와 주민번호 → `PASSWORD` 한 줄, `RRN` 한 줄).
- C·D(연락처·실명)는 기록하지 않는다. 담당자 업무에 쓰는 일반 정보라 보안 신호가 아니다.
- `SENSITIVE_INPUT`은 06 `audit_logs.event_type`에 없어 추가를 요청한다 (7장 ①). `DOC_BLOCKED`·`FILTER_FAILED`는 `result` 값이라 09 3.3 기록 표에 더한다 (M4).

### 5.3 서버 로그·Trace 규칙 (M4 결정)

| # | 규칙 | 이유 |
| --- | --- | --- |
| ① | IQ-01·IQ-08·IQ-09·TK-03의 **요청 본문을 로그에 찍지 않는다** | 이 요청들은 가리기 전 원문을 들고 있다. 여기서 찍으면 저장 전 가림이 무의미하다 |
| ② | 오류 메시지·예외에 사용자 글을 넣지 않는다 | 예외가 나면 입력값이 오류 메시지에 딸려 로그로 새기 쉽다 (07 5.7 "원인은 `traceId`와 함께 서버 로그에만 남긴다 (민감정보 제외)") |

| ⑤ | Langfuse에는 외부 모델에 보낸 것(④ 처리 뒤)과 같은 글만 보낸다 | Cloud로 바꾸면 Langfuse도 회사 밖이다 (1.1) |

### 5.4 삭제하지 않고 남길 건 (09 6.5 "보안·로그 대상 기준", M4 결정)

✏️ 10/26 정정: 질문·연결 제안·초안의 일반 이탈 삭제(2시간 안내+10분) 전에 보안·로그 대상인지 검사한다. 대상이면 삭제 대신 문의자에게 숨겨 관리자만 열람한다. AI 답변 후 5시간 삭제는 철회했으며 AI 답변 이력의 이후 삭제 범위는 미정이다. 아래 보안 보관 대상 기준은 최신 M4 결정을 유지한다.

| 남기는 경우 | 판단에 쓰는 기록 |
| --- | --- |
| 긴급 신호가 있었던 문의 (긴급인데 접수 없이 종료 등) | `audit_logs` `URGENT_CLOSED` (API 02 IQ-04, 팀 결정: 꼭 기록). TK-03 초안 취소에도 남기도록 요청 중 (09 3.3) |
| 보안(SEC) 분류 문의 | `inquiries.category_code = 'SEC'` |
| 민감정보 입력이 있었던 문의 | `audit_logs` `SENSITIVE_INPUT` (5.2) |

- 남긴 건도 A·B는 이미 가려진 상태다. 원래 값은 남지 않는다.
- ✏️ 숨긴 문의는 문의자 목록·상세·세션·메시지·이어가기·해결 확인에서 제외하며 일반 담당 그룹 조회로도 열 수 없게 한다. 관리자의 보안 조회 권한으로만 열람하고 일반 업무 통계에서 제외한다. 숨김 저장 정보와 구현 방식은 06·API에서 확정한다.
- ✏️ 숨김 보관한 문의 자체의 보관 기간·이후 삭제 시점은 미정이다. 서버 로그·Trace 30일과 혼동하지 않으며 숨긴 문의를 30일 후 자동 삭제하는 규칙을 추가하지 않는다.

## 6. 안내 문구·탐지 한계·테스트 예시

### 6.1 안내 문구 (M4 결정)

| 상황 | 문구 | 보여 주는 방법 |
| --- | --- | --- |
| A 등급을 가림 | "**민감정보가 감지되었어요.** 입력하신 정보는 안전을 위해 ●●●로 가림 처리했어요. 비밀번호나 인증번호는 입력하지 말아 주세요." | `SYSTEM` 메시지 (IQ-01·IQ-08·IQ-09 응답 `messages`, API 02). `MASK_NOTICE` |
| A 중 비밀번호를 가림 | 위 문구 + "실제 사용 중인 비밀번호라면 비밀번호 재설정 포털에서 변경해 주세요." | 〃. `MASK_NOTICE_PASSWORD`. 포털은 IT-STD-001 부록 |
| B 등급을 가림 | "**개인정보가 감지되었어요.** 입력하신 정보는 안전을 위해 ●●●로 가림 처리했어요. 문의에 필요하지 않은 개인정보는 입력하지 말아 주세요." | 〃. `MASK_NOTICE_IDENTITY` |
| TK-03 초안 수정 글을 가림 | "**민감정보가 가림 처리되었어요.** 입력하신 내용에 민감정보가 포함되어 있어 일부 내용을 가렸어요. 접수 전 내용을 확인해 주세요." | 초안 카드 위 안내 (M6). `MASK_NOTICE_DRAFT` |
| 근거가 모두 차단됨 (`ALL_BLOCKED`) | "**담당자의 확인이 필요한 문의예요.** 보안 정책에 따라 AI가 직접 안내하기 어려운 내용이에요. 담당자에게 문의할 수 있도록 도와드릴게요." | 연결 제안 (09 T09). `BLOCKED_NOTICE`. 어떤 문서가 막혔는지는 말하지 않는다 |
| 필터 실패 (3.3) | ② 저장 전 가림 실패: 일반 오류 문구 (글은 저장되지 않으니 다시 보내 달라고 안내) · ④ 치환 실패: AI 호출 실패와 같은 문구 | ② 오류 응답 · ④ 09 T11 |

- 문구는 `frontend/src/core/mask.ts`·디자인 가이드 문구 사전과 글자까지 같게 둔다. 굵은 글씨는 제목(첫 줄)이다. 서버 문구는 `backend/app/agent/sensitive/mask.py`에 있고, 화면과 다르면 시험이 실패한다.
- C·D는 DB에 그대로 두고 외부 모델에만 치환하므로 사용자에게 알리지 않는다.
- 입력창 아래 상시 안내: "비밀번호·인증번호·API 키는 입력하지 마세요." 상담·새 문의·로그인 전 상담 화면에 이미 있다 (`ChatView`·`NewInquiryView`·`ConsultPanel`의 `NOTE`).
- AI는 비밀정보를 묻지 않는다 (PRD 4.13, IT-STD-001 5장, 08 4.4).

### 6.2 탐지 한계

규칙(정규식·명부)으로 찾기 때문에 아래는 **못 잡거나 지나치게 잡는다.** MVP에서는 한계로 두고 안내 문구로 보완한다.

| 구분 | 예 | 결과 | 보완 |
| --- | --- | --- | --- |
| 못 잡음 | "어제 바꾼 거 qwer1234! 인데 안 돼요" ("비밀번호"라는 말 없이 쓴 값) | 그대로 저장·전송 | 상시 안내, 6.3 시험 예시로 관리 |
| 못 잡음 | "비밀번호 qwer1234" (이름과 값 사이에 `는`·`:` 없이 띄어 씀) | 그대로 (값이 6자리 이상 숫자만이면 숫자 규칙으로 잡힘) | 〃 |
| 못 잡음 | 5자리 이하 PIN·OTP를 이름 없이 씀 ("1234 눌렀는데") | 그대로 | 〃 |
| 못 잡음 | "김 팀장님", 영문 이름, 명부에 없는 사람 | 그대로 전송 | — |
| 못 잡음 | 숫자를 한글로 씀 ("공일공 일이삼사…"), 숫자 사이를 띄어 씀 | 그대로 | — |
| 지나치게 잡음 | 자산번호·주문번호처럼 6자리 이상 숫자 ("자산번호 202610") | ●로 가림 | 안전한 쪽으로 둔다. 담당자에게는 다시 물어보게 된다 |
| 지나치게 잡음 | 일반 단어와 같은 직원 이름 | 외부 모델에만 치환 | 명부 400명은 모두 세 글자라 가능성은 낮다 |
| 지나치게 잡음 | 영어 단어 끝이 이름과 같음 (`spin: 3`, `npw=abc1`) | ●로 가림 | 안전한 쪽으로 둔다. 경계를 걸면 `dbpassword=…`처럼 붙여 쓴 진짜 값을 놓친다 |

**보완 후보 (MVP 뒤):** 회사 안에서 돌리는 분류 모델(예: Laya)로 이름 없이 쓴 비밀번호를 찾는다. 외부 API형 분류 모델은 원문을 밖으로 보내야 하므로 쓰지 않는다. 한국어 성능과 놓침률을 6.3 예시로 평가한 뒤 검토한다.
