## 0. 개요

문의가 접수되면 **어느 담당 그룹이, 그 그룹의 누가** 맡을지 정하고, Jira Ticket의 담당자까지 채우는 규칙을 정리한 문서다.

- **포함:** 담당 그룹 결정, 담당자 선정, Jira 담당자 지정과 결과 확인, 실패·예외 처리, DB 표현
- **제외:** Jira Ticket 생성 필드 매핑(`field_mapping.yaml`), 화면 디자인(기획안 참고)

## 1. 전체 흐름

| 단계 | 처리 | 분기 |
| --- | --- | --- |
| ① 접수 저장 | 접수번호(예: `RCPT-0042`)를 한 번만 발급한다 | 같은 초안을 다시 보내면 기존 접수를 반환한다 |
| ② 담당 그룹 결정 | 분류·세부 분류로 시나리오별 담당 그룹을 찾는다 | 그룹을 정할 수 없으면 서비스데스크 확인 |
| ③ 후보 필터링 | 정해진 담당 그룹 구성원 안에서만 후보를 고른다 | 후보가 없으면 해당 그룹 팀장 확인 |
| ④ 담당자 선정·예약 | 업무량이 가장 적은 1명을 고르고 즉시 업무량에 +1 한다 | 동률이면 2.4의 순서로 결정 |
| ⑤ Jira Ticket·담당자 | Ticket 생성 → 담당자 지정. 같은 접수번호의 Ticket이 있으면 재사용한다 | — |
| ⑥ 결과 확인 | Jira 담당자를 다시 조회해 ④에서 선정한 담당자와 비교한다 | 일치 → 배정 확정 / 확실한 실패·불일치 → 예약 해제 후 팀장 확인 / 결과 불명확 → 예약 유지·재조회 |

함께 처리하는 동작
- 긴급(P1)이면 배정과 별개로, 접수 즉시 담당 그룹 전원(팀장 포함)에게 알린다.
- Jira에서 담당자나 상태가 바뀌면 웹훅, 주기 조회, 새로고침으로 ITssue에 반영하고 업무량을 다시 계산한다.
- 문의자 화면은 배정 전까지 「연결 중」, 배정 후 「담당자 배정」으로 표시한다. 관리자 화면(운영현황)에서는 배정이 막힌 건을 따로 모아 본다.

## 2. 배정 기준

### 2.1 담당 그룹
- 분류·세부 분류로 시나리오별 담당 그룹을 찾는다. 담당 그룹 추천과 예외 규칙(`routing_rules`)은 AI 판단(M4) 쪽에서 정한다.
- 담당 그룹을 판단할 수 없으면 서비스데스크가 확인한다.

### 2.2 중복 접수 방지
- 키는 **접수번호**다. ITHD 번호는 Jira가 부여하는 값이라 키로 쓰지 않는다.
- 같은 초안을 다시 보내면 새로 만들지 않고 기존 접수를 반환한다 (TK-04).
- Jira에는 Ticket을 만들기 전에 접수번호로 먼저 검색하고, 이미 있으면 그 Ticket을 쓴다.

### 2.3 담당자 후보
같은 담당 그룹 구성원 중 아래 조건을 모두 만족하는 사람이다.
- 계정이 정상이다
- 자동배정 대상이다
- 해당 세부 분류를 처리할 수 있다 (`scenario_ids`)
- 팀장은 제외한다

Jira 계정이 없는 구성원은 후보에서 뺀다(6.2 참고). 테스트 때는 담당 그룹 6개에서 1명씩을 실제 팀원 Jira 계정과 1:1로 연결한다.

### 2.4 선정과 예약
1. 업무량(RDY + WIP + 예약)이 가장 적은 1명
2. 동률이면 마지막 배정 시각이 더 오래된 사람
3. 그래도 같으면 사번 순

선정 즉시 업무량에 +1(예약)을 반영한다. 같은 시점에 접수된 두 건이 한 사람에게 몰리는 것을 막기 위해서다.

### 2.5 실패·후보 없음
- **확실한 실패, 후보 없음:** 예약을 해제하고 팀장에게 알린 뒤, 관리자 「확인 필요」 목록 맨 위에 올린다. 다른 담당 그룹으로 자동 이관하지 않는다.
- **결과 불명확(응답 시간 초과 등):** 예약을 유지한 채 재조회한다. 정한 횟수·시간 안에 확인하지 못하면 팀장 확인으로 넘긴다(6.1의 1번).

### 2.6 담당자 변경과 동기화
- Jira에서 바뀐 담당자는 웹훅(TK-13)과 주기 조회로 가져온다.
- ITssue에서 직접 바꾸면(TK-09) Jira에도 반영한다.
- 자동배정은 사람이 바꾼 담당자를 덮어쓰지 않는다.
- 담당자가 바뀌면 업무량도 새 담당자로 옮긴다.

### 2.7 긴급(P1)
배정 규칙은 동일하다. 접수 즉시 담당 그룹 전원(팀장 포함)에게 알림을 별도로 보낸다.

### 3.1 부재(연차·반차) 데이터와 반영 범위

현재 DB 설계(v0.7)에는 연차·부재를 담는 곳이 없다. `users`에는 계정 상태(`account_status`)만, `support_group_members`에는 자동배정 후보 여부(`assignable`)만 있다. 두 값은 계정 정지나 구성원 제외를 뜻하므로 연차 일정을 여기에 섞지 않고 별도 표로 둔다.

| 구분 | 내용 |
| --- | --- |
| 새 표 | `time_off`(연차·반차 일정): `id`, `user_id`(FK → users.id), `time_off_type`(`ANNUAL`/`HALF_AM`/`HALF_PM`), `start_date`, `end_date`, `note`, `created_by`, `created_at`. 반차는 `start_date = end_date`로 제한한다. 사람 단위로 한 번만 등록하며 소속 그룹이 여러 개여도 같은 일정을 쓴다. 오늘이 `start_date`~`end_date`에 들어가면 부재 |
| 시연 데이터 | `dataset/data/time_off.csv`(IT운영·보안 담당자 14건)를 시드로 넣는다. 원본인 구글 시트 「ITssue_HelpDesk_데이터셋_최종본」에 `time_off` 시트를 먼저 추가한다. 가상 회사의 HR 시스템을 대신하는 값이며, 실제 회사라면 HR 연동으로 이 표를 채운다. 테스트 계정 6명 중 2명(업무시스템팀 연차 11.11, 정보보안팀 오후 반차 11.04)이 포함돼 있다 |
| 백엔드 (민경) | ① `time_off` 모델과 마이그레이션, `time_off.csv` 시드(사번으로 `users.employee_no`를 찾아 `user_id`를 채움) ② 연차·반차 일정 조회·등록·삭제 API(권한: 본인, 관리자, 팀장은 자기 그룹 구성원 일정) ③ 배정 조회에서 오늘 부재인 `user_id` 목록을 만들어 `pick_assignee(exclude_user_ids=...)`에 전달 ④ RF-04 그룹 구성원 목록과 OP-02 내 처리 현황의 구성원에 부재 여부(`onLeave`) 필드 추가 ⑤ 팀장 부재 시 알림을 대리 확인자에게 보내는 규칙 ⑥ API 문서 수정: TK-09 자동배정 조건에 「오늘 `time_off`에 해당하지 않음」 추가, 부재자 수동 지정은 사유를 받고 허용(422로 막지 않음), RF-04·OP-02 응답에 `onLeave` 추가, `time_off` 조회·등록·삭제 API 신설 |
| Jira 연동 (현우) | 부재자 목록을 만드는 함수 `absent_user_ids(일정, 현재시각)`를 작성했다(`time_off.py`). 백엔드는 `time_off` 행을 `TimeOff`로 넘기고 결과를 `exclude_user_ids`에 전달하면 된다 |
| 프론트엔드 (나영) | ① 연차·반차 일정 등록 화면(담당자: 내 일정, 관리자: 구성원별, 팀장: 자기 그룹 구성원) ② A06 운영현황의 담당자 현황과 담당자 지정 창에 부재 표시 ③ T02 「우리 팀 현황」의 부재 인원 |
| 대시보드 | A06 운영현황과 T02 우리 팀 현황에는 반영한다. A02 대시보드는 기간 기준 처리 건수 집계라 부재 표시가 필요 없어 반영하지 않는다 |
| 반차 처리 | 오전 반차는 13시 전까지, 오후 반차는 13시부터 후보에서 뺀다. 연차는 종일 뺀다. 기준 시각은 `half_day_cutoff`(기본 13시)로 바꿀 수 있고, 현재 시각으로 거르는 일은 `absent_user_ids`가 한다 |

## 4. 구현 현황

`backend/app/integrations/jira/`에는 기존 **Ticket 생성(`create_ticket`)과 접수번호 검색(`find_by_receipt`)** 에 더해, 아래 항목의 코드를 작성했다. 모의 응답으로 한 테스트 62개(기존 27개 포함)를 통과했고, **실제 Jira로는 테스트하지 않았다.**

| 항목 | 상태 | 위치 | 담당(안) |
| --- | --- | --- | --- |
| 담당자 지정 호출 (JIRA_ASSIGN) + 지정 후 재조회 비교 | 작성 | `client.py` `assign_issue`·`get_assignee` | 현우 |
| 상태 전환 호출 (JIRA_TRANSITION) | 작성 | `client.py` `transition_issue`·`get_work_status` | 현우 |
| 웹훅 본문 해석, 서명(`X-Hub-Signature`) 검증 | 작성 | `webhook.py` | 현우 |
| 담당자 선정 (후보 필터링 + 업무량 비교) | 작성 | `assignment.py` `pick_assignee` | 현우 |
| 재시도 판단 (재시도·결과 조회·관리자 확인) | 작성, 숫자는 제안값 | `retry.py` `next_step` | 현우 |
| 연차·반차 일정에서 지금 부재인 사람 목록 만들기 | 작성 | `time_off.py`(`absent_user_ids`) | 현우 |
| 사번 ↔ Jira 계정 연결표 (테스트용 6명, 1:1) | 작성, accountId 값 입력 전 | `accounts.py`, `jira_accounts.yaml` | 현우 |
| 중복 생성 방지 | 기존 구현 (접수번호 검색) | `create_ticket` | — |
| 웹훅 수신 API (TK-13), 이벤트 저장·중복 거르기 | 없음 | — | 민경 |
| 접수·배정 API (TK-01 ~ TK-13) | 없음 (`api/`에 `health.py`만 있음) | — | 민경 |
| 구성원·업무량 조회, 예약 저장, 작업 실행(`integration_jobs`) | 없음 | — | 민경 |
| 테이블 설계서 v0.7 반영 (모델·마이그레이션) | 없음 | — | 민경 |

실제 Jira(ITHD)에서 확인할 것
- 워크플로가 RDY → CLS처럼 건너뛰는 전환을 허용하는지 (막혀 있으면 `invalid_transition` 오류)
- API 토큰 계정의 담당자 지정 권한
- 웹훅 헤더의 실제 값: 서명(`X-Hub-Signature`)과 중복 확인용 `X-Atlassian-Webhook-Identifier`가 Jira 문서대로 오는지

확인된 공백
- `assignment_revision` 등 새로 쓰는 컬럼은 모델·마이그레이션이 없다.
- 데이터셋의 `jira_account`는 사번을 그대로 복사한 값이라 실제 Jira accountId가 아니다. 테스트 기간에는 `jira_accounts.yaml`로 대신한다.

| 3 | 동기화 방식 | 정한 것: 기본 1분마다 Jira를 조회해 맞추고, 새로고침 버튼으로 바로 동기화한다(관리자·담당자 화면). 웹훅 비밀값은 Jira 관리자 웹훅의 서명 방식(`X-Hub-Signature`)을 쓴다. 남은 것: 개발 중 Jira가 웹훅을 보낼 공개 주소, API 설계서 TK-13의 헤더 서술(`X-Itssue-Webhook-Secret`)을 서명 방식으로 고치기 | 현우·민경 |
