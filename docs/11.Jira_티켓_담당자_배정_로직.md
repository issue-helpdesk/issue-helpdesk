## 0. 개요

문의가 접수되면 **어느 담당 그룹이, 그 그룹의 누가** 맡을지 정하고, Jira Ticket의 담당자까지 채우는 규칙을 정리한 문서다.

- **포함:** 담당 그룹 결정, 담당자 선정, Jira 담당자 지정과 결과 확인, 실패·예외 처리, DB 표현
- **제외:** Jira Ticket 생성 필드 매핑(`field_mapping.yaml`), 화면 디자인(기획안 참고)

## 1. 전체 흐름

| 단계 | 처리 | 분기 |
| --- | --- | --- |
| ① 접수 저장 | 접수번호(예: `RCPT-0042`)를 한 번만 발급한다 | 같은 초안을 다시 보내면 기존 접수를 반환한다 |
| ② 담당 그룹 결정 | 분류·세부 분류로 시나리오별 담당 그룹을 찾는다 | 그룹을 정할 수 없으면 서비스데스크 확인 |
| ③ 후보 필터링 | 정해진 담당 그룹 구성원 안에서만 후보를 고른다 | 후보가 없으면 해당 그룹 팀장 확인 |
| ④ 담당자 선정·예약 | 업무량이 가장 적은 1명을 고르고 즉시 업무량에 +1 한다 | 동률이면 2.4의 순서로 결정 |
| ⑤ Jira Ticket·담당자 | Ticket 생성 → 담당자 지정. 같은 접수번호의 Ticket이 있으면 재사용한다 | — |
| ⑥ 결과 확인 | Jira 담당자를 다시 조회해 ④에서 선정한 담당자와 비교한다 | 일치 → 배정 확정 / 확실한 실패·불일치 → 예약 해제 후 팀장 확인 / 결과 불명확 → 예약 유지·재조회 |

함께 처리하는 동작
- 긴급(P1) 그룹 전원 통보는 요구사항이며 현재 미구현이다. 실제 알림은 배정 확인 시 담당자 1명, FIN 확인 시 문의자에게 생성한다.
- Jira에서 담당자나 상태가 바뀌면 웹훅, 주기 조회, 새로고침으로 ITssue에 반영하고 업무량을 다시 계산한다.
- 문의자 화면은 배정 전까지 「연결 중」, 배정 후 「담당자 배정」으로 표시한다. 관리자 화면(운영현황)에서는 배정이 막힌 건을 따로 모아 본다.

## 2. 배정 기준

### 2.1 담당 그룹
- 분류·세부 분류로 시나리오별 담당 그룹을 찾는다. 현재 그룹은 서버가 세부 유형의 기본 그룹으로 정한다. AI가 그룹을 직접 확정하지 않고 `routing_rules` 예외 적용은 미구현이다.
- 담당 그룹을 판단할 수 없으면 서비스데스크가 확인한다.

### 2.2 중복 접수 방지
- 키는 **접수번호**다. ITHD 번호는 Jira가 부여하는 값이라 키로 쓰지 않는다.
- 같은 초안을 다시 보내면 새로 만들지 않고 기존 접수를 반환한다 (TK-04).
- Jira에는 Ticket을 만들기 전에 접수번호로 먼저 검색하고, 이미 있으면 그 Ticket을 쓴다.

### 2.3 담당자 후보
같은 담당 그룹 구성원 중 아래 조건을 모두 만족하는 사람이다.
- 계정이 정상이다
- 자동배정 대상이다
- 팀장은 제외한다
- 오늘 연차·반차로 부재 중이 아니다 (3.1)

세부 분류는 담당 그룹을 찾는 데만 쓴다. 담당자가 어떤 세부 분류를 처리해 왔는지(`scenario_ids`, `member_skills`)는 과거 처리 이력을 확인하는 용도이며 후보 조건이 아니다(11.04 팀 결정). 같은 그룹 구성원이면 어떤 세부 분류든 업무량과 부재 여부로만 고른다. 세부 분류가 없는 미분류 접수는 개인 자동배정을 하지 않는다.

Jira 계정이 없는 구성원은 후보에서 뺀다(6.2 참고). 테스트 때는 담당 그룹 6개에서 1명씩을 실제 팀원 Jira 계정과 1:1로 연결한다.

### 2.4 선정과 예약
1. 업무량(RDY + WIP + 예약)이 가장 적은 1명
2. 동률이면 마지막 배정 시각이 더 오래된 사람
3. 그래도 같으면 사번 순

선정 즉시 업무량에 +1(예약)을 반영한다. 같은 시점에 접수된 두 건이 한 사람에게 몰리는 것을 막기 위해서다.

### 2.5 실패·후보 없음
- **확실한 실패, 후보 없음:** 예약을 해제하고 NEEDS_ADMIN과 배정 실패 이력을 남겨 관리자 확인 목록에서 조회한다. 팀장 통보는 별도 미구현 요구다. 다른 담당 그룹으로 자동 이관하지 않는다.
- **결과 불명확(응답 시간 초과 등):** 예약을 유지한 채 재조회한다. RetryPolicy의 재조회 한도·기한을 초과하면 NEEDS_ADMIN으로 넘긴다. 기본 간격 60초·한도 3·기한 900초이며 최초 요청과 확인 횟수 계산은 4장 기준이다.

### 2.6 담당자 변경과 동기화
- Jira에서 바뀐 담당자는 웹훅(TK-13)과 주기 조회로 가져온다.
- 배정 실패로 「확인 필요」가 된 접수도 Jira에서 직접 정한 담당자가 배정 자격을 갖췄으면 받아들이고, 남아 있던 실패 작업을 닫는다. 자격이 없으면 그대로 두어 관리자가 TK-09·TK-12로 처리한다.
- ITssue에서 직접 바꾸면(TK-09) Jira에도 반영한다. 이때 이전 배정의 실패 작업은 대체됨으로 닫는다.
- 자동배정은 사람이 바꾼 담당자를 덮어쓰지 않는다.
- 담당자가 바뀌면 업무량도 새 담당자로 옮긴다.

### 2.7 긴급(P1)
배정 규칙은 동일하다. 접수 즉시 담당 그룹 전원(팀장 포함)에게 알리는 것은 미구현 요구다. 현재 배정 알림은 확인된 담당자 1명에게 생성한다.

### 3.1 부재(연차·반차) 데이터와 반영 범위

초기 DB 설계(v0.7)에는 없었으나 현재는 `time_off` 모델·마이그레이션·API가 구현돼 있다. `users`에는 계정 상태(`account_status`)만, `support_group_members`에는 자동배정 후보 여부(`assignable`)만 있다. 두 값은 계정 정지나 구성원 제외를 뜻하므로 연차 일정을 여기에 섞지 않고 별도 표로 둔다.

| 구분 | 내용 |
| --- | --- |
| 새 표 | `time_off`(연차·반차 일정): `id`, `user_id`(FK → users.id), `time_off_type`(`ANNUAL`/`HALF_AM`/`HALF_PM`), `start_date`, `end_date`, `note`, `created_by`, `created_at`. 반차는 `start_date = end_date`로 제한한다. 사람 단위로 한 번만 등록하며 소속 그룹이 여러 개여도 같은 일정을 쓴다. 연차는 기간 전체, 반차는 KST 13시 전후로 현재 부재를 계산 |
| 시연 데이터 | `dataset/data/time_off.csv`(IT운영·보안 담당자 14건)를 시드로 넣는다. 원본인 구글 시트 「ITssue_HelpDesk_데이터셋_최종본」에 `time_off` 시트를 먼저 추가한다. 가상 회사의 HR 시스템을 대신하는 값이며, 실제 회사라면 HR 연동으로 이 표를 채운다. 테스트 계정 6명 중 2명(업무시스템팀 연차 11.11, 정보보안팀 오후 반차 11.04)이 포함돼 있다 |
| 백엔드 (민경) | ① `time_off` 모델과 마이그레이션, `time_off.csv` 시드(사번으로 `users.employee_no`를 찾아 `user_id`를 채움) ② 연차·반차 일정 조회·등록·삭제 API(권한: 본인, 관리자, 팀장은 자기 그룹 구성원 일정) ③ 배정 조회에서 오늘 부재인 `user_id` 목록을 만들어 `pick_assignee(exclude_user_ids=...)`에 전달 ④ RF-04 그룹 구성원 목록과 OP-02 내 처리 현황의 구성원에 부재 여부(`onLeave`) 필드 추가 ⑤ 팀장 부재 시 알림을 대리 확인자에게 보내는 규칙 ⑥ API 문서 수정: TK-09 자동배정 조건에 「오늘 `time_off`에 해당하지 않음」 추가, 부재자 수동 지정은 사유를 받고 허용(422로 막지 않음), RF-04·OP-02 응답에 `onLeave` 추가, `time_off` 조회·등록·삭제 API 신설 |
| Jira 연동 (현우) | 부재자 목록을 만드는 함수 `absent_user_ids(일정, 현재시각)`를 작성했다(`time_off.py`). 백엔드는 `time_off` 행을 `TimeOff`로 넘기고 결과를 `exclude_user_ids`에 전달하면 된다 |

## 4. 구현 현황

현재는 클라이언트 함수뿐 아니라 TK-01~14·DB 모델·연동 작업 실행기·웹훅 수신/재조회·관리자 복구·프론트 상세 연결까지 코드가 있다. 예전의 “api에는 health.py만 있음”, “assignment_revision 모델 없음”은 더 이상 현재 상태가 아니다. 실제 Jira 계정별 권한·최종 서버 배포 성공은 별도로 확인한다.

| 기능 | 현재 구현 경로 |
|---|---|
| 초안·접수·수정 시각 재확인 | services/ticket.py create_draft·update_draft·confirm·save_ticket |
| 그룹 내 예약·잠금·revision | services/assignment.py reserve_assignment, repositories/assignment.py lock_group |
| Jira 생성·중복 확인 | services/jira_create.py, integrations/jira/confirmed_ticket.py·client.py |
| 배정 요청·재조회·알림 | services/jira_assign.py, notifications ASSIGNED |
| 상태 변경·처리 결과·확인 | services/jira_transition.py, FIN→CLS·FIN→WIP |
| 웹훅 영속화·중복 제거 | api/jira_webhook.py, services/jira_webhook.py record_webhook_event |
| 외부 값 반영 | 웹훅은 신호로 사용하고 Jira 최신 값을 다시 읽음. 댓글 이벤트는 IGNORED |
| 자동 실행·중단 복구 | integrations/jira/worker.py: 생성→배정→전이→웹훅→주기 대조 |
| 화면 | 담당자 본인 건 처리 시작·결과 입력, 관리자 지정·확인/재시도, 문의자 해결 확인 |

최초 생성은 내부 접수와 같은 트랜잭션으로 작업을 저장한다. 생성 성공 뒤 최초 자동배정을 예약한다. 담당자 지정은 요청 성공만으로 확정하지 않고 Jira 재조회 결과를 대조한다. 재지정 때 예전 실패 작업을 대체 처리하며, 실패 뒤 Jira 직접 변경도 현재 그룹 자격을 만족하면 반영한다.

RetryPolicy의 현재 기본값은 일반 오류 최초 포함 최대 3회와 대기 60·300초, 결과 불명확 재조회 간격 60초·한도 3·기한 900초다. 실제 조회 횟수는 job.attempts와 `>` 비교에 영향을 받으므로 “무조건 정확히 3분 뒤 종료”로 설명하지 않는다. 기본 워커 반복은 30초, 주기 대조는 60초 이상 오래된 접수 대상, 새로고침 재조회 최소 간격은 30초다.

## 6. 확인 필요 사항과 반영 완료

아래는 초기 협업 확인 항목이다. 함수·API 구현 여부는 4장과 실제 코드를 기준으로 보며, 초기의 담당자별 작업 요청을 현재 미구현 목록으로 그대로 읽지 않는다. P1 통보·대리 수신·운영 정책 숫자는 별도 확인이 필요하다.

### 6.1 운영 정책 확인 필요 (초기 항목·현재 구현은 4장 우선)

| # | 항목 | 정할 내용 | 관련 담당 |
| --- | --- | --- | --- |
| 1 | 결과 불명확 처리 | Jira 요청 뒤 성공 여부를 모를 때의 재조회 한도. 코드(`retry.py`)에 들어 있는 임시값은 이렇다. 재조회는 1분 간격 3회이고, 3번 조회해도 확인하지 못하면(약 3분) 팀장 확인으로 넘긴다. 재시도할 수 있는 오류(시간 초과·통신 오류·요청 한도 초과·서버 오류)는 첫 시도를 포함해 최대 3회 시도하고, 1분·5분 뒤에 다시 실행한다. 3번째도 실패하면 팀장 확인으로 넘긴다. 정할 것: ① 이 숫자를 확정할지, ② 재시도를 3번(1·5·15분)으로 늘릴지, ③ 시간 초과 때 예약을 풀지 유지할지(지금 코드와 2.5절은 유지로 가정).<br>예) 10:00:03에 담당자 지정 요청을 보냈는데 Jira 응답이 없다(시간 초과). 실제로는 지정됐을 수도 있다. 같은 요청을 다시 보내기 전에 Jira에 「지금 담당자가 누구인가」를 한 번 더 물어 확인하는 것이 재조회다. 생성도 같다. 생성 요청이 시간 초과되면 접수번호(RCPT-0042)로 Jira를 검색해, 있으면 그 Ticket을 쓰고 없으면 다시 만든다 | 현우·민경 |
| 2 | 긴급(P1) 알림 | 팀 전원 알림을 Slack으로 보낼지(알림 테이블은 있으나 발송은 Should), 화면 알림으로 대신할지 | 전체 |
| 3 | 동기화 방식 | 정한 것: 기본 1분마다 Jira를 조회해 맞추고, 새로고침 버튼으로 바로 동기화한다(관리자·담당자 화면). 웹훅 비밀값은 Jira 관리자 웹훅의 서명 방식(`X-Hub-Signature`)을 쓴다. 남은 것: 개발 중 Jira가 웹훅을 보낼 공개 주소, API 설계서 TK-13의 헤더 서술(`X-Itssue-Webhook-Secret`)을 서명 방식으로 고치기 | 현우·민경 |
| 4 | 화면 표시 기준 | ① 결과 불명확(VERIFYING) 건을 「확인 필요」로 셀지. 문의자 화면 코드(`frontend/src/views/inquiry/TicketCard.tsx`)는 VERIFYING을 확인 필요로 보지만, API 명세(`docs/api/03.접수_연동.md`의 `needsAdmin`)는 `NEEDS_ADMIN`만 센다. 같은 시점에 화면은 3건, API는 2건처럼 숫자가 다를 수 있다.<br>② 같은 상태 이름이 다르다. 문의자가 문의를 열면 보이는 진행 단계 카드(`TicketCard.tsx`)는 「운영자 확인 중」, 문의자의 「내 문의」 목록 상태 배지(`frontend/src/api/inquiryState.ts`)는 「담당자 확인 중」이다.<br>③ 화면 시연용 팀 표(`frontend/src/api/catalog.ts`)는 분류 단위라 시나리오 담당 그룹과 다르다(예: `SYS` 분류는 업무시스템팀 한 곳으로 표시하지만 실제는 세부 유형에 따라 3개 팀) | 나영·민경 |

### 6.2 반영 완료 (9건)

| 항목 | 반영한 내용 | 담당 |
| --- | --- | --- |
| Jira 계정 없는 사람 제외 | 후보에서 「유효한 Jira 계정」이 없는 구성원을 뺀다. TK-09와 같은 기준이며 `pick_assignee`의 기본값(옵션으로 끌 수 있음) | 현우 |
| 사번 ↔ Jira 계정 연결 (테스트) | 담당 그룹 6개에서 1명씩의 사번과 실제 팀원 Jira 계정을 1:1로 잇는 `jira_accounts.yaml`과 읽기 함수(`account_id_for`). 한 계정을 두 사번에 쓰면 오류. 계정 ID 값은 입력 전. **테스트 한계:** 담당 그룹마다 1명뿐이라 업무량이 가장 적은 사람을 고르는 비교는 이 테스트으로 확인할 수 없다(후보가 1명이라 항상 그 사람이 선정된다). 업무량 비교는 후보를 늘리거나 가상 데이터로 따로 테스트해야 한다 | 현우 |
| 결과 불명 시 재시도 판단 | 성공 여부를 모를 때 다시 만들지 않고 Jira 조회로만 확인하고, 한도를 넘으면 관리자 확인으로 넘기는 판단(`next_step`). 숫자는 6.1의 1번에서 정한다 | 현우 |
| 부재자 제외 자리 | 부재자 목록을 받아 후보에서 빼는 입력(`exclude_user_ids`). 부재 목록은 `absent_user_ids`로 만든다(부재 일정 방식 참고) | 현우 |
| 웹훅 본문 해석 | 이슈 번호·상태 변경·담당자 변경을 읽는다(`parse_jira_webhook`). 값을 덮어쓰지 않고 「Jira 재조회」 신호로만 쓴다(TK-13 방식) | 현우 |
| 웹훅 서명 검증 | Jira가 웹훅 본문에 비밀값으로 서명해 보내는 `X-Hub-Signature` 헤더를 검증한다(`verify_hub_signature`). 서명이 다르거나 비밀값이 없으면 거부한다 | 현우 |
| 부재 일정 방식 | 팀 결정: 연차·반차 일정을 `time_off` 표에 미리 등록해 오늘 날짜로 부재를 계산한다(시연은 가상 HR 데이터 `time_off.csv`). 등록·수정·삭제는 본인, 관리자, 팀장(자기 그룹 구성원 일정을 대신 등록)이 할 수 있다. 반차는 오전 반차 13시 전, 오후 반차 13시부터 부재로 본다. 부재 목록을 만드는 코드는 작성(`absent_user_ids`) | 전체 |
| 문의자 미해결 재처리(FIN → WIP) | 확정 기준: FIN은 담당자의 처리 완료이며 문의자의 해결 확인 전이다. 문의자가 미해결을 선택하면 남은 증상(reason)을 받아 기존 Ticket을 WIP로 복귀시킨다(SRS JIRA-06, Must). 기존 문의·세션·접수번호·Jira 번호를 유지하며 새 티켓을 만들지 않는다. TK-07은 작업 등록 후 202를 반환하고, Jira WIP 반영 확인 후 상태를 확정한다. CLS 종결 뒤 재개와 FIN의 다른 되돌림은 이 예외에 포함하지 않는다. 과거 “FIN·CLS 모두 재처리 없음” 결정은 현재 기준에서 대체됐다 | 전체 |
| 팀장 부재 시 「팀장 확인」 | 팀 결정: 팀장이 부재인 날의 「팀장 확인」 알림을 대신 받을 사람(대리 확인자)은 두지 않고, 이 경우는 이번 범위에서 다루지 않는다. 부재 일정 등록과 후보 제외는 그대로 한다. 참고: Jira에 연차를 표시해 배정에서 빼 주는 기본 기능이 있는지는 확인하지 못했다 | 전체 |

**11.08 정합성 정정:** 과거 결정에 맞춰 SRS·API의 FIN → WIP를 삭제하라는 요청은 철회한다. 현재 기준은 SRS JIRA-06과 [접수·연동 명세](api/03.접수_연동.md) TK-07이다. 미응답은 FIN 유지, 해결 확인은 CLS, 미해결은 기존 Ticket WIP 복귀로 구분한다. 재완료에는 새 처리 결과가 필수이며 완료마다의 결과는 `ticket_status_history.resolution_note`에 남는다. `finished_at`의 실행기/동기화 경로 차이는 [06 문서](api/06.프론트_연동_요청.md)의 서버 확인 항목으로 남긴다.
