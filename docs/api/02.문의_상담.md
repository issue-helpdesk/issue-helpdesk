## 0. 읽는 법

- 경로는 Base URL `/api/v1` 이후 부분이다.
- 표의 **컬럼**은 테이블 설계서의 컬럼이다. `(파생)`은 테이블 컬럼이 아닌 계산값이다.
- **공통 에러는 API별 표에서 생략한다**: `401 UNAUTHORIZED`, `401 TOKEN_EXPIRED`, `403 AUTH_ACCOUNT_INACTIVE`, `403 AUTH_PASSWORD_CHANGE_REQUIRED`, `422 VALIDATION_ERROR`, `429 TOO_MANY_REQUESTS`, `500 INTERNAL_ERROR`
- **권한이 없는 문의는 `404 INQUIRY_NOT_FOUND`** 로 응답한다 (API 설계서 3.2).
- 페이지가 없는 목록은 `{ "items": [...] }` 형식이다.

## 0.1 요청 재전송과 동시 처리

IQ-01·IQ-08·IQ-09는 `Idempotency-Key` 필수이며 [07. API 설계서](../07.API_설계서.md) 2.6.1을 따른다. 같은 키와 본문이면 최초 결과를 반환한다. 다른 본문은 `409 IDEMPOTENCY_KEY_REUSED`, 문의의 다른 변경이나 AI 처리가 진행 중이면 `409 REQUEST_IN_PROGRESS`이다. IQ-01에서 문의·메시지와 중복 요청 기록을 함께 저장하고, 응답 단절 후에도 같은 키로 조회·재시도하면 기존 문의를 재사용한다.

메시지 seq는 세션별 원자적으로 발급한다. 사용자 메시지 저장 후 AI 처리 소유권을 확인해 결과를 반영한다. AI 처리 중 종료·해결 확인·초안 생성·최종 접수·다른 메시지는 거절하며, 소유권 만료 후 늦게 돌아온 결과도 버린다. 복구 시 저장된 메시지를 다시 생성하지 않는다.


## 1. 문의 상태와 API

### 1.1 문의 상태 (`inquiries.status`) 전이

```mermaid
stateDiagram-v2
    [*] --> IN_PROGRESS: IQ-01 새 문의
    IN_PROGRESS --> AI_RESOLVED: IQ-09 해결됐어요
    IN_PROGRESS --> CLOSED_UNRESOLVED: IQ-04 연결 거절 / TK-03 초안 취소
    IN_PROGRESS --> RECEIVED: TK-04 최종 접수
    RECEIVED --> HANDED_OFF: Jira 생성·개인 배정 확인 (서버 작업)
    CLOSED_UNRESOLVED --> IN_PROGRESS: IQ-06 미해결 이어가기 (저장 전이 세부는 미결)
```

- ✏️ 기존 5시간 미응답 삭제·자동 종료·NO_RESPONSE 설정은 철회한다. `UNCONFIRMED`의 저장 의미는 미결이며 시간 경과로 이 값에 전이시키지 않는다. 위 도표의 CLOSED_UNRESOLVED 재개 저장 처리도 종료 정보와 함께 확정해야 한다. 사용자에게 제공할 재개 동작은 IQ-06을 따른다.
- `RECEIVED`·`HANDED_OFF` 이후 진행은 [03. 접수·연동](03.접수_연동.md)의 접수(Ticket) API로 한다.

### 1.1.1 일반 이탈·숨김·활동 기준 (2026.10.26)

- ✏️ 질문·연결 제안·초안의 일반 이탈 대상은 마지막 유효 활동 후 2시간에 안내하고, 이후 10분간 유효 활동이 없으면 문의·세션·메시지·출처·초안·판단 이력을 전체 삭제하며 목록·일반 통계에서 제외한다. 120분·10분은 환경변수로 관리한다.
- ✏️ AI 답변 이력이 있는 문의의 이후 삭제 범위는 미정이다. Ticket이 있는 문의는 이탈 삭제 대상에서 제외한다. 보안·로그 대상은 삭제 대신 문의자에게 숨기고 관리자 보안 조회만 허용한다. 숨긴 문의 자체의 이후 삭제 시점은 미정이다.
- ✏️ 유효 활동은 저장된 사용자 글·선택·초안 수정 및 AI 응답 완료다. 조회·읽음·새로고침·자동 안내·새 문의 선택은 이전 문의의 시간을 연장하지 않는다. 새 문의를 선택해도 이전 문의를 즉시 삭제하지 않는다.
- ✏️ 안내 후 실제 유효 활동이 있으면 삭제 예약을 취소한다. 삭제 직전 최근 활동·처리 중 여부·Ticket 생성·보관 예외를 재검사한다. AI 처리 중에는 삭제하지 않는다.
- ✏️ 숨긴 문의의 목록·상세·세션·메시지·판단 이력·재개·변경 요청은 문의자 및 일반 담당 그룹에서 제외하며 404를 반환한다. 관리자 보안 조회는 별도 권한으로 허용한다. 목록 totalCount·totalPages에도 숨김 제외 기준을 적용한다.
- 🆕 복귀 안내·안내 시각·삭제 예정 시각의 응답 필드와 물리 저장 구조는 미결이다. 프론트 자체 타이머로 삭제를 확정하지 않는다.

### 1.2 화면 표시 상태 `displayStatus` (파생)

SRS 4.5 배지 값을 쓴다. 접수 건은 접수의 업무 상태(`tickets.work_status`)를 함께 본다.

| 저장 상태 | 부가 조건·Ticket 업무 상태 | displayStatus | 화면 표시 |
|---|---|---|---|
| ✏️ `IN_PROGRESS` 등 저장 매핑 미결 | Ticket 없음·현재 AI 답변에 대한 해결 결과 선택 전 | `unconfirmed` | AI 답변 직후 미확인 (시간 초과 아님) |
| ✏️ `IN_PROGRESS` | 위 AI 확인 대기 외 질문·연결 제안·초안 | `in_progress` | 진행 중 |
| `AI_RESOLVED` | | `ai_resolved` | AI 해결 |
| ✏️ `UNCONFIRMED` | 기존 저장값·새 의미 미결 | (저장 의미 확정 후 매핑) | 코드만으로 종료·확인 대기 여부를 판단하지 않음 |
| `CLOSED_UNRESOLVED` | | `unresolved` | 미해결 |
| `RECEIVED` | (null 또는 RDY) | `received` | 접수 |
| `HANDED_OFF` | `RDY` | `assigned` | 담당자 배정 |
| `HANDED_OFF` | `WIP` | `progress` | 처리 중 |
| `HANDED_OFF` | `FIN` | `awaiting_confirm` | 해결 확인 대기 |
| `HANDED_OFF` | `CLS` | `resolved` | 해결 완료 |

✏️ `unconfirmed`는 AI 답변 직후의 확인 대기, `awaiting_confirm`은 FIN의 담당자 처리 결과 확인 대기다. 표시 계산은 저장 의미 결정과 구분한다. Ticket이 있으면 Ticket 업무 상태를 우선한다. 이어가기는 해결 결과를 대신 선택하지 않는다.

`in_progress`·`ai_resolved`·`unconfirmed`·`unresolved`는 문의 전용 값이다. SRS 4.1 및 PRD 4.5 정의를 따른다.

### 2.8 `AiTurn` — AI 처리 결과

IQ-01, IQ-08, IQ-09의 응답이다.

| 필드 | 타입 | null | 설명 |
|---|---|---|---|
| inquiry | Inquiry | | 처리 후 문의 |
| messages | Message[] | | **이번 요청으로 생긴 메시지**(사용자 메시지 + AI·SYSTEM 메시지), `seq` 순 |
| assessment | AssessmentView | Y | 이번 요청으로 판단을 새로 했으면 그 결과, 아니면 `null` |
| nextActions | string[] | | 화면에 보여줄 다음 행동 (파생) |

`nextActions` 값

| 값 | 화면 | 나오는 조건 |
|---|---|---|
| ✏️ `REPLY` | 입력창 (추가 질문 답변) | 질문 수집 단계만. 답변 확인·연결 선택·초안 단계는 글을 받지 않음 |
| `CONFIRM_RESOLUTION` | "해결됐어요 / 아직 해결되지 않았어요" 버튼 → IQ-09 | `action = ANSWER` 답변 직후 |
| `DECIDE_HANDOFF` | "담당자 연결 / 연결하지 않음" 버튼 → TK-01 / IQ-04 | `action = ESCALATE`, 또는 `resolutionResult = UNRESOLVED` |
| `START_NEW` | "새 문의" 버튼 | 문의가 종료됨 |
| 🆕 `CONFIRM_TICKET_RESOLUTION` | 기존 Ticket의 해결·미해결 버튼 → TK-07 | IQ-06 FIN 이어가기 응답 전용. AiTurn의 AI 해결 확인과 구분 |

- ✏️ `action = OUT_OF_SCOPE`이면 지원 범위 밖 안내 메시지와 함께 `DECIDE_HANDOFF`(서비스데스크 확인)를 준다 (SRS ACTION-01).

## 3. API

### IQ-01 새 문의 시작

`POST /inquiries` · 권한: 로그인 · 요구사항: INQ-01~04

**Header**

| 헤더 | 필수 | 설명 |
|---|---|---|
| `Idempotency-Key` | Y | 요청마다 새로 만든 값(예: UUID). 재전송 시 같은 값 (0.1) |

**Request Body**

| 필드 | 타입 | 필수 | 컬럼 | 제약 |
|---|---|---|---|---|
| content | string | Y | `messages.content` | 1~4000자 |

```json
{
  "content": "어제 업데이트 이후로 VPN 접속이 안 돼요. 재택 중이라 업무를 못 하고 있습니다."
}
```

**처리**

1. `content`의 민감정보를 **저장 전에 가린다** ([10. 민감정보 정책](../10.민감정보_정책.md) 4장 ②). 가린 글로 `inquiries`(`status = IN_PROGRESS`), `chat_sessions`, `messages`(`seq = 1`, `sender = USER`)를 한 트랜잭션으로 저장한다. 원문은 저장하지 않는다.
    - 가린 것이 있으면 안내 문구를 `SYSTEM` 메시지로 이어서 저장하고(10 6.1, 비밀정보·고유식별정보 각 1개), 가린 유형마다 `audit_logs`에 `SENSITIVE_INPUT`을 남긴다 (`result` = 유형, 값·원문 없이 개수만, 10 5.2). 응답 `messages`에도 포함된다.
    - 가리다 오류가 나면 아무것도 저장하지 않고 `500`으로 응답한다 (10 3.3).
2. AI 처리: 확인 항목 점검 → 긴급 징후 확인 → (정보가 충분하면) 열람 가능한 가이드 검색 → 부족하면 과거 이력 검색 → 분류·긴급도·처리 방향 판단 → 답변 또는 추가 질문.
3. `inquiry_assessments` 저장, `inquiries`의 현재 판단값·`title` 갱신, AI 메시지와 `message_sources` 저장. 모델 호출마다 `llm_calls`를 남기고, 근거 차단·AI 실패는 `audit_logs`에 남긴다 (`BLOCK`: `DOC_BLOCKED`·`ALL_BLOCKED`, `FAIL`: `AI_FAILED`·`FILTER_FAILED`, 10 5.2).
4. 외부 모델 오류·외부 전송 제한·근거 부족은 에러가 아니라 담당자 연결 제안(`action = ESCALATE`)으로 응답한다.

### IQ-06 기존 문의·세션 이어가기

`POST /inquiries/{inquiryId}/sessions` · 권한: 본인 · 요구사항: ANSWER-04

✏️ 기존 경로를 유지하되 새 세션 생성 API에서 **기존 세션 이어가기 API**로 의미를 정정한다. 새 문의·세션·접수번호·Jira 번호를 발급하지 않는다. 같은 요청을 반복해도 세션·메시지·AI 호출을 추가하지 않는다.

**Path**: `inquiryId` (number). **Request Body** 없음.

| 대상 | 이어가기 후 화면 | 후속 요청 |
| --- | --- | --- |
| ✏️ AI 미확인 | 기존 답변의 해결·미해결 선택 | IQ-09 |
| ✏️ AI 미해결 | 기존 세션에서 담당자 연결 동의/거절 | TK-01 / IQ-04 |
| ✏️ 해결 확인 대기(FIN) | 기존 Ticket의 해결·미해결 선택 | TK-07: CLS 또는 WIP |

**처리:** 소유자·숨김·삭제 여부·현재 처리 잠금을 확인한다. 기존 세션·판단 이력·질문 횟수를 유지하고 현재 상태에 맞는 행동만 돌려준다. 이어가기 자체로 해결 결과 초기화, Ticket 상태 전환 또는 AI 재판단을 하지 않는다. 이미 열려 있어도 허용 대상이면 같은 세션을 반환한다. 종료된 AI 미해결 문의의 status·endedAt·endReason·closedAt 처리 방식은 미결이며 물리 상태 전이는 구현 전에 확정한다.

**Response** ✏️ `200 OK`

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| session | Session | 기존 상담 세션 (ID 유지) |
| inquiry | Inquiry | 현재 문의·Ticket 참조 |
| nextActions | string[] | AI 미확인: CONFIRM_RESOLUTION / AI 미해결: DECIDE_HANDOFF / FIN: CONFIRM_TICKET_RESOLUTION |

🆕 `CONFIRM_TICKET_RESOLUTION`은 기존 Ticket의 TK-07 버튼을 뜻하며 IQ-09로 보내지 않는다. 단순 화면 재표시인 경우 새 메시지·알림을 생성하지 않는다. AI_RESOLVED·CLS 완료 건의 재개 확대는 이번에 확정하지 않는다.

**Errors**

| HTTP | code | 조건 | details |
| --- | --- | --- | --- |
| 404 | INQUIRY_NOT_FOUND | 문의 없음·본인 아님·숨김 건 | |
| 409 | INQUIRY_INVALID_STATE | 위 대상 외 상태 또는 Ticket이 FIN이 아님 | CURRENT_STATUS |
| 409 | REQUEST_IN_PROGRESS | 같은 문의의 다른 변경·AI 처리 중 | |

### IQ-09 해결 확인

`PUT /inquiries/{inquiryId}/resolution` · 권한: 본인 · 요구사항: ANSWER-02

AI 답변을 받은 뒤 해결 여부를 저장한다. 담당자 처리 건의 해결 확인은 TK-07(`FIN → CLS` 해결, `FIN → WIP` 미해결)을 쓴다. 미응답은 FIN 유지다.

**Path**: `inquiryId` (number)

**Header**: `Idempotency-Key` 필수 (IQ-01과 같음)

**Request Body**

| 필드 | 타입 | 필수 | 컬럼 | 제약 |
|---|---|---|---|---|
| resolutionResult | string | Y | `inquiries.resolution_result` | `RESOLVED` / `UNRESOLVED` (`NO_RESPONSE`는 기존 예약값이며 5시간 미응답으로 새로 설정하지 않음) |
| comment | string | | `messages.content` | `UNRESOLVED`일 때 남은 증상. 1~4000자. IQ-01 처리 1과 같이 저장 전에 가려 사용자 메시지로 저장 (안내 `SYSTEM` 메시지·`SENSITIVE_INPUT` 포함) |

```json
{
  "resolutionResult": "UNRESOLVED",
  "comment": "재설치했는데 같은 오류가 나요."
}
```

**처리**

| resolutionResult | 처리 |
|---|---|
| `RESOLVED` | 문의 `status = AI_RESOLVED`, `closed_at = now()`; 세션 `ended_at = now()`, `end_reason = USER_END`; SYSTEM 메시지("해결로 종료되었습니다") |
| `UNRESOLVED` | ✏️ 사용자 미해결 선택을 보존하고 담당자 연결 제안을 제공. comment는 저장만 하며 이 선택·이어가기만으로 AI를 재호출하지 않음. 종료·저장 상태 세부는 미결 |

**Response** `200 OK` — `AiTurn`

- `RESOLVED`: `nextActions = ["START_NEW"]`
- ✏️ `UNRESOLVED`: `nextActions = ["DECIDE_HANDOFF"]`

**Errors**

| HTTP | code | 조건 | details |
|---|---|---|---|
| 404 | `INQUIRY_NOT_FOUND` | 문의 없음·본인 아님 | |
| ✏️ 409 | `INQUIRY_INVALID_STATE` | AI 답변 확인 대기가 아님 (Ticket은 TK-07 사용). UNCONFIRMED 저장 매핑 확정 후 검사 구체화 | `CURRENT_STATUS` |
| 409 | `IDEMPOTENCY_KEY_REUSED` | 같은 키로 다른 본문 전송 | |
| 409 | `REQUEST_IN_PROGRESS` | 이 문의의 AI 처리·다른 변경이 진행 중 | |
| 422 | `VALIDATION_ERROR` | `resolutionResult` 값 오류(`NO_RESPONSE` 포함), `Idempotency-Key` 없음 | `resolutionResult` / `INVALID_VALUE` |

---

IQ-09 재호출: 같은 키·본문은 최초 AiTurn을 반환하고 댓글·SYSTEM 메시지·AI 처리를 반복하지 않는다. 다른 키로 이미 AI_RESOLVED인 문의에 RESOLVED를 보내도 현재 문의와 `messages: []`, `assessment: null`, `nextActions: ["START_NEW"]`를 200으로 반환한다. 그 밖의 종료 상태에서 다른 결과로 바꾸는 요청은 409이다. 해결 결과와 세션 종료·메시지·중복 요청 결과는 한 트랜잭션으로 저장한다.
