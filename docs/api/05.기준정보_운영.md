## 0. 읽는 법

- 경로는 Base URL `/api/v1` 이후 부분이다.
- 표의 **컬럼**은 테이블 설계서의 컬럼이다. `(파생)`은 테이블 컬럼이 아닌 계산값이다.
- **공통 에러는 API별 표에서 생략한다**: `401 UNAUTHORIZED`, `401 TOKEN_EXPIRED`, `403 AUTH_ACCOUNT_INACTIVE`, `403 AUTH_PASSWORD_CHANGE_REQUIRED`, `422 VALIDATION_ERROR`, `429 TOO_MANY_REQUESTS`, `500 INTERNAL_ERROR`
- 기준 정보는 건수가 적어 페이지 없이 `{ "items": [...] }`로 준다.
- 참조 객체 `GroupRef`·`UserRef`는 [02. 문의·상담](02.문의_상담.md) 2.1을 따른다.

## 1A. 연차·반차 일정 (TO)

자동배정에서 지금 부재인 사람을 빼기 위한 일정이다 ([11](../11.Jira_티켓_담당자_배정_로직.md) 3.1). 부재 판단은 회사 현지 시각(KST) 기준이다.

| 유형 | 부재 시간 |
|---|---|
| `ANNUAL` 연차 | 시작일~종료일 종일 |
| `HALF_AM` 오전 반차 | 그날 13시 전 |
| `HALF_PM` 오후 반차 | 그날 13시부터 |

**권한** (AGENT·ADMIN만, EMPLOYEE는 `403`): 현재 서버는 본인 일정, ADMIN 전체, 팀장(MANAGER)의 관리 그룹 활성 구성원 일정을 허용한다. 일정은 사람 단위로 한 번만 등록한다.

**캘린더 사용 범위(11.08 프론트 담당 확인):** 팀원 휴가 일정 조회가 화면 의도이며, 현재 화면에서도 표시된다는 확인을 받았다. 이에 따른 추가 조회 확대 요청은 [R-43](06.프론트_연동_요청.md)에서 제외한다. 아래 서버 권한 설명은 로컬 코드 기준이며, 화면에서 확인한 환경·데이터 경로와 동일하다고 가정하지 않는다. 이번 문서 정리로 조회·관리 권한을 변경하지 않는다.

**겹침**: 같은 사람의 기간이 하루라도 겹치면 `409 TIME_OFF_OVERLAP`이다. 같은 날 오전 반차와 오후 반차만 함께 등록할 수 있다.

`TimeOff`

|---|---|---|---|
| id | number | | `time_off.id` |
| userId | number | | `user_id` |
| user | UserRef | | (파생) |

### TO-01 일정 목록

`GET /time-off` · 권한: AGENT·ADMIN

**Query**: `page`, `size`, `sort`(기본 `startDate,desc`, 가능: `startDate`, `createdAt`), `userId`, `groupId`, `dateFrom`, `dateTo`(이 기간과 겹치는 일정). 조건 없이 부르면 ADMIN은 전체, 팀장(MANAGER)은 본인과 관리하는 그룹 구성원, 일반 담당자(AGENT)는 본인 일정만 조회한다. 이는 현재 로컬 API의 권한 설명이며 캘린더 동작을 바꾸라는 요청이 아니다. 프론트 담당 확인에 따라 R-43 추가 요청은 제외한다.

**Response** `200 OK` — `Page<TimeOff>`

**Errors**: `400 INVALID_REQUEST`(`dateFrom`이 `dateTo`보다 늦음), `403 FORBIDDEN`(볼 수 없는 `userId`·`groupId`)

### TO-02 일정 등록

`POST /time-off` · 권한: AGENT·ADMIN

**Request Body**

| 필드 | 타입 | 필수 | 컬럼 | 제약 |
|---|---|---|---|---|
| userId | number | | `user_id` | 없으면 본인 |
| timeOffType | string | Y | `time_off_type` | `ANNUAL` / `HALF_AM` / `HALF_PM` |
| startDate | string(date) | Y | `start_date` | |
| endDate | string(date) | Y | `end_date` | 시작일 이후. 반차는 시작일과 같아야 함 |
| note | string | | `note` | 1~500자 |

**처리**: `created_by` = 요청자.

**Response** `201 Created` — `TimeOff`

**Errors**

| HTTP | code | 조건 | details |
|---|---|---|---|
| 403 | `FORBIDDEN` | 등록할 수 없는 사람의 일정 | |
| 409 | `TIME_OFF_OVERLAP` | 기간 겹침 | `[{ "reason": "TIME_OFF_ID", "message": "겹치는 일정", "value": 7 }]` |
| 422 | `VALIDATION_ERROR` | 없는 `userId`(`NOT_FOUND`), 날짜 규칙 위반(`endDate` / `INVALID_VALUE`) | 필드별 |

### TO-03 일정 수정

`PATCH /time-off/{timeOffId}` · 권한: AGENT·ADMIN

보낸 필드만 바꾼다. TO-02의 `timeOffType`, `startDate`, `endDate`, `note`를 받는다. `userId`는 바꿀 수 없다(`NOT_ALLOWED`). 바뀐 뒤의 값으로 날짜 규칙과 겹침을 다시 확인한다.

**Response** `200 OK` — `TimeOff`

**Errors**: `404 TIME_OFF_NOT_FOUND`(없음·권한 없음), `409 TIME_OFF_OVERLAP`, `422 VALIDATION_ERROR`

### TO-04 일정 삭제

`DELETE /time-off/{timeOffId}` · 권한: AGENT·ADMIN

**Response** `204 No Content`

**Errors**: `404 TIME_OFF_NOT_FOUND`(없음·권한 없음)

## 1B. 화면 알림 (NT)

담당자 배정과 처리 완료를 화면에 알린다. Slack 발송과 Jira 댓글 알림은 포함하지 않는다.

| kind | 받는 사람 | 만드는 때 |
|---|---|---|
| `ASSIGNED` | 담당자 | Jira 배정이 확인되어 `assign_status`가 `ASSIGNED`가 될 때 (실행기·웹훅·동기화) |
| `FIN` | 문의자 | Jira 완료가 확인되어 `work_status`가 `FIN`이 될 때. 재완료도 다시 만든다 |

- 본인 알림만 볼 수 있다. 재배정되면 이전 담당자의 `ASSIGNED` 알림은 목록과 개수에서 빠진다.
- 알림 내용은 저장하지 않는다. 화면 문구는 `kind`로 만든다.

`Notification`

| 필드 | 타입 | null | 컬럼 |
|---|---|---|---|
| id | number | | `notifications.id` |
| kind | string | | `kind` |
| ticketId | number | | `ticket_id` |
| inquiryId | number | | (파생) `tickets.inquiry_id` |
| receiptNo | string | | (파생) `tickets.receipt_no` |
| summary | string | Y | (파생) `tickets.summary` |
| readAt | string(datetime) | Y | `read_at` |
| createdAt | string(datetime) | | `created_at` |

### NT-01 내 알림 목록

**Query**: `page`, `size`, `unreadOnly`(기본 `false`). 최신순이다.

### NT-02 안 읽은 개수

사이드바처럼 자주 부르는 화면용이다.

**Response** `200 OK` — `{ "count": 3, "ticketIds": [42, 57] }`. `ticketIds`는 안 읽은 알림이 있는 접수이다.

### NT-03 알림 읽음

`PUT /notifications/{notificationId}/read` · 권한: 본인

다시 불러도 처음 읽은 시각을 유지한다.

**Response** `200 OK` — `Notification`

**Errors**: `404 NOTIFICATION_NOT_FOUND` (없는 알림, 다른 사람의 알림, 재배정으로 빠진 알림)

### NT-04 접수 단위 읽음

`POST /notifications/read` · 권한: 로그인

접수 상세를 열 때 부른다. 접수 조회(TK-06)는 읽음 처리를 하지 않는다. 그 접수의 내 알림만 바꾸므로 대상이 없으면 `updatedCount`가 0이다.

**Request Body**: `{ "ticketId": 42 }`

**Response** `200 OK` — `{ "updatedCount": 2 }`

## 1C. 보안·감사 알림 (SA)

ITssue 안에서 감지한 보안 의심 신호를 정보보안팀이 확인하고 종결한다 (PRD 4.17, SRS AUDIT-01~04). 감지 유형·심각도·합치기 규칙은 [06 테이블 설계서](../06.테이블_설계서.md) `security_alerts`를 따른다. 사내 보안관제를 대체하지 않고, 대상자에게 알리거나 불이익을 주지 않는다.

- 권한은 모두 ADMIN이다. 다른 사람이 부르면 `403 FORBIDDEN`.
- 알림은 API로 만들지 않는다. 원천 사건(`SECURITY_REVIEW`, `SENSITIVE_INPUT`, `BLOCK`·`ALL_BLOCKED`, `FAIL`·`FILTER_FAILED`, `UNSAFE_REPLY`, `ACCOUNT_LOCKED`, `LOGIN_BLOCKED`, `URGENT_CLOSED`) 및 메시지량 계산을 남기는 처리에서 같은 트랜잭션으로 만든다.
- 목록·상세에는 원문을 싣지 않는다. 원문은 SA-04에서 사유를 받고 줄 때만 준다.

| status | 화면 | 다음 상태 |
|---|---|---|
| `NEW` | 신규 | `IN_REVIEW` (SA-05) |
| `IN_REVIEW` | 확인 중 | `CLOSED` (SA-06, 사유 필수) |
| `CLOSED` | 종결 | 없음 |

`SecurityAlert`

| 필드 | 타입 | null | 컬럼 | 설명 |
|---|---|---|---|---|
| id | number | | `security_alerts.id` | |
| alertType | string | | `alert_type` | `SENSITIVE_INPUT` / `BLOCKED_DOC_QUERY` / `ACCOUNT_LOCKED` / `LOGIN_BLOCKED` / `URGENT_CLOSED` / `MASS_QUERY` / `FILTER_FAILED` / `UNSAFE_REPLY` / `S01`~`S07` |
| severity | string | | `severity` | `HIGH` / `MEDIUM` / `LOW` |
| status | string | | `status` | 위 표 |
| subject | UserRef | | (파생) `subject_user_id` | 대상자 |
| subjectDepartmentName | string | Y | (파생) `departments.name` | 화면의 소속 팀 |

### 2.1 집계 공통 규칙

| 항목 | 규칙 |
|---|---|
| 기간 | `from`·`to`(date, KST) 포함. 기본 최근 30일(오늘 포함). 최대 1년 |
| 기준 시각 | 문의는 `inquiries.created_at`, 접수는 `tickets.created_at` |
| AI 해결 | `inquiries.status = AI_RESOLVED`. **담당자 처리 완료(`CLS`)와 합산하지 않는다** (SRS ADMIN-03) |
| ✏️ 미확인 | AI 답변 직후 해결·미해결 선택 전(`displayStatus=unconfirmed`). 경과 시간·UNCONFIRMED 저장값만으로 집계하지 않음 |
| ✏️ 삭제·숨김 | 삭제된 일반 이탈 문의·숨김 보안 문의는 일반 업무 통계의 건수·분포·분모·추이에서 제외. 보안 기록은 OP-04 관리자 조회로 구분 |
| ✏️ 해결 확인 대기 | 미응답은 FIN 유지. FIN → WIP 확인 후 WIP로 집계하며 미응답을 해결 완료로 합산하지 않음 |
| 확인 필요 | `jira_sync_status`, `assign_status`, `transition_status` 중 하나가 `NEEDS_ADMIN` |
| 추이 | `interval`: `DAY` / `WEEK` / `MONTH`. 기본 `DAY`. 빈 구간도 0으로 준다. `WEEK`는 `from`부터 7일씩, `MONTH`는 달력 달로 나누고 첫 구간은 `from`부터 |

DB 연결까지 확인한다. 실패하면 트래픽만 보내지 않고 재시작하지 않는다. **에러도 공통 에러 형식이 아니라 아래 형식으로 준다.**

**Response** `200 OK`

```json
{ "status": "UP", "database": "UP", "version": "0.1.0" }
```

DB에 연결할 수 없으면 `503 Service Unavailable`

```json
{ "status": "DOWN", "database": "DOWN", "version": "0.1.0" }
```
