# 프론트 → 백엔드 연동 요청 목록

화면을 실제 서버에 연결하면서 발견한 **빠진 기능, 부족한 응답 정보, 화면과 서버의 동작 차이**를 정리한 문서입니다. 각 요청에서 필요한 작업과 현재 화면의 동작을 나눠 설명합니다.

## 문서 읽는 법

- **서버 모드**: 실제 서버 API를 사용하는 모드입니다.
- **모의(mock) 모드**: 서버 대신 시연용 데이터와 응답을 사용합니다. 이 모드에서 동작해도 서버 연결이 완료된 것은 아닙니다.
- **API 번호**: `TK-05` 같은 번호는 `docs/api/01~05` 명세와 `docs/07.API_설계서.md`에서 사용합니다.
- **PR 번호**: `#132` 같은 번호는 관련 화면의 변경 사항을 담은 PR입니다.
- 화면은 시안(`design/ITssue-Prototype.html`)을 기준으로 구현합니다. 서버에 없는 기능은 모의 모드에서만 동작하거나, 서버 모드에서 안내만 표시합니다.

### 상태의 의미

| 상태 | 의미 |
|---|---|
| 요청 전 | 요청을 전달하기 전 |
| 요청함 | 요청을 전달한 상태 |
| 반영됨 | 서버에 반영된 상태 |
| 프론트 적용 | 화면과 서버의 연결이 끝난 상태 |
| 보류 | 시안을 변경하기로 한 상태 |
| 결정 필요 | 화면이나 서버를 어떻게 바꿀지 결정해야 하는 상태 |

이번 문장 정리에서는 기존 상태를 유지했습니다. 실제 배포 여부나 작업 완료 여부를 새로 판정하지 않았습니다.

### 갱신 방법

1. 화면 PR에서 서버와 맞지 않는 부분을 발견하면 요청 번호를 붙여 추가합니다.
2. PR 본문에는 “요청 R-NN 참고”처럼 해당 번호를 적습니다.
3. 서버에 반영되면 `반영됨`, 화면 연결까지 끝나면 `프론트 적용`으로 바꿉니다.
4. 문서 마지막의 갱신 이력에 변경 내용을 남깁니다.

## 요구사항 우선순위와 연동 요청의 관계

**Must / Should / Could는 개발 우선순위이고, 이 문서의 상태는 요청과 연동의 진행 상황입니다.** 예를 들어 `Must · 요청 전`은 반드시 필요한 기능이지만 아직 연동 요청을 전달하기 전이라는 뜻입니다. 우선순위만으로 구현 완료 여부를 판단하지 않습니다.

기준은 [요구사항 정의서(SRS)](../03.요구사항정의서(SRS).md)입니다.

- **Must**: MVP에 반드시 필요한 기능·보호·검증 요구사항
- **Should**: Must 완성 후 구현을 목표로 하는 요구사항
- **Could**: 일정과 추가 합의에 따라 구현을 검토하는 요구사항

아래 표는 연동 요청과 기존 요구사항을 연결한 것입니다. 요청별 세부 API·응답 필드까지 SRS에서 각각 우선순위를 확정한 것은 아닙니다. **‘관련’은 해당 요구사항을 지원하는 작업이라는 뜻이며, 요청 전체를 그 우선순위로 확정한다는 뜻은 아닙니다.** 정책이나 구현 범위의 결정이 필요한 부분은 그대로 표시했습니다.

### 작업 순서를 정할 때

먼저 Must 기능의 실제 사용을 막는 배포·접수·Jira 처리·오류 복구 문제를 확인합니다. R-16·18과 R-03·10·15의 Must 관련 범위가 여기에 해당합니다. 이 목록은 새 우선순위 확정이 아니라, 기존 Must 요구사항을 기준으로 먼저 확인할 범위입니다.

그다음 Should의 통계·목록·계정·Guide 관리 등을 연결하고, Could는 남은 일정과 합의에 따라 진행합니다. 혼합 항목은 Must에 해당하는 부분을 분리해 처리합니다. R-09의 메시지·알림 범위, R-25의 예산 표시, R-28의 종료 문의 이어가기처럼 결정이 필요한 내용은 구현 전에 확정해야 합니다.

## 1. 집계·건수

### R-01. 대시보드·통계 집계 API(OP-01·OP-02) 구현

**필요한 작업**

개요·내 현황·AI 사용 현황 집계(`GET /dashboard/overview`·`/me`·`/ai-usage`, OP-01~03)는 서버에 있어요. 화면이 더 쓰려면 아래가 필요해요.

- **관리자 대시보드용 "현재 처리 현황" 집계** (선택 기간과 무관, 과거 접수 포함)
  - 처리 대기(RDY)·처리 중(WIP)·해결 확인 대기(FIN) 건수
  - 해결 완료(CLS)를 뺀 확인 필요 접수의 원인별 건수: Jira 생성, 상태 동기화, 담당자 배정 (지금 `needsAdminCount` 는 해결된 접수까지 세고 원인도 나누지 않아요)
  - 긴급·높음(P1·P2)으로 분류된 미해결 접수의 건수와 상위 N건(긴급도·오래된 순)
- **담당자 통계(`GET /dashboard/me`)에 접수 추이(`trend`)와 긴급도 분포(`byUrgency`)**: 지금은 내 접수·팀·팀원의 상태별 건수만 있어요. 팀의 "배정 전" 건수도 없어요
- 접수 추이의 해결 완료 건수를 접수일 기준으로 (지금 `trend.closedCount` 의 기준 확인)

**불편한 점·제약**

건수를 확인하는 데 여러 번 요청해야 합니다. 서버 모드에서 접수가 100건을 넘으면 일부 접수가 계산에서 빠져 상위 N건과 통계가 정확하지 않을 수 있습니다.

- 관련 화면(PR): 내 대시보드·통계(#132), 운영 현황(#187), 관리자 대시보드(#189), 관리자 통계(#191)
- 상태: **요청 전**

### R-02. 목록 응답에 상태별 건수

**필요한 작업**

목록 조회 결과에 상태별 전체 건수를 함께 제공해야 합니다. 대상은 다음과 같습니다.

- 사용자 목록: 전체·정상·잠김·이용 제한
- 전체 문의의 상태 탭: 배정 전·진행 중·해결 확인 대기·해결 완료
- AI 처리 화면의 구분별 탭

**현재 화면 동작**

**관리자 통계**는 서버 집계(`/dashboard/overview`)로, **담당자 통계의 상태별 현황·팀원별 진행도**는 `/dashboard/me`로 연결했어요. 담당자 통계의 접수 추이·긴급도 분포는 이 집계에 없어서 접수 목록(TK-05, 서버 모드 최대 100건)으로 화면에서 세요. 분류별 진행도와 개인별 분류 분포는 서버 집계에 분류별 상태 건수가 없어 화면에서 뺐어요.

**관리자 대시보드**는 건수를 확인하려고 접수 목록(TK-05)을 한 건씩(`size=1`) 여러 번 요청하고(화면을 열 때마다 7번), 상위 N건과 확인 필요 원인별 건수는 목록 100건을 받아 화면에서 세요. 서버 집계(`overview`)는 선택 기간에 접수된 티켓만(최대 1년) 세고 해결 완료를 뺀 건수와 상위 N건이 없어서 바꾸지 않고, 위 "현재 처리 현황" 집계를 요청해요.

**불편한 점·제약**

### R-28. 담당자 연결을 거절한 문의(`CLOSED_UNRESOLVED`)는 이어갈 수 없게 두기 (결정: 서버 수정 없음)

**결정**

서버를 고치지 않고, 담당자 연결을 거절(미연결)해 닫은 문의와 접수 초안을 취소해 닫은 문의(둘 다 `CLOSED_UNRESOLVED`)는 이어갈 수 없는 것으로 확정합니다. 화면은 이어가기 창을 띄우지 않고 "새 문의로 시작해 주세요"로 안내하며, 용어는 "미해결 종료"를 "미연결 종료"로 바꿉니다. 서버에 여유가 생기면 "미연결도 AI 미해결(연결 결정 대기)에 포함"하는 방식(IQ-04가 문의를 닫지 않음)이나 IQ-06 이어가기 대상 추가를 다시 검토합니다.

**서버가 이어가기를 받는 경우 (변경 없음)**

| 상태 | 이어가면 |
|---|---|
| AI 미확인(답변 후 해결/미해결 선택 전) | 해결/미해결 선택 |
| AI 미해결(미해결을 눌렀거나 AI가 연결을 제안, 연결/미연결 결정 전, 접수 초안을 쓰는 중 포함) | 연결/미연결 선택 |
| 접수가 있고 해결 확인 대기(FIN) | 기존 접수의 해결/미해결 선택 |

그 밖의 상태(연결 거절·접수 초안 취소로 닫힌 문의, AI 해결, 해결 완료, 접수가 있고 FIN이 아닌 경우)는 409(`INQUIRY_INVALID_STATE`)예요.

**나중에 검토할 때 알아 둘 것**

- 미연결을 AI 미해결에 포함하려면 IQ-04가 문의를 닫지 않아야 해서, 긴급 거절 기록(AUDIT-04, 지금은 닫는 시점의 `URGENT_CLOSED`)을 거절 시점으로 옮기고 통계 기준(`CLOSED_UNRESOLVED` 집계)을 다시 맞춰야 해요
- 긴급 징후가 있는데 거절·취소 없이 방치된 문의는 지금도 기록되지 않아요(자동 종료는 철회된 정책). 필요하면 R-20(보안·감사 알림)에서 검토

**현재 화면 동작**

서버·모의 모두 미연결·접수 취소로 닫힌 문의에는 이어가기 창이 뜨지 않고, 입력창 자리에 이어갈 수 없다는 안내만 보여요

**불편한 점·제약**

연결을 거절한 사용자가 다시 연결을 원하면 새 문의를 만들어야 해요

- 관련 화면(PR): 문의 대화
- 상태: **프론트 적용 (서버 수정 없음, 추후 검토)**

### R-33. 새 답변·상태 변경을 알려 주는 신호 (조회 부하 줄이기)

**필요한 작업**

서버가 변화를 알려 주는 방법(SSE·웹소켓)이나, 한 번에 가볍게 확인할 수 있는 "마지막 변경 시각·새 답변 수" 조회(예: `GET /inquiries/summary` → `unreadCount`, `latestUpdatedAt`)가 필요해요. 목록 전체를 읽지 않고 이 값이 바뀔 때만 목록을 읽을 수 있어요.

**신호를 만들 때 맞춰야 할 점**

1. 연결이 끊기거나 서버를 재시작해도 놓치지 않게, 다시 연결되는 즉시 프론트가 한 번 읽을 수 있어야 해요. SSE라면 `Last-Event-ID`로 이어받고 주기적으로 하트비트를 보내 주세요. 프론트는 놓친 변화를 잡는 안전 조회를 길게(5분) 남겨 둬요
2. 신호에는 요청자 본인의 문의만 실려야 해요. 다른 사용자의 문의 번호·제목·상태가 새면 안 돼요
3. 신호에 `{ type: "INQUIRY_UPDATED" | "REPLY_ARRIVED" | "TICKET_STATUS_CHANGED", inquiryId }`처럼 무엇이 바뀌었는지 포함해 주세요. 목록 전체 대신 그 문의 하나만 읽을 수 있어요
4. 한꺼번에 많은 사용자에게 신호가 가는 경우(일괄 처리 등)를 고려해 주세요. 프론트는 신호를 받은 뒤 0~3초 무작위로 늦춰 읽어요
5. 연결 비용을 확인해 주세요. SSE·웹소켓은 사용자마다 상시 연결이라 서버가 동기 방식이면 연결 하나가 스레드 하나를 차지하고, 프록시 연결 수·타임아웃 제한도 있어요. 부담이 크면 연결 대신 가벼운 요약 조회(`unreadCount`, `latestUpdatedAt`)를 1분마다 하고 값이 바뀔 때만 목록을 읽는 방식으로 해도 돼요
6. 신호 연결은 토큰 만료(401)에서 끊기고 로그아웃에서 정리돼야 해요

**현재 화면 동작**

사이드바 문의 목록은 정해진 간격으로 다시 읽는 대신 이벤트로 읽어요: 처음 열 때, 탭이 다시 보일 때, 화면을 옮길 때(15초에 한 번), 대화 화면이 상태 변화를 알아챘을 때. 놓친 변화를 잡는 안전 조회는 2분에 한 번이에요(예전에는 20초). 대화 화면은 접수 이후 처리 중인 문의만 10초마다 읽고, 종료·접수 전 문의는 읽지 않거나 1분에 한 번만 읽어요. 읽기가 겹치면 합치고, 늦게 온 옛 응답은 반영하지 않으며, 탭 복귀를 연타해도 15초 안에는 다시 읽지 않아요

**진행 상황 (2026-11-03)**

화면 알림 API(NT-01~04)가 생겨 일부는 해결됐어요. 사이드바는 안 읽은 개수(NT-02)를 1분마다 읽고 값이 바뀔 때만 문의 목록을 다시 읽어요. 담당자 배정(`ASSIGNED`, 담당자)·처리 완료(`FIN`, 문의자) 알림이 있는 문의·접수에 새 소식 표시가 켜지고, 접수 상세를 열면 읽음(NT-04)으로 바꿔요. **남은 요청**: 알림 종류가 이 2가지뿐이라 담당자 메시지·문의자 추가 답변·AI 답변 같은 새 소식은 알림이 없어요(종류 추가 또는 위 신호). 변화를 밀어 주는 신호(푸시)와 `GET /inquiries/summary`도 여전히 필요해요

**불편한 점·제약**

다른 화면에 있을 때 새 답변 점·건수가 최대 2분 늦게 보일 수 있어요. 신호가 오면 즉시 보이고 조회 부하도 더 줄어요

- 관련 화면(PR): 사이드바, 문의 대화
- 상태: **요청 전**

### R-36. 상태 변경이 이미 반영 중일 때 같은 요청이면 진행 중인 작업을 그대로 돌려주기 [필수 아님 / 후순위]

**필요한 작업**

접수의 상태 변경(TK-07)이 Jira에 반영되는 중(`transitionStatus` 가 `PENDING`)일 때, **같은 사용자가 같은 변경**(예: 해결 `CLS`)을 다시 보내면 `409 INTEGRATION_JOB_IN_PROGRESS` 대신 지금 진행 중인 요청의 `202`와 접수 응답을 그대로 돌려주는 방식(멱등 처리)을 검토해 주세요. 다른 변경이거나 다른 사용자가 보낸 요청이면 지금처럼 409가 맞아요.

**현재 화면 동작**

접수 응답의 `transitionStatus` 가 `IDLE` 이 아니면 문의자 화면이 [해결]·[미해결] 버튼을 잠그고 "Jira에 반영하는 중이에요"를 보여요. 그래도 409가 오면 오류가 아니라 같은 안내로 보여 주고 최신 접수로 다시 그려요. 반영이 끝나 상태가 바뀌면 안내가 사라져요. 그래서 서버가 바뀌지 않아도 문제가 없어요.

**불편한 점·제약**

오래 열어 둔 화면이나 두 탭에서 같은 요청을 보내면 409를 한 번 받아요. 화면이 안내로 바꿔 보여 주므로 불편은 작아요.

- 관련 화면(PR): 문의 대화
- 상태: **요청 전 (필수 아님 / 후순위)**

### R-37. AI가 답을 못 만든 문의의 제목 저장

**필요한 작업**

새 문의를 보냈는데 AI가 답을 만들지 못하면(`503 AI_UNAVAILABLE`) 문의는 저장되지만 `title` 이 `null` 로 남아요. 이때도 첫 메시지 앞부분(예: 30자)을 제목으로 저장해 주세요. 나중에 AI가 제목을 정하면 그 값으로 바꾸면 돼요.

**현재 화면 동작**

대화 화면은 제목이 없으면 첫 메시지 앞 30자를 제목으로 보여 줘요. 목록(사이드바 최근 문의·문의 내역)은 요약 응답만 받아 첫 메시지를 몰라서 "새 문의"로 보였어요. 화면이 대화 화면에서 만든 제목을 기억해 같은 세션에서는 목록도 같은 제목을 쓰지만, 새로고침하거나 다시 로그인하면 사라져요

**불편한 점·제약**

다시 로그인하면 답을 못 받은 문의가 모두 "새 문의"로 보여서 어떤 문의인지 구분할 수 없어요

### R-38. 가이드 적재 결과 알림 (완료·실패)

**필요한 작업**

가이드 업로드(DC-07)나 다시 시도(DC-10)로 시작한 적재가 끝나면(`DONE` 또는 `FAILED`), **올린 관리자에게 알림을 하나 만들어** 주세요. 알림에는 문서 번호·버전·결과와 실패 사유(`ingest_error`)를 넣고, 기존 알림 API(안 읽은 개수 NT-02, 목록, 읽음 처리 NT-04)로 읽을 수 있게 해 주세요. 이미 쓰는 알림 구조(R-33)에 한 종류를 더하는 일이에요.

**현재 화면 동작**

서버가 변화를 알려 주지 않아서, 화면이 이 브라우저에서 올리거나 열어 본 버전만 DC-06 으로 다시 읽어 확인해요. 간격은 처음 30초 3초, 2분까지 10초, 그 뒤 30초이고, 10분이 넘으면 멈춘 것으로 알리고 읽기를 멈춰요. 실패하면 알림 창과 사이드바·분류·가이드 옆 점으로 알려요(화면 쪽 장치).

**불편한 점·제약**

- 다른 관리자가 올린 버전의 실패나, 이 브라우저가 열어 본 적 없는 버전의 실패는 알 수 없어요
- 새로고침·다른 기기에서는 이어지지 않고(브라우저 저장소 기준), 서버 목록(DC-01)은 버전의 적재 상태를 주지 않아요
- 서버를 자주 읽는 방식이라 서버·DB 부담이 있어요(R-39의 연결 한도와도 맞물려요)

알림이 생기면 버전별 조회를 없애고, 알림 개수(60초 주기로 이미 읽음)로 알림 창과 점을 띄울 수 있어요.

- 관련 화면(PR): 가이드 관리, 사이드바
- 상태: **요청 전**

### R-39. 적재가 DB 연결을 얻지 못해 PENDING 에 멈추는 문제

**필요한 작업**

1. **연결 한도 정리**: Supabase 세션 모드는 연결을 팀 전체 15개로 제한해요(`EMAXCONNSESSION`). API 서버의 SQLAlchemy 연결(`pool_size` 5 + `max_overflow` 10, `db/session.py` 에 설정 없음)만으로 15개를 다 쓸 수 있고, 업로드 적재는 별도 연결(`psycopg.connect`, `document_ingest.py`)을 하나 더 열어요. 서버 연결 수를 줄이거나 개발자별로 나눠 쓰도록 정해 주세요
2. **연결 실패 시 상태 남기기**: 적재가 DB 연결을 얻지 못하면 예외만 기록하고 `PENDING` 으로 남아 상태를 바꿀 수 없어요. 재시도하거나(또는 연결이 돌아오면 `FAILED`·사유 기록) 주기적으로 `resume_pending` 을 돌려 주세요. 지금은 서버를 시작할 때, 10분 넘은 `PENDING` 만 이어서 해요

**현재 화면 동작**

`PENDING` 이 10분 넘도록 이어지면 "10분이 넘도록 준비 중이에요. 서버에서 적재가 멈췄을 수 있어요"로 알려요. 서버가 연결을 못 얻은 상태에서는 다시 시도(DC-10)도 `FAILED` 버전만 되어서, `PENDING` 은 화면에서 복구할 수 없어요.

**불편한 점·제약**

테스트로 올린 파일이 "준비 중"에서 멈춰도 DB 를 직접 고치거나 서버를 재시작하는 수밖에 없어요(재시작 후에도 10분이 지나야 이어서 해요)

- 관련 화면(PR): 가이드 관리
- 상태: **요청 전**
