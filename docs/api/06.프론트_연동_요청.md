### (11.08 확인) FIN 미해결 재처리 — 문서 정정·서버 확인

- **확정 흐름:** 담당자 FIN → 문의자 미해결(reason 필수) → 기존 Ticket WIP 복귀. 문의·세션·접수번호·Jira 번호를 유지한다. TK-07의 202는 요청 접수이며 Jira 반영 확인 후 WIP로 확정한다. 미응답은 FIN 유지, 해결 확인은 CLS이며 종결 후 재개와 구분한다.
- **문서 정정:** 11 문서의 “재처리 없음”·SRS를 그 결정에 맞춰 수정하라는 문구를 철회했다. 완료별 결과·시각·미해결 사유는 이미 상태 이력에 남으므로 “이전 결과 보존 미결”도 정정했다.
- **서버 처리(11.08):** `jira_transition._save_confirmed`도 FIN→WIP 확인 후 `finished_at`을 비워 API 03·테이블 명세, `jira_webhook.sync_work_status`와 맞췄다. 재완료 때 새 처리 결과 필수, 새 완료 시각 저장, 이전 완료의 결과 이력 보존은 테스트로 검증했다. 프론트 변경은 필요 없다.
- **이번 마감 우선순위:** WIP 복귀·재완료의 기능 확인을 먼저 한다. Jira 직접 되돌림 정책은 9장의 마감 후 논의로 분리한다.

### (11.05 추가) R-44. 문의 답변의 출처에서 같은 문서·위치 중복 제거

- **담당 제안:** 민경님 / **화면:** 문의 대화(답변 말풍선의 출처 버튼) / **관련:** IQ 메시지 `sources[]`, 2.6 `MessageSource`
- **요청:** 한 답변의 `sources[]`에서 `docCode`·`version`·`location`이 같은 출처는 한 줄로 합쳐 내려주세요. 다만 같은 위치에 서로 다른 근거 본문이 있을 수 있으므로 `excerpt`를 첫 값 하나만 남기는 방식은 근거를 누락할 수 있습니다. 서로 다른 본문을 보존하는 응답으로 합치거나, 조각마다 구분되는 값(`chunkIndex` 등)을 주고 프론트에서 버튼만 묶는 방식으로 협의해 주세요. `LEGACY`는 문서 코드·위치가 비어 있을 수 있으므로 이 기준으로 서로 다른 사례를 합치지 않아야 합니다.
- **현재 이슈 사항:** 근거 조각(청크)마다 한 줄씩 `message_sources`에 저장되고 그대로 내려와, 한 답변에 `IT-SW-001` 위치 `2`가 네 번 오는 경우가 확인됐습니다. 화면에 같은 출처 버튼이 여러 개 보이고, React 키 중복 경고(`IT-SW-0012`)가 납니다. 프론트는 같은 문서·버전·위치를 합쳐 한 번만 보이도록 이미 처리했지만, 응답 크기와 `rank` 의미가 흐려지므로 서버에서 정리하는 편이 낫습니다.
- **서버 처리(11.09, 서버에서 합치는 방식 채택):** 메시지 응답의 `sources[]`에서 `DOCUMENT` 출처는 `docCode`·`version`·`location`이 같으면 한 항목으로 합칩니다. `excerpt`는 서로 다른 본문만 순위 순서로 이어 붙이고, `rank`·`id`는 순위가 가장 앞선 줄을 따르며 `images`는 모읍니다. `LEGACY`는 합치지 않습니다. `chunkIndex` 추가 방식은 진행하지 않습니다. DB 저장은 그대로이고 이전 답변에도 적용됩니다.
- **프론트 변경:** 필수는 아닙니다. 필드가 그대로라 현재 `uniqueSources`도 그대로 동작하며, 합쳐진 본문이 미리보기에 나옵니다.
- **우선순위 사유:** 필수가 아닙니다. 프론트 처리로 화면은 정상입니다.

### (11.05 추가, 11.07 수정) R-45. 다른 문의·화면을 보는 동안 도착한 AI 답변을 빨간 점으로 표시 — 서버·프론트 반영, 배포 확인

- **담당 제안:** 민경님 / **화면:** 사이드바 최근 문의의 새 답변 점 / **관련:** IQ 메시지, NT-01~04
- **목적·범위(11.07 프론트 담당 확인):** 같은 브라우저에서 문의 A의 답변을 기다리다가 문의 B나 FAQ로 이동했을 때, A에 AI 답변이 저장되면 A 옆에 빨간 점을 표시하려는 요청입니다. ‘다른 세션’은 다른 문의 대화를 뜻합니다. 다른 브라우저·기기 간 읽음 동기화는 필수 범위가 아닙니다.
- **기대 동작:**
  1. A를 보고 있지 않을 때 A에 AI 답변이 저장되면 다음 조회 때 A의 점을 켭니다. 기존 주기 조회를 사용할 수 있으며 즉시 푸시는 요청하지 않습니다.
  2. A를 열어 해당 답변을 확인하면 점을 끕니다. A를 보고 있는 동안 도착한 답변도 확인한 뒤에는 점이 남지 않아야 합니다.
  3. 본인이 글을 보냈거나 문의 상태만 바뀐 경우, AI 처리가 실패해 답변이 저장되지 않은 경우에는 AI 새 답변 점을 켜지 않습니다.
- **기존 기능과 부족한 부분:** [PR #217](https://github.com/issue-helpdesk/issue-helpdesk/pull/217)의 배정 알림(`ASSIGNED`, 담당자에게)·처리 완료 알림(`FIN`, 문의자에게)은 프론트에서도 이미 사용합니다. 빠진 것은 **접수 전 문의에 AI 답변이 새로 저장됐는지 구별할 정보**입니다. 기존 알림 기능을 다시 만드는 요청이 아닙니다.
- **현재 프론트 처리:** `inquirySeen.ts`에서 브라우저에 기록한 마지막 확인 시각과 문의의 `updatedAt`을 비교합니다. 문의 갱신은 새 AI 답변과 같은 뜻이 아니어서 오표시할 수 있습니다. 기존 11.07 테스트 기록에는 본인 글 저장·AI 실패 뒤 점이 켜진 사례가 있습니다. PR #329에는 열어 둔 문의의 점을 숨기고 확인 시각을 기록하는 보완까지 반영돼 있지만, 새 답변을 구별할 정보 자체는 여전히 부족합니다. 이번 검수에서는 실서버 사례를 재현하지 않았습니다.
- **백엔드 요청:** 문의별로 새 AI 답변을 구별할 정보를 주세요. 아래는 대안이며, 둘 다 구현해 달라는 요청이 아닙니다. 서버 변경이 작은 쪽으로 협의해 주세요.
  - **A. 문의 목록에 답변 기준값 제공:** 마지막 AI 답변의 메시지 ID 또는 저장 시각을 제공합니다. 프론트는 브라우저 확인 기록을 유지하되 비교 대상을 `updatedAt`에서 이 값으로 바꿉니다. 답변이 없는 문의의 값과 정확한 필드명은 API 명세에 정해 주세요.
  - **B. 기존 알림 확장:** AI 답변 저장 시 문의자에게 문의 단위 알림(예: `AI_REPLY`)을 만듭니다. 현재 DB는 `ticket_id`가 필수이고 `kind`는 두 종류로 제한됩니다. NT-01은 Ticket과 내부 조인하고 응답의 `ticketId`·`receiptNo`도 필수이므로, 종류 추가만으로 접수 전 문의를 지원할 수 없습니다. 접수 없는 알림의 저장·조회·응답을 함께 보완해야 합니다.
- **B를 선택하면 함께 필요한 API 계약:** NT-01은 기존처럼 `inquiryId`를 제공하고 접수 없는 항목의 `ticketId`·`receiptNo`를 비울 수 있어야 합니다. NT-02는 현재 `{ count, ticketIds }`이므로 어느 문의에 새 답변이 있는지 구별할 값(예: `inquiryIds`)도 필요합니다. ### R-48. 가이드 본문 조회 — 코드 반영, 배포 확인

- **현재:** DC-12 `GET /documents/{documentId}/content`, DC-13 `GET /documents/{documentId}/versions/{versionId}/content`(ADMIN)가 구현됐다. 응답은 `{ documentId, versionId, version, content, images }`이다. `guides.ts/getGuideContent`와 본문 패널도 연결됐다(PR #343·#345).
- **본문 제공 방식:** 서버 원본 파일을 요청마다 읽는다. MD는 읽고, PDF·DOCX·PPTX·TXT는 공통 파서로 md 변환한다. 변환 md를 별도 저장하거나 검색 청크를 이어 붙이지 않는다. 그림은 해당 버전 청크의 이름표와 배포 그림을 사용하며 원본 업로드 그림을 새로 추출·저장하는 기능은 아니다.
- **권한·오류:** 일반 사용자는 활성 문서의 열람 가능한 현행만 조회하고 범위 밖은 404다. 관리자 특정 버전은 파일이 남아 있으면 비현행·적재 실패도 읽을 수 있다. 파일 없음/읽기 실패는 409 `DOCUMENT_CONTENT_UNAVAILABLE`, 관리자 현행 없음은 404 `DOCUMENT_VERSION_NOT_FOUND`다.
- **프론트 처리 완료:** 표 칸의 `<br>` 줄바꿈 처리, 오류 사전 문구, 실패를 일괄 “준비 중”으로 바꾸던 처리 제거가 반영됐다. 이 작업을 다시 요청하지 않는다.
- **코드 블록 표시 완료:** 서버는 코드 블록의 ` ``` ` 줄과 안쪽 내용을 원문 그대로 내려주고(PR #348), `Markdown.tsx`가 코드 블록을 그대로 표시한다(PR #351). 이 작업을 다시 요청하지 않는다.
- **배포 후 확인:** ① 원본 `file_path`가 서버 볼륨에 실제 존재하는지 ② 본문·표 줄바꿈·그림 표시 ③ 역할별 404 ④ 파일 없음의 409 안내 ⑤ 비현행/실패 버전의 관리자 조회. 파일이 없으면 재업로드가 필요하며 코드 추가만으로 기존 파일이 복구되지는 않는다.

### R-49. 배정 실패 후 Jira 직접 지정 — 자동 반영 구현, 배포 확인

- **과거 사례:** 11.07 RCPT-0332·ITHD-386에서 배정 실패 후 Jira에 담당자를 지정해도 ITssue가 확인 필요로 남았다. 당시 원인은 열린 실패 작업이 직접 변경 반영을 차단하던 것이다. 이 사례의 현재 서버 해결 여부는 재현 확인이 필요하다.

  두 안내 모두 **"다시 등록"**을 하라고 하는데, 다시 등록하는 API(초안 등록)가 아직 없습니다. 제안을 새로 만드는 기능도 없습니다(기획은 주간 분석이 제안을 만드는 방향이지만, 현재 자동 분석 실행 경로가 없습니다. 거절 티켓 재분석 정책은 별도 확정이 필요합니다). 그래서 이 두 오류를 만난 관리자가 **화면에서 할 수 있는 일이 없습니다.** 프론트 오류 문구는 할 일을 안내하지 않고 이유만 알립니다.
  - "이 버전에는 거절한 해결 사례 제안이 들어 있어서 현행으로 전환할 수 없어요."
  - "이 버전을 만든 뒤 현행 가이드가 바뀌어서 현행으로 전환할 수 없어요."
  - 지금 우회로는 가이드 파일을 직접 새 버전으로 올리는 것(DC-07)뿐입니다. 이렇게 올린 버전은 현재 DC-07은 guide cluster 연결을 만들지 않습니다. 따라서 일반 업로드 버전에는 묶음 검사가 적용되지 않으며, 수동 편집본의 정확성은 관리자가 검토해야 합니다. 이를 신규 제안의 자동 등록 완료로 취급하지 않습니다.
- **논의가 필요한 것 (어느 쪽으로 갈지 정해 주세요):**
  1. **초안 등록(승인) API의 일정과 모양.** 프론트 시안은 "승인하고 초안 등록"을 누르면 열람 범위와 외부 AI 전송 정책을 고르고, 가이드 목록에 **현행이 아닌 새 버전**으로 등록되어 검색 준비가 시작되는 흐름입니다. 등록 때 기준 버전이 바뀌었는지(`baseChanged`)도 서버가 막아 주길 기대합니다.
  2. **거절한 항목을 뺀 "다시 등록" 방법.** 후보: (A) 같은 버전에 묶인 제안 중 거절한 것을 빼고 새 버전으로 다시 등록하는 API, (B) 등록한 초안 버전을 지우거나 취소하는 API, (C) 거절하는 순간 서버가 그 항목을 뺀 새 초안 버전을 자동으로 다시 만들어 주는 방식. 어느 쪽이든 관리자가 누르는 단추가 하나 있어야 오류 문구가 "○○해 주세요"로 바뀔 수 있습니다.
  3. **기준 가이드가 바뀐 제안의 처리.** 현재는 `baseChanged` 표시만 있고, "최신 가이드 기준으로 제안을 다시 만드는" 기능은 서버에 없습니다. 프론트 시안에는 "최신 버전과 비교 → 이 제안으로 바꾸고 다시 검토"가 있었으나, 서버에 대응하는 API가 없어 서버 연결 화면에서는 뺐습니다. 후보: (A) 서버가 기준이 바뀐 제안을 새 기준으로 다시 분석해 갱신, (B) 관리자가 비교(DC-13으로 두 버전 본문을 읽어 프론트에서 비교)한 뒤 초안을 직접 고쳐 기준 버전을 맞춤으로 표시, (C) 기준이 바뀐 제안은 거절 처리하고 다음 주간 분석에 맡김.
  4. **서버 판단 5종과 화면 종류.** 서버는 `ADD_ITEM`(항목 추가)·`CHANGE`(변경)·`NEW_GUIDE`(새 가이드)·`MANUAL_CANDIDATE`(매뉴얼 후보)·`SEC_MANUAL`(SEC 직접 검토) 5종입니다. 프론트는 지금 `ADD_ITEM`·`CHANGE`를 "기존 가이드 보강"(작은 글씨로 항목 추가/변경 표시), `NEW_GUIDE`를 "신규 가이드"로 보이고, `MANUAL_CANDIDATE`는 초안 없음, `SEC_MANUAL`의 편집 가능 여부는 실제 `draftMd` 유무와 상태로 구분합니다. 두 종류를 항상 “초안 없음”으로 묶지 않습니다. 서버 모드에서는 승인 등록 API가 없어 자동 등록을 제공하지 않습니다. 화면 이름을 서버의 5종 그대로 쓸지, 기획서 기준으로 다시 묶을지 기획 확인이 필요합니다.
  5. **`reviewInfo`에 들어가는 키.** 06 테이블 설계서·API 명세는 "판단 이유·경고·추정 표시·티켓 간 차이·수정 위치와 제안문. 키는 docs/08"이라고 하는데, docs/08에 해당 키 정의가 없습니다. 프론트는 지금 `reason`(문자열)과 `warnings`(문자열 배열)만 읽어 AI 판단 칸에 보입니다. 나머지(추정 표시, 티켓 간 차이, 변경(`CHANGE`)의 수정 위치와 제안문)는 키 이름과 모양이 정해지면 화면에 더합니다.
  6. **분석 회차 표시.** 모의 화면에는 "마지막 분석 ○월 ○일 · 다음 분석 ○월 ○일"이 있었으나 서버에는 분석 일정을 주는 API가 없어 서버 연결 화면에서는 뺐습니다. 필요하면 마지막 분석 시각과 다음 예정 시각을 어디서 받을지 정해 주세요(`createdAt`으로 "이번 회차"를 고른다고만 적혀 있습니다).
- **서버 처리(11.09):** 초안 등록 GC-06(`POST /guide-clusters/{clusterId}/register`, 04.문서_FAQ 4A장)을 추가했습니다. 논의 1번은 요청 `{ draftRevision, viewScope, transferPolicy }`이며, `baseChanged`인 묶음은 서버가 `GUIDE_CLUSTER_BASE_CHANGED`로 막습니다. 논의 2번은 (A)의 변형으로, 거절한 묶음이 있는 버전의 남은 묶음에 GC-06을 다시 부르면 **같은 버전**을 거절 항목 없이 다시 만듭니다. 응답의 `warnings`는 저장하지 않으므로 등록 직후 보여 주세요. **GC-06은 글을 받지 않고 저장된 초안만 등록합니다.** 편집창을 고친 채 바로 호출하면 에러 없이 고치기 전 글이 등록되므로, "승인하고 초안 등록"은 고친 내용이 있으면 GC-05로 먼저 저장하고 그 응답의 `draftRevision`으로 GC-06을 불러 주세요. 초안 첫 줄이 `### 3.N 제목`이 아니면 `GUIDE_CLUSTER_ASSEMBLE_FAILED`이며 사유는 `details[].message`에 옵니다. 변경(`CHANGE`) 묶음의 "기존 내용"과 반영 위치는 GC-02의 `targetMd`·`targetSection`으로 내려 주므로 `before`·`target.section`에 연결해 주세요. 판단 중 `NEW_GUIDE`는 아직 등록할 수 없고, 주간 분석의 초안 생성이 연결되기 전까지 실제로 등록할 수 있는 묶음은 없습니다. 논의 3번(기준 변경 처리)은 다시 맞추기 기능이 준비된 뒤 추가하므로, `DOCUMENT_VERSION_BASE_CHANGED`·`GUIDE_CLUSTER_BASE_CHANGED`는 아직 화면에서 해결할 방법이 없습니다.
- **화면 처리(프론트, 11.08):** `frontend/src/api/caseClusters.ts`가 GC-01~05를 호출하고, 검토 패널은 임시 저장(GC-05, 다른 관리자가 먼저 고쳤으면 최신 초안을 다시 불러옴)·거절(GC-03, 사유 필수)·직접 반영 표시(GC-04)를 합니다. 승인한 제안의 등록 버전 상태(검색 준비 중·실패·완료·현행)는 `registeredVersion.ingestStatus`·`isCurrent`로 보입니다. 위 논의가 정해지면 "승인하고 초안 등록"과 오류 문구의 "다시 등록" 안내를 연결합니다.
- **우선순위 사유:** 필수가 아니지만, 이 결정이 없으면 AI 가이드 제안은 "보고 거절하거나 직접 반영을 표시하는" 데까지만 쓸 수 있고, 제안이 가이드로 이어지는 핵심 흐름이 비어 있습니다.

## 3. Should — 이번에는 후순위로 둘 작업

새 API나 응답 확장이 필요한 미완료 항목입니다. 당장 화면을 쓰는 데 필요한 최소 경로가 있어, **이번 마감에서는 기존 기능을 사용하고 확장은 미루는 안**입니다.

### R-09. 출처 응답에 가이드 제목 제공 (후순위)

- **요청 배경:** 일반 사용자도 열람 범위 안의 문서 목록(DC-01)을 조회할 수 있습니다. 다만 제목 표시만을 위한 추가 조회를 줄이려고 출처 응답에 제목을 함께 요청합니다. **요청:** 문의 메시지의 `sources[]`(IQ)와 FAQ 출처(FQ-02)가 이미 주는 `docCode`·`version` 옆에 문서 제목 `title`도 함께 내려주세요. 없는 동안 화면은 문서 번호만 보여 줍니다. 필수가 아니라 후순위입니다.

### R-01·R-02·R-13·R-19. 집계 확장과 요청 횟수 개선

- **화면:** 관리자 대시보드·통계, 담당자 통계·팀 현황, 계정·문의 목록
- **이미 있음:** OP-01 `overview`, OP-02 `me`, OP-03 `ai-usage`. 관리자 통계와 담당자 통계의 일부는 서버 집계에 연결돼 있습니다. `overview.trend.aiResolvedCount`와 접수일 기준 `closedCount`도 있습니다.
- **남은 범위:** 기간과 무관한 현재 RDY/WIP/FIN·확인 필요 원인별 건수·긴급 상위 N건(R-01), 개인별 긴급도 분포(R-13), 미확인·미연결 종료의 기간별 추이(R-19), `/me`의 추이·긴급도 분포입니다.
- **이번 제안:** 기존 집계를 유지하고 새 집계 API는 미룹니다. 프론트 목록 기반 집계는 최대 100건 제한으로 누락될 수 있으므로 전체 집계인 것처럼 단정하지 않도록 확인합니다. R-02 본문에 잘못 섞여 있던 대시보드 설명은 여기로 합쳤습니다.

### R-03·R-04·R-05·R-06·R-07. 목록 필터·검색·정렬 확장

- **화면:** 처리할 문의·전체 문의·문의 내역·계정 관리
- **이미 있음:** TK-05 `assignStatus` 필터. 기존 검색·정렬과 문의 표시 상태를 사용한 조회는 가능합니다.
- **남은 범위:** TK-05의 `transitionStatus`·배정 전을 포함한 미완료 필터(R-03), 제목·접수번호·분류·담당자 정렬과 이름 검색(R-04·05), 사용자 부서 검색·부서/역할/상태 정렬(R-06), 문의 제목/분류/상태 정렬·가이드 제목 검색·사용한 가이드 필드(R-07)입니다.
- **이번 제안:** 지원되는 조건만 화면에 노출하고 확장은 미룹니다. 다만 관리자 확인 필요 접수를 빠뜨리는 문제가 실제로 확인되면 ADMIN-01(Must)과 관련되므로 해당 누락만 먼저 고칩니다.

### R-10. 접수 목록에 실제 오류 사유·발생 시각 추가

- **화면:** 운영 현황
- **이미 있음:** `integration-jobs`에 `lastError`·작업 생성/갱신 시각이 있습니다. 오류 원문 자체가 전혀 없는 상태는 아닙니다.
- **남은 범위:** 접수 응답에 요약 사유와 실제 오류 발생 시각을 포함해 개별 이력 조회를 줄이는 일입니다. 작업 `createdAt`은 오류 발생 시각과 같다고 볼 수 없습니다.
- **이번 제안:** 새 필드 추가는 미루고, 상세 확인에는 기존 작업 이력을 사용합니다. 주요 이력 통합 표시는 하단 R-15에 분리했습니다.

### R-11·R-33·R-38. 처리 상태·변경 신호·적재 알림

- **화면:** 문의 대화·사이드바·담당자/관리자 목록·가이드 관리
- **이미 있음:** NT-01~04와 `ASSIGNED`·`FIN` 알림, 안 읽은 개수 조회, 접수 읽음 처리. 기존 폴링으로 화면을 갱신할 수 있습니다.
- **남은 범위:** AI 처리 중 필드(R-11), 변경 요약 조회 또는 SSE/웹소켓(R-33), 적재 완료·실패 알림 종류 추가(R-38)입니다.
- **이번 제안:** 상시 연결·새 알림 배치는 만들지 않고 기존 조회를 유지합니다. 읽기 중복·주기는 프론트에서 관리합니다. 현재 대화 기본 주기는 10초이며 상태에 따라 느리게 읽거나 멈추고, 접수 목록은 15초입니다. 이전 ‘대화 4~8초’ 설명은 삭제했습니다.
- **나중에 할 경우:** 알림/신호는 본인·권한 범위, 토큰 만료·로그아웃, 재연결, 중복 이벤트를 함께 설계해야 합니다. 한 번의 대화 조회는 문의·메시지·필요 시 접수 상세의 2~3개 요청이므로 전송량 개선도 같이 검토합니다.

### R-20. 보안·감사 알림 — 감지 저장 구현, 관리 연결 미구현

- **현재 구현:** `security_alerts` 모델·마이그레이션과 감지·미종결 동일 대상 합치기가 있다. 민감정보 입력, 전송 금지 근거 질의, 계정 잠금, 제한 계정 로그인, 긴급 징후 후 접수 없이 종료의 5종 원천에 연결됐다. 감사 로그만 남기는 상태가 아니다.
- **남은 구현:** SA-01~06 목록·상세·사유 있는 원문 열람·확인/종결 API는 현재 main.py에 등록되지 않았다. `security.ts` 화면은 모의 데이터다. MASS_QUERY는 DB 허용값·모의 화면만 있고 실제 대량 질의 감지 경로는 없다.
- **요청:** 기존 DB·5종 감지를 재개발하지 않는다. 관리 API·화면 연결과 대량 질의 감지의 구현 범위·담당·시점을 결정한다. 원문 보관을 새로 허용하는 결정은 이 요청에 포함하지 않는다. 기존 가림·차단·긴급 종료 기록은 유지한다.
- **과거 PR 기록:** 기존 문서의 “11.07 PR #325 미병합”은 당시 확인 기록이다. 이번에는 원격 PR 상태를 조회하지 않았으므로 현재 병합·폐기 여부를 단정하지 않는다. 중복 작업을 시작하기 전 담당자 작업 상태를 확인한다.
- **근거:** `services/security_alert.py`, `services/auth.py`, `services/inquiry.py`, `models/ops.py`, `main.py`, `frontend/src/api/security.ts`.

### R-24. 문서 번호 자동 채번

- **화면:** 가이드 관리
- **남은 범위:** 서버의 문서 번호 자동 채번입니다. (버전 메모는 서버에 없고 요청하지 않기로 해서 화면에서도 뺐습니다.)
- **이번 제안:** 기존 입력·등록 경로를 사용하고 확장은 미룹니다. 문서 번호는 프론트가 계산하고 서버가 중복을 거절하므로 동시 등록 충돌 가능성이 있습니다.

## 5. 프론트에서 처리하거나 확인할 기록

프론트 반영 사항과 데이터 확인 요청입니다. 출처 제목의 백엔드 응답 보완 요청(R-09)은 3장으로 옮겼습니다. 이 문서 편집으로 화면 코드를 변경한 것은 아닙니다.

- **R-15 — 처리 이력 통합(일부 반영):** 접수 상세 "처리 이력"이 상태 이력과 담당자 배정 이력(`assignment-logs`: 추천·배정·재배정·실패)을 시간순으로 합쳐 보입니다. 관리자 전용인 연동 작업(`integration-jobs`)은 담당자 화면에 무리하게 연결하지 않고 아직 합치지 않았습니다.
- **R-31 — 본문 서식 재확인 (서버 데이터가 있어야 확인 가능):** 현재 청크 생성과 검색 단위 복원 코드는 줄바꿈을 사용합니다. 따라서 ‘서버가 항상 줄바꿈을 없앤다’고 단정할 수 없습니다. 프론트는 줄바꿈이 없는 본문을 줄 단위로 복원해 보여 주는 보정을 이미 두고 있습니다. **요청:** 배포 환경에서 줄바꿈·제목·표가 깨져 보이는 출처가 있으면 그 문의(또는 FAQ)와 위치를 알려 주세요. 문제 출처의 실제 `excerpt`와 적재 원문을 비교해 적재 데이터·변환·화면 중 수정 위치를 정합니다. 이미지 API는 이번에 추가하지 않습니다.

## 6. 실행 환경 확인 — 새 API 개발과 구분

- **R-16·R-18:** worker 코드·Compose 실행 설정·단건 시험 자료는 이미 있습니다. 접수·상태 변경은 `VITE_SERVER_INTAKE`가 true인 준비된 환경에서 실행하도록 연결되어 있습니다. ‘서버에 기능이 없어 무조건 막힘’이라는 이전 설명은 삭제합니다.
- **R-39:** 서버 DB에 이미 `PENDING`으로 멈춘 버전이 있는지와 그 원인은 아직 확인하지 않았습니다. 정기 복구(5분마다)는 반영되어 있으며, 파일이 서버에 없으면 `FAILED`로 끝나므로 다시 올려야 합니다.

## 7. 배포 후 확인 요청 — 프론트 반영분 (11.05~11.08 누적)

코드 반영 뒤 배포 환경에서 재확인할 목록입니다. 일부 기능은 과거 실서버 시험 기록이 있으므로 아래 모두가 “한 번도 시험하지 않음”을 뜻하지 않습니다. 확인하면 날짜·커밋·환경·결과를 남기고 종료 표시합니다. R-48·49와 GC 검토 연결도 위 항목의 배포 확인을 함께 수행합니다.

- **http 서버에서 문의 전송 (PR #284):** http 주소(`crypto.randomUUID` 없는 환경)에서 새 문의 전송, 상담 중 추가 질문 답변(IQ-08), 해결·미해결(IQ-09)이 모두 나가는지. 요청 중 예외가 나도 대기 화면이 무한 대기가 아니라 오류 문구와 "다시 시도"로 바뀌는지.
- **외부 전송 정책 완화 사유 (R-22, PR #286):** 완화(`금지 → 허용` 등)는 사유 없이 거절되고(`reason` / `REQUIRED`), 사유를 넣으면 변경되며 운영 기록(OP-04)에 사유가 남는지. 엄격하게 바꿀 때는 사유 없이도 되는지.
- **FAQ 출처 지정·수정 (R-41·R-35, PR #289):** 출처 가이드를 고르고 등록하면 문의자 FAQ에 보이고 출처가 열리는지, 출처 없이는 막히는지. FAQ 수정에서 출처를 바꾸면 통째로 교체되는지(FQ-04), "바로 게시"를 켜고 끌 때 게시 상태가 맞는지.
- **출처 선택 목록의 부하:** FAQ 등록 창은 가이드 목록(`/documents`)을 한 번 읽습니다. 가이드가 매우 많을 때 느려지지 않는지.
- **AI 상세 패널의 가이드·과거 처리 사례 (PR #292, #293):** 과거 처리 사례를 참고한 문의의 AI 처리 상세에서 "참고한 과거 처리 사례" 묶음과 사례 본문(`excerpt`)이 맞게 나오는지, 사례가 여러 건일 때 건수가 맞는지. 가이드 칩을 누르면 근거 본문이 열리는지.
- **가이드 그림(DC-11)·FAQ 출처 본문(R-30, PR #293):** 그림이 있는 가이드를 출처로 쓴 답변·FAQ의 출처 미리보기에서 `[그림] 설명` 줄이 실제 그림으로 보이는지(`GET /guide-images/{key}`가 토큰으로 열리는지), 그림이 없는 줄은 설명 상자로 남는지. FAQ 출처에서 본문이 나오고, 문서만 지정한 출처는 안내 문구가 나오는지.
- **FAQ 등록·수정의 분류별 출처 목록 (PR #293):** 분류를 바꾸면 그 분류의 전 직원용 현행 가이드로 목록이 바뀌는지.
- **계정 변경 이력 (R-14, PR #295):** 계정 화면의 "계정 변경 이력"에 운영 기록이 최근순으로 보이는지(다른 관리자가 한 변경 포함), 수행자와 변경 대상(사번 · 이름)이 맞게 나뉘는지, 목록에 없는 사용자는 번호로 나오는지.
- **처리 이력의 담당자 배정(R-15, 이번 PR):** 접수 상세 "처리 이력"에 담당 그룹 추천·배정·재배정·배정 실패가 상태 변경과 시간순으로 함께 보이는지(`GET /tickets/{id}/assignment-logs`). 관리자가 재배정하고 실행기가 Jira에 반영한 뒤 "담당자 재배정 · 이름 (그룹)"과 재배정 사유가 남는지. 담당 그룹 밖 담당자에게는 이 이력이 `404`로 와서 상태 이력만 보이는 것이 맞는지.
- **운영 기록의 접수번호(R-40, 이번 PR):** 접수·문의 대상 기록의 구분 칸에 접수번호가 보이고, 누르면 화면은 그대로 두고 오른쪽에 그 접수의 상세 패널이 열리는지. 연결된 접수가 없는 문의 기록은 접수번호 없이 보이는지.
- **계정 추가 필수 선택(이번 PR):** 부서·직급·역할을 고르지 않으면 서버에 보내지 않고 막히는지, 직급(팀원·팀장·조직장)이 서버에서 받아들여지는지.
- **서버 테스트 3차 수정(이번 PR):** 문의자 상세에서 "세부 유형 … 기본 긴급도" 문구가 안 보이는지, Jira 티켓이 없을 때 "생성 전"이 깨지지 않는지, 이어가기 창을 ✕로 닫은 뒤 해결·미해결을 바로 누를 수 있는지, 같은 출처 버튼이 한 번만 보이는지, AI가 새로 답했을 때 다른 화면의 사이드바에 새 답변 점이 켜지는지(목록 갱신 주기 120초), 문의자 화면 콘솔에 `assignment-logs` 404가 더 이상 안 뜨는지.
- **검색할 때 상태 탭 건수(이번 PR):** 전체 문의·AI 처리·계정 관리·처리할 문의·문의 내역에서 검색어·필터를 걸면 상태 탭의 숫자가 검색 결과에 맞게 바뀌고, 지우면 전체 숫자로 돌아오는지. 서로 겹치지 않는 상태 탭은 합계를 상태 미선택 시의 전체 건수와 비교하고, 상태를 선택한 목록의 "총 N건"은 그 상태 탭 건수와 비교하는지. 검색어를 칠 때 서버에 요청이 몰리지 않는지(멈춘 뒤 0.25초 기다려 보냄).
- **대화에 저장된 선택·카드 (R-29, 이번 PR):** 문의를 다시 열어도 "미해결"·"담당자 연결"·"접수하기" 말풍선과 접수 초안 카드(접수·취소된 뒤에는 읽기 전용)가 순서대로 남는지. 말풍선·카드가 두 번 보이지 않는지. 재확인 요청 뒤에는 진행 카드가 마지막 하나만 보이는지. 선택이 마지막이어도 "답변을 준비하고 있어요"나 "답변을 만들지 못했어요"가 뜨지 않는지. `db/backfill_action_messages.py`로 보정하기 전의 옛 문의는 선택 말풍선이 없을 수 있습니다.
- **담당자 상세 패널의 상태 변경 (11.06):** 본인에게 배정 확인된 담당자(AGENT)의 상세 패널에서 `처리 시작`이 바로 요청되고, `처리 완료`는 창이 열려 처리 결과(1~4,000자, 필수)를 적은 뒤 "등록하고 해결 확인 요청"으로 요청되는지. 요청 뒤 3초마다 확인해 상태·처리 이력·목록이 갱신되는지, 관리자·문의자 패널에는 이 버튼이 없는지. 실패하면 서버 메시지가 창 안에 보이고 입력이 남는지.
- **알림 종·알림 목록 (11.06):** 안 읽은 수, "안 읽음만 보기", 누르면 해당 티켓·문의로 이동하며 읽음 처리되는지, 최근 10일 것만 최근순으로 보이는지.
- **캘린더 (11.06):** 연차·반차 일정 등록·삭제, 관리자의 "내 일정 / 전체" 전환, 팀 필터가 서버 응답으로 맞게 나오는지. 프론트 담당자가 현재 팀원 일정 표시를 확인했으므로 R-43 추가 개발 요청은 제외합니다. 캘린더의 조회 데이터·실행 환경은 실제 시험 결과와 함께 기록하고, 누락이 재현될 때만 경로를 확인합니다.
- **서버 오류 문구 (11.06):** 서버 오류 코드별 한글 문구가 화면에 맞게 나오는지, 사전에 없는 코드는 서버 메시지가 그대로 나오는지.
- **새 답변 점 (R-45, 11.08):** 새 문의를 보낸 뒤 FAQ·다른 문의로 이동해 있는 동안 AI 답변이 저장되면 사이드바의 그 문의에 점이 켜지고, 문의를 열면 꺼지는지. 본인이 글을 보내거나 상태만 바뀌었을 때, AI 처리가 실패했을 때는 점이 켜지지 않는지. 다른 기기에서 만든 문의는 이 브라우저에서 처음 볼 때 점이 없는 것이 정상입니다.
- **가이드 적재 요약 (R-47, 11.08):** 다른 관리자가 올린 버전이 적재에 실패하면 가이드 관리의 분류·가이드 옆 점과 사이드바 점이 뜨는지(알림 창은 뜨지 않음). 실패했던 버전이 다시 적재에 성공하면 점이 사라지는지. 업로드한 본인에게는 결과 알림 창이 계속 뜨는지.
- **담당자용 매뉴얼의 외부 AI 전송 고정 (서버 PR #352, 11.08):** 가이드 관리에서 매뉴얼 버전의 외부 AI 전송 단추가 금지만 선택 가능하고 이유가 보이는지, 매뉴얼에 새 버전을 올릴 때 등록 설정 창에서도 금지로 고정되는지. 새 오류 문구(`DOCUMENT_MANUAL_TRANSFER_FIXED`, `DOCUMENT_VERSION_ORPHANED`, `DOCUMENT_VERSION_OUTDATED`)가 맞게 나오는지.
- **AI 가이드 제안 (GC-01~05, 11.08):** 관리자 가이드 관리의 "AI 가이드 제안" 탭이 서버 묶음(목록·상세·근거 티켓·AI 판단)을 보이는지, 초안 임시 저장(다른 관리자가 먼저 고친 경우 최신 초안을 다시 불러오는지)·거절(사유 필수)·직접 반영 표시가 되는지. 초안 등록은 서버 API가 없어 막아 둔 상태가 맞습니다(R-51). AI 판단 칸에는 `reviewInfo`의 `reason`·`warnings`만 보입니다.
- **현행 변경 차단 (11.08):** 검토할 AI 가이드 제안(등록 전)이 있는 가이드는 현행 전환을 누르면 바뀌지 않고 "제안 N건이 있어요" 창이 뜨는지, 제안 탭으로 이동되는지.
- **로그인 전 상담의 질문 버튼 5개 (11.08):** 계정 잠김·비밀번호 재설정·비밀번호 만료·아이디 불일치·휴대폰 교체 후 인증 질문에 서버가 가이드 근거로 답하는지.
- **팀 통계의 상태별 현황 (11.08):** 담당자의 팀 통계에서 상태별 현황이 숫자만 보이고 눌리지 않는지(내 통계는 눌러서 처리할 문의로 이동).

## (11.04-오후10시 추가) 확인이 필요한 표시 문구 — 운영 기록·AI 판단 이력

### R-43. 캘린더 팀 일정 — 추가 요청 제외 (11.08)

- **프론트 담당 확인:** 현재 캘린더에서 팀원 휴가 일정이 표시되고 있어, 팀 일정 조회 확대·응답 그룹 필드 추가를 백엔드에 다시 요청하지 않는다. 기존 R번호는 이력 추적용으로 유지한다.
- **코드 대조:** 로컬 `CalendarView`는 `listTimeOff()` 결과를 표시한다. `timeOff.ts`에는 서버 `/time-off` 조회와 모의 일정 경로가 있으며, 팀 구성원 조회는 관리자 필터에도 사용된다. 이번 코드 확인만으로 사용자가 확인한 실행 환경·역할·데이터 경로까지 확정한 것은 아니다. “현재 팀 일정이 안 보임” 또는 “백엔드 확장이 반드시 필요함”으로 단정하지 않는다.
- **처리:** 화면을 축소하거나 권한을 새로 변경하지 않는다. 추가 서버 개발이 필요한 것으로 재등록하지 않고, 실제 데이터 누락이 재현될 때만 기존 조회 경로와 응답을 확인한다.
