# 프론트 → 백엔드 연동 요청 목록

화면을 실제 서버에 연결하면서 발견한 **빠진 기능, 부족한 응답 정보, 화면과 서버의 동작 차이**를 정리한 문서입니다. 각 요청에서 필요한 작업과 현재 화면의 동작을 나눠 설명합니다.

## 문서 읽는 법

- **서버 모드**: 실제 서버 API를 사용하는 모드입니다.
- **모의(mock) 모드**: 서버 대신 시연용 데이터와 응답을 사용합니다. 이 모드에서 동작해도 서버 연결이 완료된 것은 아닙니다.
- **API 번호**: `TK-05` 같은 번호는 `docs/api/01~05` 명세와 `docs/07.API_설계서.md`에서 사용합니다.
- **PR 번호**: `#132` 같은 번호는 관련 화면의 변경 사항을 담은 PR입니다.
- 화면은 시안(`design/ITssue-Prototype.html`)을 기준으로 구현합니다. 서버에 없는 기능은 모의 모드에서만 동작하거나, 서버 모드에서 안내만 표시합니다.

### 상태의 의미

| 상태 | 의미 |
|---|---|
| 요청 전 | 요청을 전달하기 전 |
| 요청함 | 요청을 전달한 상태 |
| 반영됨 | 서버에 반영된 상태 |
| 프론트 적용 | 화면과 서버의 연결이 끝난 상태 |
| 보류 | 시안을 변경하기로 한 상태 |
| 결정 필요 | 화면이나 서버를 어떻게 바꿀지 결정해야 하는 상태 |

이번 문장 정리에서는 기존 상태를 유지했습니다. 실제 배포 여부나 작업 완료 여부를 새로 판정하지 않았습니다.

### 갱신 방법

1. 화면 PR에서 서버와 맞지 않는 부분을 발견하면 요청 번호를 붙여 추가합니다.
2. PR 본문에는 “요청 R-NN 참고”처럼 해당 번호를 적습니다.
3. 서버에 반영되면 `반영됨`, 화면 연결까지 끝나면 `프론트 적용`으로 바꿉니다.
4. 문서 마지막의 갱신 이력에 변경 내용을 남깁니다.

## 요구사항 우선순위와 연동 요청의 관계

**Must / Should / Could는 개발 우선순위이고, 이 문서의 상태는 요청과 연동의 진행 상황입니다.** 예를 들어 `Must · 요청 전`은 반드시 필요한 기능이지만 아직 연동 요청을 전달하기 전이라는 뜻입니다. 우선순위만으로 구현 완료 여부를 판단하지 않습니다.

기준은 [요구사항 정의서(SRS)](../03.요구사항정의서(SRS).md)입니다.

- **Must**: MVP에 반드시 필요한 기능·보호·검증 요구사항
- **Should**: Must 완성 후 구현을 목표로 하는 요구사항
- **Could**: 일정과 추가 합의에 따라 구현을 검토하는 요구사항

아래 표는 연동 요청과 기존 요구사항을 연결한 것입니다. 요청별 세부 API·응답 필드까지 SRS에서 각각 우선순위를 확정한 것은 아닙니다. **‘관련’은 해당 요구사항을 지원하는 작업이라는 뜻이며, 요청 전체를 그 우선순위로 확정한다는 뜻은 아닙니다.** 정책이나 구현 범위의 결정이 필요한 부분은 그대로 표시했습니다.

### 작업 순서를 정할 때

먼저 Must 기능의 실제 사용을 막는 배포·접수·Jira 처리·오류 복구 문제를 확인합니다. R-16·17·18과 R-03·08·10·15의 Must 관련 범위가 여기에 해당합니다. 이 목록은 새 우선순위 확정이 아니라, 기존 Must 요구사항을 기준으로 먼저 확인할 범위입니다.

그다음 Should의 통계·목록·계정·Guide 관리 등을 연결하고, Could는 남은 일정과 합의에 따라 진행합니다. 혼합 항목은 Must에 해당하는 부분을 분리해 처리합니다. R-09의 메시지·알림 범위, R-25의 예산 표시, R-28의 종료 문의 이어가기처럼 결정이 필요한 내용은 구현 전에 확정해야 합니다.

## 1. 집계·건수

### R-01. 대시보드·통계 집계 API(OP-01·OP-02) 구현

**필요한 작업**

명세(`05.기준정보_운영.md`)는 있지만 서버 구현은 없습니다. OP-01에는 화면에서 사용하는 다음 정보도 필요합니다.

- 처리 대기(RDY) 건수: 현재 `totals`에 없습니다.
- 긴급·높음으로 분류된 미해결 접수의 건수와 상위 N건
- Jira 알림 건수
- 확인이 필요한 접수의 원인별 건수: Jira 생성, 상태 동기화, 담당자 배정
- 팀·분류를 선택했을 때의 구성원별 현황과 개인별 분류 분포(도넛 차트)
- 접수 추이의 해결 완료 건수: 접수일 기준

**현재 화면 동작**

건수만 확인하려고 접수 목록(TK-05)을 한 건씩(`size=1`) 여러 번 요청합니다. 관리자 대시보드는 화면을 열 때마다 7번 요청합니다. 통계는 접수 목록을 받아 화면에서 직접 계산합니다. 계산 대상은 서버 모드에서 최대 100건, 모의 모드에서 최대 200건입니다.

**불편한 점·제약**

건수를 확인하는 데 여러 번 요청해야 합니다. 서버 모드에서 접수가 100건을 넘으면 일부 접수가 계산에서 빠져 상위 N건과 통계가 정확하지 않을 수 있습니다.

- 관련 화면(PR): 내 대시보드·통계(#132), 운영 현황(#187), 관리자 대시보드(#189), 관리자 통계(#191)
- 상태: **요청 전**

### R-02. 목록 응답에 상태별 건수

**필요한 작업**

목록 조회 결과에 상태별 전체 건수를 함께 제공해야 합니다. 대상은 다음과 같습니다.

- 사용자 목록: 전체·정상·잠김·이용 제한
- 전체 문의의 상태 탭: 배정 전·진행 중·해결 확인 대기·해결 완료
- AI 처리 화면의 구분별 탭

**현재 화면 동작**

상태별로 목록을 한 건씩 요청하고, 응답에 포함된 전체 건수를 읽습니다.

**불편한 점·제약**

상태별 건수를 확인하려고 화면을 열 때마다 요청을 5~6번 더 보냅니다.

- 관련 화면(PR): 계정 관리(#137), 전체 문의(#186)
- 상태: **요청 전**

### R-03. TK-05 필터 확장

**필요한 작업**

접수 목록(TK-05)에 배정 상태(`assignStatus`)와 상태 변경 요청의 처리 상태(`transitionStatus`) 필터를 추가해야 합니다. 또한 배정 전 접수까지 포함해, 해결 완료되지 않은 모든 접수를 조회할 수 있어야 합니다.

**현재 화면 동작**

관리자 확인이 필요한 접수를 `needsAdmin=true`로 조회한 뒤, 화면에서 원인별로 나눕니다. 배정 전 여부는 실제 배정 상태 대신 Jira 연동 상태(`jiraSyncStatus`)로 추정합니다. 현재의 “해결 완료 제외” 조건에는 배정 전 접수가 포함되지 않습니다.

**불편한 점·제약**

100건 초과 시 일부 누락, 배정 전 접수가 필터에서 빠짐

- 관련 화면(PR): 전체 문의(#186), 운영 현황(#187)
- 상태: **요청 전**


### R-19. AI 상담 결과의 기간별 추이

**필요한 작업**

문의 목록(IQ-02)을 일·주·월 단위로 묶은 건수(구분별: AI 해결·해결 확인 대기·미해결 종료)를 한 번에 주는 집계

**현재 화면 동작**

서버 모드에서는 AI 추이 선을 그리지 않고, 기간별 구분 건수만 목록 총건수(`size=1`)로 읽음. 시안의 1년 추이는 임의 시연 값이라 넣지 않음

**불편한 점·제약**

관리자 통계의 접수 추이에 AI 해결 선이 없음

- 관련 화면(PR): 관리자 통계
- 상태: **요청 전**


## 2. 정렬·검색

### R-04. TK-05 정렬 확장

**필요한 작업**

시안·모의는 "해결되지 않은 문의를 이어갈까요?" 창에서 "이어서 대화하기"로 같은 대화의 담당자 연결 제안부터 다시 시작해요. 서버 IQ-06은 미확인·미해결(연결 제안 중)·해결 확인 대기만 이어가고, IQ-04로 끝낸 문의는 `next_actions=[START_NEW]`라 409(`INQUIRY_INVALID_STATE`)를 돌려줘요

**현재 화면 동작**

서버 모드에서는 "이어서 대화하기"를 눌러도 창이 안 닫히고, 창 안에 "이미 종료된 문의는 이어갈 수 없습니다. 새 문의로 시작해 주세요."만 보여요

**불편한 점·제약**

문의 내역에서 미해결·미접수 종료 문의를 열면 이어갈 수 없음

- 관련 화면(PR): 문의 대화
- 상태: **결정 필요(서버에서 이어가기를 허용하거나, 시안에서 이 문구·버튼을 빼거나)**

### R-29. 대화 이력에 버튼 선택과 안내 저장

**필요한 작업**

모의(시안)는 내가 누른 "해결"·"미해결"·"미연결 (종료)" 말풍선과 그 뒤 AI 안내를 대화에 남기지만, 서버는 해결 때 시스템 안내 한 줄(`해결로 종료되었습니다.`)만 저장하고 미해결·연결 거절은 상태만 남겨요. 또 긴급 징후가 있던 문의를 접수 없이 끝낼 때 모의가 붙이는 보안 안내(노란 안내)는 서버가 메시지로 주지 않고(`urgent_signal`은 판단 이력에만 있음) 문의 응답에도 없어요

**현재 화면 동작**

화면이 문의의 상태(`status`·`resolutionResult`)에서 같은 대화를 다시 만들어 보여 줘요(해결·미해결·미연결 말풍선과 안내). 보안 안내는 서버 모드에서 나오지 않아요

**불편한 점·제약**

서버가 저장하면 화면의 재구성 규칙을 줄일 수 있고, 긴급 징후 종료 시 보안 안내를 붙일 수 있어요

- 관련 화면(PR): 문의 대화
- 상태: **요청 전**
