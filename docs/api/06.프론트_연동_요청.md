# 프론트 연동 요청 — 마감 전 남은 작업

**검수 기준:** 2026-11-04, `develop`의 API·응답 모델·서비스와 프론트 연결 코드. 실제 서버 호출·배포·공유 DB 데이터는 이번에 확인하지 않았습니다. 기존 R번호는 유지하고, 중복 요청은 묶었습니다.

**이번 정리의 목적은 신규 개발과 조회 부하를 줄이는 것입니다.** 아래 Must → Should → Could 순서는 [SRS](../03.요구사항정의서(SRS).md)를 바탕으로 남은 작업을 배치한 것이며, SRS 자체의 우선순위를 변경하지 않습니다. ‘후순위’는 미완료지만 이번 마감에서 제외하는 제안입니다. 이미 있는 API로 프론트에서 해결할 일은 맨 아래에 모았습니다.

## 1. Must — 테스트를 막는 문제부터

현재 남은 항목이 없습니다.

## 2. Should — 범위가 작은 보완만 우선 검토

아래 다섯 항목은 각각 독립적으로 처리할 수 있는 보완입니다. 신규 분석·배치·실시간 연결을 전제로 하지 않으며, 이번 일정에 가능한 항목만 선택합니다.

### R-37. AI 응답 실패 때도 문의 제목 저장

- **담당 제안:** 민경님 / **화면:** 사이드바·문의 내역 / **관련:** INQ-05
- **요청:** AI 처리 전에 저장하는 사용자 글에서 짧은 기본 제목을 만들어 주세요. 나중에 AI 제목이 생기면 교체할 수 있게 합니다. 민감정보 처리 후 저장하는 글을 기준으로 해야 합니다.
- **현재 이슈 사항:** `start()`는 제목 없이 문의·글을 먼저 저장하고, 제목은 AI 응답 성공 후에만 채웁니다. 실패하면 목록에서 ‘새 문의’로 보일 수 있습니다. 프론트의 임시 제목 기억은 새로고침·재로그인 후 유지되지 않습니다.

### R-22. 외부 전송 정책 완화 사유 저장

- **담당 제안:** 민경님 / **화면:** 가이드 관리 / **관련:** GUIDE-01(Should), GUIDE-07·NFR-SEC-03(Must)
- **요청:** DC-09가 정책 완화 사유(`reason`)를 받아 기존 감사 기록에 함께 저장하도록 보완해 주세요. 대상은 금지→마스킹 후 허용/허용, 마스킹 후 허용→허용입니다.
- **현재 이슈 사항:** 정책 변경 자체와 `DOCUMENT_POLICY_CHANGE` 기록은 이미 구현되어 있습니다. 다만 요청 모델에 `reason`이 없어 화면이 받은 사유를 저장하지 못합니다. 새 감사 시스템을 만들 필요는 없습니다.
- **범위:** 정책 변경 관리의 보완입니다. 기존 외부 전송 차단·권한 검사는 계속 유지해야 합니다.

### R-30. FAQ 출처에 해당 본문 제공

- **담당 제안:** 민경님·태연님 / **화면:** FAQ 출처 미리보기 / **관련:** 근거 확인 보완
- **요청:** FAQ 상세(FQ-02)의 출처에 해당 청크의 본문(`excerpt`)을 제공할 수 있는지 검토해 주세요. 현재의 출처 권한 검사를 유지하고, 이번에는 별도 이미지 API나 쪽 번호 필드까지 늘리지 않습니다.
- **현재 이슈 사항:** `FaqSource`에는 문서 ID·번호·제목·버전·위치만 있고 본문이 없습니다. 프론트도 본문을 빈 문자열로 변환하므로 위치 안내까지만 가능합니다. 줄바꿈 문제(R-31)와는 별개입니다.

### R-40. 운영 기록에 접수 ID·접수번호 제공

- **담당 제안:** 민경님 / **화면:** 운영 기록 / **관련:** LOG-01의 조회 편의 보완
- **요청:** OP-04(`/audit-logs`)의 항목에 `ticketId`·`receiptNo`를 함께 내려주세요. 접수 대상은 직접 연결하고, 문의 대상은 연결된 접수가 있을 때만 채우며 없으면 null로 둡니다. 목록 항목마다 개별 조회하지 않도록 일괄 조회·조인 방식을 검토해 주세요.
- **현재 이슈 사항:** 서버 응답에는 대상 종류와 숫자 ID만 있습니다. 화면은 접수번호를 얻으려고 추가 조회하고, 문의 대상 기록에서는 연결된 접수를 바로 열지 못합니다. 기존 로컬 문서에 추가되어 있던 요청을 유지했습니다.

### (11.04-오후9시 추가) R-41. FAQ 등록 때 연결할 가이드 문서 저장

- **담당 제안:** 민경님·태연님 / **화면:** FAQ 관리(FAQ 등록·수정) / **관련:** FQ-03·FQ-04, FAQ 게시 조건([04.문서_FAQ](04.문서_FAQ.md))
- **요청:** FQ-03·FQ-04가 연결할 문서(`sourceDocumentIds`, 문서 ID 배열)를 받아 FAQ와 문서의 연결을 저장하게 해 주세요. 게시 조건 검사도 이 연결을 인정해야 합니다. 연결 대상은 활성 문서의 현행 버전이고 열람 범위가 전 직원(ALL)인 가이드로 제한하고, 그 밖의 문서는 오류로 거절합니다. FAQ 상세(FQ-02)의 출처에도 이 연결이 보이게 하고, 문서 변경으로 공개 출처가 없어지면 기존 자동 게시 중단(`FAQ_AUTO_UNPUBLISH`)이 같은 기준으로 동작해야 합니다.
- **현재 이슈 사항:** 지금 FAQ와 문서의 연결은 FAQ에 저장되지 않고, 가이드 문서 조각의 `faq_ids`가 FAQ 번호를 가리키는 방식으로만 생깁니다. FQ-03은 FAQ 번호를 자동으로 붙이므로 새 FAQ를 만들어도 게시 조건(`FAQ_SOURCE_NOT_PUBLIC`)을 충족할 수 없어, 화면의 'FAQ 추가'가 게시까지 이어지지 않습니다. 이 요청이 반영되기 전까지 관리자가 만든 FAQ는 게시하지 못합니다. 프론트는 그동안 FAQ 등록 창의 '바로 게시'를 막고 안내 문구만 보여 줍니다.
- **프론트 대응:** 분류를 고르면 그 분류의 현행 가이드 목록(기존 DC-01 재사용)을 보여 주고 선택하게 합니다. 요청 필드가 확정되면 연결하겠습니다.
- **범위:** 연결 저장 방식(연결 표를 새로 두거나 기존 구조 활용)은 서버 설계 판단에 맡깁니다. 새 검색·배치·실시간 처리는 전제하지 않습니다.

## 3. Should — 이번에는 후순위로 둘 작업

새 API나 응답 확장이 필요한 미완료 항목입니다. 당장 화면을 쓰는 데 필요한 최소 경로가 있어, **이번 마감에서는 기존 기능을 사용하고 확장은 미루는 안**입니다.

### R-01·R-02·R-13·R-19. 집계 확장과 요청 횟수 개선

- **화면:** 관리자 대시보드·통계, 담당자 통계·팀 현황, 계정·문의 목록
- **이미 있음:** OP-01 `overview`, OP-02 `me`, OP-03 `ai-usage`. 관리자 통계와 담당자 통계의 일부는 서버 집계에 연결돼 있습니다. `overview.trend.aiResolvedCount`와 접수일 기준 `closedCount`도 있습니다.
- **남은 범위:** 기간과 무관한 현재 RDY/WIP/FIN·확인 필요 원인별 건수·긴급 상위 N건(R-01), 목록의 상태별 건수 동시 제공(R-02), 개인별 긴급도 분포(R-13), 미확인·미연결 종료의 기간별 추이(R-19), `/me`의 추이·긴급도 분포입니다.
- **이번 제안:** 기존 집계를 유지하고 새 집계 API는 미룹니다. 프론트 목록 기반 집계는 최대 100건 제한으로 누락될 수 있으므로 전체 집계인 것처럼 단정하지 않도록 확인합니다. R-02 본문에 잘못 섞여 있던 대시보드 설명은 여기로 합쳤습니다.

### R-03·R-04·R-05·R-06·R-07. 목록 필터·검색·정렬 확장

- **화면:** 처리할 문의·전체 문의·문의 내역·계정 관리
- **이미 있음:** TK-05 `assignStatus` 필터. 기존 검색·정렬과 문의 표시 상태를 사용한 조회는 가능합니다.
- **남은 범위:** TK-05의 `transitionStatus`·배정 전을 포함한 미완료 필터(R-03), 제목·접수번호·분류·담당자 정렬과 이름 검색(R-04·05), 사용자 부서 검색·부서/역할/상태 정렬(R-06), 문의 제목/분류/상태 정렬·가이드 제목 검색·사용한 가이드 필드(R-07)입니다.
- **이번 제안:** 지원되는 조건만 화면에 노출하고 확장은 미룹니다. 다만 관리자 확인 필요 접수를 빠뜨리는 문제가 실제로 확인되면 ADMIN-01(Must)과 관련되므로 해당 누락만 먼저 고칩니다.

### R-10. 접수 목록에 실제 오류 사유·발생 시각 추가

- **화면:** 운영 현황
- **이미 있음:** `integration-jobs`에 `lastError`·작업 생성/갱신 시각이 있습니다. 오류 원문 자체가 전혀 없는 상태는 아닙니다.
- **남은 범위:** 접수 응답에 요약 사유와 실제 오류 발생 시각을 포함해 개별 이력 조회를 줄이는 일입니다. 작업 `createdAt`은 오류 발생 시각과 같다고 볼 수 없습니다.
- **이번 제안:** 새 필드 추가는 미루고, 상세 확인에는 기존 작업 이력을 사용합니다. 주요 이력 통합 표시는 하단 R-15에 분리했습니다.

### R-11·R-33·R-38. 처리 상태·변경 신호·적재 알림

- **화면:** 문의 대화·사이드바·담당자/관리자 목록·가이드 관리
- **이미 있음:** NT-01~04와 `ASSIGNED`·`FIN` 알림, 안 읽은 개수 조회, 접수 읽음 처리. 기존 폴링으로 화면을 갱신할 수 있습니다.
- **남은 범위:** AI 처리 중 필드(R-11), 변경 요약 조회 또는 SSE/웹소켓(R-33), 적재 완료·실패 알림 종류 추가(R-38)입니다.
- **이번 제안:** 상시 연결·새 알림 배치는 만들지 않고 기존 조회를 유지합니다. 읽기 중복·주기는 프론트에서 관리합니다. 현재 대화 기본 주기는 10초이며 상태에 따라 느리게 읽거나 멈추고, 접수 목록은 15초입니다. 이전 ‘대화 4~8초’ 설명은 삭제했습니다.
- **나중에 할 경우:** 알림/신호는 본인·권한 범위, 토큰 만료·로그아웃, 재연결, 중복 이벤트를 함께 설계해야 합니다. 한 번의 대화 조회는 문의·메시지·필요 시 접수 상세의 2~3개 요청이므로 전송량 개선도 같이 검토합니다.

### R-20. 보안·감사 알림 관리 기능

- **화면:** 보안·감사 알림
- **이미 있음:** 로그인 차단·긴급 징후 미접수 종료 등 일부 이벤트의 감사 기록과 OP-04 조회. `actor`에는 수행자 이름도 있습니다. 전용 보안 알림 화면은 여전히 시연 데이터입니다.
- **남은 범위:** 이벤트별 감지 범위 보완, 보안 알림 목록·상세·원문 열람·사유 기록·확인/종결 상태 관리입니다. 감사 로그 조회와는 다른 기능입니다.
- **이번 제안:** 새 관리 테이블·API·감지 기능 확대는 미룹니다. 기존 민감정보 보호·접근 제한·필수 긴급 종료 기록(Must)은 유지합니다. 원문 보관을 새로 허용하는 결정도 포함하지 않습니다.
- **R-29의 남은 범위도 후순위:** 해결·미해결·연결 거절 말풍선은 현재 프론트가 상태값으로 재구성합니다. 선택·안내 메시지의 서버 저장 통일과 문의자용 긴급 종료 보안 안내 응답은 이번에 확장하지 않는 안입니다. 관리자 전용 판단 이력을 문의자 화면에서 읽는 방식으로 대체하지 않습니다.

### R-21·R-24·R-35. 가이드·FAQ 편집 편의

- **화면:** 가이드 관리·FAQ 등록
- **남은 범위:** 버전 메모와 수정 이력(R-21), 서버의 문서 번호 자동 채번(R-24), FAQ 등록/수정에서 출처를 직접 선택·저장(R-35)입니다.
- **이번 제안:** 기존 입력·등록 경로를 사용하고 확장은 미룹니다. 문서 번호는 프론트가 계산하고 서버가 중복을 거절하므로 동시 등록 충돌 가능성이 있습니다. FAQ 출처는 현재 청크의 `meta.faq_ids`에서 파생되며 직접 선택 저장 계약은 없습니다.

## 4. Could — 이번 마감에서 제외할 확장 제안

### R-23·R-26·R-32·R-36. 분석·평가·추가 상담·응답 편의

- **R-23:** 해결 사례의 자정 유사도 분석·주제 묶음·AI 초안 생성. GUIDE-08의 자정 분석은 Could입니다. GUIDE-03의 관리자 검토·Guide 등록은 Should이므로 동일 우선순위로 단정하지 않되, 새 자동화 파이프라인은 이번에 시작하지 않는 안입니다.
- **R-26:** Golden Set 결과 조회 API와 실제 평가 화면 연결(EXT-05, Could). 현재 품질 평가는 시연 데이터입니다.
- **R-32:** 로그인 전 실제 Guide 상담 API(PRE-01, Could). 현재 키워드 기반 시연 안내를 유지합니다.
- **R-36:** 같은 사용자의 동일 상태 변경 재요청에 진행 중 응답을 돌려주는 개선. SRS에 별도 우선순위가 없는 후순위 제안으로 이곳에 모았습니다. 프론트가 중복 버튼 잠금과 409 안내를 이미 처리하므로 필수 변경은 아닙니다.

### (11.04-오후9시 추가) R-42. 운영 기록 대상 표시 이름 제공 (후순위)

- **담당 제안:** 민경님 / **화면:** 운영 기록 / **관련:** LOG-01의 조회 편의 보완, R-40
- **요청:** OP-04(`/audit-logs`) 항목에 `targetLabel`을 함께 내려주세요. 접수는 접수번호, 문서는 문서 코드, FAQ는 FAQ 번호, 사용자는 이름·사번으로 하고, 문의처럼 사람이 쓰는 번호가 없는 대상은 null로 둡니다. 삭제된 대상도 기록 시점의 이름이 남도록 기록 때 함께 저장해 주세요.
- **현재 이슈 사항:** 응답에는 대상 종류와 내부 숫자 ID만 있어 화면이 사람이 알아볼 이름을 보여 줄 수 없습니다. R-40은 접수에 한해 `ticketId`·`receiptNo`를 요청하는 항목이며, 이 요청은 같은 필요를 다섯 가지 대상 전체로 넓힌 것입니다. R-40이 반영되면 접수 부분은 중복이므로 함께 정리해 주세요.
- **우선순위 사유:** 필수가 아닙니다. 프론트는 이 값이 없는 상태를 가정해, 대상 종류만 보이고 결과 칸의 코드(접수번호·문서 코드·FAQ 번호)를 활용합니다. 링크와 상세 패널은 두지 않습니다.

## 5. 프론트에서 처리하거나 확인할 기록

추가 백엔드 기능 요청에서 제외했습니다. 이 문서 편집으로 아래 화면 작업을 실행한 것은 아닙니다.

- **R-09 — 새 소식·출처 제목:** NT-01~04로 배정/FIN 알림 표시를 이미 연결했습니다. 문의자 메시지는 기존 시연 범위로 유지합니다. 출처 제목은 기존 문서 조회 재사용 여부를 먼저 확인하고, FAQ 본문 부족만 R-30에 남겼습니다.
- **R-14 — 계정 이력:** `/audit-logs?targetType=user&targetId=...`와 `actor`를 재사용해 계정 화면에 연결할 수 있습니다. 현재 패널은 임시 기록입니다. 수행자 이름과 변경 대상 사용자는 다른 정보이므로 구분해서 표시합니다.
- **R-15 — 처리 이력 통합:** 상태 이력·`assignment-logs`·`integration-jobs`가 각각 있습니다. 필요하면 프론트에서 시간순으로 합칩니다. 작업 이력은 관리자 전용이므로 담당자 화면에 무리하게 연결하지 않습니다. 통합 API·실제 문의자 메시지 전송은 추가 요청에서 제외했습니다.
- **R-25 — AI 예산:** `/dashboard/ai-usage`에 연결되어 있고 프론트가 이미 ‘기간 예산 사용’으로 표시합니다. 구간별 예산 필드 요청은 종료합니다. 다년 추이인 ‘연도별’ 보기는 서버 기간 제한에 맞춰 비활성 상태를 유지합니다.
- **R-28 — 이어가기:** 연결 거절·초안 취소로 종료한 문의는 재개하지 않는 정책과 화면 처리가 적용돼 있습니다. 서버 변경 요청을 종료합니다. 연결 결정 대기는 별도 ‘AI 미해결’ 상태를 추가하지 않고 진행 중으로 표시합니다.
- **R-31 — 본문 서식 재확인:** 현재 청크 생성과 검색 단위 복원 코드는 줄바꿈을 사용합니다. 따라서 ‘서버가 항상 줄바꿈을 없앤다’고 단정할 수 없습니다. 문제 출처의 실제 `excerpt`와 적재 원문을 비교한 뒤 적재 데이터/변환/화면 중 수정 위치를 정합니다. 이미지 API는 이번에 추가하지 않습니다.

## 6. 실행 환경 확인 — 새 API 개발과 구분

- **R-16·R-18:** worker 코드·Compose 실행 설정·단건 시험 자료는 이미 있습니다. 접수·상태 변경은 `VITE_SERVER_INTAKE`가 true인 준비된 환경에서 실행하도록 연결되어 있습니다. ‘서버에 기능이 없어 무조건 막힘’이라는 이전 설명은 삭제합니다.
- **R-39:** 서버 DB에 이미 `PENDING`으로 멈춘 버전이 있는지와 그 원인은 아직 확인하지 않았습니다. 배포 후 정기 복구가 다시 적재하며, 파일이 서버에 없으면 `FAILED`로 끝나므로 다시 올려야 합니다.
- 실제 worker 상시 실행, 테스트 계정·시험 데이터 정리, 전체 접수 흐름 검증은 환경별로 확인해야 합니다. 이번 검수에서는 운영 배포 완료나 현재 실행 여부를 확인하지 않았습니다.

## 정리한 완료 범위

- **R-08·R-12·R-17·R-27·R-34:** 기존 문서에서 이미 제거된 접수 ID, 기본 알림 API, 연동 재시도, 문서 관리 API, 배정 전 표시 상태는 재요청하지 않습니다.
- **추가로 종료:** R-25의 예산 표시 결정, R-28의 종료 문의 재개 요청.
- **R-39:** 적재가 `PENDING`에 남는 경우 서버가 시작 때와 그 뒤 5분마다 10분 넘은 버전을 다시 적재합니다 (`EMBEDDING_PRELOAD=true`인 서버만). DB 연결이 끊긴 동안에는 실패 상태도 기록할 수 없어 재시도로 처리했고, 화면·API 변경은 없습니다. DB 풀은 `DB_POOL_SIZE`·`DB_MAX_OVERFLOW`로 설정하며 코드 기본값은 5+5입니다. 팀 전체 연결 한도가 15개라는 기존 기록은 서버 설정을 확인해야 하므로 확정값으로 쓰지 않습니다.
- **기존 기능으로 대체:** R-14의 새 이력 조회 API, R-15의 새 통합 이력 API. 남은 프론트 작업은 위 기록만 참고합니다.
- **검수 범위:** API·서비스·프론트 코드 대조와 문서 정리입니다. 실제 DB/API 테스트나 배포 확인을 통과했다는 의미는 아닙니다.


## (11.04-오후10시 추가) 확인이 필요한 표시 문구 — 운영 기록·AI 판단 이력

새 기능 요청이 아니라 **뜻 확인**입니다. 화면은 서버가 준 영문 코드·값을 아래처럼 한글로 바꿔 보여 줍니다(프론트 사전: `frontend/src/api/auditLogs.ts`, `frontend/src/api/assessments.ts`). 제가 코드를 읽고 추정한 부분이라, 맞는지 서버 담당자 확인 부탁드립니다. 다르면 화면 문구만 고치면 됩니다.

- **1. 재배정 기록의 결과 값(`ASSIGN`·`REASSIGN`·`FAIL`):** 배정 이력의 종류로 보고 각각 "배정 / 재배정 / 배정 실패"로 표시합니다. 담당자가 없던 접수의 배정이 `ASSIGN`, 있던 접수의 변경이 `REASSIGN`, 정할 사람이 없을 때가 `FAIL`이 맞는지, 값이 이 세 가지뿐인지(`RECOMMEND`는 오지 않는지) 확인해 주세요.
- **2. 운영 기록 이벤트 목록:** 프론트 사전은 현재 서버가 `audit_logs`에 남기는 20가지(`SENSITIVE_INPUT`, `BLOCK`, `FAIL`, `URGENT_CLOSED`, `CONFIRM`, `REASSIGN`, `INTEGRATION_RETRY`, `DOCUMENT_ACTIVATE`, `DOCUMENT_DEACTIVATE`, `DOCUMENT_VERSION_ACTIVATE`, `DOCUMENT_VERSION_RETRY`, `DOCUMENT_POLICY_CHANGE`, `USER_CREATE`, `USER_ROLE_CHANGE`, `USER_STATUS_CHANGE`, `PASSWORD_RESET`, `LOGIN_BLOCKED`, `ACCOUNT_LOCKED`, `FAQ_DELETE`, `FAQ_AUTO_UNPUBLISH`) 기준입니다. [05.기준정보_운영](05.기준정보_운영.md) OP-04의 `eventType` 예시에는 `CLASSIFY`·`ASSIGN`이 있지만 서버가 운영 기록에 남기는 곳은 찾지 못했습니다(판단·배정 이력은 각각 `inquiry_assessments`·`assignment_logs`에 저장). 문서 예시를 실제와 맞춰 주시고, 새 이벤트가 생기면 프론트 사전에도 추가해야 하니 알려 주세요.
- **3. 결과 값 목록:** `BLOCK`(`DOC_BLOCKED`·`ALL_BLOCKED`), `FAIL`(`FILTER_FAILED`·`AI_FAILED`), `INTEGRATION_RETRY`(`QUEUED`·`ALREADY_APPLIED`·`LINKED_EXISTING`), `SENSITIVE_INPUT`(`PASSWORD`·`OTP`·`API_KEY`·`PRIVATE_KEY`·`RRN`·`CARD`·`ACCOUNT`)이 전부인지 확인해 주세요.
- **4. `FAIL` 사유의 `④`:** "④ 검색 근거 코드", "④ 외부 모델 호출 직전"처럼 숫자 기호가 붙습니다. 민감정보 필터의 네 번째 단계를 뜻하는지, 관리자 화면에 그대로 보여 줘도 되는 문구인지 확인해 주세요.
- **5. `URGENT_CLOSED`:** 결과가 항상 `CLOSED_UNRESOLVED`인지, "긴급 징후가 있었는데 담당자 연결 없이 종료"라는 표시가 맞는지 확인해 주세요.
- **6. 문서 기록의 결과 글 모양:** `DOCUMENT_POLICY_CHANGE`는 `v2 ALL/ALLOWED → ADMIN/BLOCKED`(버전, 열람 범위/외부 전송 정책의 이전 → 이후), `DOCUMENT_VERSION_ACTIVATE`는 `v1 → v2`, `DOCUMENT_VERSION_RETRY`는 `v3 파일 교체`·`v3 같은 파일` 모양입니다. 화면이 이 글자 모양을 풀어서 보여 주므로, 형식을 바꾸면 알려 주세요. 가능하면 글 대신 구조화된 값(이전/이후 필드)으로 주는 편이 안전합니다.
- **7. 계정 상태 `INACTIVE`:** 계정 관리 화면과 같이 "이용 제한"으로 표시합니다. 서버 용어와 맞는지 확인해 주세요.
- **8. AI 판단 이력의 추가 질문:** 판단의 `action`이 `ASK_MORE`이면 `missing_items`를 "AI가 더 물어본 항목"(대상 시스템·증상·발생 시점·영향 범위·시도한 조치)으로 보여 주고, 다음 판단은 그 질문에 사용자가 답해서 생긴 것으로 이어서 표시합니다. "추가 질문 → 사용자 답 → 다음 판단" 순서가 항상 맞는지 확인해 주세요.
- **9. 사용한 가이드:** AI 처리 상세에서 `/inquiries/{id}/messages`의 `sources`(`DOCUMENT`·`LEGACY`)로 "사용한 가이드"를 보여 줍니다. 관리자가 다른 사람의 문의 메시지를 이 API로 조회해도 되는지, AI 답변이 여러 개일 때 같은 문서·버전·위치를 한 번만 보여 주는 기준이 맞는지 확인해 주세요.
