# 프론트 연동 요청 — 마감 전 남은 작업

**검수 기준:** 2026-11-04, `develop`의 API·응답 모델·서비스와 프론트 연결 코드. 실제 서버 호출·배포·공유 DB 데이터는 이번에 확인하지 않았습니다. 기존 R번호는 유지하고, 중복 요청은 묶었습니다.

**이번 정리의 목적은 신규 개발과 조회 부하를 줄이는 것입니다.** 아래 Must → Should → Could 순서는 [SRS](../03.요구사항정의서(SRS).md)를 바탕으로 남은 작업을 배치한 것이며, SRS 자체의 우선순위를 변경하지 않습니다. ‘후순위’는 미완료지만 이번 마감에서 제외하는 제안입니다. 이미 있는 API로 프론트에서 해결할 일은 맨 아래에 모았습니다.

## 2. Should — 범위가 작은 보완만 우선 검토

### (11.05 추가) R-44. 문의 답변의 출처에서 같은 문서·위치 중복 제거

- **담당 제안:** 민경님 / **화면:** 문의 대화(답변 말풍선의 출처 버튼) / **관련:** IQ 메시지 `sources[]`, 2.6 `MessageSource`
- **요청:** 한 답변의 `sources[]`에서 `docCode`·`version`·`location`이 같은 출처는 한 줄로 합쳐 내려주세요. 합칠 때 `excerpt`는 비어 있지 않은 첫 값을, `images`는 모두 모은 목록을 쓰면 됩니다. 합치지 않으려면 조각마다 구분되는 값(`chunkIndex` 등)을 주세요.
- **현재 이슈 사항:** 근거 조각(청크)마다 한 줄씩 `message_sources`에 저장되고 그대로 내려와, 한 답변에 `IT-SW-001` 위치 `2`가 네 번 오는 경우가 확인됐습니다. 화면에 같은 출처 버튼이 여러 개 보이고, React 키 중복 경고(`IT-SW-0012`)가 납니다. 프론트는 같은 문서·버전·위치를 합쳐 한 번만 보이도록 이미 처리했지만, 응답 크기와 `rank` 의미가 흐려지므로 서버에서 정리하는 편이 낫습니다.
- **우선순위 사유:** 필수가 아닙니다. 프론트 처리로 화면은 정상입니다.

### (11.05 추가) R-45. AI 응답 완료 알림 종류 추가

- **담당 제안:** 민경님 / **화면:** 사이드바 문의 목록의 새 답변 점, 새 소식 / **관련:** NT-01~04
- **요청:** 알림 종류(현재 `ASSIGNED`·`FIN`)에 AI 응답 완료를 더해 주세요. 문의자가 다른 화면에 있을 때 AI가 답하면 해당 문의에 안 읽은 알림이 생기고, 문의를 열면 읽음 처리(NT-04와 같은 방식)되면 됩니다.
- **현재 이슈 사항:** AI가 새로 답해도 알림이 없어서 문의 목록의 새 답변 점이 켜지지 않습니다. 프론트는 임시로 문의의 마지막 변경 시각(`updatedAt`)이 마지막으로 본 시각보다 늦으면 점을 켜지만, 이 브라우저에만 기록되고 다른 기기에서는 따로 쌓이며 처음 쓰는 브라우저의 첫 화면에는 점이 켜지지 않습니다.
- **우선순위 사유:** 필수가 아닙니다. 임시 처리로 같은 브라우저에서는 동작합니다. 반영되면 프론트의 임시 기록(`inquirySeen`)을 걷어냅니다.

### (11.05 추가) R-46. 목록 응답에 상태별 건수 함께 제공 (R-02 구체화)

- **담당 제안:** 민경님 / **화면:** 전체 문의·계정 관리·처리할 문의·문의 내역의 상태 탭 건수 / **관련:** R-02, TK-05, US-01, IQ-02
- **요청:** 목록 응답(`GET /tickets`, `GET /users`, `GET /inquiries`)에 현재 검색어·필터를 그대로 적용한 **상태별 건수**를 함께 내려주세요. 예: `statusCounts: { "RDY": 3, "WIP": 5, "FIN": 1, "CLS": 7 }`. 상태 조건 자체(`workStatus`·`accountStatus`·`displayStatus`)만 빼고 세고, 나머지 조건(검색어·분류·긴급도·팀·담당자·기간 등)은 목록과 같게 적용합니다.
- **현재 이슈 사항:** 검색하면 탭의 숫자도 검색 결과에 맞게 바뀌도록 프론트를 고쳤는데, 서버가 상태별 건수를 주지 않아 탭마다 `size=1` 요청으로 `totalCount`만 읽습니다. 전체 문의는 6개, 계정 관리는 3개, 처리할 문의는 4개의 요청이 목록 요청과 별도로 추가됩니다(검색어를 멈춘 뒤 0.25초 기다려 보냅니다). 문의 내역은 최근 100건을 읽어 세는 방식이라 100건을 넘으면 상태별 숫자가 100건 안에서만 맞습니다.
- **우선순위 사유:** 필수가 아닙니다. 지금도 동작하고, 서버가 주면 프론트의 추가 요청을 목록 요청 하나로 줄입니다.

### (11.05 추가) R-47. 가이드 목록에서 적재 실패·진행 중인 버전이 있는지 함께 제공

- **담당 제안:** 민경님 / **화면:** 가이드 관리(목록의 빨간 점, 사이드바 가이드 관리 점) / **관련:** DC-01, DC-05, DC-08, R-38
- **요청:** 문서 목록(`GET /documents`, ADMIN) 응답의 각 문서에 버전 적재 요약을 넣어 주세요. 예: `ingestSummary: { failed: 1, pending: 0 }` (각각 `ingest_status = FAILED`·`PENDING`인 버전 수). 가능하면 마지막 실패 사유(`lastIngestError`)도 함께 주세요.
- **현재 이슈 사항:** 적재 상태(`ingestStatus`·`ingestError`)는 문서의 버전 목록(DC-05)에만 있고, 문서 목록에는 없습니다. 그래서 프론트는 "이 브라우저에서 올리거나 펼쳐 본 버전"의 실패만 브라우저 저장소에 기억해 빨간 점을 켭니다. 그 결과 (1) 다른 관리자가 올린 버전이나 펼쳐 본 적 없는 버전의 실패는 모릅니다. (2) 기록은 이 브라우저에만 남아 다른 컴퓨터에서는 점이 없습니다. (3) 실패했던 버전이 지워지거나 바뀌어도 기록이 남아 점이 계속 켜집니다(11.05 실서버 테스트에서 확인: 보이는 버전은 모두 "준비 완료"인데 점만 남음). 프론트가 목록을 읽을 때마다 없는 버전의 기록을 지우도록 보완하겠지만, 서버 값으로 대체하는 쪽이 정확합니다.
- **반영되면:** 프론트는 브라우저 저장소 추적을 걷어내고 목록 응답만으로 점·"적재 실패 N건" 안내를 보여 줍니다.
- **참고:** 업로드한 파일명은 요청하지 않습니다. 버전에는 이미 `registeredAt`(올린 시각)과 `registeredByUser`가 있어 프론트가 "올린 시각"과 "방금 올림(24시간)" 표시에 쓰겠습니다.
- **우선순위 사유:** 필수가 아닙니다. 프론트 보완으로 동작하며, 서버가 주면 다른 관리자·다른 기기에서도 정확해집니다.

## 3. Should — 이번에는 후순위로 둘 작업

새 API나 응답 확장이 필요한 미완료 항목입니다. 당장 화면을 쓰는 데 필요한 최소 경로가 있어, **이번 마감에서는 기존 기능을 사용하고 확장은 미루는 안**입니다.

### R-01·R-02·R-13·R-19. 집계 확장과 요청 횟수 개선

- **화면:** 관리자 대시보드·통계, 담당자 통계·팀 현황, 계정·문의 목록
- **이미 있음:** OP-01 `overview`, OP-02 `me`, OP-03 `ai-usage`. 관리자 통계와 담당자 통계의 일부는 서버 집계에 연결돼 있습니다. `overview.trend.aiResolvedCount`와 접수일 기준 `closedCount`도 있습니다.
- **남은 범위:** 기간과 무관한 현재 RDY/WIP/FIN·확인 필요 원인별 건수·긴급 상위 N건(R-01), 목록의 상태별 건수 동시 제공(R-02), 개인별 긴급도 분포(R-13), 미확인·미연결 종료의 기간별 추이(R-19), `/me`의 추이·긴급도 분포입니다.
- **이번 제안:** 기존 집계를 유지하고 새 집계 API는 미룹니다. 프론트 목록 기반 집계는 최대 100건 제한으로 누락될 수 있으므로 전체 집계인 것처럼 단정하지 않도록 확인합니다. R-02 본문에 잘못 섞여 있던 대시보드 설명은 여기로 합쳤습니다.

### R-03·R-04·R-05·R-06·R-07. 목록 필터·검색·정렬 확장

- **화면:** 처리할 문의·전체 문의·문의 내역·계정 관리
- **이미 있음:** TK-05 `assignStatus` 필터. 기존 검색·정렬과 문의 표시 상태를 사용한 조회는 가능합니다.
- **남은 범위:** TK-05의 `transitionStatus`·배정 전을 포함한 미완료 필터(R-03), 제목·접수번호·분류·담당자 정렬과 이름 검색(R-04·05), 사용자 부서 검색·부서/역할/상태 정렬(R-06), 문의 제목/분류/상태 정렬·가이드 제목 검색·사용한 가이드 필드(R-07)입니다.
- **이번 제안:** 지원되는 조건만 화면에 노출하고 확장은 미룹니다. 다만 관리자 확인 필요 접수를 빠뜨리는 문제가 실제로 확인되면 ADMIN-01(Must)과 관련되므로 해당 누락만 먼저 고칩니다.

### R-10. 접수 목록에 실제 오류 사유·발생 시각 추가

- **화면:** 운영 현황
- **이미 있음:** `integration-jobs`에 `lastError`·작업 생성/갱신 시각이 있습니다. 오류 원문 자체가 전혀 없는 상태는 아닙니다.
- **남은 범위:** 접수 응답에 요약 사유와 실제 오류 발생 시각을 포함해 개별 이력 조회를 줄이는 일입니다. 작업 `createdAt`은 오류 발생 시각과 같다고 볼 수 없습니다.
- **이번 제안:** 새 필드 추가는 미루고, 상세 확인에는 기존 작업 이력을 사용합니다. 주요 이력 통합 표시는 하단 R-15에 분리했습니다.

### R-11·R-33·R-38. 처리 상태·변경 신호·적재 알림

- **화면:** 문의 대화·사이드바·담당자/관리자 목록·가이드 관리
- **이미 있음:** NT-01~04와 `ASSIGNED`·`FIN` 알림, 안 읽은 개수 조회, 접수 읽음 처리. 기존 폴링으로 화면을 갱신할 수 있습니다.
- **남은 범위:** AI 처리 중 필드(R-11), 변경 요약 조회 또는 SSE/웹소켓(R-33), 적재 완료·실패 알림 종류 추가(R-38)입니다.
- **이번 제안:** 상시 연결·새 알림 배치는 만들지 않고 기존 조회를 유지합니다. 읽기 중복·주기는 프론트에서 관리합니다. 현재 대화 기본 주기는 10초이며 상태에 따라 느리게 읽거나 멈추고, 접수 목록은 15초입니다. 이전 ‘대화 4~8초’ 설명은 삭제했습니다.
- **나중에 할 경우:** 알림/신호는 본인·권한 범위, 토큰 만료·로그아웃, 재연결, 중복 이벤트를 함께 설계해야 합니다. 한 번의 대화 조회는 문의·메시지·필요 시 접수 상세의 2~3개 요청이므로 전송량 개선도 같이 검토합니다.

### R-20. 보안·감사 알림 관리 기능

- **화면:** 보안·감사 알림
- **이미 있음:** 로그인 차단·긴급 징후 미접수 종료 등 일부 이벤트의 감사 기록과 OP-04 조회. `actor`에는 수행자 이름도 있습니다. 전용 보안 알림 화면은 여전히 시연 데이터입니다.
- **남은 범위:** 이벤트별 감지 범위 보완, 보안 알림 목록·상세·원문 열람·사유 기록·확인/종결 상태 관리입니다. 감사 로그 조회와는 다른 기능입니다.
- **이번 제안:** 새 관리 테이블·API·감지 기능 확대는 미룹니다. 기존 민감정보 보호·접근 제한·필수 긴급 종료 기록(Must)은 유지합니다. 원문 보관을 새로 허용하는 결정도 포함하지 않습니다.

### R-29. 접수 전후 선택·카드 저장 — 서버 반영, 프론트 작업 필요

- **담당 제안:** 프론트 / **화면:** 문의 대화 / **관련:** IQ-04·07·09, TK-01·03·04·07, [메시지 종류](02.문의_상담.md)
- **서버 변경:** 누른 버튼과 카드 자리를 `messages`에 저장합니다. 문구는 저장하지 않으며 화면이 정합니다. `Message`에 `kind`, `code`, `draft`(IQ-07의 `DRAFT_CARD`만)가 추가되고, `content`는 `TEXT`·`NOTICE` 외에는 `null`입니다.
- **대화 순서 예:** AI 답변 → `UNRESOLVED` → `CONNECT` → `DRAFT_CARD` → `CONFIRM` → `TICKET_CARD`
- **요청 — 재구성 코드 제거:** `toMessages`에서 상태값으로 말풍선과 카드를 만드는 부분, `RESOLVED_NOTICE` 거르기를 걷어내 주세요. 그대로 두면 말풍선과 카드가 두 번 보입니다.
- **요청 — `code`별 문구 (`CHOICE`):** 지금 모의(`chatEngine`) 문구를 그대로 쓰면 됩니다.
  - `RESOLVED`: `해결` 말풍선과 AI 해결 안내
  - `UNRESOLVED`: `미해결` 말풍선과 담당자 연결 안내
  - `CONNECT`: `담당자 연결` 말풍선
  - `NO_CONNECT`: `미연결 (종료)` 말풍선과 종료 안내
  - `CONFIRM`: `접수하기` 말풍선
  - `CANCEL`: `접수 안 함` 말풍선과 종료 안내
  - `TICKET_RESOLVED`: `해결` 말풍선
  - `TICKET_UNRESOLVED`: `미해결` 말풍선. 뒤이어 남은 증상(`TEXT`)이 옵니다.
- **요청 — 카드 표시:**
  - `DRAFT_CARD`: 초안 안내 문구와 `draft` 카드. `draft.status`가 `EDITING`일 때만 수정·접수·취소를 보여 주고, 그 밖에는 읽기 전용입니다.
  - `TICKET_CARD`: 접수 또는 재확인 안내 문구와 진행 카드. 접수번호는 문의의 `ticket.receiptNo`로 채웁니다. 재확인 요청으로 여러 개일 수 있으니 현재 진행 카드는 마지막 하나만 보여 주세요. 지난 시점의 상태는 저장하지 않습니다.
- **요청 — 단계 판단:** `isAnswering`, `stepOf`, 답변 생성 실패 안내처럼 마지막 메시지의 `sender`를 보는 곳은 `kind === 'TEXT'`인 메시지만 보아 주세요. 선택은 `USER`로 저장되므로 그대로 두면 답변 대기나 연결 제안으로 잘못 판단합니다.
- **요청 — `content` null 처리:** `content`를 문자열로 가정하는 코드를 확인해 주세요. `NOTICE`는 지금처럼 민감정보 안내로 표시합니다.
- **기존 문의:** `db/backfill_action_messages.py`로 보정합니다. 완료된 접수의 이전 `미해결`과 처리 후 재요청(FIN → WIP) 왕복은 남은 기록이 없어 복원되지 않습니다.
- **범위 밖:** 문의자용 긴급 종료 보안 안내는 포함하지 않습니다. 관리자 전용 판단 이력을 문의자 화면에서 읽는 방식으로 대체하지 않습니다.

## 7. 배포 후 확인 요청 — 프론트 반영분 (2026-11-05)

프론트에서 반영을 마쳤고, 실제 서버에서 아직 시험하지 못한 것입니다. 확인되면 이 항목을 지워 주세요.

- **http 서버에서 문의 전송 (PR #284):** http 주소(`crypto.randomUUID` 없는 환경)에서 새 문의 전송, 상담 중 추가 질문 답변(IQ-08), 해결·미해결(IQ-09)이 모두 나가는지. 요청 중 예외가 나도 대기 화면이 무한 대기가 아니라 오류 문구와 "다시 시도"로 바뀌는지.
- **외부 전송 정책 완화 사유 (R-22, PR #286):** 완화(`금지 → 허용` 등)는 사유 없이 거절되고(`reason` / `REQUIRED`), 사유를 넣으면 변경되며 운영 기록(OP-04)에 사유가 남는지. 엄격하게 바꿀 때는 사유 없이도 되는지.
- **FAQ 출처 지정·수정 (R-41·R-35, PR #289):** 출처 가이드를 고르고 등록하면 문의자 FAQ에 보이고 출처가 열리는지, 출처 없이는 막히는지. FAQ 수정에서 출처를 바꾸면 통째로 교체되는지(FQ-04), "바로 게시"를 켜고 끌 때 게시 상태가 맞는지.
- **출처 선택 목록의 부하:** FAQ 등록 창은 가이드 목록(`/documents`)을 한 번 읽습니다. 가이드가 매우 많을 때 느려지지 않는지.
- **AI 상세 패널의 가이드·과거 처리 사례 (PR #292, #293):** 과거 처리 사례를 참고한 문의의 AI 처리 상세에서 "참고한 과거 처리 사례" 묶음과 사례 본문(`excerpt`)이 맞게 나오는지, 사례가 여러 건일 때 건수가 맞는지. 가이드 칩을 누르면 근거 본문이 열리는지.
- **가이드 그림(DC-11)·FAQ 출처 본문(R-30, PR #293):** 그림이 있는 가이드를 출처로 쓴 답변·FAQ의 출처 미리보기에서 `[그림] 설명` 줄이 실제 그림으로 보이는지(`GET /guide-images/{key}`가 토큰으로 열리는지), 그림이 없는 줄은 설명 상자로 남는지. FAQ 출처에서 본문이 나오고, 문서만 지정한 출처는 안내 문구가 나오는지.
- **FAQ 등록·수정의 분류별 출처 목록 (PR #293):** 분류를 바꾸면 그 분류의 전 직원용 현행 가이드로 목록이 바뀌는지.
- **계정 변경 이력 (R-14, PR #295):** 계정 화면의 "계정 변경 이력"에 운영 기록이 최근순으로 보이는지(다른 관리자가 한 변경 포함), 수행자와 변경 대상(사번 · 이름)이 맞게 나뉘는지, 목록에 없는 사용자는 번호로 나오는지.
- **처리 이력의 담당자 배정(R-15, 이번 PR):** 접수 상세 "처리 이력"에 담당 그룹 추천·배정·재배정·배정 실패가 상태 변경과 시간순으로 함께 보이는지(`GET /tickets/{id}/assignment-logs`). 관리자가 재배정하고 실행기가 Jira에 반영한 뒤 "담당자 재배정 · 이름 (그룹)"과 재배정 사유가 남는지. 담당 그룹 밖 담당자에게는 이 이력이 `404`로 와서 상태 이력만 보이는 것이 맞는지.
- **운영 기록의 접수번호(R-40, 이번 PR):** 접수·문의 대상 기록의 구분 칸에 접수번호가 보이고, 누르면 화면은 그대로 두고 오른쪽에 그 접수의 상세 패널이 열리는지. 연결된 접수가 없는 문의 기록은 접수번호 없이 보이는지.
- **계정 추가 필수 선택(이번 PR):** 부서·직급·역할을 고르지 않으면 서버에 보내지 않고 막히는지, 직급(팀원·팀장·조직장)이 서버에서 받아들여지는지.
- **서버 테스트 3차 수정(이번 PR):** 문의자 상세에서 "세부 유형 … 기본 긴급도" 문구가 안 보이는지, Jira 티켓이 없을 때 "생성 전"이 깨지지 않는지, 이어가기 창을 ✕로 닫은 뒤 해결·미해결을 바로 누를 수 있는지, 같은 출처 버튼이 한 번만 보이는지, AI가 새로 답했을 때 다른 화면의 사이드바에 새 답변 점이 켜지는지(목록 갱신 주기 120초), 문의자 화면 콘솔에 `assignment-logs` 404가 더 이상 안 뜨는지.
- **검색할 때 상태 탭 건수(이번 PR):** 전체 문의·AI 처리·계정 관리·처리할 문의·문의 내역에서 검색어·필터를 걸면 상태 탭의 숫자가 검색 결과에 맞게 바뀌고, 지우면 전체 숫자로 돌아오는지. 탭 숫자의 합이 목록의 "총 N건"과 같은지. 검색어를 칠 때 서버에 요청이 몰리지 않는지(멈춘 뒤 0.25초 기다려 보냄).

- **R-37:** 문의를 시작할 때 민감정보를 가린 사용자 글의 첫 줄로 기본 제목(최대 40자)을 저장하고, 첫 판단이 생기면 AI 제목으로 바꿉니다. IQ-01이 `503`으로 실패한 문의도 목록에 제목이 보입니다. 모델 오류로 판단이 남는 경우는 지금처럼 `IT 문의 (자동 분류 실패)`입니다. 기본 제목은 Jira로 보내지 않고, 판단 없이 접수되면 Jira 제목은 문의 요약입니다.
- **R-22:** DC-09가 `reason`을 받아 `DOCUMENT_POLICY_CHANGE` 기록에 저장합니다. `BLOCKED` → `MASKED`·`ALLOWED`, `MASKED` → `ALLOWED`로 바꿀 때는 필수이고, 없으면 `422 VALIDATION_ERROR`(`reason` / `REQUIRED`)입니다. 프론트는 `setGuideTransfer`가 PATCH 본문에 `reason`을 넣어 보내도록 반영했습니다.
- **R-41·R-35:** FQ-03·FQ-04가 `sourceDocumentIds`를 받아 FAQ와 문서의 연결을 저장합니다. 활성 문서의 현행 버전이고 열람 범위가 ALL인 GUIDE만 허용합니다. 게시 조건·FQ-02 출처·자동 게시 중단이 이 연결을 함께 봅니다. 기존 `meta.faq_ids` 연결도 그대로 인정합니다. 프론트는 FAQ 등록 창의 문서 선택과 '바로 게시' 복구를 연결해 주세요. 마이그레이션 `a3d94f7c1e62` 적용이 먼저 필요합니다.
- **R-30:** FQ-02의 `FaqSource`에 `excerpt`를 추가했습니다. 청크로 연결된 출처는 본문을 주고, 문서를 직접 지정한 출처는 `excerpt`·`location`이 모두 `null`입니다. 열람 범위 밖 출처는 지금처럼 응답에서 빠집니다.
- **R-39:** 적재가 `PENDING`에 남는 경우 서버가 시작 때와 그 뒤 5분마다 10분 넘은 버전을 다시 적재합니다 (`EMBEDDING_PRELOAD=true`인 서버만). DB 연결이 끊긴 동안에는 실패 상태도 기록할 수 없어 재시도로 처리했고, 화면·API 변경은 없습니다. DB 풀은 `DB_POOL_SIZE`·`DB_MAX_OVERFLOW`로 설정하며 코드 기본값은 5+5입니다. 팀 전체 연결 한도가 15개라는 기존 기록은 서버 설정을 확인해야 하므로 확정값으로 쓰지 않습니다.
- **기존 기능으로 대체:** R-14의 새 이력 조회 API, R-15의 새 통합 이력 API. 남은 프론트 작업은 위 기록만 참고합니다.
- **검수 범위:** API·서비스·프론트 코드 대조와 문서 정리입니다. 실제 DB/API 테스트나 배포 확인을 통과했다는 의미는 아닙니다.


## (11.04-오후10시 추가) 확인이 필요한 표시 문구 — 운영 기록·AI 판단 이력

서버 코드와 대조한 답변입니다 (2026-11-05, `develop` 기준). 화면 수정이 필요한 곳은 **프론트 확인**으로 표시했습니다. 프론트 사전은 `frontend/src/api/auditLogs.ts`, `frontend/src/api/assessments.ts`입니다.

- **1. 재배정 기록의 결과 값:** 표시가 맞습니다. 담당자가 없던 접수의 배정이 `ASSIGN`, 있던 접수의 변경이 `REASSIGN`, 정할 사람이 없을 때가 `FAIL`입니다. 운영 기록(`/audit-logs`)에는 이 세 값만 옵니다. `RECOMMEND`는 접수 확정 때 `assignment_logs`에만 남으므로, 배정 이력(`assignment-logs`)을 표시하는 화면에서는 올 수 있습니다.
- **2. 운영 기록 이벤트 목록:** 현재 서버가 남기는 값은 프론트 사전의 20가지와 같습니다. `CLASSIFY`·`ASSIGN`은 운영 기록에 남지 않아 [05.기준정보_운영](05.기준정보_운영.md) OP-04의 예시를 실제 목록으로 고쳤습니다. 응답 예시의 `result`도 실제 값(`REASSIGN`)으로 고쳤습니다.
- **3. 결과 값 목록:** 적어 주신 목록이 전부입니다. 다만 `FAIL`·`AI_FAILED`의 `reason`에는 내부 오류 코드가 그대로 들어갑니다.
- **4. `FAIL` 사유의 `④`:** [민감정보 정책](../10.민감정보_정책.md) 4장의 네 번째 적용 지점인 "외부 모델 호출 직전"을 뜻하는 내부 번호입니다. 관리자에게는 의미가 없는 표시입니다. **프론트 확인:** 화면에서 `④ `를 떼고 보여 주세요. 이미 쌓인 기록이 있어 서버 문구는 그대로 둡니다.
- **5. `URGENT_CLOSED`:** 결과는 항상 `CLOSED_UNRESOLVED`입니다. 문의 판단 이력에 긴급 징후가 한 번이라도 있었는데 접수 없이 닫힐 때(문의 종료, 초안 취소) 남으므로 표시가 맞습니다.
- **6. 문서 기록의 결과 글 모양:** 적어 주신 모양이 맞습니다. 추가로 `DOCUMENT_VERSION_ACTIVATE`는 이전 현행이 없으면 `없음 → v1`입니다. 구조화된 값은 이번에 추가하지 않았고, 형식을 바꾸면 알려 드리겠습니다.
- **7. 계정 상태 `INACTIVE`:** "이용 제한"이 맞습니다. 서버 오류 문구도 "이용이 제한된 계정"을 씁니다.
- **8. AI 판단 이력의 추가 질문:** 판단은 문의 시작과 추가 질문의 답변에서만 생기고, 답변은 직전 판단이 `ASK_MORE`일 때만 받으므로 순서는 맞습니다. 다만 AI 호출이 503으로 실패하면 사용자 글은 남고 판단은 남지 않습니다. 이때는 다음 판단 앞에 사용자 글이 둘 이상일 수 있어, "답 하나에 판단 하나"로 단정하지 말아 주세요. 항목 코드 5가지는 프론트 사전과 같습니다.
- **9. 사용한 가이드:** ADMIN은 다른 사람의 문의 메시지와 모든 열람 범위의 출처를 이 API로 조회할 수 있습니다. 중복 제거 기준(종류·문서·버전·위치)도 괜찮습니다. **프론트 확인:** `LEGACY`는 가이드가 아니라 과거 처리 사례이고 문서 코드가 없으므로, "사용한 가이드"에 섞어 보여 줄지 구분해 주세요.
