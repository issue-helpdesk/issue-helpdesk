### (11.05 추가, 11.07 수정) R-45. 알림 체계 보완 — AI 답변 완료를 비롯한 문의 단위 알림

- **담당 제안:** 민경님 / **화면:** 사이드바 문의 목록의 새 답변 점, 알림 종·알림 목록 / **관련:** NT-01~04, `notifications` 테이블
- **11.07 정정:** 처음에는 "알림 종류에 AI 응답 완료만 더해 달라"고 적었는데, 구조를 다시 보니 종류만 더해서는 안 됩니다. `notifications`는 `ticket_id`가 필수이고 `kind`는 `ASSIGNED`·`FIN` 두 가지로 제한돼 있습니다(`CheckConstraint`). AI 답변은 **접수 전(티켓이 없는) 단계**에서 생기므로 지금 구조로는 담을 수 없습니다.
- **어떤 상황에서 문제인가(예시):**
  1. 문의자가 새 문의를 보내고 "답변을 준비하고 있어요"가 보이는 동안 사이드바의 다른 문의나 FAQ 화면으로 이동합니다. 접수 전이라 티켓이 없습니다.
  2. 서버에서 AI 답변이 완성되어 저장됩니다. 이때 서버는 알림을 만들지 않습니다(알림이 티켓 기준이라 만들 수 없음).
  3. 문의자는 다른 화면에 있어서 답변이 왔는지 알 수 없습니다. 사이드바의 "최근 문의"에 새 답변 표시가 있어야 하는데, 서버 알림이 없으니 프론트가 임시 규칙으로 흉내 냅니다.
  4. 임시 규칙은 "문의의 마지막 변경 시각이 내가 마지막으로 본 시각보다 늦으면 새 답변"입니다. 그런데 내가 글을 보낸 직후나 AI 처리가 실패한 직후에도 변경 시각이 움직여서, 새 메시지가 없는데 점이 켜지는 경우가 11.07 실서버 테스트에서 확인됐습니다. 반대로 처음 쓰는 브라우저나 다른 기기에서는 점이 켜지지 않습니다.
  5. 담당자·관리자 쪽도 비슷합니다. 예를 들어 문의자가 "미해결"로 응답해 접수가 처리 중으로 되돌아와도(03 문서 TK-07의 재처리 흐름) 담당자에게 알림이 가지 않아 놓치기 쉽습니다.
- **지금 상황:**
  - 서버 알림은 두 가지입니다. `ASSIGNED`는 담당자에게(배정 확인·Jira 담당자 변경 반영 때), `FIN`은 문의자에게(처리 완료 때) 갑니다. 프론트의 알림 종·알림 목록(11.06)은 이 두 가지만 보여 주고, 누르면 해당 티켓·문의로 이동하며 읽음 처리(NT-04)합니다.
  - AI 새 답변은 알림이 없어서 프론트가 임시 규칙(문의의 `updatedAt`이 이 브라우저에서 마지막으로 본 시각보다 늦으면 점을 켬)으로 점을 켭니다. **이 규칙은 알림을 쓰지 못합니다.** 서버 알림과 별개이고 이 브라우저에만 기록됩니다.
  - 11.07 실서버 테스트에서 이 규칙의 한계가 확인됐습니다. 내 글을 저장하거나 AI 처리가 실패해도 `updatedAt`이 바뀌어서, 새 메시지가 없는데 점이 켜지는 경우가 있습니다. 프론트에서 완화하겠지만 서버 알림 없이는 완전히 막을 수 없습니다.
- **근본적으로 필요한 알림(수신자별 제안):**

| 수신자 | 알림 | 지금 | 비고 |
|---|---|---|---|
| 문의자 | AI 답변 완료(다른 화면에 있을 때) | 없음 | 접수 전이라 문의 단위. 이번 요청의 핵심 |
| 문의자 | 처리 완료(해결 확인 요청) | `FIN` 있음 | 그대로 |
| 문의자 | 담당자 배정·처리 시작 | 없음 | 후순위. 문의 상세에서 상태로 확인 가능 |
| 담당자 | 새 배정 | `ASSIGNED` 있음 | 그대로 |
| 담당자 | 재배정으로 담당에서 빠짐 | 없음 | 후순위 |
| 담당자 | 문의자의 미해결 응답(처리 중으로 되돌아옴) | 없음 | 놓치기 쉬운 재처리 건 |
| 관리자 | 확인 필요 발생(연동 실패·배정 확인 필요) | 없음 | 운영 현황 카드와 배지로 대체 중 |
| 관리자 | 가이드 적재 완료·실패 | 없음 | R-38 |
| 관리자 | 보안·감사 알림 | 없음 | R-20, SA-01~06과 함께 정리 |

- **요청(최소 범위):**
  1. `notifications`를 문의 단위로도 쓸 수 있게 `inquiry_id`를 두고 `ticket_id`를 비울 수 있게 해 주세요.
  2. `kind`에 AI 답변 완료(예: `AI_REPLY`)를 추가해 주세요. 수신자는 문의자이고, 문의를 열면 읽음 처리(NT-04와 같은 방식, 문의 기준으로도 호출 가능하게)됩니다.
  3. 알림 목록·안 읽은 수 응답에 `inquiryId`가 이미 있으면 그대로, 티켓 없는 알림도 내려줄 수 있는지 확인해 주세요.
  - 위 표의 나머지 알림은 이번 요청에 넣지 않았고, 필요해지면 같은 구조에 `kind`만 더하면 됩니다.
- **프론트 처리:** 반영되면 임시 기록(`inquirySeen`)을 걷어내고 안 읽은 알림 기준으로 점을 켭니다. 알림 종·목록은 새 종류의 문구와 이동 위치만 더합니다.
- **우선순위 사유:** 필수가 아닙니다. 임시 규칙으로 같은 브라우저에서는 동작하고, 알림 목록은 `ASSIGNED`·`FIN`으로 동작합니다.

### (11.05 추가) R-47. 가이드 목록에서 적재 실패·진행 중인 버전이 있는지 함께 제공

- **담당 제안:** 민경님 / **화면:** 가이드 관리(목록의 빨간 점, 사이드바 가이드 관리 점) / **관련:** DC-01, DC-05, DC-08, R-38
- **요청:** 문서 목록(`GET /documents`, ADMIN) 응답의 각 문서에 버전 적재 요약을 넣어 주세요. 예: `ingestSummary: { failed: 1, pending: 0 }` (각각 `ingest_status = FAILED`·`PENDING`인 버전 수). 가능하면 마지막 실패 사유(`lastIngestError`)도 함께 주세요.
- **현재 이슈 사항:** 적재 상태(`ingestStatus`·`ingestError`)는 문서의 버전 목록(DC-05)에만 있고, 문서 목록에는 없습니다. 그래서 프론트는 "이 브라우저에서 올리거나 펼쳐 본 버전"의 실패만 브라우저 저장소에 기억해 빨간 점을 켭니다. 그 결과 (1) 다른 관리자가 올린 버전이나 펼쳐 본 적 없는 버전의 실패는 모릅니다. (2) 기록은 이 브라우저에만 남아 다른 컴퓨터에서는 점이 없습니다. (3) 실패했던 버전이 지워지거나 바뀌어도 기록이 남아 점이 계속 켜집니다(11.05 실서버 테스트에서 확인: 보이는 버전은 모두 "준비 완료"인데 점만 남음). 프론트가 목록을 읽을 때마다 없는 버전의 기록을 지우도록 보완하겠지만, 서버 값으로 대체하는 쪽이 정확합니다.
- **반영되면:** 프론트는 브라우저 저장소 추적을 걷어내고 목록 응답만으로 점·"적재 실패 N건" 안내를 보여 줍니다.
- **참고:** 업로드한 파일명은 요청하지 않습니다. 버전에는 이미 `registeredAt`(올린 시각)과 `registeredByUser`가 있어 프론트가 "올린 시각"과 "방금 올림(24시간)" 표시에 쓰겠습니다.
- **우선순위 사유:** 필수가 아닙니다. 프론트 보완으로 동작하며, 서버가 주면 다른 관리자·다른 기기에서도 정확해집니다.

### (11.07 추가) R-48. 가이드 본문(원문) 조회

- **우선순위 사유:** 필수가 아닙니다. 다만 문의자·담당자가 가이드를 직접 찾아 읽는 화면이 이 API에 달려 있습니다.

  1. 접수 후 배정(`JIRA_ASSIGN`)이 실패해서 접수가 "담당자 배정 확인 필요"(`assignStatus = NEEDS_ADMIN`)가 됩니다.
  2. 담당자를 Jira에서 직접 정해서 바꿨습니다(예: 박서연).
  3. ITssue 화면에는 여전히 "배정 확인 필요", 담당자 "배정 전"입니다. 직접 정한 담당자의 "처리할 문의"에도 이 건이 없고, 문의자의 접수 카드는 "담당자 배정 · 운영자 확인 중"으로 남습니다.
  4. 전체 문의에는 이 건이 "확인 필요"로 보이는데, 운영 현황 카드에서는 찾기 어려웠습니다. 카드가 기본 3건만 보여 주고 나머지는 "나머지 N건 보기"로 펼치는 방식이라 가려졌을 가능성이 있어 프론트에서 확인 중입니다.
- **원인으로 보이는 서버 동작(코드 확인, 서버 담당 확인 요청):**
  - `sync_assignee`는 재처리를 기다리는 실패 작업(`JIRA_ASSIGN`이 `FAILED`·`NEEDS_ADMIN`이고 다른 작업이 `retry_of_job_id`로 이어받지 않은 것)이 있으면 Jira 담당자 변경을 일부러 반영하지 않습니다(관리자 판단을 웹훅이 덮어쓰지 않기 위한 의도).
  - 그래서 실패 작업이 열려 있는 동안 Jira에서 직접 바꾼 담당자는 ITssue에 들어오지 않고, 해결하려면 운영 현황의 재처리(TK-12)나 TK-09 재지정을 해야 합니다.
  - 또 TK-09로 새로 지정해 성공해도 옛 실패 작업이 "재처리됨"으로 이어지지 않으면 계속 열린 실패로 남아, 이후의 Jira 직접 변경도 계속 무시될 수 있습니다.
- **정책 제안(정해야 하는 것):** Jira에서만 처리하도록 막기보다 **ITssue를 기준으로 하되 Jira 직접 변경도 받아들이는 양방향을 유지**하고, **충돌은 사람이 고르게** 하는 방향입니다. 근거: 요구사항 ASSIGN-05·ADMIN-01은 ITssue의 재배정(사유·이력)을 전제로 하고, 정상 상태에서는 이미 양방향으로 동작합니다.
- **요청:**
  1. 실패 작업이 열려 있어 Jira 담당자 변경을 반영하지 못한 접수는 그 사실과 Jira 담당자를 접수 응답에 내려주세요(예: `jiraAssignee { accountId, userId?, name }`, `assignConflict: true`).
  2. 관리자가 "Jira 담당자 그대로 받아들이기"를 고르면 서버가 실패 작업을 닫고(재처리됨/해결됨으로 표시) Jira 담당자를 반영하는 동작을 주세요. 예: `POST /tickets/{id}/integration-jobs`에 `resolution: ACCEPT_JIRA`. 이 담당자가 그룹 구성원이 아니면 지금처럼 확인 필요로 남기고 이유를 알려 주세요.
  3. TK-09 또는 TK-12로 새 배정이 성공하면 이전에 열려 있던 `JIRA_ASSIGN` 실패 작업을 "대체됨"으로 닫아서, 이후 Jira 직접 변경이 계속 무시되지 않게 해 주세요.
- **화면 처리(프론트):** 접수 상세 패널(운영 현황의 두 카드에서 열림)에서 "담당자 지정"·"ITSM 확인·재시도"를 바로 할 수 있게 했습니다(11.07). 위 요청이 반영되면 충돌 상황에서 "Jira 담당자(○○) 그대로 받아들이기 / 내가 정한 담당자로 다시 시도" 두 단추를 같은 패널에 더합니다.
- **우선순위 사유:** 후순위가 아닙니다. 배정 실패는 연동 중 가장 자주 만나는 운영 문제이고, 지금은 Jira에서 직접 고쳐도 ITssue가 따라오지 않아 문의자 화면에도 "운영자 확인 중"이 계속 남습니다.

## 3. Should — 이번에는 후순위로 둘 작업

새 API나 응답 확장이 필요한 미완료 항목입니다. 당장 화면을 쓰는 데 필요한 최소 경로가 있어, **이번 마감에서는 기존 기능을 사용하고 확장은 미루는 안**입니다.

### R-01·R-02·R-13·R-19. 집계 확장과 요청 횟수 개선

- **화면:** 관리자 대시보드·통계, 담당자 통계·팀 현황, 계정·문의 목록
- **이미 있음:** OP-01 `overview`, OP-02 `me`, OP-03 `ai-usage`. 관리자 통계와 담당자 통계의 일부는 서버 집계에 연결돼 있습니다. `overview.trend.aiResolvedCount`와 접수일 기준 `closedCount`도 있습니다.
- **남은 범위:** 기간과 무관한 현재 RDY/WIP/FIN·확인 필요 원인별 건수·긴급 상위 N건(R-01), 목록의 상태별 건수 동시 제공(R-02), 개인별 긴급도 분포(R-13), 미확인·미연결 종료의 기간별 추이(R-19), `/me`의 추이·긴급도 분포입니다.
- **이번 제안:** 기존 집계를 유지하고 새 집계 API는 미룹니다. 프론트 목록 기반 집계는 최대 100건 제한으로 누락될 수 있으므로 전체 집계인 것처럼 단정하지 않도록 확인합니다. R-02 본문에 잘못 섞여 있던 대시보드 설명은 여기로 합쳤습니다.

### R-03·R-04·R-05·R-06·R-07. 목록 필터·검색·정렬 확장

- **화면:** 처리할 문의·전체 문의·문의 내역·계정 관리
- **이미 있음:** TK-05 `assignStatus` 필터. 기존 검색·정렬과 문의 표시 상태를 사용한 조회는 가능합니다.
- **남은 범위:** TK-05의 `transitionStatus`·배정 전을 포함한 미완료 필터(R-03), 제목·접수번호·분류·담당자 정렬과 이름 검색(R-04·05), 사용자 부서 검색·부서/역할/상태 정렬(R-06), 문의 제목/분류/상태 정렬·가이드 제목 검색·사용한 가이드 필드(R-07)입니다.
- **이번 제안:** 지원되는 조건만 화면에 노출하고 확장은 미룹니다. 다만 관리자 확인 필요 접수를 빠뜨리는 문제가 실제로 확인되면 ADMIN-01(Must)과 관련되므로 해당 누락만 먼저 고칩니다.

### R-10. 접수 목록에 실제 오류 사유·발생 시각 추가

- **화면:** 운영 현황
- **이미 있음:** `integration-jobs`에 `lastError`·작업 생성/갱신 시각이 있습니다. 오류 원문 자체가 전혀 없는 상태는 아닙니다.
- **남은 범위:** 접수 응답에 요약 사유와 실제 오류 발생 시각을 포함해 개별 이력 조회를 줄이는 일입니다. 작업 `createdAt`은 오류 발생 시각과 같다고 볼 수 없습니다.
- **이번 제안:** 새 필드 추가는 미루고, 상세 확인에는 기존 작업 이력을 사용합니다. 주요 이력 통합 표시는 하단 R-15에 분리했습니다.

### R-11·R-33·R-38. 처리 상태·변경 신호·적재 알림

- **화면:** 문의 대화·사이드바·담당자/관리자 목록·가이드 관리
- **이미 있음:** NT-01~04와 `ASSIGNED`·`FIN` 알림, 안 읽은 개수 조회, 접수 읽음 처리. 기존 폴링으로 화면을 갱신할 수 있습니다.
- **남은 범위:** AI 처리 중 필드(R-11), 변경 요약 조회 또는 SSE/웹소켓(R-33), 적재 완료·실패 알림 종류 추가(R-38)입니다.
- **이번 제안:** 상시 연결·새 알림 배치는 만들지 않고 기존 조회를 유지합니다. 읽기 중복·주기는 프론트에서 관리합니다. 현재 대화 기본 주기는 10초이며 상태에 따라 느리게 읽거나 멈추고, 접수 목록은 15초입니다. 이전 ‘대화 4~8초’ 설명은 삭제했습니다.
- **나중에 할 경우:** 알림/신호는 본인·권한 범위, 토큰 만료·로그아웃, 재연결, 중복 이벤트를 함께 설계해야 합니다. 한 번의 대화 조회는 문의·메시지·필요 시 접수 상세의 2~3개 요청이므로 전송량 개선도 같이 검토합니다.

### R-20. 보안·감사 알림 관리 기능

- **화면:** 보안·감사 알림
- **이미 있음:** 로그인 차단·긴급 징후 미접수 종료 등 일부 이벤트의 감사 기록과 OP-04 조회. `actor`에는 수행자 이름도 있습니다. 전용 보안 알림 화면은 여전히 시연 데이터입니다.
- **남은 범위:** 이벤트별 감지 범위 보완, 보안 알림 목록·상세·원문 열람·사유 기록·확인/종결 상태 관리입니다. 감사 로그 조회와는 다른 기능입니다.
- **이번 제안:** 새 관리 테이블·API·감지 기능 확대는 미룹니다. 기존 민감정보 보호·접근 제한·필수 긴급 종료 기록(Must)은 유지합니다. 원문 보관을 새로 허용하는 결정도 포함하지 않습니다.
- **(11.06 개발 예정):** 서버에 `security_alerts` 테이블과 SA-01~06 명세([05.기준정보_운영](05.기준정보_운영.md), [07.API 설계서](../07.API_설계서.md) 4.7B)가 추가됐고 API 구현은 아직입니다. 서버 구현이 끝나면 프론트 `frontend/src/api/security.ts`의 시연 데이터를 이 API로 바꿔 연결합니다. 그 전까지 화면은 시연 데이터로 동작하며 "제안" 표시를 유지합니다.

### R-24. 문서 번호 자동 채번

- **화면:** 가이드 관리
- **남은 범위:** 서버의 문서 번호 자동 채번입니다. (버전 메모는 서버에 없고 요청하지 않기로 해서 화면에서도 뺐습니다.)
- **이번 제안:** 기존 입력·등록 경로를 사용하고 확장은 미룹니다. 문서 번호는 프론트가 계산하고 서버가 중복을 거절하므로 동시 등록 충돌 가능성이 있습니다.

## 4. Could — 이번 마감에서 제외할 확장 제안

### R-23·R-26·R-32·R-36. 분석·평가·추가 상담·응답 편의

- **R-23:** 해결 사례의 자정 유사도 분석·주제 묶음·AI 초안 생성. GUIDE-08의 자정 분석은 Could입니다. GUIDE-03의 관리자 검토·Guide 등록은 Should이므로 동일 우선순위로 단정하지 않되, 새 자동화 파이프라인은 이번에 시작하지 않는 안입니다. **(11.06 개발 예정):** 해결 사례의 가이드화는 개발을 받을 예정이며, 서버 API가 나오면 프론트 `guides.ts`의 해결 사례 묶음 호출(서버 모드에서 현재 사용 불가)을 연결합니다.
- **R-26:** Golden Set 결과 조회 API와 실제 평가 화면 연결(EXT-05, Could). 현재 품질 평가는 시연 데이터입니다. **(11.06 개발 예정):** 골든셋 평가는 개발을 받을 예정이며, 결과 조회 API가 나오면 프론트 `aiOps.ts`의 시연 데이터를 연결합니다.
- **R-32:** 로그인 전 실제 Guide 상담 API(PRE-01, Could). 현재 키워드 기반 시연 안내를 유지합니다.
- **R-36:** 같은 사용자의 동일 상태 변경 재요청에 진행 중 응답을 돌려주는 개선. SRS에 별도 우선순위가 없는 후순위 제안으로 이곳에 모았습니다. 프론트가 중복 버튼 잠금과 409 안내를 이미 처리하므로 필수 변경은 아닙니다.

### (11.06 추가) R-43. 캘린더 팀 일정 조회와 팀 필터 (후순위)

- **담당 제안:** 민경님 / **화면:** 캘린더(담당자·관리자) / **관련:** TO-01
- **요청 1 — 일반 담당자의 팀 일정 조회:** 일반 담당자(`AGENT`)도 같은 담당 그룹 구성원의 일정을 `GET /time-off`로 볼 수 있게 해 주세요(읽기만, 등록·수정·삭제는 지금처럼 본인 것만). 지금은 본인 일정만 내려와서, 화면의 "내 일정 / 팀 일정" 전환에서 팀 일정이 비어 보입니다.
- **요청 2 — 일정 응답에 소속 그룹:** 항목의 `user`에 담당 그룹(`groupId`, `groupName`)을 함께 내려주세요. 관리자 캘린더의 팀 필터가 이 값으로 바로 동작합니다. `groupId` 조건은 이미 있는 것으로 압니다.
- **현재 이슈 사항:** 팀 필터는 팀 구성원 표(RF-04)로 일정 주인을 팀에 맞춰 대응하고 있습니다. 그룹을 옮긴 사람의 지난 일정은 현재 소속으로 걸러질 수 있습니다.
- **우선순위 사유:** 필수가 아닙니다. 요청 1이 반영되지 않아도 화면은 서버가 주는 범위만 보여 주며 동작합니다. 요청 2가 없어도 구성원 표로 대체할 수 있습니다.
- **화면 처리:** 서버가 팀 일정을 주면 담당자 화면에서 별도 수정 없이 "팀 일정"에 보입니다.

### (11.04-오후9시 추가) R-42. 운영 기록 대상 표시 이름 제공 (후순위)

- **담당 제안:** 민경님 / **화면:** 운영 기록 / **관련:** LOG-01의 조회 편의 보완, R-40
- **요청:** OP-04(`/audit-logs`) 항목에 `targetLabel`을 함께 내려주세요. 접수는 접수번호, 문서는 문서 코드, FAQ는 FAQ 번호, 사용자는 이름·사번으로 하고, 문의처럼 사람이 쓰는 번호가 없는 대상은 null로 둡니다. 삭제된 대상도 기록 시점의 이름이 남도록 기록 때 함께 저장해 주세요.
- **현재 이슈 사항:** 응답에는 대상 종류와 내부 숫자 ID만 있어 화면이 사람이 알아볼 이름을 보여 줄 수 없습니다. 접수는 R-40의 `ticketId`·`receiptNo`로 제공되며, 이 요청은 같은 필요를 다섯 가지 대상 전체로 넓힌 것입니다. 진행할 때 접수 부분의 중복을 함께 정리해 주세요.
- **우선순위 사유:** 필수가 아닙니다. 프론트는 이 값이 없는 상태를 가정해, 대상 종류만 보이고 결과 칸의 코드(접수번호·문서 코드·FAQ 번호)를 활용합니다. 사용자 대상 기록은 계정 목록(US-01)에서 이름·사번을 찾아 보여 주고, 누르면 계정 관리로 연결합니다. 다른 대상의 링크는 접수번호만 있습니다.

## 5. 프론트에서 처리하거나 확인할 기록

추가 백엔드 기능 요청에서 제외했습니다. 이 문서 편집으로 아래 화면 작업을 실행한 것은 아닙니다.

- **R-09 — 출처 제목 (프론트만으로는 할 수 없음):** NT-01~04로 배정/FIN 알림 표시는 이미 연결했습니다. 문의 출처에 가이드 제목을 붙이려면 문서 목록을 읽어야 하는데 일반 사용자에게는 그 권한이 없습니다. **요청:** 문의 메시지의 `sources[]`(IQ)와 FAQ 출처(FQ-02)가 이미 주는 `docCode`·`version` 옆에 문서 제목 `title`도 함께 내려주세요. 없는 동안 화면은 문서 번호만 보여 줍니다. 필수가 아니라 후순위입니다.
- **R-15 — 처리 이력 통합(일부 반영):** 접수 상세 "처리 이력"이 상태 이력과 담당자 배정 이력(`assignment-logs`: 추천·배정·재배정·실패)을 시간순으로 합쳐 보입니다. 관리자 전용인 연동 작업(`integration-jobs`)은 담당자 화면에 무리하게 연결하지 않고 아직 합치지 않았습니다.
- **R-31 — 본문 서식 재확인 (서버 데이터가 있어야 확인 가능):** 현재 청크 생성과 검색 단위 복원 코드는 줄바꿈을 사용합니다. 따라서 ‘서버가 항상 줄바꿈을 없앤다’고 단정할 수 없습니다. 프론트는 줄바꿈이 없는 본문을 줄 단위로 복원해 보여 주는 보정을 이미 두고 있습니다. **요청:** 배포 환경에서 줄바꿈·제목·표가 깨져 보이는 출처가 있으면 그 문의(또는 FAQ)와 위치를 알려 주세요. 문제 출처의 실제 `excerpt`와 적재 원문을 비교해 적재 데이터·변환·화면 중 수정 위치를 정합니다. 이미지 API는 이번에 추가하지 않습니다.

## 7. 배포 후 확인 요청 — 프론트 반영분 (2026-11-05)

프론트에서 반영을 마쳤고, 실제 서버에서 아직 시험하지 못한 것입니다. 확인되면 이 항목을 지워 주세요.

- **http 서버에서 문의 전송 (PR #284):** http 주소(`crypto.randomUUID` 없는 환경)에서 새 문의 전송, 상담 중 추가 질문 답변(IQ-08), 해결·미해결(IQ-09)이 모두 나가는지. 요청 중 예외가 나도 대기 화면이 무한 대기가 아니라 오류 문구와 "다시 시도"로 바뀌는지.
- **외부 전송 정책 완화 사유 (R-22, PR #286):** 완화(`금지 → 허용` 등)는 사유 없이 거절되고(`reason` / `REQUIRED`), 사유를 넣으면 변경되며 운영 기록(OP-04)에 사유가 남는지. 엄격하게 바꿀 때는 사유 없이도 되는지.
- **FAQ 출처 지정·수정 (R-41·R-35, PR #289):** 출처 가이드를 고르고 등록하면 문의자 FAQ에 보이고 출처가 열리는지, 출처 없이는 막히는지. FAQ 수정에서 출처를 바꾸면 통째로 교체되는지(FQ-04), "바로 게시"를 켜고 끌 때 게시 상태가 맞는지.
- **출처 선택 목록의 부하:** FAQ 등록 창은 가이드 목록(`/documents`)을 한 번 읽습니다. 가이드가 매우 많을 때 느려지지 않는지.
- **AI 상세 패널의 가이드·과거 처리 사례 (PR #292, #293):** 과거 처리 사례를 참고한 문의의 AI 처리 상세에서 "참고한 과거 처리 사례" 묶음과 사례 본문(`excerpt`)이 맞게 나오는지, 사례가 여러 건일 때 건수가 맞는지. 가이드 칩을 누르면 근거 본문이 열리는지.
- **가이드 그림(DC-11)·FAQ 출처 본문(R-30, PR #293):** 그림이 있는 가이드를 출처로 쓴 답변·FAQ의 출처 미리보기에서 `[그림] 설명` 줄이 실제 그림으로 보이는지(`GET /guide-images/{key}`가 토큰으로 열리는지), 그림이 없는 줄은 설명 상자로 남는지. FAQ 출처에서 본문이 나오고, 문서만 지정한 출처는 안내 문구가 나오는지.
- **FAQ 등록·수정의 분류별 출처 목록 (PR #293):** 분류를 바꾸면 그 분류의 전 직원용 현행 가이드로 목록이 바뀌는지.

## (11.04-오후10시 추가) 확인이 필요한 표시 문구 — 운영 기록·AI 판단 이력

서버 코드와 대조한 답변입니다 (2026-11-05, `develop` 기준). 화면 수정이 필요한 곳은 **프론트 확인**으로 표시했습니다. 프론트 사전은 `frontend/src/api/auditLogs.ts`, `frontend/src/api/assessments.ts`입니다.

- **1. 재배정 기록의 결과 값:** 표시가 맞습니다. 담당자가 없던 접수의 배정이 `ASSIGN`, 있던 접수의 변경이 `REASSIGN`, 정할 사람이 없을 때가 `FAIL`입니다. 운영 기록(`/audit-logs`)에는 이 세 값만 옵니다. `RECOMMEND`는 접수 확정 때 `assignment_logs`에만 남으므로, 배정 이력(`assignment-logs`)을 표시하는 화면에서는 올 수 있습니다.
- **2. 운영 기록 이벤트 목록:** 현재 서버가 남기는 값은 프론트 사전의 20가지와 같습니다. `CLASSIFY`·`ASSIGN`은 운영 기록에 남지 않아 [05.기준정보_운영](05.기준정보_운영.md) OP-04의 예시를 실제 목록으로 고쳤습니다. 응답 예시의 `result`도 실제 값(`REASSIGN`)으로 고쳤습니다.
- **3. 결과 값 목록:** 적어 주신 목록이 전부입니다. 다만 `FAIL`·`AI_FAILED`의 `reason`에는 내부 오류 코드가 그대로 들어갑니다.
- **4. `FAIL` 사유의 `④`:** [민감정보 정책](../10.민감정보_정책.md) 4장의 네 번째 적용 지점인 "외부 모델 호출 직전"을 뜻하는 내부 번호입니다. 관리자에게는 의미가 없는 표시입니다. **프론트 확인:** 화면에서 `④ `를 떼고 보여 주세요. 이미 쌓인 기록이 있어 서버 문구는 그대로 둡니다. **(11.06 프론트 반영 완료)**
- **5. `URGENT_CLOSED`:** 결과는 항상 `CLOSED_UNRESOLVED`입니다. 문의 판단 이력에 긴급 징후가 한 번이라도 있었는데 접수 없이 닫힐 때(문의 종료, 초안 취소) 남으므로 표시가 맞습니다.
- **6. 문서 기록의 결과 글 모양:** 적어 주신 모양이 맞습니다. 추가로 `DOCUMENT_VERSION_ACTIVATE`는 이전 현행이 없으면 `없음 → v1`입니다. 구조화된 값은 이번에 추가하지 않았고, 형식을 바꾸면 알려 드리겠습니다.
- **7. 계정 상태 `INACTIVE`:** "이용 제한"이 맞습니다. 서버 오류 문구도 "이용이 제한된 계정"을 씁니다.
- **8. AI 판단 이력의 추가 질문:** 판단은 문의 시작과 추가 질문의 답변에서만 생기고, 답변은 직전 판단이 `ASK_MORE`일 때만 받으므로 순서는 맞습니다. 다만 AI 호출이 503으로 실패하면 사용자 글은 남고 판단은 남지 않습니다. 이때는 다음 판단 앞에 사용자 글이 둘 이상일 수 있어, "답 하나에 판단 하나"로 단정하지 말아 주세요. 항목 코드 5가지는 프론트 사전과 같습니다.
- **9. 사용한 가이드:** ADMIN은 다른 사람의 문의 메시지와 모든 열람 범위의 출처를 이 API로 조회할 수 있습니다. 중복 제거 기준(종류·문서·버전·위치)도 괜찮습니다. **프론트 확인:** `LEGACY`는 가이드가 아니라 과거 처리 사례이고 문서 코드가 없으므로, "사용한 가이드"에 섞어 보여 줄지 구분해 주세요. **(11.06 확인: AI 처리 상세에서 "사용한 가이드"와 "참고한 과거 처리 사례"를 나눠 보여 주고 있습니다.)**
