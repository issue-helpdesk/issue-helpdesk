# AI 호출 안정성·응답 시간 점검

2026-11-08 · 팀 검토안 · 코드 확인 기준: develop `0b175b0` · 운영 시험 전

## 1. 이번 마감의 판단 기준

**현재 요청 구조를 유지하면서 실제 지연과 실패·복구를 먼저 확인하고, 확인된 문제만 작게 수정하는 안을 제안한다.** 마감까지 1~2일 남아 별도 작업 큐 전환은 기본 개발 범위로 두지 않는다. 목표는 안정적인 답변 수신과 수용 가능한 대기 시간이다.

| 확인 결과 | 처리 방향 |
|---|---|
| 대기 시간이 수용 가능하고 이동·복귀·오류 안내가 정상 | 현재 구조 유지. 측정 결과와 확인된 한계를 공유 |
| 첫 문의만 특히 느림 | 임베딩 모델 초기 로딩·준비 상태·배포 설정부터 확인 |
| CLASSIFY·ANSWER 호출이 오래 걸리거나 재호출이 많음 | 호출 기록으로 원인 확인 후 출력·검색 근거·재시도 설정 등 해당 부분만 조정하고 재시험 |
| 모델 시간은 짧은데 전체 대기가 김 | 검색·DB·요청 대기·화면 갱신 구간을 구분해 측정 |
| 반복적인 연결 종료·답변 누락·중복·무한 대기 발생 | 속도 최적화보다 복구 문제 우선 수정. 작업 분리가 필요하면 배포·회귀 시험 시간을 확보할 수 있는지 별도 결정 |

정상 대기 목표와 장시간 대기 시 안내·실패/담당자 연결 기준은 실측과 시연 요구를 보고 팀에서 정한다. 평균만으로 판단하지 않고 느린 사례·실패 건도 확인한다. 제한 시간만 늘리거나 재시도·안전 검사를 일괄 제거하는 방식은 피한다.

## 2. 현재 구조와 변경 규모

프론트는 문의 요청 중 FAQ 등으로 이동할 수 있다. 요청이 끝나면 목록을 즉시 갱신하는 경로와 별도 주기 조회가 있다. 서버 IQ-01·IQ-08은 질문을 먼저 저장하고, 같은 HTTP 요청에서 **1차 AI 판단 → 검색 → 2차 답변**을 진행한 뒤 응답한다. 일부 경로는 1차에서 끝난다. 화면의 비동기 동작과 서버의 별도 작업 처리는 구분한다.

별도 작업 처리로 전환하려면 문의/작업 ID 선반환, 영속 작업·상태, worker·재시도·재시작 복구, 중복 방지와 질문 순서, API·프론트 대기/복구, 배포·회귀 시험까지 필요하다. **async 선언만 바꾸는 작은 수정이 아니며, AI 생성 자체를 빠르게 한다는 보장도 없다.** SSE/웹소켓은 필수가 아니다. 이번에는 현재 구조를 먼저 검증한다.

## 3. 우선 실행할 점검

1. **프론트:** 같은 배포 환경에서 정상 문의 5~10건과 추가 질문·담당자 연결·실패 사례를 확인한다. 문의 ID, 전송→응답 시간, 응답→표시 시간, 성공/오류를 기록한다. 첫 요청과 느린 사례를 따로 남긴다.
2. **백엔드·AI 담당:** 같은 문의의 llm_calls에서 CLASSIFY·ANSWER별 시간·호출 수·성공·오류 코드를 대조한다. 모델 로딩 로그, `EMBEDDING_PRELOAD`, 실제 프록시 제한과 재시도 설정을 확인한다. 레포 설정은 SDK 호출 제한 30초·재시도 1회, nginx 무응답 제한 120초이며 상위 재생성도 가능하다. 실제 배포값은 별도로 확인한다.
3. **함께:** FAQ 이동 후 복귀, 답변 전 새로고침, 연결 종료 후 재전송, 2~3명 동시 문의를 시험한다. 질문·답변 중복/누락, 무한 대기, 답변 표시·목록 갱신을 확인한다. 질문이 저장됐다는 사실만으로 답변 완료·복구를 보장하지 않는다. AI 새 답변 점의 정확성 보완은 [06 문서 R-45](06.프론트_연동_요청.md) 범위다.

초기 소수 시험은 문제를 찾기 위한 점검이며 부하 안정성 검증은 아니다. 담당과 실행 범위를 합의하고 **측정 결과 → 원인 → 수정 범위 → 같은 사례 재시험 결과**를 공유한다. 모델·프롬프트 변경 시 답변 정확성·근거·담당자 연결·민감정보 보호도 확인한다.

- 관리자 화면의 “평균 응답”은 **모델 호출 1회의 평균**이다. 사용자 질문 1건의 전체 시간과 다르며, 단계별 비교는 API의 byPurpose 또는 DB로 확인한다. 새 통계 화면은 필요하지 않다.
- 원본 확인 항목: `inquiry_id`, `purpose`, `adapter`, `model`, `latency_ms`, `input_tokens`, `output_tokens`, `success`, `error_code`. 실제 모델 기록과 모의 기록을 구분한다.
- latency_ms는 호출 직전부터 응답 형식 검사까지이며 내부 SDK 재시도도 포함될 수 있다. 검색·모델 초기 로딩·다른 DB 처리·화면 시간은 별도다. 한 문의의 여러 질문 기록이 섞일 수 있어 시험 순서와 대조한다.
- 기록은 결과 저장 경로에서 남으며 `created_at`은 DB 기록 시각이다. 기록이 없다고 미호출로 단정하거나 생성 시각을 호출 시작 시각으로 사용하지 않는다.

코드·병합 이력만 확인한 검토안이다. 현재 운영 시간·부하·복구는 아직 검증하지 않았으며, 이 문서로 설정·API·배포 변경을 확정하지 않는다.
