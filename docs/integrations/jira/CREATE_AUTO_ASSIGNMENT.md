# Jira 생성 후 최초 배정 예약

`services/jira_create.py`의 생성 성공 저장에 최초 배정 예약을 연결했습니다. Jira 담당자 지정은 기존 JIRA_ASSIGN 실행 서비스가 처리합니다.

| 상황 | 처리 |
|---|---|
| 생성·기존 이슈 연결·저장된 키 확인 성공 | 최신 Ticket을 잠그고, RDY·WIP의 미배정 접수에 공용 reserve_assignment() 호출 |
| 생성 전 담당자 예약 있음 | 선정된 담당자·revision·배정 이력을 유지하고 JIRA_ASSIGN 작업만 등록 |
| 배정 작업 있음 | PENDING·RUNNING·완료·실패 모두 중복 등록하지 않음 |
| ASSIGNED·NEEDS_ADMIN 또는 기존 배정 판단 있음 | 자동으로 다시 선정하지 않음. 재처리는 TK-09로 요청 |
| 후보 없음·미분류 | 공용 함수의 NEEDS_ADMIN·FAIL 처리. 생성 결과는 SYNCED·DONE 유지 |
| 담당 그룹 없음·비활성 또는 세부 유형 비활성 | 배정만 NEEDS_ADMIN·FAIL 처리 |
| FIN·CLS·매핑되지 않은 상태 | 최초 자동배정 생략 |
| 생성 실패·결과 불명확 | 배정 예약하지 않음. 생성 결과 확인 후 진행 |

최초 선정은 공용 함수의 자격·업무량·동률 기준을 사용합니다. 생성 전 예약은 자동 선정 기준으로 다시 걸러내지 않습니다. 해당 예약의 Jira 계정은 현재 그룹 구성원 정보에서 읽으며, 자격 변경·계정 누락은 기존 배정 실행기가 Jira 호출 전에 검사합니다.

## 저장과 복구

생성 결과(jira_key·SYNCED·생성 작업 DONE)와 배정 예약·이력·JIRA_ASSIGN 작업을 한 트랜잭션으로 커밋합니다. 배정 저장에서 DB 예외가 나면 호출자가 rollback/세션 종료하고, 기존 stale RUNNING 복구가 VERIFYING으로 전환합니다. 다음 실행은 Jira를 새로 만들지 않고 접수번호로 찾아 연결한 뒤 예약을 저장합니다.

배정 저장 오류를 jira_key 중복으로 오인하지 않도록 생성 결과의 flush와 배정 예약 구간을 나눴습니다. Ticket 잠금으로 TK-09와 저장 구간을 직렬화하며, 신규 선정 시 공용 함수의 그룹 잠금도 사용합니다.

## 남은 작업

- worker의 JIRA_ASSIGN 소비·서버 배포. 이 변경만으로 Jira 담당자 지정까지 자동 실행되지는 않습니다.
- time_off DB·API 연결. 현재 신규 선정은 공용 함수의 기본 입력을 사용하며 부재 일정은 아직 조회하지 않습니다.
- 실제 Jira·PostgreSQL 잠금·동시 실행 통합 시험. 모의 HTTP·SQLite로 확인한 범위와 구분합니다.

## 검증

신규 26개를 포함해 티켓·인증·문의 API와 Jira 관련 테스트 664개 통과(모의 HTTP·임시 SQLite). 생성·연결·저장된 키 경로, 기존 예약·작업 유지, 후보 없음, DB 저장 실패 후 조회 복구, 생성 중 직접 지정, 배정 실행기 연결을 확인했습니다.
