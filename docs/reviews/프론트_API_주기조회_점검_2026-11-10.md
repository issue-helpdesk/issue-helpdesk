# 프론트 API 주기 조회 점검

**11.11 후속 보완:** 담당자 통계·운영 기록 구독 정리, 보안 조회의 숨김 탭 중단·복귀 조회, 보안·안 읽은 건수 공유와 중첩 방지를 적용했다. 아래 표는 11.10 당시 점검 이력이며, 변경 범위·검증은 [후속 기록](폴링_조회_보완_2026-11-11.md)을 따른다. 운영 기록은 당시 목록 API가 주기 재호출되던 것은 아니며, 불필요한 티켓 구독이 남아 있던 것으로 정정한다.

기준: `develop ccb08bc` 이후 관리자 화면 보완 작업. 코드에서 서버 모드의 호출 경로를 추적했다. 배포 서버의 접속자 수·실제 응답 시간·부하는 측정하지 않았다.

콜백은 결과를 받은 뒤 실행하는 함수이고, 일정 간격으로 API를 다시 읽는 방식은 폴링이다. 폴링 자체를 없애기보다 **필요한 상태만 조회하고, 동일 조회는 공유하며, 이전 조회가 끝나기 전에 중첩하지 않는 것**을 기준으로 삼는다.

## 우선순위 제안

1. **현재 반영:** 관리자 통계의 자동 재조회 제거. AI 상태 점·대시보드 긴급 범위 등 화면 보완과 함께 검증한다.
2. **다음 작은 변경 후보:** 담당자 통계·운영 기록의 정기 갱신 제거, 보안 조회의 숨김 탭 중단. 조회 시점을 바꾸므로 적용 전에 화면 요구를 확인한다.
3. **별도 변경:** 보안 건수·안 읽은 알림 응답 공유. 읽음 처리 직후 갱신, 로그인 사용자 전환 시 초기화, 마지막 구독 해제, 실패 후 재시도까지 묶어서 검증해야 한다.
4. **그 다음:** 티켓 목록·운영 현황·메뉴 건수의 동일 요청 공유, 가이드 적재 조회 통합. 페이지네이션으로 여러 쪽을 읽는 요청은 주기 하나가 HTTP 한 번을 뜻하지 않는다.

이번 점검으로 백엔드 API 추가나 WebSocket 전환을 요청하지 않는다. 프론트의 구독·요청 공유부터 개선할 수 있다. 모든 목록을 수동 갱신으로 바꾸면 신규 배정·새 답변 안내가 늦어질 수 있다.

## 구현 근거와 주의점

- `frontend/src/core/poll.ts`: 대부분 조회는 브라우저 탭이 숨겨지면 중단하고, 돌아오면 한 번 조회한다. 앱 내부 화면 이탈은 각 Effect의 구독 해제로 처리한다. 타이머를 해제하는 것과 이미 전송된 HTTP 요청 취소는 별개다.
- `frontend/src/api/tickets.ts`: `watchTickets`의 타이머는 공유하지만 구독자의 API 결과까지 공유하지 않는다. `Sidebar`, `DashView`, `OpsView`, `TeamBoard` 등이 각각 조회한다.
- `frontend/src/api/security.ts`, `securityServer.ts`: `watchSecurity`가 호출될 때마다 별도 타이머가 생긴다. 보안 목록 응답도 별도로 `/security-alerts/counts`를 읽는다.
- `frontend/src/api/notifications.ts`: `watchUnread`마다 `getUnreadCount`와 타이머가 생긴다. 값이 같으면 화면 통지만 생략하며 HTTP 요청 자체는 수행한다.
- `frontend/src/api/inquiries.ts`: 문의 목록은 실행 중 표시·재조회 예약으로 동시 실행을 막는다. 이 보호가 모든 폴링에 공통 적용된 것은 아니다.
- `frontend/src/api/chat.ts`: `inflight`는 답변 전송 중 화면 보호용이며 모든 조회 요청의 중첩을 막는 공통 잠금은 아니다. 조회가 느릴 때의 보호를 따로 검증할 필요가 있다.
- 공통 `visiblePoll`은 고정 간격 타이머다. 네트워크가 주기보다 느릴 때 요청이 겹치지 않게 하려면 호출부의 실행 중 보호나 완료 후 다음 조회 예약이 필요하다. [MDN의 서버 폴링 주의사항](https://developer.mozilla.org/en-US/docs/Web/API/Window/setInterval#ensure_that_execution_duration_is_shorter_than_interval_frequency)
- 개발 서버의 `StrictMode`는 최초 Effect를 추가 실행할 수 있다. 이것은 배포 모드의 정기 조회와 구분한다. 검사를 끄는 방식으로 해결하지 않는다. [React 공식 설명](https://react.dev/reference/react/StrictMode#fixing-bugs-found-by-re-running-effects-in-development)

## 검증 범위

관리자 화면은 로컬 Chrome의 네 화면 모드에서 확인했다. 통계는 서버 어댑터를 사용하되 HTTP 응답을 브라우저에서 대체해 조회 횟수를 점검했다. 개발 모드에서 운영 집계 초기 요청은 4회(요약·추이 각 2회)였고, 가상 시간 45초 동안 추가 요청은 0회, 추이의 새로고침 버튼을 누르면 1회 추가됐다. 이는 실제 배포 서버 부하 시험이 아니다. 점검 스크립트·캡처는 저장소 밖 `tmp/admin-consistency-20261110` 및 `tmp/guide-review/admin-consistency.cjs`에 둔다.
