# 보안 검토 탐지와 관리자 알림

## 변경되는 동작

문의마다 LLM이 공통 보안 기준 S01~S07을 평가하고 `security_rule_ids`를 반환합니다. 기존 사고 의심 불리언도 S01로 연결합니다. 검색 전 위험 요청은 검색·답변 생성을 더 진행하지 않고 안전한 담당자 연결 문구로 보정합니다. 검색 뒤 새로 발견된 신호도 합칩니다. 다시 생성한 답변이 실패하더라도 이미 감지한 신호는 유지합니다.

S01은 보안 사고 의심이므로 긴급 연결·최소 P2입니다. S02~S07은 관리자 검토이며 그 이유만으로 긴급도나 사고 의심 불리언을 올리지 않습니다. 사용자를 공격자로 확정하거나 대상자에게 보안 알림을 보내지 않습니다.

원천 사건 저장과 알림 생성은 같은 DB 트랜잭션입니다. 열린 알림은 대상·유형별로 합치고 종결 뒤 재감지되면 새 알림을 만듭니다. 사용자 행 잠금과 부분 UNIQUE 인덱스로 중복 열린 알림을 막습니다. 확인·종결·열람 이력은 기존 `audit_logs`에 저장합니다.

## 기준

| 코드 | 관리자 확인 대상 | 제외 예 |
| --- | --- | --- |
| S01 | 실제 발생·진행 중 보안 사고 의심 | 예방 교육·가정 질문 |
| S02 | 권한·승인 우회 요청 | 정식 권한 신청 |
| S03 | 보안 통제 무력화·기록 은폐 | 공식 예외 검토 신청 |
| S04 | 타인·제한 정보 무단 추출 | 본인 문의·공식 문의처 조회 |
| S05 | 자료 반출 통제 우회 | 정식 반출·마스킹 신청 |
| S06 | AI 지침·역할 조작을 통한 제한 정보 요구 | 교육용 분석·무해한 형식 변경 |
| S07 | 거절 이후 동일 제한 목적 재요청 | 거절 사유 질문·정상 절차로 전환 |

LLM은 현재 메시지와 최대 10개 이전 대화에서 의미를 판단합니다. 서버는 같은 사용자·같은 위험 코드(S02~S06)가 10분 내 서로 다른 문의 3건 이상에 기록되면 S07을 별도로 만듭니다. 여러 코드가 한 문의에 잡힌 것만으로 이 횟수를 올리지 않습니다.

## 기존 코드 기반 신호 연결

- `SENSITIVE_INPUT`: 한 메시지/수정 요청당 한 알림 발생 횟수. 유형별 개수는 합칩니다. OTP만이면 MEDIUM, 다른 비밀·식별·금융 패턴이 있으면 HIGH입니다. 숫자 패턴 오탐 가능성을 관리자가 확인합니다.
- `BLOCK / ALL_BLOCKED`: 모든 검색 근거가 전송 금지로 제외되면 `BLOCKED_DOC_QUERY`. 일부 문서만 빠진 `DOC_BLOCKED`는 기존 감사 로그만 남깁니다.
- `FAIL / FILTER_FAILED`: 검색 근거 또는 외부 모델 호출 직전 필터 실패. 저장 전 가림 예외·로그 핸들러 내부 오류 전체를 수집하는 기능은 아닙니다.
- `UNSAFE_REPLY`: 재생성 후에도 비밀값을 요구하거나 실행 전 완료를 주장하는 AI 출력이 남으면 기록합니다.
- `ACCOUNT_LOCKED`, `LOGIN_BLOCKED`, `URGENT_CLOSED`: 기존 감사 기록에서 알림을 생성합니다. 긴급 종료에는 일반 장애도 포함될 수 있습니다. 브라우저 종료 전체 감지는 아닙니다.
- `MASS_QUERY`: 저장에 성공한 USER 메시지 3분 내 41건 이상. AI·SYSTEM 메시지, 선택 버튼, 페이지 조회, 저장 실패 요청은 제외합니다. 개인별 평소 사용량 비교는 하지 않습니다. 공격 확정·자동 계정 차단 조건이 아닙니다.

## 관리자 API와 화면

기존 SA-01~06 설계를 따릅니다. 모두 ADMIN만 허용하며 일반 사용자·담당자는 403입니다.

| 경로 | 동작 |
| --- | --- |
| GET `/security-alerts` | 페이지·상태·alertType 필터, 고정 정렬 |
| GET `/security-alerts/counts` | 필터와 무관한 전체 건수 |
| GET `/security-alerts/{id}` | 상세·처리 이력(최근 100개 + 처음 감지) |
| POST `/security-alerts/{id}/review` | NEW → IN_REVIEW |
| POST `/security-alerts/{id}/close` | 사유 필수, IN_REVIEW → CLOSED |
| POST `/security-alerts/{id}/original` | 사유 필수, 저장된 USER 메시지만 열람. user 대상은 409 |

원문·모델 자유 텍스트를 알림 목록에 복제하지 않습니다. 사유도 비밀값 가림 후 저장합니다. 원문 열람은 저장 당시 가려진 메시지이며 인증정보를 복원하지 않습니다. 열람 감사 기록 커밋이 실패하면 내용도 반환하지 않습니다.

문의 서버 모드(`VITE_USE_MOCK_INQUIRY=false`)에서는 실제 API를 사용하고, 모의 모드만 시연 데이터입니다. 관리자 사이드바·대시보드·목록은 30초 간격으로 갱신합니다. 외부 이메일·메신저·푸시 발송은 포함하지 않습니다.

## 적용과 검증

1. 서버 코드 실행 전에 `PYTHONPATH=backend python -m alembic -c backend/alembic.ini upgrade head`로 기존 `security_alerts`의 보안 유형 제약을 확장합니다. 테이블은 선행 `f8a2c6d41b97`에서 생성하고, 유형 확장은 최신 가이드 묶음 마이그레이션 `d3a7f2c9e184` 뒤에 적용합니다. 이번 변경이 생긴 이후 이벤트부터 수집하며 과거 감사 기록을 자동 이관하지 않습니다.
2. 서버·웹을 재배포합니다. 프롬프트 변경만으로 이미 실행 중인 서버에 적용되지는 않습니다.
3. 자동 검증은 합성 Mock 출력으로 흐름 보정·DB 저장·권한·상태·가림·웹 API 변환을 확인합니다. 실제 LLM의 140문항 분류 정확도를 보장하는 결과는 아닙니다.
4. 실제 모델 평가가 필요하면 `SCENARIOS.md`의 명령을 사용합니다. 기본 실행은 외부 호출이 없는 자료 확인입니다.

질문 예시는 [SCENARIOS.md](SCENARIOS.md)에 140개, 코드 기반 보호 기능 점검은 추가 20개입니다. 실제 배포·실제 LLM·운영 PostgreSQL에서의 동시 요청 검증은 별도입니다.
